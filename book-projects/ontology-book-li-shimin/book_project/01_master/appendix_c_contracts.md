# 附錄 C｜把一條規則交給正確的負責層

本表供設計檢查，不是已部署服務的驗收報告。

| 要問的事 | 應明確檢查的責任 | 不能因此推得 |
|---|---|---|
| 這個詞與關係是什麼意思 | 概念模型、正式語意及領域審查 | 現實資料全部正確 |
| 這批 RDF 資料符合指定條件嗎 | SHACL 的輸入、目標、形狀與報告 | 使用者有操作權 |
| 已確認報名如何占位 | 有效業務政策與具體計算 | AI 可以新增報名 |
| 當下可執行嗎 | 可信身分、政策、核准、權限及最新狀態 | 送出後一定成功 |
| 操作最後做了什麼 | 原操作紀錄、正式回執、對帳與錯誤處理 | 外部副作用可以任意撤回 |

只讀查詢契約可以先寫成中文：指定班別、可信請求者、允許資料範圍；輸出容量、已確認數、可用數、資料時間、政策版本、來源與缺項。未知班別、資料不完整、服務錯誤應分開回覆；不得把錯誤當成零名額。

變更提案應帶對象、數量或金額、用途、來源、政策與提案版本、缺項及識別。核准應綁定這些內容；內容改變後重新檢查。執行端不能只接受一句「主管說可以」，也不能讓模型以文字自報身分取得許可。

操作狀態至少要分得清拒絕、待核准、受理、完成、失敗與結果待確認。狀態設計可以依服務調整，但不能把沒有收到結果寫成成功，也不能把逾時當成必然沒有副作用。

重試要查原操作及相應契約，處理相同識別但參數不同、不同識別卻是同一業務意圖、以及識別保留期限等情況。這是設計檢查清單；真正服務的去重、併行與補償能力需要另外實測。

請填：操作目的＿＿；對象與版本＿＿；可信身分來源＿＿；有效政策＿＿；核准涵蓋內容＿＿；執行端再驗＿＿；請求識別及保留規則＿＿；結果回執＿＿；未知結果處理＿＿；部分成功處理＿＿；可回復與不可回復部分＿＿。
