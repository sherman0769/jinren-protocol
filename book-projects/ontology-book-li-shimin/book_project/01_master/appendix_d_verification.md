# 附錄 D｜哪些結果可重算，哪些尚未實測

本書保留三種不同證據，不把它們統稱為技術通過。

第一種是固定資料的離線檢查。出版包的 `examples/` 內保留 `04_cases/example_data.json` 與 `scripts/case_checks.py`。在該範例目錄以 Python 3.10 以上執行：

```sh
python -B scripts/case_checks.py
```

它檢查有限的資料連結、容量、重複占位、名額與未知付款結果。程式不連外、不呼叫模型，也不做退款或報名。書稿製作時已實際執行這種檢查；它不等於企業服務端到端測試。

第二種是對標準語意的逐步手算。假設模型要求每筆報名恰有一個班別，卻沒有提供具體班別連結，OWL 的開放世界語意可以容許一個尚未命名的對象；它不因此提供可查的班別編號。若指定資料驗證要求一個班別值，現有資料為零個值，則應回報缺值。

再假設同一筆報名連到兩個不同名稱。若未聲明名稱指向不同個體，OWL 的數量條件可能要求它們指同一個對象；加入明確不同的要求後才會與「最多一個」衝突。對原始資料圖作數量驗證時，兩個不同 RDF 項仍是兩個值，不能未交代前處理就當成一個。

這些是固定前提下的語意推導，書稿製作沒有執行 OWL 推理器或 SHACL 驗證器。本書正文與此附錄以中文說明，不提供偽裝成已測程式的正式語法檔。要進一步實作，需另外固定引擎版本、輸入、推理設定與原始報告。

第三種是行動與協作的設計題。退款核准、最後一席競爭、工具逾時、跨助理交接和攝影送件，在本書都是契約或測試預期；沒有真實服務的測試回執。讀者應先在適當測試環境實作，再決定是否能用於生產。

判讀任何驗收時，請問它真正驗了哪一層：檔案存在、資料結構、形式語意、任務答案、授權執行，還是人真的能使用？一個通過符號，只對它實際涵蓋的範圍負責。
