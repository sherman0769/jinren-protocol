# EP02｜本體不是一個難字，而是一組能被追問的約定

來源：第 2 章正式稿 1.0.0；精確 SHA、字元及版本見 derivation.json。
口播版本：1.0.0。單講者文字設計，尚非錄音。

有一天，你對助理說：「請取消這位學員的課程。」現在請想像，助理真的要照做。它應該取消什麼？是這個人某一次的報名？是十月的其中一個班？還是把整門課從工作室的安排裡刪掉？

日常聊天時，我們可能靠前後文猜得出來。但當同一門課開了兩班，同一位學員也可能報過不同次，這句話就需要更多說明。真正重要的，不是助理能不能讀懂每一個中文字，而是它把那些字連到了什麼對象。

這一集，我們來認識本體。你不需要先知道英文，也不用先安裝軟體。目標是聽完後，能用自己的話說明它在處理什麼，而且能指出它沒有包辦哪些事情。

我們繼續使用虛構的晨光學習工作室。如果你第一次聽，也只要知道幾個設定：一門叫做 AI 基礎應用的課，可以開不同班別；人透過報名紀錄連到班別；付款則另外保存。這些是教學假設，不是作者真實營運故事。

先想第一個問題：我們這次到底要談多大範圍？工作室可能有租金、器材、社群貼文和薪資，但如果眼前只需要處理報名與名額，沒有必要把全部生活一次搬進模型。

為了這次目的，選定要描述的知識範圍，可以稱為領域。你可以先記成「這次我們要認真說清楚的部分」。範圍不是越小越好，也不是越大越完整就越厲害。應該回到問題檢查：少了某個對象，還能不能正確回答？

如果只記姓名，沒有記報名哪一班，就不能知道取消後哪一班空出位置。這時班別必須留下來。但如果這次不處理器材折舊，暫時不建那部分，並不表示器材在現實中不存在或不重要。

再來，要決定怎麼理解這個範圍。我們把課程看成可重複開設的內容，把某一天開課的安排看成班別，再把一個人對某班的申請看成一筆報名。這種為了目的選擇對象與關係的簡化方式，叫作概念化。

同一間工作室，招生可能先看詢問、接觸與報名，教務可能先看班別、講師與名額。兩種看法可以各自有用。需要比較的是能否支撐自己的任務，不是誰把所有東西都畫進去了。

當我們把選定概念的意思、關係和使用條件明確表達，讓人或系統能依循，就走到本書談的本體。英文是 Ontology；如果現在只記住中文也完全可以。先理解它是一份關於「我們這裡把哪些東西分開，以及它們如何相連」的明確約定。

這份約定並不包含公司的全部世界。它不會自動擁有每一位同事的判斷、默契或感受。模型能說明省略了什麼，反而讓使用者更知道該怎麼依賴它。

你可能覺得，這很像詞彙表。這個比喻有幫助，因為同一個詞有穩定解釋，大家比較容易溝通。但只停在詞彙表，還少了一件重要的事：這些詞怎麼一起工作。

讓我們從一筆報名開始。取消這筆報名，不等於刪掉整門課，也不等於取消同班其他人的報名。付款連到某筆報名，不能只因名字相同，就任意接到另一個班。這些關系，才讓名詞能夠支撐一個可以使用的描述。

再想一句常見的話：「這門課有三個名額。」如果同一門課開兩班，第一班容量三人，第二班容量兩人，你知道這句話在說哪個班嗎？名額應該屬於一次開班的安排，而不是把課程內容本身當成一個固定容量的盒子。

在晨光的固定例子裡，第一班是 S101，容量三；第二班 S102，容量二。你不必背代號，只要記住同一門課的兩次開班，各有自己的容量。把它們分開，才能正確問還有多少位置。

畫圖會有幫助，但圖上的線也要有意思。假設我只畫「學員連到課程」，那條線是在說他問過、報名過、修完，還是他可以教這門課？如果每個看圖的人都能自由補意思，模糊沒有消失，只是換了一種形狀。

因此，本體可以由文字文件承載，用圖來呈現，也可以用有明確語意的語言交給軟體處理。不能只看副檔名或畫面漂亮，就宣布已經完成。反過來，也不必在第一天把每一張中文定義卡都轉成複雜程式。

如果某些結論需要由機器按同一套邏輯推出，才進一步選擇合適的形式規格與工具。這要從任務往下決定，而不是因為聽到一個名詞，就覺得自己缺了某套大型軟體。

本體這個詞讓人困惑，還有一個原因：不同文章可能在不同語境使用它。在哲學裡，它和存在及其類型有關；在本書的知識工程語境，我們關心如何明確描述一個選定範圍。你不必先解決所有哲學問題，才有資格學會本書的方法。

早期的本體研究把問題放在知識共享：系統收到同樣格式的資料，是否就知道內容在說什麼？想像你傳出一個寫著「確認」的欄位，對方的程式可以順利讀取。但這是確認收件、確認保留名額，還是確認付款？格式讀得進來，意思還需要約定。

這個工作室例子是本書自己的說明，不是早期論文裡的企業實驗。研究討論共享概念，不能直接被改說成「任何公司建本體都會省錢」。如何達成共識、是否真的改善任務，仍要另外檢查。

還有第三種語境，是商業平台。某些平台把概念模型、資料連接、運算、行動和權限放在一起，並用 Ontology 這個名稱介紹它的整套能力。這時，你讀到的除了概念，也包括廠商選擇整合哪些功能。

例如，Palantir 的官方文件用資料、邏輯、行動與安全，說明它的營運模型。這是該產品的分類方式，不能倒過來說所有學術本體都必須內建退款按鈕或權限系統，否則就不算本體。

Microsoft Fabric 的本體文件，則把共同企業詞彙與資料綁定放在產品情境裡。本書在二〇二六年九月二十八日查閱時，頁面仍標預覽。這是一個有日期的產品觀察，不是永遠不變的狀態，更不是某家公司已經導入成功的證據。

所以，讀到介紹時，先問它談的是通用的概念約定、可以交給推理工具的規格，還是某家平台的能力。確認語境之後，再問版本、限制與實際驗收。你不需要把各家的功能清單拼成一個什麼都有的超級定義。

接下來，我們把一條規則拆開。假設模型說，已確認報名會占用班別名額。這句話有用，但它沒有同時完成所有工作。

第一種工作，是依明確前提推論。假設我們約定每位講師都是人，知道周言青是講師，就能推出他是人。這個結論跟著前提成立，不代表工具到現場確認過他的身分，也不代表他因此就是工作室員工。固定案例裡，他其實是外部合作講師。

第二種工作，是檢查資料有沒有符合指定條件。報名處理需要班別識別，資料卻漏了這個欄位，就應指出缺項。第三種，是按有效的業務規則計算，像哪些狀態占位。第四種，才是某個人或服務在當下有沒有權限改動。

這四種工作可以合作，也可能被同一個平台整合。但是，資料檢查通過，不會讓沒有權限的人突然可以退款；在文件裡描述規則，也不會自動阻止兩個請求搶同一席。保留各自的責任，才能在出錯時知道去哪裡修。

現在做一張不用畫面的定義卡。請替「已確認報名」說六件事：名稱、意思、範圍、例子、反例，以及由誰維護。這是本書的練習方式，不是新的國際標準。

名稱盡量不要只寫「正式」。意思可以說：這是在指定班別中，被列為已確認状態，依本案例規則會占用名額的一筆報名。聽出來嗎？我們定義的是報名紀錄，不是永久貼在某個人身上的標籤，也沒有把已付款偷偷塞進去。

範圍則說清楚，是晨光教學案例現行的名額政策。例子用第一筆已確認報名；反例用候補，因為這份政策下候補不占位。若有人說「他以前也來上過課」，你應該能回答，過去的上課經驗不足以決定這一次報名的狀態。

維護者也不要只寫 AI。在一個真正工作流程裡，應由有權維護這個口徑的人負責，例如被指定的教務角色。這只是角色設計建議，不表示虛構資料已任命某一個人。責任還沒有被接受以前，多一個負責人欄位，並不等於已經有人接手。

怎樣知道卡片夠不夠清楚？換一個人來用。告訴他有一筆報名已確認，但付款未知，問他是否占位。依本題規則，他應回答占位。若他還得猜「已確認是不是代表付過錢」，你的卡片就還需要補強。

再問一題：這張卡能判斷退款資格嗎？不能。它的工作是名額安排，本題也沒有完整退款資格政策。好的定義會告訴你能用到哪裡，也會讓你知道哪些問題需要其他來源。

正式定義還有一種風險，就是讓整齊看起來比實用更重要。假設所有部門被強迫只能把已付款者叫學員，那教務要怎麼稱呼已確認名額、尚待對帳的人？客服要怎麼描述以前上過課、這次還沒報名的人？統一名稱如果抹掉需要的差別，工作反而更難做。

比較合適的做法，是保留清楚的限定詞與關系。要看報名就說報名，要查入帳就看付款。真正需要共同使用的地方再明確對應，而不是把不同任務全部壓成同一個状態。

定義也會變。假設未來政策允許某些候補暫時保留位置，那就需要更新定義卡、計算方式與測試。但這是未來假設，不是目前晨光的政策。新版本出來，要讓舊報表仍然看得出原來依據，不能靜悄悄改掉意思。

方法指南提醒建模者，先問用途、要回答的問題，以及誰使用與維護，並接受反覆修訂。這對小型工作室很實際：可以先觀察現有文件是否已經足夠，不必把所有日常用語都變成需要專人照顧的大工程。

最後，請試著把本體說給一位沒聽過的人。你可以說：我們挑出這項工作需要分辨的對象，把意思、關系與使用條件說清楚，讓人和系統少靠猜測。但模型只有選定範圍，資料是否真實、動作是否被允許，還要分開檢查。

接著讓對方分辨三句話。第一句，本體在問存在是什麼。第二句，本體讓系統共享概念。第三句，某個 Ontology 平台能操作企業流程。你們應該能說，第一句是哲學語境，第二句是知識工程，第三句要回到特定產品查證，不能互相套用。

如果你能配上一筆報名的例子，並指出定義卡不能決定退款資格，就已經完成這一集的主要練習。下一集，我們進一步把對象拆清楚：一門課、一次開班、一筆報名，為什麼值得分開，而不是全部塞在一張學員名單裡？
