第五章｜資源、素材與資料：哪些東西應該被保存與重複使用

一張玩家圖片、一個玩家場景、一份角色數值、一個生命值變數，明明都跟「玩家」有關，為什麼要放在不同地方？

這是初學者開始建立專案時最容易混亂的地方。畫面素材被直接塞進腳本，角色速度寫死在函式裡，每個敵人複製一份相同數值，場景同時承擔結構與設定。專案小時，看起來沒有問題；一旦要調整十種敵人、切換難度、保存玩家進度或讓 Codex 批次修改，資料放錯位置的代價就會快速放大。

這一章要建立的判斷是：

Node 承擔 Runtime 角色與行為，Scene 保存可組合的節點結構，Resource 保存可重複使用的資料，變數保存某個實例在當下需要記住的狀態，Asset 則是進入專案的原始內容。

這四句不是僵硬規則，而是一張資料責任地圖。

Asset：從外部進入專案的原始內容

Asset 通常翻成素材或資產。它可以是 PNG 圖片、SVG、音訊、字型、3D 模型、動畫來源檔、Shader、外掛或其他可供作品使用的內容。素材可能由你製作、委託創作者、購買、下載、使用開放授權來源，或透過 AI 工具生成。

素材首先回答的是「內容從哪裡來、可以如何使用」。它不只是一個技術檔案，也帶著來源、授權、作者署名、修改權與再散布限制。

例如，同樣是一張玩家圖像：

- 你自己繪製，權利關係相對清楚。

- 從商店購買，可能允許商業遊戲使用但禁止把原始檔單獨轉售。

- 使用 Creative Commons 素材，可能需要署名或以相同方式分享。

- AI 生成素材，還要確認模型服務條款、輸入素材權利、發布平台規則與是否能證明來源。

Godot 引擎採 MIT License，不代表放進 Godot 專案的所有素材都自動變成 MIT，也不代表你可以忽略第三方授權。引擎授權、外掛授權、素材授權與你自己的遊戲授權，是不同層次。

因此，正式專案最好建立素材登錄：檔名、來源、作者、授權、取得日期、是否修改、是否需要署名。Codex 可以幫你整理登錄，但不能替你憑空證明一份素材有合法權利。

Resource：Godot 中的資料容器

Godot 的 Resource 是資料容器。圖片載入後會成為 Texture2D 類型的資源，音訊檔可能成為 AudioStream，字型、材質、動畫與場景本身也都透過資源系統被載入與引用。

Resource 的特點是可以被保存、載入、共享與由 Inspector 編輯。自訂 Resource 還能把一組有意義的資料包成自己的類型。例如，建立 CharacterStats 資源：

```gdscriptclass_name CharacterStatsextends Resource

@export var max_health: int = 3@export var move_speed: float = 220.0@export var contact_damage: int = 1```

這段程式的重點不是語法，而是責任。CharacterStats 不負責移動，也不會自己扣血；它保存「某類角色的設定資料」。Player 或 Enemy 可以引用一份 CharacterStats，Runtime 再依資料建立自己的當前狀態。

官方資源系統支援序列化，也能將自訂 Resource 存成文字格式.tres。這使資料可以由 Inspector 編輯，也較適合版本控制。匯出遊戲時，引擎可能把資源轉成更適合執行的格式，但你的正式來源仍是專案中的原始資源設定。

Node 與 Resource：行為者和資料的差異

一個直覺判斷是：Node 通常需要存在於場景樹中，會參與生命週期、處理、訊號或空間；Resource 通常不需要成為場景樹成員，而是被 Node 或其他 Resource 引用。

以能量物件為例：

- EnergyPickup 的 Area2D、Sprite2D、CollisionShape2D 是節點，因為它們要進入 Runtime、顯示、碰撞與發出事件。

- 能量圖像是 Texture2D 資源。

- 收集音效是 AudioStream 資源。

- 能量價值、顏色與重生時間可以放在自訂 PickupData 資源。

- 「目前是否已收集」則是這個實例的 Runtime 狀態。

如果把所有資料都變成節點，場景樹會充滿只為保存數值而存在的物件；如果把所有東西都做成 Resource，又會失去 Runtime 生命週期與空間關係。判斷關鍵不是哪一種比較高級，而是它需不需要成為活動樹中的角色。

Scene 與 Resource：結構資料和設定資料

場景保存節點結構與屬性，也因此包含資料；Resource 也能引用其他 Resource，甚至 PackedScene 本身就是 Resource。那為什麼還要區分？因為設計時關注的問題不同。

當你問「一個敵人由哪些節點組成、根節點是什麼、碰撞與動畫放在哪裡」，你在設計場景結構。

當你問「這種敵人有多少生命、移動多快、掉落哪種物品、顯示什麼名稱」，你在設計資料配置。

把結構與設定分離的好處，是同一套 Enemy 場景可以引用不同 EnemyData，成為速度快但生命低的敵人，或速度慢但生命高的敵人。你不用複製整個場景與腳本，只為改幾個數值。

但也不要過早建立一個萬用資料系統。若遊戲只有一個玩家，速度也暫時不需要切換，先用匯出屬性即可。當資料開始出現多種版本、需要批次調整、由設計者在 Inspector 建立，或多個場景要共享時，自訂 Resource 的價值才會明顯。

變數：保存某個實例此刻的狀態

Resource 中的 max_health 可以是角色最大生命設定；Player 實例中的 current_health 則是當前生命狀態。這兩個數值即使一開始相同，也有不同責任。

```gdscript@export var stats: CharacterStatsvar current_health: int

func _ready() -> void:current_health = stats.max_health```

概念上，Resource 提供初始規則，實例變數保存 Runtime 變化。玩家受傷時，應改 current_health，而不是直接把共用 stats.max_health 改小。若多個敵人引用同一份 Resource，你改了那份共享資料，其他引用者也可能看到變化。

這正是資源共享最需要小心的地方：

共用資料適合表達共同設定，不適合不經思考地承載每個實例不同的即時狀態。

Godot 提供複製 Resource、local to scene 等相關能力，但初學時先掌握責任會比背選項更重要。若一份資料應隨每個實例獨立變化，就建立獨立狀態或明確複製；若它應由所有實例共同讀取，就避免在 Runtime 任意修改。

寫死數值的問題不只是「不好看」

所謂硬編碼，不是程式裡出現任何數字都錯，而是具有設計意義、會調整、需要共享或需要被理解的數值，散落在難以追蹤的位置。

假設玩家速度 220.0 同時出現在移動、衝刺與動畫計算裡。未來要把速度改成 240，Codex 可能只改其中一處；角色移動變快，動畫卻仍依舊值計算。若速度是一個命名清楚的匯出屬性或 Resource 欄位，修改入口就會集中。

可以用三個問題判斷數值是否應外部化：

1. 這個值是否會由設計或平衡反覆調整？

2. 這個值是否被多個地方或多個實例使用？

3. 讀程式的人是否需要知道這個數字代表什麼？

若答案多半是「是」，它就不應只以匿名數字散落在函式裡。

不過，外部化也有成本。把每個微小常數都做成 Resource，會讓資料層比遊戲規則更難讀。好的資料設計不是把所有值搬出去，而是讓「需要調整的設計參數」與「程式內部實作細節」各自待在適合的地方。

資料驅動：讓內容差異不必複製邏輯

資料驅動的核心，不是使用某種檔案格式，而是讓相同邏輯能依不同資料產生不同內容。

能量收集者可以有三種能量：

- 藍色能量：一分，常見。

- 金色能量：五分，稀有，播放不同音效。

- 回復能量：不加分，恢復一點生命。

最直接的作法，是複製三個場景與三份腳本，再分別修改。短期很快，之後修正收集流程時要改三次。另一種作法是保留一個 Pickup 場景與腳本，引用不同 PickupData：類型、分數、圖像、音效、效果。場景負責偵測與事件，資料決定內容差異。

資料驅動有助於 Codex 的原因是：你可以要求它「新增一份金色能量資料」，而不是「複製整個收集系統並改幾個地方」。變更範圍更小，驗收也更清楚。

但資料驅動不等於把所有規則變成一張萬能表。若三種物件的互動流程完全不同，強迫它們共用同一腳本可能產生大量條件分支。先找共同骨架，再判斷差異能否由資料表達。

設定、內容與存檔是三種不同資料

專案中常把「資料」全部混稱，實際上至少可以分三類。

設計設定：角色最大生命、敵人速度、關卡目標等。它們通常隨專案發行，由 Resource、Inspector 或設定檔提供。

內容素材：圖像、音效、文字、關卡資料等。它們構成作品內容，也隨版本更新。

玩家存檔：目前分數、已解鎖關卡、偏好設定等。它們在 Runtime 產生，屬於某位使用者，通常存到 user://。

若把最大生命和目前生命放在同一份可共享資料裡，容易混淆基準與進度；若把玩家存檔放回.tres 專案資源，匯出後可能無法正確寫入；若把關卡內容全部塞進存檔，版本更新又難以遷移。

資料設計的本質是生命週期：這份資料何時建立、由誰修改、要保存多久、是否跨實例共享、是否隨作品發行。

Resource 的共享、快取與意外副作用

Godot 載入同一路徑資源時，常會重用已載入的資源實例。這能節省記憶體，也符合「同一份材質或設定被多處引用」的需求。但如果你在 Runtime 修改共享資源，變更可能同時影響所有引用者。

典型例子是多個敵人共用同一份材質。你為其中一個敵人把材質顏色改紅，結果所有敵人一起變紅。問題不在 Godot 壞掉，而在你修改的是共享 Resource，不是單一實例的獨立副本。

解法要依目的選擇：

- 若所有實例本來就應一起改，維持共享。

- 若每個實例需要獨立變化，建立副本或使用適合的 local 設定。

- 若只是一段暫時視覺回饋，也可考慮節點層的 modulate、Shader 參數實例或其他不改共享來源的方式。

Codex 看到「把受傷敵人染紅」時，可能直接修改共享材質。驗收不能只測一個敵人，要同時放兩個實例，確認只有受傷者改變。

自訂 Resource 的公開介面

一份好的自訂 Resource 不只是欄位集合。它應該有明確語意、合理預設值、必要範圍與可理解命名。

例如 EnemyData 可以包含：顯示名稱、最大生命、移動速度、接觸傷害、分數價值、外觀與掉落設定。不要把 Runtime 中不應共享的「目前目標」「當前生命」「是否已死亡」放進共同資料。

匯出欄位可以加範圍提示，使 Inspector 更容易編輯；Resource 也可以包含簡單驗證方法。但若它開始控制移動、播放動畫、存取場景樹，就可能跨越資料容器的責任。資料可以有計算與驗證，卻不應偷偷變成依賴 Runtime 的萬能物件。

素材與 AI 的授權風險

使用 AI 產生角色圖、音效或文字時，技術上能匯入 Godot，不代表出版與商業使用風險已解決。你需要至少確認：生成服務是否允許預定用途；輸入是否包含你無權使用的內容；結果是否明顯模仿受保護角色或商標；發布平台是否要求揭露；團隊是否保留生成紀錄與條款版本。

本書不提供法律結論，也不把「AI 生成」視為天然無版權或天然侵權。最實際的工作方法，是建立來源登錄與風險標記。若無法確認，就使用臨時 placeholder，在正式發布前替換成權利清楚的素材。

Codex 可以幫你掃描素材目錄、找出缺少登錄的檔案，卻不能從檔名推斷授權。它若自動從網路下載素材，更需要明確禁止未授權來源。

用能量收集者建立資料關係

可以為 Player 建立 PlayerStats Resource，保存最大生命、移動速度與受傷無敵時間。Player 場景引用這份設定，Runtime 另有 current_health 與 is_invulnerable。

EnergyPickup 場景引用 PickupData，資料包含類型、分數價值、圖像與音效。每個實例有自己的 collected 狀態；收集後從 SceneTree 移除。

GameConfig 可以保存目標分數、起始關卡與一般規則；SaveData 則是寫入 user:// 的玩家進度。兩者都叫資料，但一個隨作品發布，一個隨使用者變化。

從左到右說一次：原始 PNG 與音效是 Asset；匯入後成為 Texture2D 與 AudioStream Resource；PickupData 引用這些 Resource 並保存設計參數；EnergyPickup Scene 組合顯示、碰撞與腳本；每次實例化後，Runtime 變數保存它當下是否已被收集。

這條鏈正是本章的資料地圖。

可以直接交給 Codex 的四個任務

任務一：資料責任盤點

只讀取目前 Player 與 Enemy 腳本。將每個欄位分成「設計設定」「Runtime 狀態」「暫時計算」「外部資源引用」四類，指出任何分類可疑或被多個腳本重複定義的資料。不要先建立 Resource。

任務二：提出最小自訂 Resource

目前有三種 EnergyPickup，只在分數、圖像與音效上不同。請提出一個最小 PickupData Resource 欄位設計，以及 Pickup 場景如何引用。不要把是否已收集、目前位置或場景節點引用放進共享資料。先提供設計與驗收，不修改檔案。

任務三：檢查共享資源副作用

閱讀所有在 Runtime 修改 Material、Texture、Animation 或自訂 Resource 的程式。指出哪些資源可能被多個實例共享，為每一處設計「兩個實例同時測試」的驗收情境，再提出最小修正方案。

任務四：建立素材登錄

掃描 assets/，建立 CSV 或 Markdown 清單，欄位包括路徑、類型、來源、作者、授權、取得日期、需否署名、狀態。對無法由專案確定的項目填「待確認」，不要猜測，也不要自動下載替代素材。

Codex 可能做錯什麼

第一，把目前生命與最大生命都放進共享 Resource，導致多個實例互相影響。

第二，為了「資料驅動」建立過度通用的字典，所有欄位都是沒有型別與說明的鍵值。短期彈性，長期卻難以在 Inspector、程式與驗證中理解。

第三，把每個數值都抽成外部檔案，讓簡單規則需要穿過多層才能看懂。資料分離應服務變更，不是追求抽象數量。

第四，直接修改共享材質或資源，只測單一實例，沒有發現其他物件一起改變。

第五，看到素材檔名就自行填寫授權。凡是來源不明，都必須標示待確認。

如何把這一章教給別人

教學時可以準備四個盒子：Asset、Resource、Scene、Runtime State。拿一張角色圖片、一份角色設定、一個 Player 場景與一張「目前生命為二」的卡片，請學員放進適合盒子。

接著做共享實驗。讓兩個敵人引用同一份 Resource，修改共用欄位，觀察兩者同時變化；再改成各自的 Runtime current_health，讓其中一個受傷。這個對比能直接說明「共同設定」與「個別狀態」。

最後讓學員把一個畫面需求寫成資料鏈：原始素材如何匯入、成為哪種 Resource、被哪個 Scene 引用、在 Runtime 中產生哪些變數。當學員能說出這條鏈，就不會再把所有東西都丟進腳本。

口語概念地圖

從最左邊開始，是外部進來的 Asset。Godot 將素材匯入並表示成可載入的 Resource。自訂 Resource 可以把多份素材與設計參數組成一份有意義的設定。Scene 引用 Resource，並用節點組成可運作結構。Scene 被實例化後，變數保存這個個體當下的狀態。若需要跨執行保存，狀態再被轉成 SaveData，寫入 user://。

每往右一步，資料的生命週期就更接近玩家當下的遊戲。每往左一步，資料就更接近可重複使用的來源與設定。

聽完後的自我檢查

1. Asset、Resource、Scene、Node 與 Runtime 變數各自主要負責什麼？

2. 為什麼最大生命與目前生命不應不加區分地放在同一份共享資料？

3. 什麼情況值得建立自訂 Resource，什麼情況先用匯出屬性即可？

4. 同一路徑的 Resource 被多個實例引用時，Runtime 修改可能產生什麼副作用？

5. Godot 採 MIT License，為什麼仍需逐一管理素材授權？

章末金句

- 資料放在哪裡，取決於它由誰修改、共享多久、保存到何時。

- Asset 帶著來源與權利，Resource 帶著可載入的資料，Scene 帶著可運作的結構。

- 最大生命是規則，當前生命是狀態；兩者數字相同，責任仍然不同。

- 共用資源能節省重複，也可能放大意外修改。

- 資料驅動不是把所有東西搬進表格，而是讓內容差異不必複製邏輯。

- 寫死的真正問題，不是數字出現在程式裡，而是設計意義散落到無法維護。

- 引擎授權清楚，不代表第三方素材授權自動清楚。

- Codex 能整理資料，不能替你發明權利來源。
