第二章｜遊戲不是畫面，而是一套持續運轉的規則

如果把畫面、音效與美術素材全部暫時拿掉，一個遊戲還剩下什麼？

你可能會先想到程式碼。但程式碼仍然只是表達手段。更底層的答案是：遊戲剩下一組會隨玩家輸入與時間持續改變的規則與狀態。

角色向右移動，是因為系統讀到輸入，依速度與時間計算新位置；能量物件消失，是因為碰撞規則判定玩家已收集它；分數從九變十，是因為狀態被修改；畫面顯示「完成」，是因為完成條件已成立。你在螢幕上看到的是結果，真正讓遊戲成立的是背後不斷運轉的判斷。

這一章要建立一個最重要的 Runtime 觀念：

輸入進來，規則判斷，狀態改變，結果呈現，然後進入下一輪。

畫面是結果，不是起點

初學者描述遊戲時，常從畫面開始：「有一個角色、一個敵人、幾個寶物，碰到之後出現特效。」這種描述對溝通概念很有用，卻還不是可以實作的規格。

因為畫面沒有回答幾個問題：角色為什麼移動？敵人何時攻擊？寶物如何判定被收集？特效播放期間，玩家能不能再次觸發？若同一幀發生兩次碰撞，分數要增加一次還是兩次？

把畫面翻譯成規則時，可以使用四個基本元素：

輸入：玩家、網路、計時器或其他系統送進來的訊息。判斷：根據規則決定現在應該發生什麼。狀態：系統目前記住的值，例如位置、生命、分數與遊戲階段。輸出：畫面、聲音、震動、介面或下一個事件。

假設玩家按下右方向。輸入層得到「向右」；規則層把方向乘上速度；狀態層更新玩家位置；輸出層在下一次繪製時讓角色出現在新位置。這個流程快速重複，人眼就感受到連續移動。

狀態是遊戲此刻的記憶

「狀態（state）」是遊戲開發裡最常出現，也最容易被說得太抽象的詞。最白話的理解是：系統在這一刻需要記住什麼，才能決定下一刻要做什麼。

能量收集者可能有下列狀態：

- 玩家位置是 (320, 180)。

- 玩家剩下兩點生命。

- 目前分數是七。

- 遊戲正在 Playing，而不是 Paused 或 GameOver。

- 某個敵人正在追逐，而不是巡邏。

- 玩家剛受傷，還有零點六秒無敵時間。

狀態不是畫面，但畫面通常依狀態呈現。生命值變成零，失敗面板才顯示；遊戲切換到暫停，敵人的移動與計時才停止；無敵時間尚未結束，玩家才不會連續扣血。

真正的 Bug 往往不是「畫面壞掉」，而是狀態與畫面不一致。介面顯示三點生命，內部其實只剩兩點；分數已達十，完成條件卻沒執行；遊戲看似暫停，某個 Timer 還在倒數。除錯時，必須問的不只是「我看見什麼」，還要問「系統目前相信什麼」。

規則把輸入與狀態連起來

規則可以寫成「當……就……」的句子。

- 當玩家按下向右，且遊戲處於 Playing，就把水平速度設為正值。

- 當玩家進入能量物件的碰撞範圍，就增加分數並移除該物件。

- 當生命值小於或等於零，就切換到 GameOver。

- 當遊戲處於 Paused，就停止需要暫停的更新。

這種句子比「做一個移動功能」更適合交給 Codex，因為它包含觸發條件、前置狀態與結果。若還能補上例外與驗收，規格會更完整。例如：「長按右鍵時持續移動；放開後停止；不同幀率下十秒移動距離應大致一致；暫停時不得移動。」

你可以把每個功能先寫成三行：

1. 什麼觸發？

2. 哪些狀態被讀取或改變？

3. 玩家如何觀察結果？

這三行就是從想法進入工程的第一道橋梁。

遊戲迴路：為什麼系統要一直跑

一般靜態文件不需要每秒重新計算。你打開一段文字，它可以停在原地，等你閱讀。遊戲不同。角色、敵人、計時器、動畫、物理與畫面都可能隨時間改變，因此系統需要一個持續運轉的主迴路，也就是遊戲迴路（game loop）。

以概念來說，每一輪大致做幾件事：收集輸入、更新規則與狀態、處理物理、更新聲音與動畫、繪製畫面，再進入下一輪。實際引擎會把不同工作安排在適合的階段，並處理作業系統事件、執行緒、渲染與平台差異；初學時不必先掌握所有底層細節，但必須知道遊戲不是「執行一次就結束」的腳本。

Godot 的 SceneTree 管理活動中的節點樹，也負責主迴路相關工作。節點可在不同生命週期回呼中接收更新。後面會詳細說明 _process(delta) 與 _physics_process(delta)，現在先把它們理解成兩種被引擎定期呼叫的入口：一個跟每個顯示幀的更新有關，一個跟固定物理節奏有關。

幀率不是遊戲速度

「幀（frame）」可以想成一次畫面更新。每秒顯示的幀數稱為幀率。電腦快時，也許一秒更新一百多次；裝置慢時，可能只有三十次。如果你每一幀都讓角色固定往右移動五個像素，那麼幀率越高，角色每秒移動距離就越遠。

因此，很多隨時間持續改變的數值會乘上 delta。Delta 是距離上一次更新經過的時間。若速度是每秒二百像素，那麼這一幀的位移可以概念化為：

```gdscriptposition += direction * speed * delta```

朗讀這行程式時，不必逐字念符號。它表達的是：「用方向乘上每秒速度，再乘上這一幀實際經過的時間，得到本次應移動的距離。」

這個模型的目的，是讓時間而不是電腦速度決定移動。不同幀率仍可能帶來輸入感受、物理精度與渲染差異，但至少不會因為一秒跑了更多幀，就讓角色基本速度直接倍增。

顯示更新與物理更新為什麼分開

畫面更新希望盡量流暢，通常跟實際渲染幀率有關；物理模擬則需要較穩定的時間步長，才容易保持碰撞與移動的一致性。Godot 因此區分 idle processing 與 physics processing。

_process(delta) 適合不必依固定物理節奏的更新，例如某些介面動畫、非物理視覺效果或一般每幀邏輯。_physics_process(delta) 適合角色移動、碰撞相關判斷與需要跟物理同步的工作。

這不是說一切移動都機械地放進某一個函式，而是提醒你：先問這段行為是否需要跟物理世界保持一致。若玩家角色用 CharacterBody2D 移動並與牆壁碰撞，通常就應在物理處理中更新。

同樣重要的是，不要在兩個迴路重複改同一個關鍵狀態。若 _process() 與 _physics_process() 都改玩家位置，結果可能難以預測。責任要清楚：輸入可以被讀取，但物理位置由哪一條路徑更新，必須單一且可追蹤。

編輯階段與 Runtime 是兩個世界

在編輯器裡放置節點、修改 Inspector 數值、連接訊號，屬於建立與設定專案的階段。按下執行後，Godot 會載入主場景，實例化節點，進入 Runtime。這時你看到的是「專案依規則運轉的實例」，而不是單純的編輯器資料。

這個差異能解釋很多初學困惑。

你在 Runtime 中把一個敵人移除，並不代表硬碟裡的敵人場景檔被刪除；下次重新執行，場景仍可再次實例化。你在遊戲中把玩家生命改成一，若沒有存檔，停止遊戲後通常不會永久寫回編輯器的初始值。你在 Remote 場景樹看到的是運轉中的節點，而 Local 場景資料則是編輯時的結構。

所以，除錯時要先問：錯誤發生在「設計資料」還是「執行實例」？某個節點根本沒被存進場景，和節點已經存在但 Runtime 中被移除，是兩種完全不同的問題。

事件驅動與持續更新不是對立

遊戲裡有些工作需要每輪檢查，例如角色持續移動；另一些工作只在事件發生時執行，例如玩家收集能量、按下按鈕或生命歸零。

若每一幀都問「分數是否改變」，可能浪費工作，也讓邏輯分散。比較自然的做法是：收集事件發生時發出訊號，分數系統接到訊號後更新一次。相反地，若角色必須依持續按鍵移動，就需要在更新迴路中讀取目前輸入強度。

因此，完整遊戲通常同時包含兩種節奏：

- 迴路式更新：適合連續時間、移動、物理與持續狀態。

- 事件式反應：適合按鈕、收集、死亡、關卡完成等離散事件。

學會分辨這兩者，能避免 Codex 把所有事都塞進 _process()，也能避免把本來應持續更新的移動寫成只反應一次的事件。

從 AI Agent 的 Loop 遷移過來

若你熟悉 AI Agent，可以把遊戲迴路想成另一種 Runtime Loop。Agent 可能反覆進行：接收觀察、更新上下文、選擇行動、呼叫工具、檢查結果。遊戲則反覆進行：讀取輸入、套用規則、更新狀態、處理物理與呈現結果。

兩者都有狀態、觸發、工具能力、執行順序與停止條件。兩者也都有常見風險：狀態失真、重複執行、事件遺漏、無限迴圈與缺乏可觀察性。

但不要把比喻當成完全相同。遊戲通常對時間與畫面更新更敏感，物理模擬也有固定節奏；Agent 則可能以任務步驟、工具回傳或模型回合為核心。知識遷移的目的，是借用熟悉框架建立入口，而不是抹去領域差異。

用能量收集者走一遍完整迴路

玩家按下向右鍵。Input Map 把實體按鍵映射成 move_right 動作。Player 腳本讀取這個動作，形成方向向量。物理更新依方向、速度與 delta 計算移動，再由 CharacterBody2D 處理碰撞。

玩家進入 EnergyPickup 的偵測範圍。收集物件判斷碰撞對象是玩家，發出 collected 訊號，播放或觸發回饋，然後從場景樹移除。分數系統接到事件，將分數從九改成十。規則檢查十是否達到目標；若達到，就把遊戲狀態切換成 Completed。HUD 依新狀態顯示完成訊息。

注意，這段描述沒有先談程式碼細節，卻已經包含輸入流、物理流、事件流、資料更新與狀態切換。只要你能把需求說成這種流程，Codex 就比較不必猜測。

可以交給 Codex 的四個任務

任務一：把畫面描述改寫成規則

我想做一個 2D 能量收集遊戲。先不要寫程式。請把「玩家移動、收集能量、碰到敵人扣血、生命歸零失敗」拆成輸入、前置條件、狀態變更、輸出回饋與例外情況。每條規則都要有可觀察的驗收方式。

任務二：找出需要迴路或事件的行為

依照上述規則，將所有行為分成「需要持續更新」「只在事件發生時執行」「初始化時執行」「結束或清理時執行」四類。說明理由，不修改專案。

任務三：檢查幀率相依風險

閱讀玩家移動腳本，找出任何直接以每幀固定數值改變位置、速度、倒數或透明度的程式。列出可能受幀率影響的地方，提出最小修改方案；在我確認前不要改檔。

任務四：建立狀態觀察點

為玩家位置、生命值、分數與目前遊戲狀態設計最小除錯輸出。避免每一幀大量列印；只在狀態真正改變時輸出，並說明每一筆日誌能驗證哪條規則。

Codex 可能做錯什麼

Codex 常見的第一個錯誤，是把所有邏輯塞進 _process()。能量是否被收集、生命是否歸零、介面是否更新，全都每幀輪詢。功能可能暫時能跑，卻讓事件與責任難以追蹤。

第二個錯誤，是忽略 delta。它也許寫出看似正確的角色移動，卻在不同幀率下速度不同。你要要求它說明某個數值的單位：是「每秒」，還是「每幀」？

第三個錯誤，是讓畫面成為唯一真相。它直接改 Label 文字，卻沒有更新分數資料；或播放死亡動畫，卻沒有切換 GameOver 狀態。驗收時要同時觀察狀態與輸出，不只看畫面。

第四個錯誤，是一個事件被處理兩次。例如碰撞訊號與每幀距離檢查都增加分數。這時應追蹤「誰擁有改分數的權限」，讓同一狀態的變更入口清楚。

如何把這一章教給別人

可以先播放一段沒有 UI 的角色移動畫面，請學員猜背後至少需要哪些狀態。接著把答案寫成四欄：輸入、規則、狀態、輸出。讓學員看到「向右鍵」不等於「向右移動」，中間還要經過遊戲狀態、速度、時間與碰撞。

第二個示範是故意移除 delta。讓相同程式在不同幀率限制下執行，觀察角色速度差異。這比直接背誦「要乘 delta」更能建立因果理解。

第三個示範則把分數更新分成兩種：每幀檢查與收集事件發生時更新。讓學員比較兩者在日誌、可讀性與責任上的差異。教學重點不是說輪詢永遠錯，而是學會依問題節奏選擇機制。

口語概念地圖

先想像一個圓環。圓環最上方是輸入，往右是規則判斷，往下是狀態改變，往左是畫面、聲音與介面回饋，最後回到輸入。圓環外面有一個時間軸，讓每一輪持續前進。

事件像是圓環裡突然亮起的燈：碰撞、按鈕、死亡或完成只在特定時刻發生。持續更新像是圓環本身的轉動：移動、物理、計時與動畫依時間前進。遊戲就是這兩種節奏共同作用的系統。

聽完後的自我檢查

1. 為什麼遊戲畫面只是狀態與規則的結果？

2. 你能把一個「玩家撿到能量」需求拆成輸入、判斷、狀態與輸出嗎？

3. Delta 解決的核心問題是什麼？

4. 哪些工作適合持續更新，哪些工作適合事件驅動？

5. 編輯器裡的初始資料與 Runtime 中的實例狀態有何不同？

章末金句

- 遊戲不是一張會動的圖，而是一套會持續改變的規則。

- 畫面告訴你玩家看見什麼，狀態告訴你系統相信什麼。

- 每個功能都應回答：什麼觸發、改了什麼、如何被觀察。

- 幀率應影響流暢度，不應直接決定遊戲速度。

- 需要持續更新的事交給迴路，只在特定時刻發生的事交給事件。

- 除錯不是只看畫面，而是追蹤輸入如何一路改變狀態。

- 能把遊戲描述成流程，就已經走出「只會描述畫面」的階段。
