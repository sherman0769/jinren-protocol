第三章｜打開 Godot 之後：專案、編輯器與檔案正在做什麼

Godot 編輯器裡明明看得到場景、節點與屬性，硬碟裡卻只是一堆檔案。Codex 沒有像人一樣用滑鼠點 Inspector，為什麼它改完檔案後，Godot 又能顯示出變更？

這個問題的核心，是編輯器視圖與專案資料之間的對應。編輯器不是把內容藏進一個神祕資料庫，而是讀取專案資料夾中的場景、資源、腳本、素材與設定，再把它們呈現在適合操作的介面裡。

只要這層關係看懂，你就不必把 Godot 當成只能靠滑鼠操作的黑盒子。你會知道哪些內容適合由編輯器產生，哪些檔案能讓 Codex安全地修改，哪些目錄只是快取，以及哪一類變更一定要回到 Runtime 驗證。

專案不是一個檔案，而是一個有邊界的工作空間

一個 Godot 專案通常是一個資料夾。資料夾裡包含專案設定、場景、腳本、資源、匯入素材與其他必要檔案。Godot 透過專案根目錄下的 project.godot 辨認這是一個專案，並從中讀取專案層級的設定。

你可以把專案想成一個有明確根目錄的世界。專案內部的檔案使用 res:// 作為根路徑。假設玩家場景在 scenes/player/player.tscn，Godot 內部可以把它表示為：

```textres://scenes/player/player.tscn```

res:// 不代表你電腦上的固定磁碟位置，而是「目前專案資源根目錄」。這讓專案移到另一台電腦、另一個資料夾或版本控制環境時，內部路徑仍能維持相對關係。

另一個常見路徑是 user://。它指向這個應用程式可寫入的使用者資料位置，實際對應會依作業系統與專案設定而不同。存檔、使用者偏好與執行時產生的資料，通常比寫回 res:// 更適合放在 user://。

這兩個路徑代表兩種責任：

- res:// 主要是隨作品一起發行的專案資源。

- user:// 主要是某位使用者在執行後產生或修改的資料。

若把存檔寫進專案資源目錄，開發時也許暫時可行，匯出後卻可能遇到唯讀、封裝或平台差異。因此，資料放在哪裡，不只是檔案整理問題，也是 Runtime 設計的一部分。

Project Manager 管的是入口，不是遊戲內容

啟動 Godot 後，通常先進入 Project Manager。它用來建立、匯入、掃描、重新命名或移除專案清單中的項目。這裡的「移除」常是從清單移除，不一定等同刪除硬碟資料；執行前仍要看清楚操作提示。

Project Manager 幫你選擇要進入哪一個專案，也能在建立專案時設定名稱、位置、渲染方法與版本控制中繼資料。它不負責定義玩家如何移動，也不等於遊戲主選單。這兩個畫面都可能有「Project」或「Start」字樣，但一個屬於開發工具，一個屬於作品 Runtime。

對 Codex 而言，專案入口最重要的資訊是根目錄。若它在錯誤資料夾工作，可能找不到 project.godot、把檔案建到專案外，或讀錯另一個同名專案。因此，每個任務都應明確指出專案路徑與只允許修改的範圍。

編輯器的主要區域，各自看哪一種真相

Godot 編輯器有幾個經常使用的區域。你不用一開始記住所有按鈕，只要知道每一區主要回答什麼問題。

Scene Dock 回答：「這個場景由哪些節點組成，它們的父子關係是什麼？」你會在這裡新增、重新命名、重排節點，或確認訊號連接與場景實例。

Viewport 回答：「這些節點在 2D、3D 或 UI 空間裡如何被安排？」你可在這裡移動物件、調整尺寸、操作攝影機或預覽控制項版面。

Inspector 回答：「目前選取的物件有哪些可設定屬性？」位置、速度、紋理、碰撞層、字型、資源引用或腳本匯出變數，都可能在這裡出現。Inspector 不是另一份資料；它是對選取物件可序列化屬性的編輯介面。

FileSystem Dock 回答：「專案根目錄中有哪些可被 Godot 辨認的檔案？」你會在這裡看到場景、腳本、圖像、音效與資源。對專案內檔案進行移動或重新命名時，優先從 Godot 內進行，通常更容易讓引用關係同步更新；大量外部操作後要留意重新掃描與失效路徑。

Script Editor 回答：「行為是如何被程式表達的？」它能編輯 GDScript，顯示方法、錯誤、警告與文件提示。你也可以使用外部編輯器，但仍應回到 Godot 執行與檢查引擎層錯誤。

底部面板通常包含輸出、除錯器、音訊、動畫或效能相關工具。它回答的是：「執行與工具操作剛才發生了什麼？」當遊戲看似沒有反應，這裡往往比盯著畫面更早提供線索。

編輯器操作如何變成檔案

當你建立一個場景、加入節點、設定屬性並儲存時，Godot 會把可保存的結構序列化到場景檔。以文字格式保存的.tscn 通常可以被版本控制與文字工具讀取。自訂 Resource 常可存成.tres；匯入的外部素材會由 Godot 建立必要的匯入中繼資料與快取。

這表示 Codex 可以在文字層修改.gd、.tscn、.tres 與部分設定檔。但「可以修改」不等於「適合盲改」。場景檔有特定語法、資源 ID、節點路徑與引用關係。若 Codex 大幅重寫檔案，可能讓 Godot 無法解析，或悄悄遺失編輯器保存的設定。

比較安全的原則是：

1. 腳本可由 Codex 直接建立與修改，但要執行語法與啟動檢查。

2. 簡單場景可由 Codex 產生文字檔，但應立刻由 Godot 載入驗證。

3. 複雜場景、動畫軌、匯入資源與外掛設定，若能由官方 API、編輯器或小步修改完成，通常比整檔重寫安全。

4. 修改前先讀現況，修改後列出差異，不要每次重新生成所有檔案。

編輯器與文字工具不是競爭關係。編輯器適合視覺結構、資源選擇、動畫與即時預覽；Codex 適合搜尋、批次修改、產生腳本、整理結構與建立重複性工作。成熟的流程是讓兩者共享同一份專案來源，並用版本控制記錄變更。

project.godot 是專案設定入口

project.godot 保存許多專案層級設定，例如應用程式名稱、主場景、顯示、輸入動作、渲染與其他 Project Settings。它通常是文字格式，也能由 Godot 編輯器的 Project Settings 介面修改。

這個檔案重要，但不應被神化成「整個遊戲」。場景與腳本仍在各自檔案中；project.godot 比較像全域設定與入口索引。若主場景尚未設定，按下執行專案時，Godot 會要求你指定；若 Input Map 沒有 move_left，腳本讀取這個動作就無法得到預期輸入。

Codex 修改 project.godot 時，最常見風險是覆蓋既有設定、產生重複區段或加入錯誤屬性。你可以要求它只做最小差異，例如「只新增四個 Input Map 動作，不改渲染、視窗與主場景設定」。修改後要在 Project Settings 裡確認，也要啟動專案驗證。

.godot 目錄不是你的正式內容來源

Godot 專案常包含.godot/ 目錄，用來保存匯入快取與編輯器產生的中間資料。官方版本控制指南通常建議忽略這個目錄，因為它可以由專案來源重新建立，而且不同電腦或版本可能產生差異。

初學者有時看到.godot 裡大量檔案，以為那是引擎「自動產生的程式」，便想讓 Codex 修改或把它全部提交。比較正確的理解是：你的正式內容來源主要是專案中的場景、腳本、資源、素材與設定；快取是加速與工作狀態，不應取代來源檔。

若匯入異常，有時刪除適當快取讓 Godot 重建能解決問題，但這不是通用除錯魔法。刪除前要關閉編輯器、保留專案來源與版本控制，並了解重新匯入可能花時間。更不能在不確定時刪除所有隱藏目錄。

素材匯入：原始檔與引擎使用版本的關係

把 PNG、WAV、OGG、字型或 3D 模型放進專案後，Godot 會偵測並匯入。原始素材仍保留在專案中，引擎另外建立適合執行的匯入結果與中繼資料。你可以在 Import 設定調整壓縮、篩選、循環等選項，再重新匯入。

這裡要分清楚三層：

- 原始素材回答「創作者提供了什麼檔案」。

- 匯入設定回答「引擎要如何解讀與轉換」。

- Runtime 資源回答「遊戲執行時實際載入什麼」。

若畫面模糊，不一定要立刻換圖片，也可能是匯入篩選與縮放策略；若音效沒有循環，不一定是腳本錯誤，也可能是音訊匯入或串流設定。Codex 若只看腳本，可能忽略資源設定，因此問題描述要包含相關 Inspector 或 Import 資訊。

Local 與 Remote：場景樹的兩種觀察角度

編輯器中看到的本地場景，主要是保存下來的設計結構。遊戲執行後，Godot 可以讓你查看 Remote 場景樹，也就是當下真正存在於 Runtime 的節點。

兩者可能不同。遊戲會動態實例化敵人、移除收集物、切換關卡、建立特效；這些節點不一定永久寫在原始場景裡。反過來，原始場景中的某個節點可能因條件而未啟用，或在啟動後被移除。

除錯時，Remote 場景樹是一個極有價值的觀察點。若 Codex 說「已建立 EnemySpawner」，你不只檢查檔案是否存在，還要在執行時確認生成的 Enemy 是否真的成為預期父節點的子節點、數量是否正確、離開畫面後是否被清理。

哪些檔案適合修改，哪些必須特別小心

通常適合由 Codex 修改

-.gd 腳本。

- README、設計說明與測試清單。

- 簡單、可重建的.tscn 與.tres。

- 明確指定區段的 project.godot。

-.gitignore、格式設定與開發工具檔。

需要小步修改並立刻驗證

- 複雜場景檔與大量外部資源引用。

- 動畫軌、AnimationTree、TileMap／TileSet 資料。

- 匯出 preset、平台簽章與工具鏈設定。

- 外掛設定、原生擴充與版本遷移。

不應把它當正式來源直接手改

-.godot/ 中的快取與匯入結果。

- 已匯出的執行檔或打包產物。

- 不明來源的二進位資源。

- 平台 SDK、憑證與秘密金鑰。

這不是絕對禁止清單，而是風險分級。越難從文字差異理解、越容易包含工具生成的內部關係，越需要由編輯器或專用流程修改。

建立一個可讀的專案骨架

能量收集者可以先用簡單結構開始：

```textres://├── project.godot├── scenes/│ ├── main/│ ├── player/│ ├── enemies/│ ├── pickups/│ └── ui/├── scripts/├── resources/├── assets/│ ├── images/│ ├── audio/│ └── fonts/└── tests_or_checks/```

這不是 Godot 官方唯一標準，也不是每個小專案都需要完全照抄。重點是讓檔案位置能反映責任，並讓場景、腳本、資料與原始素材有可預測的落點。

有些團隊偏好把腳本放在對應場景旁邊，例如 player/player.gd 與 player/player.tscn 同目錄；有些團隊集中放進 scripts/。兩種方式都可以，關鍵是規則一致、引用清楚、團隊找得到。不要讓 Codex在每次任務中自行發明新的目錄習慣。

Codex 修改專案的安全協議

可以要求 Codex遵守下列順序：

1. 先找到 project.godot，確認專案根目錄與版本基準。

2. 只讀取與任務相關的場景、腳本、資源與設定。

3. 先回報目前結構與預定修改，不立即重寫。

4. 一次完成一個可驗證單元。

5. 修改後列出新增、修改、刪除檔案。

6. 執行可用的語法檢查、無頭啟動或專案啟動檢查。

7. 提醒仍需在編輯器或目標平台人工驗證的項目。

這套順序的價值，是把「AI 能修改檔案」轉成「AI 在專案邊界內可被監督地修改」。

可以直接交給 Codex 的四個任務

任務一：只讀盤點專案

先尋找 project.godot 並確認專案根目錄。只讀取檔案，不做修改。請列出主場景、場景目錄、腳本、Resource、原始素材、外掛、匯出 preset 與版本控制忽略項目；最後指出三個最需要人工確認的地方。

任務二：解釋編輯器與檔案對應

針對 Player 場景，說明 Scene Dock 的節點、Inspector 屬性、掛載腳本與硬碟中的.tscn／.gd 如何對應。不要逐行轉錄場景檔，只指出主要關係與可能風險。

任務三：建立最小資料夾骨架

目前是 Godot 4.7 Stable 的小型 2D 專案。只建立 scenes、assets、resources 與必要子目錄，以及一份 README 說明命名規則。不要建立任何遊戲管理器、腳本或場景。完成後回報實際新增目錄。

任務四：檢查不應提交的內容

檢查 Git 狀態與.gitignore。確認.godot/ 等可重建快取沒有被納入；不要刪除任何尚未確認的來源素材。列出建議忽略項目及理由，等待確認後才修改.gitignore。

Codex 在這一章最可能犯的錯

第一，找錯專案根目錄。它在父資料夾建立檔案，Godot 自然看不到。驗收時先確認所有新檔都位於含有 project.godot 的根目錄下。

第二，整份覆寫設定。它為了新增 Input Map，把 project.godot 其他設定重建成自己想像的內容。要求最小差異，並在變更前後比較檔案。

第三，直接改快取或匯入產物。這類修改可能下一次匯入就消失。要追溯到原始素材、匯入設定或正式資源。

第四，文字檔看似有效，Godot 卻無法解析。任何.tscn、.tres 與設定變更，都要經過 Godot 載入、啟動與錯誤面板驗證。

第五，忽略路徑大小寫。某些開發環境看似容忍，換到大小寫敏感平台後才失效。命名應一致，引用不靠平台寬容。

如何把這一章教給別人

教學時可以做一個「同一份資料的三個視角」示範。先在 Scene Dock 新增一個 Label，再在 Inspector 修改文字，儲存後用文字編輯器開啟.tscn，最後執行遊戲查看 Runtime。學員會看到：編輯器操作、文字檔與執行結果不是三份內容，而是同一個結構在不同階段的呈現。

接著在 Runtime 動態新增一個節點，打開 Remote 場景樹，再停止遊戲。讓學員觀察動態節點為什麼消失，而原始場景檔沒有被永久改變。

最後示範 res:// 與 user://。讀取一份專案內設定，再把玩家偏好寫入使用者資料路徑。這能建立「作品來源」與「執行後資料」的邊界。

口語概念地圖

把專案資料夾想成地面。project.godot 是入口標誌，場景、腳本、資源與素材都放在這塊地面上。編輯器像一棟有不同觀察窗的控制中心：Scene Dock 看樹、Viewport 看空間、Inspector 看屬性、FileSystem 看檔案、Debugger 看執行。

按下執行後，專案資料被載入成 Runtime 的節點實例。這些實例可以新增、改變與消失，但除非你明確存檔，它們不會自動改寫原始設計。Codex站在地面上直接修改來源檔；Godot 編輯器則把修改重新讀進控制中心。兩者之間靠的不是魔法，而是同一套可序列化的專案資料。

聽完後的自我檢查

1. res:// 與 user:// 分別適合什麼資料？

2. Scene Dock、Inspector、FileSystem Dock 與 Remote 場景樹各自回答什麼問題？

3. 為什麼.godot/ 通常不應當成正式內容來源？

4. Codex 可以直接修改.tscn，為什麼仍需要 Godot 載入驗證？

5. 你拿到陌生專案後，第一個應尋找的檔案與邊界是什麼？

章末金句

- 編輯器不是黑盒子，它是專案資料的可視化控制台。

- res:// 是作品來源的根，user:// 是執行後資料的家。

- 看得見檔案，不代表適合整份重寫；可修改性與修改風險是兩件事。

- Runtime 中出現的節點，不一定永久存在於原始場景。

- 快取可以重建，來源才需要被保護。

- Codex 修改的是檔案，Godot 驗證的是這些檔案能否成為一個運轉中的專案。

- 一個安全的 AI 工作流，從確認專案根目錄與只讀盤點開始。
