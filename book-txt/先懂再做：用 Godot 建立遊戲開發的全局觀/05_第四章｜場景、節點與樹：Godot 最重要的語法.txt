第四章｜場景、節點與樹：Godot 最重要的語法

場景明明是一個可以儲存的檔案，為什麼執行後又會出現在場景樹裡？節點明明是場景的一部分，為什麼一整個場景又能被放進另一個場景，像一個節點一樣使用？

這兩個問題一旦釐清，Godot 的很多設計就會突然連成一條線。節點、場景與場景樹不是三套彼此分離的功能，而是同一個組合模型在不同層次的名稱。

官方文件把 Node 稱為 Godot 的基本構成單位。節點可以成為另一個節點的子節點，形成樹狀關係；一棵節點樹可以被保存成場景，場景又能被實例化到其他場景中。執行時，活動節點共同存在於 SceneTree 裡。

如果只記一句話，可以記住：

節點是有責任的零件，場景是可保存與重複使用的組裝模組，場景樹是這些實例在 Runtime 中的組織關係。

Node 不是畫面物件的同義詞

初學者第一次看到節點，常把它理解成「畫面上的一個東西」。這只適用於部分節點。Sprite2D 可以顯示圖像，Label 可以顯示文字，MeshInstance3D 可以顯示 3D 網格；但 Timer 看不見，AudioStreamPlayer 主要負責聲音，Node 本身甚至不帶 2D 或 3D 位置。

比較準確的理解是：一個節點代表一組責任與能力。節點類型告訴引擎它能參與哪一種系統。

- Node2D 及其子類別屬於 2D 空間，具備 2D 變換。

- Node3D 及其子類別屬於 3D 空間，具備 3D 變換。

- Control 及其子類別屬於 UI 版面系統。

- Timer 負責計時與 timeout 事件。

- AnimationPlayer 保存並播放動畫軌。

- AudioStreamPlayer 負責播放音訊串流。

- Area2D 用於偵測其他碰撞物進入或離開指定區域。

因此，替場景新增節點時，不應先問「我要新增哪個圖示」，而是問「現在缺少哪一種責任」。角色需要可控制的物理移動，就考慮 CharacterBody2D；角色需要畫面，就加入 Sprite2D 或 AnimatedSprite2D；需要碰撞範圍，就加入 CollisionShape2D；需要受傷後短暫無敵，就可能加入 Timer。

節點類型不是裝飾名稱，而是你向引擎借用能力的方式。

父子關係同時代表組織、生命週期與變換

在場景樹中，一個節點可以有父節點，也可以有多個子節點。這種關係首先代表組織：Player 節點底下可以有外觀、碰撞、攝影機與計時器。當你在 Scene Dock 展開 Player，就能看見它的內部構成。

父子關係也影響生命週期。當父節點進入 SceneTree，子節點會跟著加入；父節點被移除時，整個子樹通常也會離開。這讓一個角色能以完整單位被建立與清理，而不必逐一處理每個內部節點。

對 2D、3D 與 UI 節點而言，父子關係還可能影響座標與變換。玩家移動時，作為子節點的 Sprite2D 與 CollisionShape2D 會隨父節點一起移動。子節點的 local position 是相對父節點的位置；global position 則是經過整條父鏈計算後，在更大空間中的位置。

但是，父子關係不等於「所有邏輯都應由父節點控制」。父節點可以協調整個角色，子節點仍應保留自己的明確責任。AnimationPlayer 負責播放動畫，不需要同時決定玩家分數；Hitbox 負責偵測攻擊，不需要管理關卡切換。

Scene 是保存下來的節點樹

在 Godot 裡建立一個根節點，再加入子節點並儲存，就得到一個場景檔。場景不是只能代表「一個關卡」。它可以小到一個按鈕、一顆子彈、一個角色，也可以大到主選單或完整關卡。

場景的價值在於，它把一棵有意義的節點樹封裝成可命名、可保存、可重複建立的模組。

例如 Player 場景可以是：

```textPlayer (CharacterBody2D)├── Sprite (AnimatedSprite2D)├── CollisionShape (CollisionShape2D)├── Hurtbox (Area2D)│ └── Shape (CollisionShape2D)├── InvulnerabilityTimer (Timer)└── Camera (Camera2D)```

這棵樹的根是 Player。根節點代表外部世界與這個場景互動時主要看見的角色；內部子節點負責外觀、碰撞、受傷偵測、無敵時間與攝影機。

儲存後，Main 場景可以實例化 Player。這個實例在 Main 的 Scene Dock 中通常像一個節點出現，但它背後仍是整棵 Player 子樹。你可以把它想成「摺疊起來的模組」：外部先看根節點，必要時再進入其內部編輯。

場景既是設計檔，也是可實例化的資源

這裡有一個容易混淆但非常重要的細節。日常設計時，我們把 Scene 與 Resource 分開談：場景偏向節點結構，資源偏向資料。然而在 Godot 的檔案與載入模型中，保存的場景由 PackedScene 表示，而 PackedScene 本身是 Resource。

這表示兩句話都可以成立：

- 在架構思考上，場景是可實例化的節點結構。

- 在載入與保存層，場景檔也是一種能被載入的資源。

本書仍會把「場景」與「資料資源」分開說明，因為它們在設計責任上不同；但不要把兩者想成完全沒有交集的宇宙。理解這一點，也能解釋為什麼程式可以 preload() 一個場景，再呼叫 instantiate() 產生節點實例。

概念如下：

```gdscriptconst ENERGY_SCENE = preload("res://scenes/pickups/energy_pickup.tscn")

func spawn_energy() -> void:var pickup = ENERGY_SCENE.instantiate()add_child(pickup)```

這段程式不是直接把檔案「放到畫面上」。它先取得 PackedScene，再建立一棵新的節點實例，最後把根節點加入目前的場景樹。只有加入 SceneTree 後，這個實例才開始參與生命週期與 Runtime。

Instance：從藍圖變成正在運作的個體

場景檔可以被重複實例化。假設 EnergyPickup 場景只有一份，你卻可以在關卡中放二十個能量物件。這二十個是二十個實例，共用同一份結構來源，卻各自有位置、是否已被收集等 Runtime 狀態。

這和物件導向裡「類別與物件」有相似之處，但不必強迫一一對應。場景更像一個可保存的組合模板，其中不只包含一個類別，也包含多個節點、資源引用與屬性設定。

實例化帶來三個重要能力：

1. 重複使用：不用複製二十份相同節點結構。

2. 集中維護：修改 EnergyPickup 原始場景，可讓所有未覆寫的實例取得更新。

3. 局部差異：每個實例仍能有不同位置、數值或外觀設定。

但局部覆寫也需要管理。如果每個實例都修改很多內部細節，原始場景一更新，差異可能變得難以追蹤。比較好的方式是把真正需要變化的內容暴露成清楚參數，或透過 Resource 提供資料，而不是在每個實例裡任意拆改內部結構。

場景樹是 Runtime 的組織骨架

SceneTree 裡的 /root 是引擎建立的根 Viewport，下面可能包含 Autoload 與目前執行的主場景。當遊戲切換場景、建立敵人、生成特效或移除收集物時，活動樹會持續變化。

每個正在運作的節點都有自己的路徑。若 Main 底下有 Player，Player 底下有 Camera，路徑可以理解為：

```text/root/Main/Player/Camera```

節點可以透過 NodePath、get_node()、$ 簡寫、匯出節點引用或其他方式取得彼此。但路徑越長、越跨越場景邊界，耦合風險越高。若一段腳本硬寫 /root/Main/Level/Player/HUD/ScoreLabel，場景只要重組，引用就可能失效。

封裝思維是：一個場景外部應盡量透過根節點的公開方法、屬性與訊號互動，而不是深入抓取內部每個子節點。就像使用一台機器時，你操作控制面板，而不是每次都伸手轉動裡面的齒輪。

根節點決定場景對外的身分

建立場景時，第一個節點是根節點。根節點類型會影響這個場景的主要身分與能力。Player 若需要直接參與角色移動與碰撞，常以 CharacterBody2D 作根；純 UI 面板可能用 Control；沒有空間位置、只負責協調的服務節點可以用 Node。

選根節點時，可以問：

- 外部世界把這個場景當成什麼？

- 這個場景最主要需要哪一種內建能力？

- 移動、顯示、版面或生命週期應由誰承擔？

- 若內部節點替換，根節點的公開介面能否保持穩定？

不必為了「看起來架構化」而多包一層沒有責任的 Node。也不要只因第一個加入的是 Sprite2D，就讓整個角色以 Sprite2D 作根，後面再勉強掛上物理。根節點是場景的對外合約，應從角色責任出發。

組合優先：讓能力可以拆換

Godot 的場景與節點模型自然鼓勵組合。組合不是說完全不用繼承，而是優先把不同責任放進可替換單元，讓一個物件由多個能力組成。

例如敵人可能包含：

- 外觀與動畫。

- 移動策略。

- 偵測範圍。

- 生命與受傷能力。

- 掉落物生成能力。

- 音效與視覺回饋。

若所有行為都寫進一個兩千行 Enemy 腳本，任何變更都可能牽動全體。若生命能力由獨立 HealthComponent 管理，受傷時發出 health_changed 與 died 訊號，玩家、敵人甚至可破壞物件都能重用。

但組合也不是越碎越好。把每個變數都拆成一個節點，只會增加導覽成本。判斷是否值得拆分，可以看三個條件：責任是否獨立？是否有自己的生命週期或事件？是否會在多個場景重複使用？至少符合其中一到兩項，拆成元件才可能有價值。

Ownership：看得見不等於會被一起存下來

Godot 的 Node 有 owner 概念，會影響節點是否隨某個場景保存。透過編輯器建立節點時，Godot 通常會替你處理；用程式動態建立節點時，加入場景樹不等於自動成為某個 PackedScene 的保存內容。

對初學者而言，不必立刻深入所有 owner API，但要知道兩件事：

1. Runtime 中 add_child() 建立的節點通常只是當下實例的一部分，停止遊戲後不會自動寫回場景檔。

2. 若在編輯器工具或程式中建立要永久保存的場景內容，除了父子關係，還要正確處理 ownership 與保存流程。

這能避免一個常見誤解：「我明明在 Remote 樹裡看到它，為什麼重新開啟場景後不見？」因為活動樹與保存來源是不同層次。

場景應該拆多大

沒有一個固定節點數可以判定場景太大。場景邊界應由責任、重用與變更理由決定。

Player 適合成為場景，因為它有清楚身分，可在不同關卡重複使用，也有自己的內部結構。EnergyPickup 適合成為場景，因為關卡中會多次實例化。HUD 適合成為場景，因為它有獨立版面與更新介面。

相反地，一個只在某關卡出現、結構非常簡單、沒有獨立生命週期的小裝飾，未必需要單獨場景。過度拆分會讓你在大量小檔案之間跳轉；完全不拆則讓主場景變成難以維護的巨樹。

可以用「三個獨立」作判斷：

- 能否獨立理解？

- 能否獨立測試？

- 能否獨立重用或替換？

三者越多成立，越適合成為場景。

對外介面：場景不是只靠節點路徑被操作

一個可維護場景應有清楚的對外介面。介面可以包含：

- 根節點上公開的方法，例如 take_damage(amount)。

- 可由 Inspector 設定的匯出屬性，例如移動速度。

- 代表事件的訊號，例如 died。

- 必要時的 Resource 配置，例如角色數值資料。

外部 Main 場景不應知道 Player 的無敵 Timer 名稱，也不應直接改 Player 內部動畫。它只要呼叫 take_damage(1)，Player 自己決定扣血、無敵、動畫與訊號。這就是封裝：內部可以變，外部合約盡量穩定。

Codex 特別容易為了「快速完成」而跨越邊界。它可能在 Enemy 腳本裡直接抓取 Player/HUD/HealthLabel，再把文字減一。功能能跑，卻讓敵人同時知道玩家內部與 UI 結構。你的驗收應問：這次修改是否穿透了不應知道的場景內部？

能量收集者的場景組合

一個初步 Main 場景可以是：

```textMain (Node)├── World (Node2D)│ ├── Level (Node2D)│ ├── Player (Player scene instance)│ ├── Pickups (Node2D)│ └── Enemies (Node2D)└── UI (HUD scene instance)```

Player、EnergyPickup、Enemy 與 HUD 都是獨立場景。Main 負責把主要模組組合起來，並協調遊戲開始、失敗與重來。World 提供 2D 世界的組織節點，Pickups 與 Enemies 作為動態實例容器，讓 Remote 場景樹更容易觀察與清理。

這只是合理起點，不是唯一答案。小型遊戲也可以讓 Main 以 Node2D 作根，直接包含世界物件；更大型專案則可能把關卡、遊戲流程與 UI 再拆開。重點不是追求最多層，而是每一層都有可說明的責任。

可以直接交給 Codex 的四個任務

任務一：先設計場景樹，不寫程式

以 Godot 4.7 Stable 的小型 2D「能量收集者」為例，只設計 Main、Player、EnergyPickup、Enemy、HUD 五個場景的根節點類型與主要子節點。每個節點都要附一句責任說明。不要建立檔案，也不要加入沒有當前需求的管理器。

驗收：根節點是否符合主要身分？同一責任是否被放在多個節點？是否出現沒有理由的深層階層？

任務二：把巨大角色拆成組合

閱讀目前 Player 場景與腳本，找出同時負責輸入、移動、生命、動畫、音效與 UI 的部分。提出最小拆分方案，只選一個最值得先分離的責任，說明其公開方法、訊號與子節點；在我確認前不要重構。

驗收：Codex 是否一次拆得過度細碎？新元件是否有獨立責任與可驗證介面？

任務三：檢查跨場景路徑

搜尋所有硬編碼的長 NodePath 與從外部深入場景內部的 get_node()。列出路徑、使用目的與失效風險。優先建議以根節點公開方法、匯出引用或 Signal 改善，但不要把所有直接呼叫機械地改成 Signal。

驗收：它是否理解「降低耦合」不是「禁止函式呼叫」？

任務四：驗證動態實例的生命週期

為 EnergyPickup 的動態生成設計一個最小驗收：建立三個實例、加入 Pickups 容器、收集後只移除對應實例，停止與重新啟動後回到初始狀態。請列出需要觀察的 Remote 場景樹位置與日誌，不先實作。

Codex 可能做錯什麼

第一個錯誤，是把「場景」誤解成只能代表整個關卡。結果所有角色與物件都直接建在 Main，失去重用與獨立測試能力。

第二個錯誤，是反向過度拆分。每個視覺節點都做成獨立場景，每個小數值都做一個元件，導致檔案與訊號比真正規則還多。

第三個錯誤，是用長路徑穿透所有邊界。短期省事，場景一改名或換父節點就全部失效。

第四個錯誤，是混淆來源與實例。它修改某個 Runtime 實例，希望所有場景來源一起改；或修改原始場景，卻忽略某些實例已經覆寫屬性。

第五個錯誤，是為了修一個節點名稱，整份重寫.tscn，造成資源 ID、訊號連接或其他屬性遺失。應要求最小變更並用 Godot 重新載入。

如何把這一章教給別人

教學時，可以準備一個「角色模型盒」。第一步只放一張 Player 卡片；第二步打開卡片，露出外觀、碰撞、生命、動畫與計時器；第三步複製三張 Player 實例卡放進不同關卡。學員會直覺理解：場景是可重用模組，實例是正在使用的個體。

接著用積木示範父子關係。移動父積木，子積木跟著移動；移除父積木，整組離開。再提醒：跟著移動不表示父積木要替每一個子積木做所有決策。

最後打開 Remote 場景樹，在 Runtime 生成與移除 EnergyPickup。讓學員看到「場景檔」「實例」「活動樹」三者的差異。這比只背定義更容易形成長期記憶。

口語概念地圖

先想像一個節點。節點有自己的類型與責任。把幾個節點依父子關係接起來，就形成一棵小樹。當這棵樹有明確意義並被保存，它成為場景。場景檔被載入後可以實例化，每一次實例化都產生一棵新的節點子樹。把這棵子樹加入活動 SceneTree，它才進入 Runtime、接收生命週期與處理。

場景還能被放進另一個場景，所以小樹能成為大樹的一個分支。整個遊戲不是一棵一次寫死的大樹，而是許多可保存、可實例化、可替換的小樹，在 Runtime 中組成活動森林。

聽完後的自我檢查

1. Node、Scene、PackedScene、Instance 與 SceneTree 分別位於哪個層次？

2. 為什麼節點不等同於可見畫面物件？

3. 父子關係會影響哪些組織、生命週期與空間行為？

4. 場景適合拆分的「三個獨立」是什麼？

5. 外部場景為什麼應優先透過根節點公開介面，而不是深入抓取內部節點？

章末金句

- 節點不是一個圖示，而是一組被引擎理解的責任。

- 場景是保存下來的節點樹，也是可以反覆實例化的結構模組。

- Runtime 裡存在的是實例，不是硬碟上的場景檔本身。

- 父子關係讓能力一起移動與生滅，卻不代表所有責任都交給父節點。

- 場景邊界應跟著責任與重用走，不跟著節點數量走。

- 組合的目的不是拆得最多，而是讓改變發生在正確的地方。

- 一個好的場景對外提供穩定合約，對內保留可替換結構。

- 當你看懂場景樹，就開始看見遊戲的組織骨架。
