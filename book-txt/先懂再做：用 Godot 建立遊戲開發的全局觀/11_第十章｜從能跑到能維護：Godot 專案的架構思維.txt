第十章｜從能跑到能維護：Godot 專案的架構思維

一個功能能跑，和一個專案能繼續成長，是兩件不同的事。

最初只有 Player、Pickup 與一個分數 Label 時，任何程式放在哪裡似乎都可以。Player 直接更新 HUD，Pickup 直接改全域分數，Main 同時生成敵人、播放音樂、存檔與切換場景。功能少時，這種方式甚至看起來最快。

問題通常在下一次變更才出現。要新增第二個關卡，Main 裡寫死的節點路徑失效；要讓 HUD 換版面，Player 腳本也跟著要改；要測試 Enemy，卻必須先啟動完整遊戲；要讓 Codex 修分數，結果它碰到存檔與場景切換。專案不是因為檔案很多才變複雜，而是因為改一件事會不可預測地影響其他事。

架構的目的不是讓專案看起來專業，而是讓變更範圍可預測、責任可說明、錯誤可定位、AI 修改可驗收。

單一責任不是「每個檔案只做一行」

單一責任原則常被誤解成把程式拆得越細越好。更實用的定義是：一個模組應有一個主要的變更理由。

Player 會因角色移動規則變更而修改；HUD 會因畫面呈現變更而修改；SaveService 會因存檔格式與儲存策略變更而修改。若 Player 腳本同時處理 UI 版面與存檔，它就有多個不相關的變更理由。

責任大小要符合專案規模。小型角色腳本同時處理輸入與移動可能合理，因為兩者高度相關；但當要支援 AI 控制、網路同步或多種輸入來源時，輸入意圖與移動執行就可能值得分離。

不要在需求尚未出現前為每個可能性建立抽象層。好的架構不是預測所有未來，而是讓今天的責任清楚，明天需要變更時有可拆的接縫。

場景邊界與腳本邊界要互相支持

場景負責組合節點，腳本負責表達行為。若一個場景被視為獨立模組，它的腳本也應提供清楚對外介面。

例如 Player 場景內部可以有 HealthComponent、AnimatedSprite2D 與 InvulnerabilityTimer。外部只看 Player 根節點的方法 take_damage()、reset()，以及 signals health_changed、died。內部節點名稱、動畫切換與 Timer 細節不必被 Main 知道。

反過來，若腳本宣稱 Player 是封裝模組，外部卻到處用 $Player/Hurtbox/InvulnerabilityTimer，場景邊界就只停留在檔案表面。

審查一個場景時，可以問：

- 外部需要知道哪些公開方法、屬性與事件？

- 哪些內部節點應允許替換而不影響外部？

- 誰負責建立與清理這個場景？

- 能否在一個小測試場景中獨立運行？

若這四題說得清楚，場景通常有健康邊界。

高耦合與低耦合不是有沒有連線

耦合是模組彼此依賴的程度。完全沒有耦合的遊戲無法互動，因此目標不是零耦合，而是讓依賴明確、必要、方向合理。

高風險耦合常見於：

- 依賴固定的深層 NodePath。

- 直接讀寫其他模組的內部變數。

- 雙方互相持有並在生命週期上彼此假設。

- 一個全域管理器知道所有場景細節。

- 修改一個資料格式，需要同時改許多無關模組。

較健康的依賴通常是：

- 父場景明確擁有子場景。

- 呼叫對方公開方法，而非內部節點。

- 以 Signal 宣告已發生事件。

- 透過 Resource 傳遞清楚資料。

- 依賴抽象角色或群組契約，而不是具體場景路徑。

低耦合仍需要可追蹤。若事件經過三層全域匯流排才到接收者，表面上雙方沒有引用，實際上除錯更困難。架構要同時追求依賴少與事件路徑可見。

Autoload：長生命週期工具，不是萬物收納箱

Godot 的 Autoload 可以在專案啟動時自動加入節點或腳本，並在場景切換間持續存在。常見用途包括遊戲流程、使用者設定、音訊服務、全域事件或資料庫入口。

它的便利也使它容易被濫用。任何地方都能存取 Autoload，於是分數、玩家、HUD、存檔、聲音、網路與場景切換全塞進 Global.gd。短期少傳幾個引用，長期卻形成無邊界的共享狀態。

判斷是否適合 Autoload，可以問：

1. 這個服務是否真的需要跨場景長期存在？

2. 是否應該只有一個實例？

3. 它是否提供明確介面，而不是公開大量可任意改的變數？

4. 是否能在測試時替換或重設？

5. 若拿掉全域存取，誰應該擁有它？

例如 UserSettings 適合跨場景存在；目前關卡裡的一隻 Enemy 不適合。GameFlow 可能適合管理主選單與關卡切換，但不應因此深入修改每個 Player 子節點。

官方最佳實務也提醒，要考慮 Autoload 與一般節點的取捨。能由場景自然擁有的依賴，不必為方便全部提升成全域。

GameManager 的適用與濫用

「建立 GameManager」是 AI 常見答案，因為它聽起來能集中管理。但 GameManager 這個名稱本身沒有責任邊界。

一個合理的 GameFlow 可以只管理遊戲階段與場景轉換；ScoreService 管分數規則；SaveService 管存檔；AudioService 管全域音訊。是否要分成多個 Autoload，仍取決於規模，但至少命名應表達責任。

若一個 GameManager 有五十個變數、二十個 NodePath、知道所有 UI、玩家、敵人與資源，任何功能都會依賴它。它成為 God Object：看似中心，實際上是變更瓶頸。

改善方法不是立刻把它切成十個 Manager，而是先列出它有哪些變更理由，再挑最獨立、最常變或最容易測試的責任分離。小步重構比一次性重新架構安全。

組態、設計資料、Runtime 狀態與存檔要分層

專案架構常因資料生命週期混亂而失控。可以分成四層：

- 組態：視窗、輸入、語言、音量預設、功能開關。

- 設計資料：角色能力、關卡目標、敵人數值、物品內容。

- Runtime 狀態：目前生命、分數、場上敵人、當前階段。

- 持久存檔：要跨啟動保存的進度、解鎖、偏好。

同一個概念可能跨層，但不能混成同一份可任意修改資料。例如最大生命是設計資料，目前生命是 Runtime 狀態；玩家選擇的音量是持久偏好，實際 AudioServer 當下音量是 Runtime 表現。

存檔不應直接序列化整棵 SceneTree。場景中有暫時節點、引擎引用、訊號連線與不可穩定保存的狀態。較好的方法是由明確對象輸出可保存資料，再由載入流程重建 Runtime。

存檔是一份版本化合約

最簡單的存檔可能只有：

```json{"version": 1,"high_score": 42,"unlocked_levels": [1, 2, 3]}```

一旦發布，這份格式就成為舊玩家資料與新版遊戲之間的合約。未來新增欄位、重新命名、改型別，都要考慮舊檔如何遷移、缺少欄位如何給預設值、損毀檔如何回復。

Codex 很容易只寫「儲存」與「載入」成功路徑，忽略：檔案不存在、JSON 解析失敗、版本太舊、寫入中斷、資料值超出範圍、平台儲存限制。小型教學專案可以簡化，但仍要在架構上保留版本欄位與錯誤處理。

存檔也不等於防作弊。純本地 JSON 很容易被修改；若產品需要安全性、雲端同步或交易完整性，就需要另一套威脅模型。本書只建立資料生命週期，不承諾簡單存檔足以處理所有商業需求。

場景切換：先決定誰擁有流程

切換場景可以很簡單，但專案一大，常需要淡入淡出、載入畫面、保存狀態、釋放舊資源與處理失敗。

若每個按鈕、敵人與關卡都能直接呼叫 change_scene_to_file()，流程會分散。比較清楚的方式是由 GameFlow 或主層協調：UI 發出 start_requested，關卡發出 completed，GameFlow 決定下一個場景與轉場政策。

場景切換時要確認：

- 哪些 Autoload 會保留？

- 舊場景是否有未完成 await、Timer 或外部引用？

- 音樂是否持續或切換？

- 玩家進度何時保存？

- 新場景載入失敗時怎麼處理？

- 是否重複連接全域訊號？

這些都是生命週期與所有權的延伸。

可重用元件：從第二次重複開始辨認

重用不一定要一開始設計。很多真正有價值的元件，是在第二次或第三次出現相似需求時才被看見。

例如 Player 與 Enemy 都需要生命、受傷與死亡事件。你可以抽出 HealthComponent。抽取前先確認共同部分：最大生命、目前生命、take_damage、heal、health_changed、died。不同部分如玩家無敵、敵人掉落、Boss 階段，不一定塞進同一元件。

一個可重用元件應有：

- 清楚輸入與公開方法。

- 清楚事件輸出。

- 最少的場景外部假設。

- 可設定資料。

- 獨立測試情境。

若元件仍硬寫 /root/Main/Player，它只是換了檔名，沒有真正可重用。

資料夾與命名：讓人與 Codex 都能預測

架構也存在於檔案系統。命名不必追求一個全球唯一規則，但要一致。

可以選擇以功能垂直分組：

```textfeatures/├── player/├── pickups/├── enemies/└── hud/```

也可以依資產類型分組：

```textscenes/scripts/resources/assets/```

小型專案採類型分組容易理解；功能增加後，垂直分組能讓同一功能的場景、腳本、Resource 與測試靠近。最重要的是不要兩種規則混用到找不到東西。

命名應讓路徑在口語中可辨認。player_controller.gd 比 pc_new2.gd 清楚；energy_pickup.tscn 比 thing.tscn 可搜尋。Node 名稱也要穩定，尤其程式使用 NodePath 時。

Codex 對規則一致的專案表現通常更好，因為它能從附近檔案推測模式。README、命名規則與小型架構說明，不只是給人看的文件，也是在縮小 AI 的自由猜測空間。

小型與大型專案的架構不應一樣

小型遊戲的價值是回饋快。過早加入依賴注入框架、事件總線、資料庫層、複雜狀態機與建置管線，可能讓學習焦點從遊戲規則轉成架構維護。

大型專案則需要更明確的模組、資產流程、自動測試、版本控制策略、建置與發布管線。多人團隊還要管理檔案衝突、責任界面與審查。

架構應隨風險成長。可以用三個階段：

1. 原型：驗證核心玩法，允許暫時簡化，但保留基本命名與版本控制。

2. 可玩版本：建立場景邊界、資料責任、狀態流程與重複測試。

3. 可交付版本：加上存檔遷移、平台設定、效能量測、錯誤處理、文件與建置驗證。

不要拿大型產品標準阻止原型，也不要把原型債務假裝成可交付架構。

重構：保持行為，改善結構

重構的核心，是在不改變外部預期行為的前提下改善內部結構。它需要測試或至少明確驗收，否則「重構」很容易變成無法分辨的新功能與重寫。

讓 Codex 重構時，先固定行為：玩家速度、受傷規則、訊號、場景入口與存檔格式不變。一次只處理一個責任，例如把生命邏輯移到 HealthComponent。完成後跑既有驗收，再進下一步。

不要用「請優化整個專案」作指令。AI 可能更名、搬檔、改 API、重寫場景與格式，讓問題範圍不可控。重構必須指定不變條件與回退點。

能量收集者的建議責任圖

- Main／GameFlow：啟動、遊戲階段、關卡與轉場協調。

- World／Level：世界內容與生成容器。

- Player：輸入意圖、移動與角色公開介面。

- HealthComponent：生命規則與事件。

- Pickup：偵測收集、提供價值、發出事件。

- GameState／ScoreModel：分數與目標的唯一真相。

- HUD：顯示狀態、提出 UI 意圖。

- SaveService：將可持久資料寫入與讀出 user://。

- UserSettings：音量、語言與顯示偏好。

這張圖不要求每一項都是 Autoload 或獨立腳本。它先表達責任，再由規模決定實作邊界。

可以直接交給 Codex 的五個任務

任務一：建立責任盤點

只讀取專案。以場景／腳本為單位，列出每個模組的主要責任、公開方法、signals、擁有的資料、外部依賴與變更理由。標出責任超過三類或跨越 UI、存檔、世界規則的檔案，不先修改。

任務二：找出全域狀態風險

審查 Autoload 與任何 Global／GameManager。列出每個欄位由誰讀、由誰寫、是否跨場景需要、是否有重設方法。將「合理長生命週期服務」與「為方便而全域化的狀態」分開。

任務三：最小元件抽取

Player 與 Enemy 都有生命邏輯。提出 HealthComponent 的最小公開介面、Resource 依賴、signals 與測試場景。保證外部 take_damage 行為不變，只選一個角色先遷移，完成驗收後再處理另一個。

任務四：存檔合約

先設計 SaveData v1，不寫檔。列出欄位、型別、預設、驗證、未知欄位處理、檔案不存在、損毀與未來版本遷移策略。區分設計資料與玩家持久狀態。

任務五：受控重構

這次唯一目標是把 HUD 更新從 Player 移除，改由 health_changed Signal 驅動。不可改玩家受傷規則、節點名稱、存檔格式與場景切換。修改前列計畫，修改後列檔案差異與人工驗收步驟。

Codex 可能做錯什麼

第一，看到架構問題就重寫完整專案，讓行為與結構同時變動，無法驗收。

第二，將所有服務改成 Autoload，表面降低傳參，實際增加全域耦合。

第三，為每個責任建立 Manager，產生大量只有轉呼叫的中介層。

第四，把 Runtime SceneTree 直接序列化成存檔，忽略不穩定引用與版本遷移。

第五，抽取元件後仍依賴固定 Player 路徑，沒有真正形成公開介面。

第六，搬移檔案卻未更新.tscn、.tres、腳本與 Resource 路徑，或大小寫不一致。

第七，以「最佳實務」為名增加與當前需求無關的抽象。架構應解決可觀察問題。

如何把這一章教給別人

先準備一份刻意混亂的小專案圖：Player 連 HUD、HUD 改分數、Enemy 直接切換場景、Global 保存所有節點引用。請學員只做一件事：沿著「玩家受傷」追蹤所有被修改的模組。

接著把同一流程重畫成公開方法、生命元件、Signal 與 HUD 顯示。比較兩張圖，不談抽象名詞，直接看「改受傷規則要碰幾個地方」。

再讓學員替 GameManager 內容分類。把音量、分數、玩家引用、存檔、場景切換、語言放到不同責任盒子，決定哪些真的需要跨場景。這能破解「全域比較方便」的直覺。

最後做受控重構：先寫不變條件，讓 Codex 只移動一個責任，完成後按清單驗收。學員會看到架構不是畫完就好，而是一種可回退的變更方法。

口語概念地圖

場景界定結構，腳本界定行為，Resource 界定設計資料，Runtime 對象擁有當下狀態。父場景擁有子場景，模組透過公開方法與 Signal 溝通。只有需要跨場景且單一存在的服務才提升到 Autoload。存檔把經挑選的持久狀態寫入 user 路徑，不複製整棵 Runtime 樹。

架構像道路系統。不是讓每兩棟房子都沒有連線，而是讓主要道路、入口與責任清楚，避免任何人為了近路穿過別人的客廳。

聽完後的自我檢查

1. 單一責任真正指的是一個模組只有一行工作，還是一個主要變更理由？

2. 低耦合與沒有依賴有什麼差異？

3. 哪些條件使一個服務適合 Autoload？

4. 組態、設計資料、Runtime 狀態與持久存檔如何區分？

5. 為什麼存檔應被視為版本化合約？

6. 受控重構必須先固定哪些不變條件？

章末金句

- 能跑是功能完成的起點，不是專案可維護的證明。

- 單一責任不是拆得最細，而是讓變更理由保持清楚。

- 低耦合不是沒有道路，而是道路不穿過不該知道的內部。

- Autoload 適合長生命週期服務，不適合收納所有方便取得的狀態。

- GameManager 的名字不能代替責任邊界。

- 存檔不是 SceneTree 的快照，而是經選擇、可版本化的資料合約。

- 架構應隨風險成長，原型與可交付產品需要不同強度。

- 重構先保護行為，再改善結構；沒有驗收的重寫不能叫受控重構。
