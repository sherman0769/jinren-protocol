第十一章｜如何指揮 Codex 開發 Godot，而不是讓它自由發揮

「幫我做一個 Godot 遊戲」不是一個開發規格，而是一張邀請 AI 自行猜測的空白支票。

Codex 的確能讀取專案、修改檔案、執行指令、回答程式碼問題與協助除錯。以 Codex CLI 為例，官方文件將它描述為可在所選專案目錄中檢查、編輯與執行程式的 coding agent；也建議在工作前後建立 Git checkpoint，讓變更可檢查與回復。

但工具能力越完整，任務邊界越重要。Codex 能一次改十個檔案，不代表你應該一次要求十個互相依賴的功能。它能執行命令，不代表已在真正圖形環境、目標平台與玩家流程完成驗收。它能說明自己做了什麼，也不代表說明必然與實際差異完全一致。

本章的核心方法是：

人負責定義意圖、邊界與驗收；Codex 負責在邊界內讀取、修改、執行與回報；Godot 與目標平台負責提供最後證據。

把 Codex 看成可操作專案的工程代理

若把 Codex 只看成「比較會寫程式的聊天機器人」，你容易把工作停在產生程式碼片段。若把它看成工程代理，就會關心完整迴路：讀取現況、提出計畫、修改檔案、執行檢查、查看輸出、修正失敗、整理差異與交付說明。

Codex 可出現在不同介面與執行環境，例如本機 CLI、IDE 整合、桌面／ChatGPT 介面或雲端任務。每個環境的權限、檔案可見範圍、網路、工具與執行時間不同。這些產品細節會更新，因此書中不把某個按鈕位置當成永久流程；穩定原則是：先確認它能看見什麼、能修改什麼、能執行什麼，以及哪些動作需要你的核准。

對 Godot 專案尤其要確認：

- Codex 是否在包含 project.godot 的正確根目錄工作？

- 環境是否已安裝相符版本的 Godot 可執行檔？

- 是否能執行無頭啟動、語法解析或測試命令？

- 圖形、音訊、輸入與目標平台行為是否仍需人工驗證？

- 是否有 Git 或其他回退機制？

- 秘密、簽章憑證與平台 SDK 是否被正確隔離？

能力不清楚，就不能把「沒有報錯」當成「功能完成」。

先讓 Codex 閱讀，不要讓它先猜

拿到既有專案，第一個任務通常不應是「重構」或「新增功能」，而是盤點。

要求 Codex 找到專案根目錄、主場景、Autoload、Input Map、場景樹、核心腳本、Resource、外掛、匯出 preset 與測試方式。讓它說明目前命名規則與相似功能如何實作，再提出修改計畫。

這樣做有三個好處。

第一，它比較不會在已有 GameFlow 時又建立 GameManager。

第二，它能沿用專案既有場景、訊號與資料模式，降低風格分裂。

第三，你能先檢查它是否真正理解專案。若它連主場景都認錯，現在就阻止修改，比改完十個檔案後才發現便宜得多。

一個有效的只讀指令可以是：

找到 project.godot 後只讀取相關檔案。請畫出從 Main 到 Player、Pickup、GameState 與 HUD 的場景／事件關係，列出分數與生命的單一真相來源，以及目前可用的啟動與測試命令。在我確認前不要修改任何檔案。

「不要修改」不是禮貌語，而是任務權限。

用八格規格單把願望變成工作

本書提出「八格規格單」，作為與 Codex 協作的固定入口。這不是 OpenAI 或 Godot 官方標準，而是一個降低猜測的工作模板。

第一格：目前版本

寫出 Godot 4.7 Stable、標準版或.NET 版、GDScript 或 C#、目標作業系統、渲染方法與重要外掛版本。若不確定，也要寫「待確認」，不要讓 Codex自行選擇後假裝是既定條件。

第二格：專案現況

指出專案根目錄、主場景、相關場景與腳本，以及功能目前怎麼運作。若有錯誤，附上完整錯誤訊息、重現步驟與最近變更。

第三格：這次唯一目標

一次只說一個可驗證結果。例如「新增受傷後一秒無敵」，而不是「把戰鬥系統做好」。唯一目標不代表只改一行，而是所有修改都服務同一個結果。

第四格：不可破壞事項

寫出必須維持的行為、公開方法、Signal、節點名稱、存檔格式、平台與效能限制。這是受控變更的護欄。

第五格：預期結構

描述場景樹、檔案位置、資料所有權與公開介面。你不必指定每行程式，但要說明責任應放在哪裡。

第六格：預期行為

使用觸發、前置狀態、狀態變更、輸出與例外描述。例如：「Player 在 Playing 且非無敵時接觸 Enemy，生命減一，啟動一秒無敵；無敵期間再次接觸不扣血；生命歸零只發出一次 died。」

第七格：驗收條件

列出可觀察證據：啟動無解析錯誤、兩次快速碰撞只扣一次、HUD 同步、GameOver 只出現一次、重新開始後無敵狀態歸零、三十與一百二十 FPS 下時間一致。

第八格：修改回報

要求 Codex 列出新增／修改／刪除檔案、關鍵設計決策、實際執行命令、結果、未驗證事項與回退方法。

八格填得越清楚，Codex 越少需要以一般慣例替你補空白。

一份完整的 Godot 任務指令

下面是一份可直接改寫的範例：

版本：Godot 4.7 Stable，標準版，GDScript，2D，Compatibility renderer。現況：專案根目錄含 project.godot；Player 場景根為 CharacterBody2D，已有 take_damage(amount) 與 health_changed、died signals；Enemy 以 Area2D 接觸傷害。唯一目標：新增玩家受傷後一秒無敵。不可破壞：不得更名既有 signals、不得改 HUD 與存檔格式、不得建立新的 Autoload、不得重寫完整 Player 場景。預期結構：無敵狀態由 Player 擁有；可使用現有或新增 Timer 子節點；Enemy 只呼叫 Player 公開的受傷介面，不得直接改生命或 HUD。預期行為：只有 Playing、生命大於零且非無敵時扣血；扣血後無敵一秒；期間接觸不扣血；時間到恢復；死亡只觸發一次。驗收：連續碰撞十次只扣一點；一秒後可再受傷；暫停期間無敵計時政策需先說明並一致；重新開始後狀態重設；Godot 啟動無解析錯誤。回報：先讀取並提出計畫；修改後列檔案 diff 摘要、執行命令與尚需人工在編輯器驗證的項目。

這份指令沒有規定每一行，但已限制結構、所有權、行為與證據。這才是「指揮」，不是把完整答案先自己寫出來。

一次只修改一個可驗證單元

AI 擅長把相連需求一起展開。你說加入收集物，它可能順便加分數、UI、音效、存檔與關卡完成。從展示角度很驚喜，從工程角度卻難以定位錯誤。

較好的分解順序是：

1. 建立 EnergyPickup 場景與碰撞事件。

2. 驗證玩家進入時只發出一次 collected。

3. 連接 GameState，更新唯一分數。

4. 連接 HUD，顯示 score_changed。

5. 加入收集動畫與音效。

6. 加入目標分數與完成狀態。

7. 最後決定是否保存最高分。

每一步都有可觀察輸入與輸出。若第三步失敗，你不用在 UI、音效與存檔中一起找。

「小步」不是要求 Codex 每次只改一行，而是讓一次變更能被完整驗收與回退。

要求它先計畫，但計畫不能取代結果

對跨多檔案任務，讓 Codex 先提出計畫很有用。計畫應包含：現況理解、預計修改檔案、責任分配、測試與風險。你可以在它尚未改檔前發現過度架構或版本誤解。

但計畫不是完成。AI 可能寫出漂亮計畫，實際 diff 卻走另一條路。因此修改後仍要比較：

- 計畫中的檔案與實際檔案是否一致？

- 宣稱執行的命令是否真的有輸出？

- 驗收條件是否逐項有證據？

- 有沒有順手修改未在計畫中的內容？

- 有沒有把無法驗證的項目誤寫成已通過？

讓 Codex「說明做了什麼」只是第一層；Git diff、Godot 錯誤面板與 Runtime 行為才是證據。

Git checkpoint：讓每次協作都有回退點

官方 Codex CLI 快速入門建議在任務前後建立 Git checkpoint。這個習慣對 Godot 特別重要，因為場景、資源、設定與腳本可能同時變更。

基本流程是：

1. 任務前確認工作樹狀態，提交或暫存自己尚未完成的變更。

2. 建立清楚 checkpoint 或分支。

3. 讓 Codex 完成單一任務。

4. 檢查 diff，排除快取、秘密與意外搬移。

5. 執行 Godot 啟動、測試與人工驗收。

6. 通過後提交；不通過就針對差異修正或回退。

如果專案一開始就有大量未提交變更，AI 修改與原本工作混在一起，回退會非常困難。版本控制不是最後備份，而是協作邊界。

Godot 專案還要注意.godot/ 等快取忽略、文字場景衝突與資源路徑。不要讓 Codex 為了「清理」刪除未知但尚未提交的素材。

AGENTS.md 與專案內指示：把穩定規則放進儲存庫

Codex 可使用專案內的 AGENTS.md 等指示檔理解工作規則。產品與語法可能更新，實際使用時應查最新官方文件；概念上，它能保存每次都不想重新口述的穩定資訊。

一份適合 Godot 專案的指示可包含：

- 技術基準：Godot 4.7 Stable、GDScript。

- 啟動與檢查命令。

- 資料夾與命名規則。

-.godot/ 不修改、不提交。

- 場景檔只做最小差異，複雜動畫不整檔重寫。

- 不新增 Autoload，除非任務明確要求。

- signals、公開方法與存檔格式的相容政策。

- 修改前閱讀哪些架構文件。

- 完成時必須回報哪些驗收證據。

指示檔不宜把整本書塞進去。它應像專案入口索引：短、穩定、可操作，並指向更詳細文件。過長且互相矛盾的規則也會讓代理難以決策。

如何讓 Codex 執行 Godot 檢查

Godot 支援命令列與無頭模式，可用來啟動專案、執行腳本、匯入資源、跑測試工具或匯出。具體參數要以 Godot 4.7 官方命令列文件與專案環境為準。

一個基本自動檢查層級可以是：

1. 確認 project.godot 可被相符 Godot 版本讀取。

2. 以無頭模式啟動並在短時間後退出，觀察解析與載入錯誤。

3. 執行專案已有的單元或整合測試。

4. 檢查關鍵場景是否可載入。

5. 在可用環境執行 export preset 的 dry run 或實際匯出。

6. 最後由人以圖形模式測試輸入、畫面、音訊與手感。

命令成功只能證明它涵蓋的範圍。無頭啟動通過，不等於碰撞手感正確；場景可載入，不等於 UI 在手機安全區可用。驗收要把「自動證據」與「人工觀察」分開。

如何把錯誤訊息交還 Codex

不要只說「不能跑」。提供：

- 完整錯誤訊息與堆疊。

- Godot 版本與執行方式。

- 發生前的操作步驟。

- 預期與實際結果。

- 是否每次發生。

- 最近一次已知正常版本或 diff。

- 相關場景樹與資料狀態。

然後要求 Codex 先建立假設排序，不要直接試十種修法：

根據錯誤與堆疊列出最多三個可能原因；每個原因附支持證據、最小驗證與可能修正。先執行不破壞資料的檢查，確認原因後再修改。

這能避免「散彈式除錯」：改節點名、加 null 檢查、延遲一幀、搬到 _ready()，最後錯誤消失，卻沒有人知道為什麼。

防止 API 幻覺與版本混用

Codex 可能產生不存在的類別、方法、屬性或訊號，也可能混入 Godot 3、4.6 或 4.8 的寫法。這不是只靠提醒「不要幻覺」就能消除，需要建立驗證流程。

1. 指令明寫 Godot 4.7 Stable。

2. 要求列出新增使用的關鍵 API。

3. 對不確定 API 查 Godot 4.7 stable docs 類別頁。

4. 讓 Godot 實際解析與載入。

5. 對版本敏感功能加入來源與查閱日期。

6. 不讓 Codex 以 blog 或舊教學取代官方文件。

若 Codex 無網路，也可以把必要官方文件或類別說明加入專案知識檔；但要記錄版本，避免本地文件本身過期。

API 幻覺不只是不合法名稱。有時方法存在，卻不適合該節點類型、執行階段或平台。真正驗證仍需回到類別合約與 Runtime。

權限與安全：能做不等於應該直接做

Codex 可能有權執行命令、安裝套件、存取網路或修改廣泛檔案。權限應依任務最小化。

- 只需要讀取時，不給寫入。

- 只修改專案時，不讓它碰使用者其他目錄。

- 不把商店憑證、API key、簽章金鑰放進可讀的公開專案。

- 安裝外掛或系統套件前先審查來源與版本。

- 執行刪除、大量搬移、重置 Git 等破壞性命令前要求核准。

- 雲端任務要確認資料與儲存庫存取政策。

這不是不信任 AI，而是一般工程最小權限原則。可靠協作來自可見邊界，不是把所有權限一次開滿。

何時重構，何時不要重寫

出現下列情況時，可考慮小步重構：

- 同一規則重複三次以上。

- 一個模組有多個不相關變更理由。

- 測試功能必須啟動完整遊戲。

- 長 NodePath 與全域狀態讓修改經常失效。

- 新需求明確被現有結構阻礙。

不應只因 Codex 說「可以更乾淨」就重寫。若功能穩定、需求不會擴張、沒有測試、交付在即，大規模重構風險可能高於收益。

要重寫前至少回答：現有結構哪個具體問題不能小修？哪些行為必須不變？如何逐步遷移？如何回退？如何比較舊與新？

AI 很擅長產生新版本，卻不自然地承擔舊資料、既有使用者與邊界相容成本。人必須把相容性寫進任務。

Codex 回報的標準格式

可以要求每次完成後固定回報：

1. 任務結果：完成、部分完成或未完成。

2. 修改檔案：新增、修改、刪除。

3. 設計決策：為什麼放在這個場景、節點或 Resource。

4. 實際命令：執行過哪些檢查。

5. 檢查結果：通過、失敗與完整關鍵輸出。

6. 人工驗收：還需在 Godot 編輯器做什麼。

7. 已知限制：尚未處理與版本風險。

8. 回退方式：checkpoint、commit 或需要還原的檔案。

這個格式讓你能比較不同任務，也讓下一次 Codex 會話更容易接手。

一次完整協作迴路

以新增金色能量為例：

第一步，人定義：金色能量使用既有 Pickup 場景，只透過 PickupData 改圖像、音效與 value，不複製收集邏輯。

第二步，Codex 只讀取 Pickup、PickupData、GameState 與資源目錄，提出新增一份.tres 的計畫。

第三步，人確認不可破壞：普通能量行為、signal 名稱、分數唯一來源不變。

第四步，Codex 建立資源並在測試關卡加入一個實例，執行 Godot 載入檢查。

第五步，人驗收：普通能量加一，金色加五；兩者只被收集一次；只有金色播放新音效；重新開始後都重建。

第六步，檢查 diff，確認沒有複製腳本、修改共享材質或加入不明素材。

第七步，提交 checkpoint 與更新資源登錄。

這個流程不需要你親手打完程式，但每個決策與證據都在你的控制之下。

可以直接使用的四組指令

指令一：陌生專案接手

你現在位於一個 Godot 4.7 Stable 專案。先找到 project.godot，只讀取專案。回報主場景、Autoload、Input Map、渲染方法、目標平台、核心場景與腳本、Resource、測試／啟動命令、Git 狀態與三個最高風險。不要修改、安裝或刪除任何內容。

指令二：單一功能修改

使用八格規格單執行。先重述版本、現況、唯一目標、不變條件、結構、行為、驗收與回報格式；指出任何缺口並採最保守假設。先列計畫，經現有資料可判斷時直接做最小修改，不擴張需求。

指令三：除錯

不要先改程式。根據完整錯誤、堆疊、重現步驟與最近 diff，列最多三個原因；每個原因提供證據、最小檢查與預期結果。依破壞性最低順序執行，確認根因後只修該問題，最後重跑原重現步驟。

指令四：交付前審查

以審查者角色工作，不新增功能。比較需求、Git diff、Godot 啟動輸出與人工驗收清單。找出版本混用、場景檔整體重寫、深層 NodePath、全域狀態、共享 Resource 修改、未處理錯誤、未更新文件與未驗證平台項目。每項附檔案與證據。

Codex 可能做錯什麼

第一，沒有讀現況就建立平行架構。

第二，把「完成」理解成程式碼已生成，而不是驗收已通過。

第三，執行了某個命令就宣稱圖形、音訊與手感都正確。

第四，引用不存在或錯版本 API，或把網路範例當 4.7 官方事實。

第五，為解決局部問題順手格式化、搬移或重寫大量檔案，使 diff 難以審查。

第六，忽略未提交變更，回退時覆蓋人的工作。

第七，為了通過錯誤而吞掉例外、加入大量 null 檢查或延遲，沒有修根因。

第八，把秘密、憑證或平台 SDK 當成一般專案檔處理。

如何把這一章教給別人

第一個活動是比較兩個 Prompt。一個只有「幫我加無敵功能」，另一個使用八格規格單。讓學員預測 Codex 可能自行決定哪些事情，再比較輸出差異。

第二個活動是「只讀接手」。給一個小專案，要求學員不能改檔，只能請 Codex 畫場景、事件與資料圖。這能訓練先理解再操作。

第三個活動是故意放入一個舊版本 API。讓 Codex 提出修法後，學員必須用 4.7 stable docs 與 Godot 解析確認，不能只相信語氣。

第四個活動是 diff 審查。Codex 宣稱只加無敵，實際卻更名節點、建立 GameManager、重排資料夾。學員要指出哪些變更超出唯一目標。

教學重點不是讓學員找到「神奇 Prompt」，而是建立一個可重複的工程迴路。

口語概念地圖

人先建立八格規格單，把版本、現況、目標、護欄、結構、行為、驗收與回報說清楚。Codex 先讀專案，再計畫，再做最小修改，接著執行它能執行的檢查。Git diff 記錄實際變更，Godot 提供解析與 Runtime 證據，人在目標平台完成畫面、輸入、音訊與手感驗收。通過後才提交 checkpoint，成為下一次任務的穩定基礎。

這是一個閉環。任何一步被省略，AI 的速度都可能把不確定性帶到下一輪。

聽完後的自我檢查

1. 為什麼「幫我做一個遊戲」不是可驗收規格？

2. 八格規格單的八個欄位是什麼？

3. 為什麼 Codex 應先只讀盤點專案？

4. 自動命令通過與玩家流程通過有何差異？

5. 如何用 Git checkpoint 讓 AI 變更可回退？

6. 防止 API 幻覺需要哪些流程，而不只是口頭提醒？

7. 什麼情況值得重構，什麼情況不應因「更乾淨」就重寫？

章末金句

- 模糊 Prompt 不是給 AI 自由，而是把未說清楚的決策交給猜測。

- Codex 能操作專案，人必須界定它操作的目的、範圍與證據。

- 先讀現況再修改，是 AI 協作最便宜的風險控制。

- 一次只做一個可驗證單元，才能知道成功與失敗來自哪裡。

- 計畫是承諾，diff 才是事實，Runtime 才是證據。

- Git checkpoint 不是備份習慣，而是人與代理之間的回退邊界。

- API 是否存在，要由相符版本文件與實際解析證明，不由回答語氣決定。

- 人不必逐行寫完所有程式，但必須逐項定義什麼叫完成。
