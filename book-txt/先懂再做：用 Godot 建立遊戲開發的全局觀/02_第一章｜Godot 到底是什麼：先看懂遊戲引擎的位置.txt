第一章｜Godot 到底是什麼：先看懂遊戲引擎的位置

當你打開 Godot 時，你打開的究竟是什麼？它是遊戲本身、寫程式的工具、素材編輯器，還是一套替你處理底層工作的引擎？

初學者很容易把這些層次混在一起。有人以為學 Godot 就等於學 GDScript；有人把編輯器畫面當成引擎本身；也有人認為只要安裝一套引擎，遊戲就會自動完成。這些說法都碰到了一部分，卻沒有把整個系統分清楚。

這一章的任務只有一個：把 Godot 放回遊戲開發的全貌。當位置清楚之後，後面出現的場景、節點、資源、腳本、訊號與匯出，才不會像彼此無關的功能。

先把四個常被混淆的東西拆開

第一個是遊戲作品。遊戲作品是玩家最後執行的產品。玩家看見角色、畫面、規則、聲音與介面，卻不需要知道你用什麼引擎製作。它是設計、程式、美術、音效、測試與發行共同形成的結果。

第二個是遊戲引擎（game engine）。引擎提供一套共通能力，讓開發者不必從零處理視窗、輸入、畫面渲染、聲音播放、物理模擬、資源載入、場景管理與平台匯出。你仍然要定義自己的遊戲規則，但不用先寫出一整套底層框架才能讓角色出現在螢幕上。

第三個是編輯器（editor）。編輯器是你與引擎互動的工作環境。你在其中建立場景、安排節點、設定屬性、編輯動畫、查看檔案、啟動遊戲、閱讀錯誤與分析效能。編輯器是入口與控制台，不等於執行中的遊戲。

第四個是程式語言。GDScript、C# 或透過 GDExtension 使用的 C／C++，是你描述行為的方式。語言能告訴角色如何移動、何時扣血、怎麼發出訊號，卻不等於完整引擎。就像你可以用語言寫食譜，但廚房、爐具、食材與上菜流程仍是不同層次。

把四者連在一起，可以這樣說：

你在 Godot 編輯器裡，使用引擎提供的能力與一種程式語言，建立最後要交給玩家執行的遊戲作品。

這一句話看似簡單，卻是之後所有學習的定位基準。

引擎替你做了什麼，又沒有替你做什麼

遊戲引擎最重要的價值，不是替你產生創意，而是把大量重複又底層的問題整理成可使用的能力。

假設你不用引擎，要做「能量收集者」。你至少要決定如何建立視窗、如何接收鍵盤與手把輸入、如何載入圖片、如何把圖片畫在正確座標、如何偵測碰撞、如何播放聲音、如何維持更新迴路、如何管理不同畫面，以及如何把結果打包到 Windows 或 Web。這還沒開始談遊戲特色，就已經是一大組工程任務。

Godot 把這些共通能力放進引擎。你可以使用 Sprite2D 顯示圖像，用 CharacterBody2D 承載由玩家控制的角色，用 CollisionShape2D 描述碰撞範圍，用 AudioStreamPlayer 播放聲音，用 Control 節點建立介面，再透過場景樹讓這些單元組成一個正在運作的遊戲。

可是，引擎不會替你決定：收集能量是否有時間限制？敵人碰撞後要扣多少生命？分數是否會影響難度？玩家失敗後要立即重來，還是回到主選單？這些是遊戲規則與設計決策。引擎提供語彙與機制，作品仍然需要人來定義目的。

這正是與 Codex 協作時的關鍵。Codex 可以熟悉引擎語彙，卻需要你把規則說清楚。你若只說「做一個好玩的收集遊戲」，它缺少可驗收的設計；你若能說「玩家以四方向移動，每次收集能量增加一分，收集十個後進入完成狀態，碰到敵人時扣一點生命並有一秒無敵時間」，它才有可能建立符合預期的結構。

Godot 是一套什麼樣的引擎

Godot 官方把它定位為自由、開源、由社群驅動的 2D 與 3D 遊戲引擎。它採 MIT License，能用於個人、教育與商業專案；發布作品時仍應依授權要求保留 Godot 的授權文字，第三方素材與外掛則各自遵循其授權。

「自由與開源」不只代表免費下載。它也代表引擎原始碼公開，開發由基金會、核心維護者、受贊助開發者與廣泛社群共同推進。你能閱讀原始碼、提出問題、回報錯誤、提交改進，或依授權建立自己的版本。相對地，開源也不代表每一個需求都會依個人時程被完成；版本方向、維護資源與貢獻流程仍需要治理。

Godot 的一個核心設計是「場景驅動（scene-driven）」：用節點作為簡單的構成單位，再將節點組成可重用的場景。這種結構讓角色、敵人、介面、關卡與特效都能以模組存在，並在更大的場景中反覆實例化。後面幾章會深入處理這個模型，現在只要先記得：Godot 並不是把整個遊戲塞進一個巨大物件，而是鼓勵你用較小的責任單元組合出系統。

Godot 同時提供 2D、3D 與 UI 工具。這並不表示三者完全相同，而是它們共享節點、場景、資源、腳本與訊號等核心思想。你從 2D 學到的結構能力，往往能遷移到 3D；UI 雖有自己的版面規則，也仍然存在於同一棵場景樹中。

為什麼這本書選 Godot，而不是宣布它是「最好」

選擇工具時，最容易掉進「哪一個引擎最好」的問題。這個問題缺少條件，因此幾乎沒有單一答案。不同引擎在授權、團隊經驗、生態系、視覺需求、目標平台、現有程式碼、外掛與人才市場上各有不同取捨。

Unity、Unreal Engine 與 Godot 都能建立遊戲，卻有不同的工作模型與專案環境。對這本書的讀者而言，Godot 的價值不在於擊敗其他工具，而在於它提供一個相對完整、開放、可直接接觸場景樹與專案檔案的學習環境。你可以從小型 2D 專案開始，把注意力放在結構、事件與 Runtime，而不必先承擔過大的工具鏈。

做選擇時，可以問六個問題：

- 目標作品是 2D、3D、XR，還是互動工具？

- 要發行到哪些平台？

- 團隊已經熟悉什麼語言與流程？

- 是否依賴某些特定外掛、資產或商業服務？

- 授權、維護與長期成本能否接受？

- 作品需要的畫面、效能與製作規模，是否與團隊能力相符？

本書選 Godot，是為了建立一條從零理解遊戲引擎、再與 Codex 協作的清楚路徑，不是要把工具選擇變成信仰。

版本號不只是數字，而是風險標記

截至 2026 年 7 月 12 日，Godot 的正式穩定基準是 4.7 Stable，發布於 2026 年 6 月 18 日。官方封存頁同時列出 4.7.1 RC2 與 4.8 dev1，但它們屬於不同階段。

Stable 是正式穩定版。它不是保證完全沒有錯誤，而是代表已完成該次發布週期的穩定程序，適合作為一般專案與教學的基準。

Release Candidate，簡稱 RC，是候選版。它通常接近正式發布，主要用來發現回歸問題與最後風險。候選版適合測試，不應在沒有備份與評估的情況下直接替換正式專案基準。

Beta 代表功能大致進入測試，但仍可能有較多改動與錯誤。它適合回報問題、驗證相容性，不適合把所有教學都建立在仍可能改變的細節上。

Dev snapshot 或開發快照，位於更早的開發階段。它能讓社群提早測試未來功能，卻也最需要版本控制、備份與風險意識。

對初學者而言，最重要的不是追到最新數字，而是讓教學、文件、外掛與專案使用同一條版本線。Codex 很容易混入其他版本的 API 或舊範例，因此每次指令都應先指定「Godot 4.7 Stable、GDScript、2D 專案」之類的基準。

版本更新為什麼會影響你的專案

引擎升級可能帶來新功能、修正與效能改進，也可能包含名稱變更、行為調整、檔案格式變化或破壞性改動。官方為 4.6 升級到 4.7 提供遷移指南，就是因為「能開啟」不等於「所有行為都完全相同」。

比較安全的升級方式不是直接覆蓋唯一專案，而是：先建立版本控制或完整備份，在分支或副本中用新版本開啟，閱讀官方遷移指南，執行主要遊戲流程，檢查錯誤與警告，再決定是否升級正式主線。

這也是一個重要的知識遷移：版本管理不是 Godot 獨有問題。任何 Runtime、框架、模型 API 或部署環境，都會有「新功能」與「穩定性」之間的取捨。真正成熟的做法，不是永遠拒絕更新，也不是看到新版就立刻切換，而是把更新當成需要驗證的變更。

官方 Priorities 不是交付承諾

開源專案常會公開方向、提案、議題與優先事項。Godot 的 Priorities 頁面用來呈現重要方向，但官方明確把它視為願望與優先清單，而不是承諾某個功能必定在某天、某個版本交付。

這個區分很重要。當你在網路上看到「Godot 正在做某功能」，至少要再問：它已經進入 stable 嗎？只是 dev snapshot 嗎？是一個 proposal，還是已合併到主分支？是否有目標版本，還是只是社群期待？

書寫技術內容時，必須把「已發布」「測試中」「開發方向」「社群推測」分開。否則，一本看似最新的書可能在出版時就已經失真。

用「能量收集者」看引擎的位置

現在把「能量收集者」放進四個層次。

遊戲作品是玩家最後打開的成品：他控制角色、收集能量、躲避敵人、看到分數與生命值。

Godot 引擎提供輸入、2D 顯示、碰撞、聲音、動畫、場景管理與匯出能力。

Godot 編輯器讓我們建立 Player、EnergyPickup、Enemy、HUD 與 Main 等場景，設定屬性，執行測試並查看錯誤。

GDScript 則表達具體行為：讀取輸入、設定速度、發出 collected 訊號、更新分數、切換遊戲狀態。

Codex 可以在這四者之間協助，但你的指令必須說明它正在修改哪一層。若只是調整角色速度，主要是規則與腳本；若把 Player 拆成可重用場景，涉及結構；若設定 Web 匯出，則進入平台與交付層。

可以直接交給 Codex 的三個任務

任務一：建立版本一致的空專案說明

以 Godot 4.7 Stable、標準版與 GDScript 為基準，規劃一個名為 EnergyCollector 的 2D 空專案。先不要建立完整遊戲。請提出建議資料夾、主場景名稱、渲染方法選擇理由與版本控制忽略項目。回覆時區分「必須設定」與「可以稍後決定」，不要使用 4.8 開發版 API。

驗收重點：它是否明確鎖定版本？是否把資料夾規劃與功能實作分開？是否避免在沒有需求時自行加入大量管理器？

任務二：說明工具層次

請以本專案為例，分別說明 Godot 引擎、Godot 編輯器、GDScript、專案檔案與匯出成品扮演的角色。每一項只用三句話，並指出一個初學者常見誤解。不要直接修改檔案。

驗收重點：回答是否把引擎與編輯器混為一談？是否把 GDScript 說成 Godot 唯一可能的語言？

任務三：做升級前差異盤點

目前專案基準是 Godot 4.7 Stable。請只閱讀專案，不修改任何檔案；列出若未來升級到下一個穩定小版本，應檢查的場景、腳本、外掛、匯出 preset 與平台功能。若缺少官方升級資訊，請明確標示未知，不要推測不存在的 API。

驗收重點：Codex 是否尊重「只讀」？是否能把不確定內容標示出來，而不是自信補完？

Codex 在這一章最可能犯的錯

第一個錯誤是版本混用。它可能從舊資料記起 Godot 3 的類別名稱，也可能引用 4.8 開發中的功能。解法是每個任務開頭都寫版本，並要求列出參考的類別與方法名稱。

第二個錯誤是過度建置。你只要求空專案，它卻一次建立狀態機、事件匯流排、存檔系統與十幾個資料夾。這些內容未必錯，但讓尚未被驗證的架構提早固定。解法是給出唯一目標，並寫明「這次不要做什麼」。

第三個錯誤是把工具偏好當成需求。Codex 可能直接選定.NET 版、特定渲染方法或第三方外掛，卻沒有解釋目標平台與理由。解法是要求它把「事實」「建議」「待決策」分欄回報。

如何把這一章教給別人

教學時，不要先從安裝畫面開始。先拿一個完成的遊戲當終點，再倒著拆出五張卡片：遊戲作品、引擎、編輯器、語言、專案檔案。讓學員把「顯示角色」「接收輸入」「決定扣血」「設定屬性」「匯出執行檔」分別放到適合的卡片上。

接著問一個刻意有陷阱的問題：「GDScript 能不能自己把圖片畫到螢幕上？」答案不是單純的能或不能，而是程式需要透過引擎 API 與節點系統完成顯示。這能讓學員看到，語言負責表達指令，引擎提供執行能力。

最後再打開 Godot，學員就會知道眼前是工作環境，而不是遊戲本身。這時介紹 Project Manager、編輯器與執行視窗，名詞就有位置，不只是介面導覽。

口語概念地圖

請在腦中從左到右排列五個位置。

最左邊是玩家想要的體驗。體驗往右變成遊戲規則。規則需要引擎提供輸入、畫面、物理與聲音。你透過編輯器安排這些能力，再用程式語言描述專屬行為。所有內容被保存成專案檔案，最後由引擎與匯出工具打包成玩家執行的作品。

Codex 可以在編輯器以外直接修改專案檔案，也可以替你撰寫腳本；但它每次修改仍然必須回到同一條鏈上接受檢查：這項變更服務了哪條規則？用了哪個引擎能力？改了哪些檔案？最後如何在執行作品中被觀察？

聽完後的自我檢查

1. Godot 引擎、Godot 編輯器與 GDScript 分別負責什麼？

2. 遊戲引擎替你解決哪些共通問題，又不會替你決定哪些設計？

3. 為什麼選擇 Godot 不等於宣稱它在所有情境都勝過其他引擎？

4. Stable、RC、Beta 與 Dev snapshot 的差異，會如何影響你的專案基準？

5. 當 Codex 提出一個工具或版本選擇時，你會要求它說明哪些條件？

章末金句

- 打開 Godot，不是打開一款遊戲，而是進入一個能建造遊戲的工作環境。

- 引擎提供能力，規則仍需要人定義。

- 程式語言描述行為，遊戲引擎讓行為進入畫面、時間與互動。

- 工具沒有脫離條件的「最好」，只有是否符合這個作品與這個團隊。

- 最新版本不一定是最佳專案基準；可驗證的一致版本才是。

- 開源的價值包含自由，也包含理解治理、版本與維護現實。

- 官方方向不等於交付承諾，開發快照也不等於穩定功能。

- 每次要求 Codex 修改前，先說清楚它正在動哪一層。
