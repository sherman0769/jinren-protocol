附錄｜把概念變成可查、可下指令、可教學的工作工具

這一組附錄不是另一套正文，而是把全書的概念壓縮成可在實作時反覆使用的查詢工具。術語表用來定位名詞；Codex 模板用來把需求變成可驗收工作；專案閱讀清單用來接手陌生程式庫；六堂課框架用來轉成教學；學習路線則協助你在完成第一個閉環後選擇下一步。

附錄一｜Godot 核心術語表

術語的目標不是提供百科式定義，而是回答五件事：它是什麼、和誰有關、何時使用、常見誤解，以及它在全書地圖中的位置。

1. Godot Engine｜Godot 遊戲引擎

- 白話定義：自由、開源、社群驅動的 2D 與 3D 遊戲引擎與工具集。

- 關聯概念：編輯器、專案、Runtime、場景與節點。

- 使用時機：用來建立、測試並匯出互動作品。

- 常見誤解：它不是一款遊戲，也不等於 GDScript。

2. Editor｜編輯器

- 白話定義：開發者用來建立場景、設定屬性、編輯腳本、執行與除錯的工作環境。

- 關聯概念：Scene Dock、Viewport、Inspector、FileSystem。

- 使用時機：安排專案來源並觀察 Runtime。

- 常見誤解：編輯器畫面不是玩家最後執行的成品。

3. Project｜專案

- 白話定義：以含有 project.godot 的根目錄為邊界，集合場景、腳本、資源、素材與設定。

- 關聯概念：res://、版本控制、主場景。

- 使用時機：作為 Codex 與 Godot 共同工作的檔案範圍。

- 常見誤解：專案不是單一場景，也不是匯出的執行檔。

4. Runtime｜執行時期

- 白話定義：按下執行後，場景被實例化、節點進入 SceneTree 並依規則運轉的階段。

- 關聯概念：生命週期、遊戲迴路、狀態。

- 使用時機：觀察動態節點、輸入、物理與事件。

- 常見誤解：Runtime 中的變化通常不會自動寫回原始場景。

5. Stable｜穩定版

- 白話定義：完成正式發布流程、適合作為一般專案基準的版本狀態。

- 關聯概念：RC、Beta、版本遷移。

- 使用時機：本書以 Godot 4.7 Stable 為基準。

- 常見誤解：穩定版不代表完全沒有錯誤。

6. Release Candidate｜候選版

- 白話定義：接近正式發布、用於發現最後回歸問題的預發布版本，常縮寫為 RC。

- 關聯概念：Stable、回歸測試。

- 使用時機：可用來驗證相容性，不宜無備份取代正式基準。

- 常見誤解：RC 並不等於已經正式發布。

7. Beta｜測試版

- 白話定義：功能大致成形但仍可能改動或包含較多問題的預發布階段。

- 關聯概念：Dev Snapshot、RC。

- 使用時機：適合提前測試、回報問題。

- 常見誤解：不應把 Beta 行為寫成長期穩定承諾。

8. Dev Snapshot｜開發快照

- 白話定義：較早期的開發版本，用於讓社群試驗尚未穩定的功能。

- 關聯概念：Beta、版本控制、備份。

- 使用時機：觀察未來方向與測試特定變更。

- 常見誤解：最新的 dev 數字不代表最適合正式專案。

9. MIT License｜MIT 授權

- 白話定義：Godot 引擎採用的寬鬆開源授權，允許個人、教育與商業使用並要求保留授權文字。

- 關聯概念：第三方素材、外掛授權。

- 使用時機：發布 Godot 作品時處理引擎授權聲明。

- 常見誤解：Godot 採 MIT 不代表專案內所有素材都自動採 MIT。

10. Standard Build｜標準版

- 白話定義：以 GDScript 與 GDExtension 等為主要使用方式、不包含.NET/C# 支援的 Godot 發行版本。

- 關聯概念：.NET Build、GDScript。

- 使用時機：本書以標準版與 GDScript 為主要基準。

- 常見誤解：標準版不是功能不足版，只是語言工具鏈不同。

11..NET Build｜.NET 版

- 白話定義：加入 C#/.NET 支援的 Godot 發行版本，需要相符.NET 工具鏈。

- 關聯概念：C#、Export Templates、平台支援。

- 使用時機：既有 C# 團隊或需要.NET 生態時使用。

- 常見誤解：不能假設它在所有平台與標準版的匯出能力完全相同。

12. Renderer｜渲染器

- 白話定義：把場景中的幾何、材質、光線與畫面資料轉成螢幕影像的系統。

- 關聯概念：Rendering Method、GPU、Shader。

- 使用時機：決定畫面功能與效能路徑。

- 常見誤解：渲染器不是一個單純的畫質高低按鈕。

13. Rendering Method｜渲染方法

- 白話定義：Godot 專案依平台與功能選擇的渲染路徑，例如 Forward+、Mobile 或 Compatibility。

- 關聯概念：Renderer、目標平台、驅動。

- 使用時機：建立專案時依硬體範圍與功能做取捨。

- 常見誤解：不能脫離平台條件宣稱某一種永遠最好。

14. Export Template｜匯出範本

- 白話定義：Godot 用來為各目標平台建立成品所需的引擎範本。

- 關聯概念：Export Preset、Godot 版本。

- 使用時機：匯出 Windows、Web、Android 等平台。

- 常見誤解：版本不相符的範本可能造成匯出失敗。

15. Export Preset｜匯出設定檔

- 白話定義：針對某一平台保存架構、資源、圖示、簽章等匯出選項的設定。

- 關聯概念：export_presets.cfg、Export Template。

- 使用時機：讓同一專案可重複產生平台成品。

- 常見誤解：成功建立 preset 不等於已在目標裝置驗收。

16. Debug Build｜除錯建置

- 白話定義：保留較多診斷資訊、方便開發與追蹤錯誤的成品模式。

- 關聯概念：Release Build、Debugger。

- 使用時機：開發測試與錯誤定位。

- 常見誤解：Debug 表現不能直接代表正式版效能。

17. Release Build｜發行建置

- 白話定義：偏向正式散布與效能的建置模式，通常較少除錯資訊。

- 關聯概念：Debug Build、平台驗收。

- 使用時機：建立實際交付成品並在目標裝置測試。

- 常見誤解：Release 檔生成成功不代表所有功能與授權都完成。

18. Node｜節點

- 白話定義：Godot 的基本構成單位，每種 Node 類型代表一組責任與引擎能力。

- 關聯概念：Scene、SceneTree、父子關係。

- 使用時機：組合顯示、物理、聲音、計時與 UI。

- 常見誤解：Node 不一定可見，也不等於一張圖片。

19. Scene｜場景

- 白話定義：一棵具有意義、可保存與可重複實例化的節點樹。

- 關聯概念：Node、PackedScene、Instance。

- 使用時機：表示角色、物件、UI、關卡或主流程。

- 常見誤解：Scene 不只代表完整關卡。

20. SceneTree｜場景樹管理器

- 白話定義：管理 Runtime 中活動節點樹與主迴路的 Godot 類別。

- 關聯概念：Node、生命週期、Group、暫停。

- 使用時機：存取當前場景、群組與全域暫停狀態。

- 常見誤解：它不是硬碟上的單一.tscn 檔。

21. Main Scene｜主場景

- 白話定義：專案執行時最先載入的場景入口。

- 關聯概念：project.godot、GameFlow。

- 使用時機：啟動主選單、遊戲流程或最上層組合。

- 常見誤解：主場景不一定要包含所有遊戲內容。

22. Root Node｜根節點

- 白話定義：一個場景最上層的節點，代表該場景對外的主要身分。

- 關聯概念：Scene、公開介面。

- 使用時機：Player 可用 CharacterBody2D 作根，UI 可用 Control。

- 常見誤解：根節點不應只依第一個方便加入的類型決定。

23. Parent Node｜父節點

- 白話定義：在樹狀結構中直接擁有子節點的上層節點。

- 關聯概念：Child Node、Transform、生命週期。

- 使用時機：組織子能力並影響其加入、移除與局部變換。

- 常見誤解：父節點不必承擔所有子節點的業務邏輯。

24. Child Node｜子節點

- 白話定義：隸屬於某個父節點的節點，會參與同一子樹的生命週期。

- 關聯概念：Parent Node、local transform。

- 使用時機：把角色外觀、碰撞、動畫與計時組合在根節點下。

- 常見誤解：子節點的 local position 不是世界座標。

25. NodePath｜節點路徑

- 白話定義：用名稱與階層描述 SceneTree 中節點位置的路徑資料。

- 關聯概念：get_node、$、封裝。

- 使用時機：取得場景內部或已知節點引用。

- 常見誤解：長而跨場景的硬編碼路徑容易因重構失效。

26. Instance｜實例

- 白話定義：依場景或類別定義建立出的具體 Runtime 個體。

- 關聯概念：PackedScene、instantiate、狀態。

- 使用時機：同一 Pickup 場景可建立多個各自有位置與狀態的物件。

- 常見誤解：修改一個實例不一定會改原始場景或其他實例。

27. PackedScene｜封裝場景資源

- 白話定義：保存場景節點結構並可在程式中 instantiate 的 Resource 類型。

- 關聯概念：Scene、Resource、Instance。

- 使用時機：預載子彈、敵人或關卡場景後動態建立。

- 常見誤解：它是場景資料，不是已加入 SceneTree 的活動節點。

28. Owner｜場景擁有者

- 白話定義：Node 的保存所有權資訊，決定節點是否隨某個 PackedScene 一起保存。

- 關聯概念：Parent、PackedScene、工具腳本。

- 使用時機：程式化建立要永久保存的場景內容時處理。

- 常見誤解：成為 child 不一定就自動成為場景保存內容。

29. Composition｜組合

- 白話定義：以多個具有清楚責任的節點或元件共同構成更複雜角色。

- 關聯概念：Node、Scene、元件。

- 使用時機：Player 由外觀、碰撞、生命與動畫組成。

- 常見誤解：組合不是把每個變數都拆成一個節點。

30. Inheritance｜繼承

- 白話定義：讓腳本或類別在既有類型能力上擴充行為的機制。

- 關聯概念：extends、基底類別、組合。

- 使用時機：GDScript 腳本 extends CharacterBody2D。

- 常見誤解：繼承不是所有重用問題的唯一解法。

31. Encapsulation｜封裝

- 白話定義：透過公開方法、屬性與訊號隱藏可替換的內部細節。

- 關聯概念：場景邊界、耦合。

- 使用時機：外部呼叫 Player.take_damage，而不深入修改 Timer 與動畫。

- 常見誤解：封裝不是禁止所有互動，而是控制互動入口。

32. Autoload｜自動載入／全域單例

- 白話定義：專案啟動時自動加入並可跨場景持續存在的節點或腳本。

- 關聯概念：SceneTree、全域狀態、服務。

- 使用時機：管理使用者設定、音訊或遊戲流程等長生命週期責任。

- 常見誤解：不應把所有方便取得的變數都塞進一個 Global。

33. Group｜群組

- 白話定義：附加在節點上的標籤，SceneTree 可用它查找或批次呼叫一群節點。

- 關聯概念：SceneTree、共同身分。

- 使用時機：標記 enemies、pickups 或 damageable。

- 常見誤解：加入群組不會自動保證所有成員都有同一方法。

34. Signal｜訊號

- 白話定義：物件在事件發生時發出的訊息，連接者可據此呼叫回應函式。

- 關聯概念：Event、Callable、低耦合。

- 使用時機：Player 發出 died，HUD 或 GameFlow 各自反應。

- 常見誤解：Signal 適合宣告事件，不是把所有直接方法呼叫全部替換。

35. Callable｜可呼叫物件

- 白話定義：封裝某個可被呼叫方法及其目標的 Godot 資料型別。

- 關聯概念：Signal、method。

- 使用時機：連接訊號、延遲或動態呼叫。

- 常見誤解：Callable 有效不代表目標物件永遠仍存在。

36. Local Scene｜本地場景視圖

- 白話定義：編輯器中保存與編輯的場景來源結構。

- 關聯概念：Remote SceneTree、.tscn。

- 使用時機：設計節點與初始屬性。

- 常見誤解：它不會顯示所有 Runtime 動態生成的節點。

37. Remote SceneTree｜遠端場景樹

- 白話定義：遊戲執行時，編輯器顯示的實際活動節點樹。

- 關聯概念：Runtime、除錯、Instance。

- 使用時機：檢查動態生成、移除、重複節點與實際屬性。

- 常見誤解：停止遊戲後 Remote 變化不會自動保存回場景來源。

38. Asset｜素材／資產

- 白話定義：從外部進入專案的圖片、音訊、字型、模型、外掛等內容與來源。

- 關聯概念：Resource、授權、Import。

- 使用時機：建立作品的視覺、聲音與內容。

- 常見誤解：素材能被 Godot 匯入，不代表使用權已經確認。

39. Resource｜資源

- 白話定義：可保存、載入、共享並由 Inspector 編輯的資料容器。

- 關聯概念：Node、Custom Resource、.tres。

- 使用時機：保存 Texture、AudioStream、Material 與角色設定。

- 常見誤解：Resource 通常不需要成為 SceneTree 節點。

40. Custom Resource｜自訂資源

- 白話定義：由腳本 extends Resource 所建立、具有專案語意的資料類型。

- 關聯概念：Resource、@export、資料驅動。

- 使用時機：保存 CharacterStats、PickupData 或關卡設定。

- 常見誤解：不應把每個實例的即時狀態無差別放進共用資源。

41. Texture2D｜二維紋理資源

- 白話定義：保存可供 2D 顯示與 UI 使用的圖像資料。

- 關聯概念：Sprite2D、TextureRect、Import。

- 使用時機：由 Sprite2D 或 Control 節點顯示圖片。

- 常見誤解：Texture2D 是資料，不具有自己的世界位置。

42. AudioStream｜音訊串流資源

- 白話定義：表示可由音訊播放節點載入與播放的聲音資料。

- 關聯概念：AudioStreamPlayer、Import。

- 使用時機：播放音效、音樂與環境聲。

- 常見誤解：它不是播放節點，單獨 Resource 不會自己發聲。

43. Material｜材質

- 白話定義：描述表面如何被渲染的資源，可引用 Shader 與紋理。

- 關聯概念：Mesh、Shader、共享 Resource。

- 使用時機：控制 2D 或 3D 物件顏色、光照與特效。

- 常見誤解：修改共用 Material 可能讓所有引用實例一起變化。

44. Shader｜著色器

- 白話定義：在圖形管線中運算像素、頂點或其他視覺效果的程式。

- 關聯概念：Material、Renderer、GPU。

- 使用時機：建立溶解、描邊、水波或自訂光影。

- 常見誤解：Shader 能做特效，不代表所有遊戲規則都應放進 GPU。

45. Theme｜介面主題資源

- 白話定義：集中定義 Control 節點的字型、顏色、樣式盒與其他 UI 外觀。

- 關聯概念：Control、Font、StyleBox。

- 使用時機：讓多個按鈕與面板維持一致設計。

- 常見誤解：修改共用 Theme 會影響所有使用者，單一例外要另行覆寫。

46..tres｜文字資源檔

- 白話定義：Godot 可讀、較適合版本控制的文字格式 Resource 檔。

- 關聯概念：Resource、Custom Resource、Git。

- 使用時機：保存角色資料、Theme、材質與其他資源。

- 常見誤解：文字可讀不代表適合無限制整檔重寫。

47..res｜二進位資源檔

- 白話定義：Godot 的二進位 Resource 格式，通常較不適合人工差異審查。

- 關聯概念：Resource、.tres。

- 使用時機：保存或匯出時使用二進位資源。

- 常見誤解：它不是一般文字檔，不能期待 Codex 直接安全編輯。

48..tscn｜文字場景檔

- 白話定義：以文字形式保存場景節點、屬性與資源引用的檔案。

- 關聯概念：Scene、PackedScene、Git。

- 使用時機：作為可版本控制的正式場景來源。

- 常見誤解：複雜.tscn 含 ID 與引用，整份重寫可能遺失關係。

49. project.godot｜專案設定檔

- 白話定義：Godot 專案根目錄的入口與專案層級設定檔。

- 關聯概念：Project Settings、Input Map、Main Scene。

- 使用時機：保存應用名稱、主場景、輸入與渲染等設定。

- 常見誤解：它不是整個遊戲，也不應為加一項設定而整份覆寫。

50. res://｜專案資源根路徑

- 白話定義：指向目前 Godot 專案根目錄的虛擬路徑前綴。

- 關聯概念：Project、ResourceLoader、檔案引用。

- 使用時機：以可攜相對路徑引用場景、腳本與素材。

- 常見誤解：它不是電腦上固定的絕對磁碟路徑。

51. user://｜使用者資料路徑

- 白話定義：指向應用在目前平台可寫入之使用者資料位置的虛擬路徑。

- 關聯概念：Save Data、偏好設定。

- 使用時機：保存存檔、設定與執行後產生資料。

- 常見誤解：它在各作業系統的實際路徑不同。

52..godot/｜Godot 快取目錄

- 白話定義：保存匯入快取與編輯器產生中間資料的可重建目錄。

- 關聯概念：Import、Git ignore。

- 使用時機：加速資源匯入與編輯工作。

- 常見誤解：通常不應當成正式來源提交或讓 Codex 直接維護。

53. Import｜匯入

- 白話定義：Godot 將外部素材轉成引擎可使用資料與快取的流程。

- 關聯概念：Asset、Resource、.godot。

- 使用時機：設定圖片篩選、音訊循環、模型選項。

- 常見誤解：原始素材、匯入設定與 Runtime 資源是不同層次。

54. GDScript｜Godot 腳本語言

- 白話定義：與 Godot 深度整合、支援物件導向與逐步型別的高階腳本語言。

- 關聯概念：Node、Resource、Signal。

- 使用時機：撰寫遊戲規則、工具與場景行為。

- 常見誤解：學 Godot 不等於只背 GDScript 語法。

55. C#｜C# 語言

- 白話定義：Godot.NET 版正式支援的程式語言與工具鏈選項。

- 關聯概念：.NET Build、平台匯出。

- 使用時機：既有.NET 團隊或需要 C# 生態時使用。

- 常見誤解：不能把 GDScript API 寫法直接逐字換成 C#。

56. GDExtension｜原生擴充介面

- 白話定義：讓原生程式庫與 Godot 互動而不必自行維護完整引擎分支的擴充機制。

- 關聯概念：C、C++、效能、外掛。

- 使用時機：整合原生功能或高效能模組。

- 常見誤解：它不是初學者每個功能都需要的最佳化捷徑。

57. extends｜繼承宣告

- 白話定義：GDScript 指定目前腳本建立在哪個基底類別能力上的語法。

- 關聯概念：Node、Resource、Inheritance。

- 使用時機：extends CharacterBody2D 讓腳本取得角色物理能力。

- 常見誤解：extends 的類型與腳本掛載節點不相容會造成問題。

58. class_name｜全域類別名稱

- 白話定義：讓 GDScript 類別以專案可識別名稱出現在型別與編輯器中的宣告。

- 關聯概念：Type Hint、Custom Resource。

- 使用時機：建立 CharacterStats 或 HealthComponent 等明確類型。

- 常見誤解：不是每個小腳本都必須宣告全域名稱。

59. @export｜匯出屬性註記

- 白話定義：讓腳本欄位可在 Inspector 設定與序列化的 GDScript 註記。

- 關聯概念：Inspector、設計參數。

- 使用時機：暴露速度、Resource 引用或可調範圍。

- 常見誤解：不應把所有內部變數都公開給 Inspector。

60. @onready｜準備時初始化註記

- 白話定義：讓變數在節點接近 ready 階段時初始化，常用於取得子節點引用。

- 關聯概念：_ready、NodePath。

- 使用時機：@onready var sprite = $Sprite。

- 常見誤解：方便取得節點不代表長路徑耦合自動消失。

61. Variable｜變數

- 白話定義：保存會依實例或執行狀態改變資料的具名位置。

- 關聯概念：State、Type Hint、Resource。

- 使用時機：保存目前生命、分數或節點引用。

- 常見誤解：同一個數值也要區分設計設定與 Runtime 狀態。

62. Constant｜常數

- 白話定義：在腳本中用來表達不應於 Runtime 任意改變的具名值或引用。

- 關聯概念：Variable、預載資源。

- 使用時機：保存固定比例、鍵名或預載場景。

- 常見誤解：宣告為常數不代表其引用的 Resource 內容絕對不可變。

63. Function｜函式

- 白話定義：具有名稱、輸入、輸出與可能副作用的一段可呼叫行為。

- 關聯概念：Method、Callable、公開介面。

- 使用時機：封裝 take_damage、add_score 或 change_phase。

- 常見誤解：函式名稱若無法說明副作用，結構可能過度混雜。

64. Type Hint｜型別提示

- 白話定義：明確指出變數、參數與回傳值預期資料類型的註記。

- 關聯概念：GDScript、靜態檢查。

- 使用時機：讓編輯器、Codex 與讀者更早發現誤用。

- 常見誤解：型別不只為效能，也是一份合約。

65. _enter_tree()｜進入樹回呼

- 白話定義：節點加入 SceneTree 時由引擎呼叫的生命週期方法。

- 關聯概念：_ready、父子順序。

- 使用時機：處理需要在子節點 ready 前發生的樹狀註冊。

- 常見誤解：不等同所有初始化都應放在這裡。

66. _ready()｜準備完成回呼

- 白話定義：節點與必要子樹準備完成後由引擎呼叫的方法。

- 關聯概念：@onready、初始化。

- 使用時機：取得子節點、套用資料與發出初始狀態。

- 常見誤解：同一實例移出再加入樹時不應假設一定自動再次呼叫。

67. _process()｜閒置幀處理

- 白話定義：依顯示幀率反覆呼叫、接收 delta 的更新方法。

- 關聯概念：delta、_physics_process。

- 使用時機：處理非物理的每幀視覺或一般更新。

- 常見誤解：不應把只在事件發生時需要的工作全部每幀重做。

68. _physics_process()｜物理幀處理

- 白話定義：以固定物理節奏反覆呼叫、適合物理與角色移動的更新方法。

- 關聯概念：CharacterBody2D、delta。

- 使用時機：設定 velocity、執行 move_and_slide。

- 常見誤解：實際頻率可設定，不必硬記永遠六十次。

69. delta｜幀間時間差

- 白話定義：距離上一次處理經過的秒數，用來把每幀變化轉成時間相關變化。

- 關聯概念：速度、計時、process。

- 使用時機：自己積分位置、旋轉或倒數時使用。

- 常見誤解：不是所有 API 都要再乘 delta；有些方法已處理時間。

70. _input()｜輸入事件回呼

- 白話定義：節點接收輸入事件時由引擎呼叫的回呼之一。

- 關聯概念：Input Event、Input Map。

- 使用時機：處理需要事件細節的鍵盤、滑鼠或手把輸入。

- 常見誤解：持續移動不一定只靠單次 _input 事件。

71. await｜等待

- 白話定義：暫停目前函式流程，直到訊號或可等待結果完成後再繼續。

- 關聯概念：Signal、Timer、Animation。

- 使用時機：等待動畫結束或計時完成。

- 常見誤解：等待期間世界仍會改變，節點可能被移除或流程重入。

72. queue_free()｜排程釋放節點

- 白話定義：把節點安排在安全時機從場景樹移除並釋放。

- 關聯概念：生命週期、Instance。

- 使用時機：收集物消失、敵人死亡後清理。

- 常見誤解：呼叫後不要假設節點與所有引用仍可長期使用。

73. Process Mode｜處理模式

- 白話定義：決定節點在一般、暫停或特定條件下是否繼續處理的設定。

- 關聯概念：Pause、SceneTree。

- 使用時機：讓暫停選單仍接收輸入，而世界停止。

- 常見誤解：只設定 get_tree().paused 不代表所有節點都符合需求。

74. Input Map｜輸入映射

- 白話定義：把實體按鍵、按鈕或軸轉成遊戲抽象動作的設定系統。

- 關聯概念：Action、Input Event、project.godot。

- 使用時機：用 move_left 或 pause 取代硬編碼鍵碼。

- 常見誤解：動作字串拼錯時，程式可能只表現成沒有反應。

75. Input Event｜輸入事件

- 白話定義：描述鍵盤、滑鼠、手把、觸控等一次輸入資訊的事件物件。

- 關聯概念：_input、Input Map。

- 使用時機：處理剛按下、位置、按鍵與裝置細節。

- 常見誤解：原始事件不應直接滲透所有遊戲規則。

76. Action Strength｜動作強度

- 白話定義：Input Map 動作目前的數值強度，可表達數位按鍵或類比軸。

- 關聯概念：Input Map、Vector2。

- 使用時機：計算手把搖桿方向與幅度。

- 常見誤解：它不一定只有零或一。

77. Vector2｜二維向量

- 白話定義：含 X、Y 兩個分量的資料型別，可表達位置、方向、速度或尺寸。

- 關聯概念：Node2D、Velocity。

- 使用時機：計算玩家移動方向與距離。

- 常見誤解：同一 Vector2 值需辨認它是位置、方向還是速度。

78. Velocity｜速度向量

- 白話定義：描述物體每單位時間移動方向與速率的向量。

- 關聯概念：CharacterBody2D、delta。

- 使用時機：設定角色移動。

- 常見誤解：速度與本次位移不是同一個量。

79. CharacterBody2D｜二維角色物理節點

- 白話定義：適合由程式控制並與世界碰撞的 2D 角色 Body。

- 關聯概念：velocity、move_and_slide、CollisionShape2D。

- 使用時機：玩家與具明確控制邏輯的敵人。

- 常見誤解：不要把一般 position 積分公式無條件套到其所有移動 API。

80. RigidBody2D｜二維剛體

- 白話定義：主要由物理模擬、力與碰撞反應控制的 2D Body。

- 關聯概念：Force、Impulse、Physics。

- 使用時機：箱子、彈跳物件、受力道具。

- 常見誤解：每幀硬改 transform 可能與物理模擬對抗。

81. StaticBody2D｜二維靜態物體

- 白話定義：通常代表不移動的物理碰撞環境。

- 關聯概念：牆、地面、CollisionShape2D。

- 使用時機：建立關卡邊界與固定障礙。

- 常見誤解：不適合直接拿來做持續移動的角色。

82. AnimatableBody2D｜二維可動畫物體

- 白話定義：由程式或動畫移動、同時希望正確影響其他物理物件的 Body。

- 關聯概念：移動平台、Physics。

- 使用時機：製作移動地板或升降台。

- 常見誤解：它與由力控制的 RigidBody2D 角色不同。

83. Area2D｜二維偵測區域

- 白話定義：偵測 Body 或其他 Area 進入、離開與重疊的 2D 節點。

- 關聯概念：Signal、Layer、Mask。

- 使用時機：收集物、傷害區、觸發區與感知範圍。

- 常見誤解：Area2D 通常不是用來像牆一樣阻擋角色。

84. CollisionShape2D｜二維碰撞形狀節點

- 白話定義：為父 Body 或 Area 提供實際碰撞邊界的節點。

- 關聯概念：Shape2D Resource、Physics。

- 使用時機：使用矩形、圓形或膠囊近似角色邊界。

- 常見誤解：只建立節點而沒有指定 Shape Resource 不會得到有效碰撞。

85. Collision Layer｜碰撞層

- 白話定義：表示物理物件屬於哪些分類的位元設定，可口語理解為「我是誰」。

- 關聯概念：Collision Mask、Project Settings。

- 使用時機：標記 player、enemy、world、pickup。

- 常見誤解：Layer 本身不等於它會偵測誰。

86. Collision Mask｜碰撞遮罩

- 白話定義：表示物理物件關心或偵測哪些碰撞層，可理解為「我要看誰」。

- 關聯概念：Collision Layer、Area2D。

- 使用時機：讓 Pickup 只偵測 player。

- 常見誤解：Layer 與 Mask 未匹配時，形狀重疊也可能沒有事件。

87. Timer｜計時器節點

- 白話定義：在指定時間後發出 timeout，或週期性觸發的時間工具。

- 關聯概念：Signal、無敵時間、生成。

- 使用時機：處理冷卻、倒數、延遲與週期。

- 常見誤解：暫停政策與 process mode 會影響是否繼續計時。

88. Tween｜補間動畫

- 白話定義：以程式建立，把數值從起點平滑過渡到終點的時間流程。

- 關聯概念：UI、視覺回饋、AnimationPlayer。

- 使用時機：淡入淡出、縮放、相機晃動。

- 常見誤解：Tween 適合插值，不應取代所有狀態與遊戲規則。

89. AnimationPlayer｜動畫播放器

- 白話定義：保存並播放可編輯的多軌屬性動畫。

- 關聯概念：Animation、Signal、await。

- 使用時機：角色死亡、UI 面板、場景效果。

- 常見誤解：每幀重播同一動畫可能讓它永遠停在開頭。

90. AnimationTree｜動畫樹

- 白話定義：用節點圖混合與控制複雜動畫狀態的系統。

- 關聯概念：AnimationPlayer、State Machine。

- 使用時機：角色移動混合、狀態切換與 BlendSpace。

- 常見誤解：小型單一動畫不一定需要先建立 AnimationTree。

91. Control｜介面控制節點

- 白話定義：Godot UI 系統的基礎節點，使用錨點、尺寸與容器版面。

- 關聯概念：Container、Anchor、Theme。

- 使用時機：建立 Label、Button、Panel 與 HUD。

- 常見誤解：不應只把 Control 當成可自由擺放的 Sprite2D。

92. Container｜介面容器

- 白話定義：依規則自動排列與調整子 Control 節點的 UI 節點。

- 關聯概念：HBox、VBox、Grid、size flags。

- 使用時機：建立能適應內容與解析度的版面。

- 常見誤解：容器擁有子項版面，手動位置常會被重新計算。

93. Anchor｜錨點

- 白話定義：Control 相對父節點尺寸的比例參考位置。

- 關聯概念：Offset、Responsive UI。

- 使用時機：讓面板貼齊右下或隨視窗伸展。

- 常見誤解：Anchor 不是直接以像素表示位置。

94. Offset｜位移邊界

- 白話定義：Control 在 Anchor 參考位置上增加的像素邊界差。

- 關聯概念：Anchor、Control。

- 使用時機：設定與父邊緣的具體距離。

- 常見誤解：只調 Offset 而不理解 Anchor，視窗變化時容易跑版。

95. CanvasLayer｜畫布層

- 白話定義：讓 2D 子節點在獨立畫布層中繪製，不受一般世界 Camera2D 變換的節點。

- 關聯概念：HUD、Camera2D。

- 使用時機：讓分數與生命固定在螢幕。

- 常見誤解：CanvasLayer 不是遊戲狀態管理器。

96. Camera2D｜二維攝影機

- 白話定義：決定 2D 世界哪一區域與如何映射到視窗的節點。

- 關聯概念：World coordinates、CanvasLayer。

- 使用時機：跟隨玩家、限制關卡邊界、縮放與晃動。

- 常見誤解：玩家世界位置與螢幕位置不是同一座標。

97. Node3D｜三維節點

- 白話定義：具有 3D 位置、旋轉與縮放的空間節點基礎。

- 關聯概念：Transform3D、Camera3D、Mesh。

- 使用時機：組成 3D 角色、世界與物件。

- 常見誤解：從 2D 遷移時仍需重新學三維方向與旋轉。

98. Transform｜變換

- 白話定義：描述物件位置、旋轉與縮放，以及它如何從局部空間映射到父空間。

- 關聯概念：Local、Global、父子階層。

- 使用時機：移動角色、放置模型、安排 UI。

- 常見誤解：Transform 不是只有 position 一個值。

99. Local Coordinates｜局部座標

- 白話定義：相對父節點所表示的位置或方向。

- 關聯概念：Global Coordinates、Transform。

- 使用時機：設定 Sprite 相對 Player 根節點的偏移。

- 常見誤解：同一 local position 在不同父節點下會對應不同世界位置。

100. Global Coordinates｜全域座標

- 白話定義：經父節點變換鏈組合後，在整個世界或畫布中的位置。

- 關聯概念：Local Coordinates、Camera。

- 使用時機：比較不同分支物件的位置或在世界生成。

- 常見誤解：滑鼠 viewport 座標不能不轉換就當世界 global position。

101. State｜狀態

- 白話定義：系統此刻記住的資料或模式，會影響下一步允許的行為。

- 關聯概念：Game Loop、State Machine。

- 使用時機：生命、分數、Playing、Paused、GameOver。

- 常見誤解：畫面看起來暫停不代表內部狀態與所有系統都已暫停。

102. State Machine｜狀態機

- 白話定義：集中管理有限狀態、轉換條件、進入與退出行為的模型。

- 關聯概念：State、AnimationTree、流程。

- 使用時機：管理角色 Idle／Moving／Hurt／Dead。

- 常見誤解：狀態少時不一定要先建立大型通用框架。

103. Coupling｜耦合

- 白話定義：模組彼此依賴的程度與方式。

- 關聯概念：Encapsulation、Signal、NodePath。

- 使用時機：評估修改一個場景會影響多少其他模組。

- 常見誤解：目標不是零耦合，而是必要、清楚且方向合理的依賴。

104. Single Source of Truth｜單一真相來源

- 白話定義：同一核心狀態由一個明確擁有者保存與修改，其他對象只讀取或接收事件。

- 關聯概念：Data Flow、HUD、GameState。

- 使用時機：讓分數只由 ScoreModel 擁有。

- 常見誤解：不是說整個遊戲只能有一個全域物件。

105. Save Data｜存檔資料

- 白話定義：從 Runtime 狀態中挑選、序列化並跨啟動保存的版本化資料。

- 關聯概念：user://、Resource、版本遷移。

- 使用時機：保存最高分、解鎖、偏好與進度。

- 常見誤解：不應直接把整棵 SceneTree 當成可靠存檔。

106. Debugger｜除錯器

- 白話定義：提供錯誤、堆疊、變數與 Runtime 診斷資訊的工具。

- 關聯概念：Output、Remote SceneTree、Profiler。

- 使用時機：定位解析、Runtime 與邏輯問題。

- 常見誤解：只把錯誤訊息隱藏不等於完成除錯。

107. Profiler｜效能分析器

- 白話定義：量測腳本、物理、渲染與其他系統耗時或資源使用的工具。

- 關聯概念：Optimization、目標裝置。

- 使用時機：先找真正瓶頸，再做最小優化。

- 常見誤解：它不會替你自動決定所有效能目標。

- 白話定義：在 AI 任務前後建立可比較、可提交與可回退的版本狀態。

- 關聯概念：Diff、Codex、版本控制。

- 使用時機：隔離單一功能修改與保護人的未提交工作。

- 常見誤解：Git 不只是最後備份，checkpoint 應在變更前建立。

109. Headless Mode｜無頭模式

- 白話定義：在沒有圖形編輯器視窗的環境執行 Godot 指令、檢查或匯出的方式。

- 關聯概念：Web Export、WebGL、伺服器。

- 使用時機：建立瀏覽器可執行遊戲。

- 白話定義：Google Play 常用的 Android 發布封裝格式，副檔名通常為 AAB。

- 關聯概念：Android Export、簽章、版本碼。

- 使用時機：上架商店並由平台產生裝置適用 APK。

- 常見誤解：AAB 產生成功不代表觸控、背景切換與商店規則已驗收。

- 白話定義：OpenAI 的 coding agent，可在授權環境中閱讀、修改、執行與審查程式碼。

- 使用時機：接手 Godot 專案、實作小步功能、除錯與建立文件。

- 白話定義：可放在程式庫中的代理工作指示與導覽文件，實際支援方式依 Codex 最新文件。

- 常見誤解：不應塞入所有背景造成冗長矛盾，也不能取代每次任務目標。

114. Acceptance Criteria｜驗收條件

- 白話定義：用可觀察結果定義一項工作何時算完成的條件。

- 關聯概念：八格規格單、測試、交付。

- 使用時機：指定行為、錯誤、平台與不變事項。

- 常見誤解：「程式碼已產生」或「看起來可以」不是充分驗收。

附錄三｜拿到陌生 Godot 專案後的閱讀清單

接手專案的目標不是立刻懂完每一行，而是建立一條從入口、結構、資料、事件到 Runtime 的導航。以下順序可以交給自己，也可以交給 Codex 做只讀盤點。

1. 保護現況

確認 Git 狀態、未提交變更、目前分支與可回退點。不要在不知道工作樹內容時執行清理或重置。

2. 找到專案根

尋找 project.godot，確認 Codex 與命令都在正確目錄。

3. 確認版本

從文件、CI、下載記錄與專案設定判斷 Godot 版本、標準／.NET 版與必要外掛。

4. 讀主場景

確認 run/main_scene 指向哪裡，主場景是選單、GameFlow 還是直接關卡。

5. 讀 Autoload

列出每個全域服務、資料與公開介面，辨認是否有巨大 Global。

6. 讀 Project Settings

查看 Input Map、顯示、renderer、物理層、語言與平台設定。

7. 掃描檔案結構

辨認 scenes、scripts、resources、assets、addons、tests 與 docs 的命名規則。

8. 畫核心場景樹

從 Main、Player、Enemy、HUD 等根節點開始，只畫主要責任，不先展開所有裝飾。

9. 找公開介面

記錄每個核心場景的公開方法、signals、export 欄位與 Resource 依賴。

10. 找資料真相

生命、分數、遊戲狀態、設定與存檔各由誰擁有，是否有重複維護。

11. 畫事件流

選一條關鍵流程，例如受傷或收集，追蹤觸發、Signal、狀態與顯示。

12. 畫時間線

確認初始化、process、physics、Timer、await、場景切換與清理。

13. 查動態建立

搜尋 instantiate、add_child、queue_free，確認生成容器與生命週期。

14. 查長路徑與群組

找硬編碼 NodePath、get_nodes_in_group 與跨場景內部存取。

15. 查 Resource 共享

找 Runtime 修改 Material、Theme、自訂 Resource 等可能影響多實例的地方。

16. 讀存檔

確認 user://、格式版本、錯誤處理、設計資料與持久資料的界線。

17. 讀外掛與原生擴充

確認 addons、GDExtension、SDK 與第三方套件版本、授權與啟動要求。

18. 找到啟動與測試命令

閱讀 README、CI、腳本與 Godot CLI，先執行最小不破壞檢查。

19. 看 Runtime

以編輯器執行，觀察 Output、Debugger、Remote SceneTree 與主要玩家流程。

20. 建立風險清單

依阻擋啟動、資料損失、版本混用、結構風險、平台未測排序，不急著一次修完。

完成這二十步後，你不一定已理解所有細節，但應能回答：入口在哪裡、主要模組是誰、資料由誰擁有、事件怎麼走、每一幀做什麼、如何啟動與回退。這已足以讓下一個修改不再盲目。

附錄四｜六堂 Godot＋Codex 入門課

這六堂課以每堂二到三小時的工作坊為設計基準，可依學員背景拆成更多次。課程目標不是一次完成華麗遊戲，而是讓每堂建立一個可回教、可驗收的認知閉環。

第一堂｜遊戲不是畫面：引擎、規則與迴路

- 學習目標：能區分作品、引擎、編輯器、語言與 Runtime，並用輸入、規則、狀態、輸出描述移動。

- 實作主線：建立空專案與 Main；定義 Input Map；讓一個簡單角色在平面移動。

- Codex 使用邊界：先要求 Codex 只讀說明專案層次，再用八格規格單建立最小移動。

- 驗收與挑戰：改變幀率與輸入裝置，口述為什麼速度仍應一致。

- 教學節奏：問題開場 → 口語概念地圖 → 講師示範 → 學員規格 → Codex 小步執行 → Godot 驗證 → 變化題 → 口語回教。

第二堂｜節點與場景：把角色組成可重用模組

- 學習目標：理解 Node、Scene、Instance、SceneTree 與父子 Transform。

- 實作主線：建立 Player 與 EnergyPickup 場景，在 Main 中實例化多個 Pickup。

- Codex 使用邊界：Codex 先提出場景樹與每個節點責任，學員審查後才建立。

- 驗收與挑戰：增加第二種外觀但保留同一收集結構，說明哪些是 Scene、哪些是 Resource。

- 教學節奏：問題開場 → 口語概念地圖 → 講師示範 → 學員規格 → Codex 小步執行 → Godot 驗證 → 變化題 → 口語回教。

第三堂｜事件與資料：收集、分數與 HUD

- 學習目標：區分直接呼叫、Signal、事件流、資料流與單一真相來源。

- 實作主線：Pickup 發出 collected，GameState 改分數，HUD 顯示 score_changed。

- Codex 使用邊界：要求 Codex 畫兩條流，禁止 HUD 直接擁有遊戲分數。

- 驗收與挑戰：同時收集兩個物件，確認事件只處理一次；把 HUD 換版面而不改 Pickup。

- 教學節奏：問題開場 → 口語概念地圖 → 講師示範 → 學員規格 → Codex 小步執行 → Godot 驗證 → 變化題 → 口語回教。

第四堂｜時間與物理：敵人、受傷、無敵與動畫

- 學習目標：理解 physics process、Body／Area、Layer／Mask、Timer、動畫與等待。

- 實作主線：加入 Enemy 接觸傷害、Player 一秒無敵、受傷回饋與死亡。

- Codex 使用邊界：Codex 必須先標出時間單位、碰撞角色與死亡防重入。

- 驗收與挑戰：在不同 FPS、暫停與連續碰撞下驗收；讓學員口述完整時間線。

- 教學節奏：問題開場 → 口語概念地圖 → 講師示範 → 學員規格 → Codex 小步執行 → Godot 驗證 → 變化題 → 口語回教。

第五堂｜從能跑到能維護：Resource、狀態與存檔

- 學習目標：區分設計資料、Runtime 狀態、Autoload 與持久存檔。

- 實作主線：建立 PickupData／PlayerStats，加入遊戲階段與最小 SaveData v1。

- Codex 使用邊界：以受控重構模板執行，先固定行為與 Git checkpoint。

附錄六｜十二張口語概念關係卡

這十二張卡不是摘要比賽，也不是把正文縮成標語。它們的用途，是讓你在搭車、散步、備課或準備向 Codex 下指令前，用幾分鐘重新喚回整章的關係鏈。每張卡都從一個核心問題開始，再依序回答「概念怎麼連」「容易錯在哪裡」「Codex 能做什麼」「人要驗收什麼」，最後用一句可回教的說法收束。

關係卡一｜我打開 Godot 時，究竟進入哪一層？

先把五個層次分開。遊戲作品是玩家最後使用的成品；遊戲引擎提供輸入、渲染、聲音、物理、資源與匯出等共通能力；編輯器是開發者操作引擎的工作環境；GDScript 是描述行為的語言；專案則是場景、腳本、資源、素材與設定共同形成的檔案邊界。它們的關係不是五選一，而是：你在編輯器中，使用引擎能力與程式語言，修改專案來源，最後產生遊戲作品。

最常見的錯誤，是把「學 Godot」縮成「背 GDScript」。語法能表達行為，卻不能替你決定系統邊界，也不能自動形成可維護作品。交給 Codex 的任務應先鎖定版本、語言、專案類型與本次層次；例如「只規劃 Godot 4.7 Stable 的 2D 專案骨架，不做完整遊戲」。人要驗收的不是它寫了多少檔案，而是它有沒有混用版本、偷換工具鏈，或把尚未決定的設計當成既定需求。

回教時可以說：Godot 不是遊戲、不是單一編輯器，也不是 GDScript；它是一套讓我們把規則變成可執行互動作品的引擎與工具集。

關係卡二｜遊戲為什麼不是一張會動的畫？

一個遊戲先有狀態，再有規則。玩家按下方向鍵只是輸入；系統依目前狀態與規則判斷是否能移動；狀態改變後，畫面、音效與介面才呈現結果。接著下一輪輸入又進來，形成「輸入、判斷、狀態改變、輸出、再循環」的遊戲迴路。畫面只是迴路的一個輸出面，不是遊戲的全部。

初學者常把需求寫成外觀描述，例如「角色要有速度感」。這種說法無法直接驗收。較好的拆法是指出輸入、速度、加速度、摩擦、碰撞與動畫各自扮演什麼角色。Codex 可以把這些規則翻譯成節點、腳本與參數，但人要先界定狀態所有權，以及哪些行為跟每幀更新有關。驗收時要問：在不同幀率、暫停、碰撞與重啟後，規則是否仍一致？

回教時可以說：遊戲不是畫面持續播放，而是狀態被規則持續改變，畫面只是把改變顯示出來。

關係卡三｜編輯器裡看到的東西，和硬碟上的檔案怎麼對應？

Godot 專案以含有 project.godot 的資料夾為邊界。res:// 指向專案來源；.tscn 常是場景文字檔；.gd 是 GDScript；.tres 是文字資源；圖片、聲音與字型屬於素材；.godot 多半是可重建的匯入與編輯器快取。Scene Dock 顯示目前場景的節點結構，FileSystem Dock 顯示來源檔案，Inspector 顯示選取物件的屬性。執行後，Remote SceneTree 顯示的是 Runtime 中真正存在的節點，不等於原始場景檔已被改寫。

最危險的誤解，是以為文字格式代表可以任意大量改檔。Codex 確實能讀寫場景與腳本，但仍可能製造遺失引用、無效資源 ID、版本不相容或不必要的快取變更。安全工作流是：先 Git checkpoint，讓 Codex 列出預計修改檔案，限制唯一目標，修改後由 Godot 重新載入並查看 Output、Debugger 與 Remote 樹。

回教時可以說：編輯器不是另一個世界，它是專案檔案的視覺入口；Runtime 則是那些來源被載入、實例化並開始運轉的結果。

關係卡四｜節點、場景與場景樹為什麼是 Godot 的核心語法？

節點是具有明確責任的基本單元；節點透過父子關係形成樹；一棵有意義的節點樹可以保存為場景；場景又能被實例化到更大的場景中。以 Player 為例，CharacterBody2D 承擔移動與物理身分，Sprite2D 負責外觀，CollisionShape2D 描述碰撞範圍，AnimationPlayer 管理動畫。Player 場景保存這組結構，Main 場景只需要實例化 Player，不必重新組裝每個零件。

常見錯誤有兩種。一種把每個小東西都拆成獨立場景，讓關係碎裂；另一種把全遊戲放進巨大主場景與單一腳本，讓責任纏在一起。Codex 在建立結構前，應先回報預期場景樹、每個節點責任、資料由誰擁有，以及哪些子節點屬於可替換細節。人要驗收的是組合邊界，而不是只看遊戲能不能跑。

回教時可以說：節點是零件，場景是可保存、可重用的組裝模組，SceneTree 是這些模組在 Runtime 裡共同存在的組織圖。

關係卡五｜一個東西應該是節點、場景、資源，還是變數？

判斷時先問它是「行為中的物件」「可重用結構」「可保存資料」還是「短暫狀態」。需要進入 SceneTree、接收生命週期或參與空間關係的，通常是 Node；一組節點要重複實例化，通常保存為 Scene；可共享、可序列化的設計資料，適合 Resource；只在一次執行中短暫存在的值，可能只是變數。圖片與音效等外部檔案是 Asset，匯入後也會以 Godot 資源形式被使用。

最容易出錯的是把設計資料、Runtime 狀態與持久存檔混在一起。例如敵人基礎生命值可放自訂 Resource；某一隻敵人當下剩餘生命是 Runtime 狀態；玩家跨次啟動仍要保留的進度才寫入 user://。Codex 建立資料模型時，應列出可共享與不可共享欄位，並說明修改 Resource 是否會同時影響多個實例。人要驗收資料所有權、複製時機與存檔邊界。

回教時可以說：場景回答「東西怎麼組」，Resource 回答「資料怎麼保存與重用」，Runtime 變數回答「這一刻發生了什麼」。

關係卡六｜不背 GDScript，最低限度要看懂什麼？

閱讀腳本先看它 extends 哪一種節點，知道它繼承了什麼能力；再看匯出的參數與一般變數，判斷資料來源；接著找 _ready()、_process()、_physics_process() 等生命週期入口；再看公開方法、訊號、輸入與外部依賴；最後才逐行追條件與計算。類別是能力藍圖，物件是實際實例，屬性保存資料，方法改變行為，條件與迴圈負責控制流程。

最不可靠的讀法，是從第一行開始逐字翻譯，卻不知道整個腳本的責任。Codex 可以解釋程式碼，但應要求它分成「腳本責任、資料、入口、外部依賴、副作用與風險」，而不是只加註解。人要特別檢查型別是否合理、節點路徑是否脆弱、每幀工作是否過重，以及方法是否同時做了太多事情。

回教時可以說：讀 GDScript 不是先背每個符號，而是先辨認這個腳本屬於誰、擁有什麼資料、在何時被叫用，以及會改變誰。

關係卡七｜物件如何溝通，又不彼此綁死？

Input Map 把實體按鍵映射成語意動作；直接呼叫適合明確的一對一命令；Signal 適合「事情已發生」的通知；Group 能依角色集合節點；狀態則描述系統現在處於開始、遊玩、暫停、失敗或完成等哪一階段。事件流回答「什麼事情發生、誰被通知」，資料流回答「哪個值從哪裡來、由誰保存、誰能修改」。兩條流需要分開描述，再在責任清楚的節點相遇。

常見耦合是 Pickup 直接找到 HUD 並改文字，或 Enemy 自己控制整個遊戲結束。較好的關係是 Pickup 發出 collected，遊戲狀態更新分數，再發出 score_changed，HUD 只負責呈現。Codex 在實作前應先列事件名稱、發送者、接收者、資料內容與狀態所有者。人要驗收是否重複連線、事件重入、循環通知，或用全域物件掩蓋所有權問題。

回教時可以說：訊號不是讓所有東西彼此知道，而是讓發生事件的節點說出事實，由真正有責任的人決定怎麼回應。

關係卡八｜每一幀、每一個碰撞與每一段動畫，時間上怎麼接起來？

節點被加入 SceneTree 後，先經歷進入樹、準備完成，再進入持續處理；離開時也有相應生命週期。一般視覺或非固定更新可放 _process(delta)，物理移動與碰撞通常放 _physics_process(delta)。delta 是前後更新的時間差，讓速度能以每秒為單位，而不是每幀增加固定距離。Body 負責實體移動，Area 偏向偵測，Collision Layer 說明自己在哪一層，Mask 說明想偵測哪一層。

常見錯誤是忘記乘 delta、把物理移動放錯迴路、碰撞形狀與畫面不一致、同一傷害事件連續觸發，或等待動畫時讓狀態卡住。Codex 寫時間相關程式前，應先列出時間單位、更新入口、碰撞角色、重入保護與取消條件。人要用不同 FPS、暫停、連續碰撞、重來與節點提早刪除等情境驗收。

回教時可以說：遊戲會動，不是因為某段程式一直跑，而是不同責任在正確生命週期與時間軸上，被引擎反覆安排執行。

關係卡九｜2D、3D 與 UI 是三套世界，還是同一套觀念？

三者共享節點、場景、資源、腳本、訊號與 Runtime，但使用不同空間語彙。2D 以二維座標、旋轉與 Sprite 為主；3D 多一個深度軸，也要處理三維旋轉、Mesh、材質、光照與 Camera3D；UI 使用 Control 節點與版面規則，重點是 Anchor、Offset、Container、字型與不同螢幕尺寸。Local Transform 相對父節點，Global Transform 是在整個場景中的結果；Camera 決定世界如何被觀看，卻不改變物件本身的位置。

常見錯誤是用固定座標排滿 UI、把 2D 與 Control 節點混放卻不理解縮放，或把 3D 問題只當成多一個數字。Codex 建立介面時應先說明版面約束與目標尺寸；建立 3D 場景時應列座標方向、Camera、光照與碰撞。人要驗收不同長寬比、視窗縮放、父子 Transform 與相機移動下的結果。

回教時可以說：2D、3D 與 UI 的表面工具不同，但都在回答同一個問題：物件如何存在於一個空間、如何被組織、如何被看見與互動。

關係卡十｜專案從能跑走向能維護，真正改變的是什麼？

小型原型可以靠直覺增加節點與腳本，但規模擴大後，需要用責任邊界控制變更。單一責任讓一個模組有清楚理由被修改；低耦合讓替換 HUD 不必改 Pickup；Autoload 適合少數真正跨場景且生命週期一致的服務，不是所有共享資料的垃圾桶；狀態、設計資料、組態與存檔要分開；資料夾與命名要反映領域，而不是只按檔案副檔名堆放。

常見錯誤是建立萬能 GameManager、巨大腳本、長 NodePath、循環訊號與難以追蹤的全域狀態。Codex 重構前應先建立 Git checkpoint，描述現有行為，提出最小變更步驟，列出每一步驗收與回退方式。人要確認重構沒有偷偷改遊戲規則，並用場景啟動、主要事件流、存檔與匯出做回歸檢查。

回教時可以說：可維護不是檔案變多，而是每個變更都能定位責任、預測影響、獨立驗收，並在失敗時安全回退。

關係卡十一｜如何指揮 Codex，而不是讓它自由發揮？

Codex 是能閱讀、修改並執行程式工作的代理型協作者，但它不會自動知道你的產品意圖、風險邊界與驗收標準。每次任務至少要交付八格：目前版本、專案現況、唯一目標、不可破壞事項、預期結構、預期行為、驗收條件、修改回報。大型需求先拆成「讀取與盤點、提出方案、最小修改、執行檢查、人工驗收」的小迴路，不要一次要求它完成整款遊戲。

最常見的失敗不是語法錯，而是規格空白被模型自行補滿。它可能引入未要求的外掛、混用 API、重寫可工作的檔案，或把無法執行的測試說成已通過。因此，人要要求它區分已讀事實、推論與建議，列出實際命令、結果、未測項目與改動檔案；任何破壞性操作都要先有版本控制與明確授權。

回教時可以說：讓 Codex 寫得快不是最高目標；最高目標是讓每一次修改都可理解、可驗證、可回退，並持續靠近明確的作品意圖。

關係卡十二｜什麼時候才算完成，而且已經能教？

「在自己的電腦能跑」只代表一條路徑暫時成功。可交付版本還需要錯誤與警告盤點、主要流程測試、效能觀察、版本控制、目標平台匯出、實體環境驗收、授權與第三方素材清單、README、已知限制與可回退版本。Windows、Web、Android 的匯出條件不同，成功按下 Export 不代表瀏覽器、裝置、簽章、權限與儲存都已通過。

能教也不等於把開發過程重播一次。教學需要把內容拆成學習目標、必要背景、示範、受限練習、變化題、驗收與回教。Codex 可以協助產生檢查清單、示範專案與講義草稿，但不能替講師判斷學員是否真的建立了概念關係。人要能不看程式碼，口述輸入、規則、狀態、事件、資料、Runtime 與交付的完整鏈條。

回教時可以說：作品完成的證據是它能在目標條件下被重現與驗收；學習完成的證據，是你能把同一套關係用別人的語言重新教出來。

十分鐘全書口語複習稿

現在，試著不看畫面，用一條完整的口語路線回顧這本書。我要做的不是先叫 AI 寫程式，而是先把一個遊戲想法說成規則。規則裡要有玩家能做什麼、系統怎麼判斷、狀態如何改變，以及結果如何被看見。這條輸入、判斷、狀態、輸出、再循環的路，就是遊戲迴路。

當規則進入 Godot，我要把角色、物件、環境與介面拆成節點。節點有各自責任，透過父子關係形成樹；一組有意義的節點可以保存為場景，再被實例化到更大的場景。需要重複使用的設計資料放進 Resource；只在這一次執行中變化的值屬於 Runtime 狀態；跨次啟動仍要保留的內容才進入存檔。

腳本不是孤立的文字。它附著於節點，繼承節點能力，保存屬性，在生命週期的特定時間執行方法。輸入最好先經過 Input Map 變成語意動作。明確的一對一要求可以直接呼叫；事情發生後要通知其他責任者，則可以發出 Signal。事件流告訴我誰宣布了什麼，資料流告訴我真正的值由誰擁有與修改；狀態則決定目前哪些行為可以發生。

遊戲能動，是因為節點進入 SceneTree 後，在一般更新、物理更新、計時器、動畫與事件中持續工作。速度要以時間為基準，碰撞要區分 Body、Area、Layer 與 Mask，動畫要服務狀態，而不能只把畫面做得像有反應。2D、3D 與 UI 雖然使用不同座標與版面工具，仍共享場景、節點、資源、腳本與訊號的核心模型。

專案變大時，我要用責任邊界控制複雜度。不是建立更多管理器，而是讓場景能獨立理解，讓資料有明確所有者，讓跨場景服務保持少而清楚，讓每次重構都有版本控制、最小步驟、驗收與回退。

當我把任務交給 Codex，我要提供版本、現況、唯一目標、不可破壞事項、預期結構、預期行為、驗收條件與修改回報。Codex 可以讀、改、跑與解釋，但它不能替我決定產品意圖，也不能把未測項目變成已通過。我的工作是限制任務、閱讀差異、執行 Godot、觀察錯誤與 Remote 場景樹，並用真實證據判斷結果。

最後，作品的完成不是「在我的電腦跑過一次」，而是能在指定版本、指定平台與指定流程中被重現、測試、匯出、說明與回退。學習的完成也不是背完術語，而是我能從遊戲想法一路口述到規則、結構、資料、事件、Runtime、AI 協作與交付，並把這條路教給另一個人。

這就是全書最短的導航句：人定義意圖與規則，Godot承載結構與執行，Codex協助產生與修改，人再用可觀察、可驗證、可回退的證據完成閉環。

十二張卡的串接方式

把十二張卡連起來，會得到一條完整路線：先辨認工具層次，再看見遊戲迴路；再把編輯器與檔案對齊，把規則裝進節點、場景與資源；接著用腳本、訊號與狀態讓系統溝通，在生命週期與空間中運轉；然後以架構控制變更，以八格規格單指揮 Codex；最後用可重現的交付證據與可回教的學習設計完成閉環。

當你忘記某個 API 時，可以查文件；當版本更新時，可以重新驗證；但只要這條關係鏈仍在，你就不會因為工具畫面改變而失去方向。

附錄收束｜把工具變成自己的導航系統

術語表讓你在遇到陌生字時回到角色與關係；指令模板讓你在交給 Codex 前先完成自己的思考；閱讀清單避免接手專案時從隨機檔案開始；六堂課把知識轉成可教的認知推進；九條路線則提醒你，下一步不是無限增加功能，而是選一個新領域，再次走完意圖、規則、結構、執行與協作驗證五層。

真正成熟的學習工具，不是替你記住所有答案，而是在答案改變時，仍然知道該問什麼。
