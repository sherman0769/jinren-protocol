第七章｜輸入、訊號、事件與狀態：遊戲物件如何互相溝通

玩家按下鍵盤，Player 開始移動；玩家撿到能量，分數介面更新；生命歸零，遊戲切換到失敗畫面。這些事情看起來像一條自然流程，但在專案裡，真正的問題是：誰先知道？誰有權改資料？誰只需要接收通知？

若每個節點都直接抓取其他節點並修改它的內部資料，遊戲很快會變成一張緊密纏繞的網。Player 知道 HUD，Enemy 知道 Player 內部的 HealthLabel，Pickup 知道 GameManager 的資料結構。任何一個名稱或層級改變，都可能讓多處失效。

相反地，若所有互動都被抽象成無數訊號，簡單流程也可能變得難以追蹤。降低耦合不代表消滅直接呼叫，而是讓每一種溝通方式符合責任與距離。

這一章要建立一張「訊息與控制流」地圖：輸入如何進入、方法如何直接要求行為、Signal 如何發布事件、Group 如何標記一群節點、State 如何限制當下允許的行為。

Input Map：把實體按鍵翻譯成遊戲意圖

玩家可以用鍵盤、滑鼠、手把或觸控操作。如果腳本直接寫死「按下鍵盤 D 就向右」，輸入裝置與遊戲規則會綁在一起。未來改鍵、支援手把、做無障礙設定或讓兩位玩家使用不同控制，就需要修改行為程式。

Godot 的 Input Map 讓你先定義抽象動作，例如：

- move_left

- move_right

- move_up

- move_down

- interact

- pause

再把實體按鍵、手把按鈕或軸映射到動作。Player 腳本只問「move_right 目前是否按下」，不用知道它來自 D、右方向鍵或手把搖桿。

這是一種重要的知識遷移：把「裝置事件」翻譯成「領域意圖」。就像 AI 系統不應把某個前端按鈕名稱直接當成核心業務規則，遊戲也不應讓硬體鍵碼滲透所有行為。

Codex 建立輸入時，要同時檢查兩個地方：project.godot 或 Project Settings 裡是否真的定義動作；腳本使用的字串是否完全一致。動作名稱拼錯不一定在編輯時立即顯眼，Runtime 中只會表現成「按了沒反應」。

輪詢與事件：兩種讀取輸入的節奏

持續移動常用輪詢，也就是在物理更新中詢問某個動作目前的強度。Input.get_vector() 可以把四個方向動作組成向量，適合角色連續移動。

一次性操作則常適合事件或 just pressed 判斷。例如按一次暫停鍵、確認選單、觸發互動，不應因按住十幾幀就重複切換十幾次。

概念上可以這樣分：

- 狀態式輸入：目前是否按住、搖桿目前偏多少。適合持續移動與瞄準。

- 邊緣式輸入：剛按下、剛放開。適合跳躍、互動、暫停與確認。

- 原始事件：包含裝置、位置、按鍵、文字等細節。適合自訂輸入、UI 或需要攔截的情況。

選擇方式取決於行為節奏，不是 API 偏好。Codex 若把暫停寫成「只要按住就切換」，遊戲可能在 Paused 與 Playing 之間快速震盪；若把移動只寫成一次按下事件，角色就只動一下。

直接方法呼叫：我知道對方，現在要它做一件事

最直接的溝通，是取得某個物件的引用並呼叫方法。

```gdscriptplayer.take_damage(1)```

這種方式清楚、可追蹤，也能立即表達命令：呼叫者知道接收者，要求它執行一個公開行為。直接呼叫不是壞耦合的同義詞。Player 的 HealthComponent 呼叫自己的內部方法，或 Main 對明確擁有的子場景呼叫 start_round()，都可能非常合理。

問題出在呼叫者是否知道太多，或跨越不應跨越的邊界。例如 Enemy 不只呼叫 player.take_damage(1)，還深入修改 player.current_health、播放 Player 的動畫、更新 HUD 並寫入存檔。這時一個碰撞事件牽動多個不屬於 Enemy 的責任。

可以用兩個問題判斷直接呼叫是否合理：

1. 呼叫者是否本來就擁有或明確依賴接收者？

2. 被呼叫的是公開行為，還是內部細節？

若答案是「明確依賴、公開行為」，直接方法通常比繞一大圈訊號更清楚。

Signal：事情已經發生，關心的人可以反應

Signal 是 Godot 內建的事件機制。節點可以發出訊號，其他物件連接後在事件發生時呼叫對應函式。官方文件強調，訊號能讓一個物件對另一個物件的變化做出反應，而不必彼此直接引用，因而降低耦合。

例如 EnergyPickup 不需要知道分數系統、音效系統與任務系統各自放在哪裡。它只要在被收集時發出：

```gdscriptsignal collected(value: int)```

外部的 Main 或其他協調者可以連接這個訊號，更新分數；音效也可由收集物自己播放，或由另一個服務回應。發送者只宣告「事件發生」，不控制所有後續。

訊號最適合的情境包括：

- 一個事件可能有多個關心者。

- 發送者不應知道接收者是誰。

- 事件代表狀態已改變，而不是要求對方立刻回傳結果。

- 場景希望對外提供穩定事件介面。

例如 Player 發出 health_changed 與 died；HUD 關心生命變化，Main 關心死亡，音效或成就系統也可能關心。Player 不必直接抓取每一個接收者。

訊號名稱要表達「已發生」，不是模糊命令

好的訊號通常使用事件語氣：collected、health_changed、died、round_started。它告訴接收者某件事已經發生。

若訊號名稱是 do_update_everything 或 please_save_and_change_scene，表示發送者可能仍在控制接收者。這種命名讓事件變成隱藏命令，降低耦合的目的也失去。

訊號參數應帶上接收者真正需要的最低資料。例如 health_changed(current, maximum) 讓 HUD 不必再反向讀取 Player 內部；collected(value) 傳分數價值，不必傳整個 Pickup 節點，除非接收者確實需要來源資訊。

參數也不能無限擴張。若訊號一次傳十幾個位置參數，可能表示事件缺少資料物件，或發送者與接收者邊界不清。可考慮使用有型別的 Resource、Dictionary 或專用資料類型，但仍需避免把整個世界狀態塞進事件。

誰負責連接訊號

訊號可以在編輯器連接，也可由程式連接。兩種方式都合理，選擇取決於關係是否固定、是否動態生成，以及連線是否需要在程式中更可見。

- 場景內固定關係，例如 Button 的 pressed 連到同一個 UI 場景，可以在編輯器連接。

- 動態生成的 Enemy 或 Pickup，通常由生成或擁有它們的協調者在程式中連接。

- 需要帶 Callable、一次性或動態條件的連線，程式通常較清楚。

關鍵是所有權：誰建立實例，誰通常最適合負責連接與斷開其外部事件。若 Main 生成 Pickup，Main 可以連接 pickup.collected。Pickup 本身不應搜尋 /root/Main/HUD 再自行連接，否則它不再可重用。

Godot 會在物件被釋放時處理許多訊號連線，但涉及外部非節點資源、重複連接或長生命週期服務時，仍要注意是否重連多次、回呼對象是否有效。

Event Flow 與 Data Flow 是兩張不同地圖

「事件流」回答：什麼時候發生什麼事，通知了誰。「資料流」回答：哪一份資料從哪裡被讀取，在哪裡被修改，誰持有真相。

玩家收集能量時，事件流可能是：Area2D 偵測 → Pickup 發出 collected → Main 接收 → GameState 更新 → HUD 接收 score_changed。

資料流則是：PickupData 提供 value → GameState 的 score 加上 value → HUD 讀到 current score 與 target score。

若只看事件流，你可能不知道分數真正存在哪裡；若只看資料流，你可能不知道更新在何時被觸發。架構審查應同時畫兩張圖。

一個重要原則是「單一真相來源」。HUD 顯示分數，不應同時自己維護另一份分數；Pickup 也不應改 Label。分數由明確對象擁有，其他系統透過公開介面讀取或接收變更事件。

Group：用標籤找到一群具有共同身分的節點

Godot 的 Group 可以把節點標記為某個群組，例如 player、enemies、pickups、damageable。SceneTree 能查詢群組中的節點，或對一群節點呼叫方法。

Group 很像標籤，而不是繼承或完整介面。加入 damageable 群組不會自動保證節點真的有 take_damage()。如果程式對整個群組呼叫方法，你仍要確保所有成員遵守約定。

Group 適合：

- 從碰撞對象判斷是否屬於某類角色。

- 暫停或啟用一群具有共同責任的節點。

- 尋找玩家、敵人或互動物件，而不依賴固定路徑。

- 讓場景以多個標籤參與不同系統。

不適合把 Group 當成全域搜尋的萬用替代。若每個腳本都在 Runtime 反覆 get_nodes_in_group() 找依賴，關係仍然隱藏，而且可能有效能與生命週期問題。能由擁有者傳入引用時，就不必每次全樹搜尋。

狀態：決定現在允許哪些行為

遊戲物件不只保存數值，也常處於一種「模式」。Player 可能是 Idle、Moving、Hurt、Dead；遊戲可能是 Menu、Playing、Paused、GameOver。

狀態的價值，是把「目前允許什麼」集中表達。若遊戲已 GameOver，玩家輸入不應繼續移動；若 Player 處於 Hurt 且無敵，接觸傷害不應再次扣血；若在 Paused，特定 UI 仍需回應，但世界物理停止。

最簡單的狀態可以是一個 enum 與條件：

```gdscriptenum GamePhase { MENU, PLAYING, PAUSED, GAME_OVER }var phase: GamePhase = GamePhase.MENU```

切換狀態時，不只是改一個值，而要明確執行離開舊狀態與進入新狀態的工作。例如進入 Paused 時顯示面板、設定場景樹暫停；離開 Paused 時恢復。若切換邏輯散落在多個按鈕與腳本，很容易出現畫面顯示暫停但世界仍在動。

狀態機不必一開始就做成大型框架

State Machine 是管理狀態與轉換的常見方法。它可以小到一個 match phase，也可以大到每個狀態一個獨立節點或 Resource。選擇取決於行為複雜度。

當狀態很少、轉換簡單，enum 加集中函式就足夠。當每個狀態有獨立輸入、進入、更新、退出邏輯，或角色行為持續增加，才值得拆成狀態物件。

Codex 特別容易在聽到「狀態」後直接產生通用狀態機框架、十幾個檔案與抽象基底。這不一定錯，卻可能比遊戲本身更難理解。要求它先列出實際狀態、轉換條件與共享資料，再決定實作形式。

暫停是一個跨系統狀態

暫停看似只是按一個鍵，實際上會牽涉輸入、SceneTree、process mode、UI、音效、計時器與動畫。Godot 可以暫停場景樹，但每個節點的處理模式決定它在暫停時是否仍執行。

典型需求是：世界停止，暫停選單繼續接收輸入；背景音樂可能降低音量但不中斷；某些 UI 動畫繼續；儲存流程仍可執行。這些都需要先定義，而不是只設定 get_tree().paused = true。

因此，Paused 是一個狀態，也是一份政策：哪些系統停、哪些系統繼續。Codex 實作暫停時，驗收要包含敵人、玩家、Timer、動畫、UI 與再次按鍵解除，而不只是確認面板出現。

能量收集者的溝通鏈

完整走一次：

1. Input Map 把鍵盤或手把翻譯成 move_* 動作。

2. Player 在物理更新中讀取方向，更新 velocity。

3. Player 進入 Pickup 的 Area2D。

4. Pickup 驗證碰撞對象，發出 collected(value)。

5. Main 或 GameState 接收事件，透過 add_score(value) 修改唯一分數。

6. GameState 發出 score_changed(current, target)。

7. HUD 接收事件，只更新顯示。

8. 若 current 達 target，GameState 切換到 Completed，發出 phase_changed。

9. Main 顯示完成流程並停止或調整世界更新。

每個角色知道的事情有限：Pickup 不知道 HUD；HUD 不改分數；GameState 不偵測碰撞；Player 不直接切換完成畫面。這就是把溝通與責任拆清楚。

可以直接交給 Codex 的四個任務

任務一：建立 Input Map 規格

以 Godot 4.7 Stable 建立輸入規格，不先改檔：列出 move_left、move_right、move_up、move_down、interact、pause 的鍵盤與手把映射。區分持續狀態、剛按下與原始事件的使用方式，並提出重新綁定時要保留的抽象邊界。

任務二：畫事件流與資料流

只讀取收集、分數與 HUD 相關腳本，分別列出事件流和資料流。指出分數的單一真相來源、所有修改入口與重複維護風險。不要先重構。

任務三：審查訊號與直接呼叫

搜尋 signals、connect、emit 與跨場景方法呼叫。對每一個關係分類為「合理直接依賴」「適合事件通知」「可能穿透內部」。不要把所有呼叫都改成 Signal；先說明判斷依據。

任務四：定義最小遊戲狀態

針對 Menu、Playing、Paused、GameOver 四種狀態，建立轉換表：觸發、允許來源、進入動作、退出動作、禁止行為、驗收情境。先用文字與 enum 方案，不建立通用狀態機框架。

Codex 可能做錯什麼

第一，把所有直接呼叫視為壞耦合，產生大量難追蹤訊號。事件與命令有不同語意，不能只追求抽象。

第二，訊號重複連接。場景每次進入時 connect，離開或重啟後又連一次，事件便被處理多次。驗收要重複切換場景與重新開始。

第三，HUD 自己保存並修改分數，與 GameState 形成兩份真相。顯示層應接收狀態，不擁有遊戲規則。

第四，使用 Group 取得節點後假設方法一定存在。需要群組契約、型別或安全檢查。

第五，暫停時只顯示面板，世界仍運作；或整棵樹暫停後，暫停選單也不能接收解除輸入。

第六，狀態切換沒有防重入。GameOver 事件被多次觸發，重複建立畫面、播放聲音與寫入存檔。

如何把這一章教給別人

可以用三種卡片演示。紅色卡是命令：「玩家，請扣一點生命。」藍色卡是事件：「玩家生命已改變。」綠色卡是查詢：「目前生命是多少？」讓學員把實際互動放進適合類型。

接著用兩條線畫「撿到能量」。上面一條是事件流，下面一條是資料流。學員會發現同一件事有時間順序，也有資料所有權。

最後做狀態轉換演練。請一位學員扮演 Playing，一位扮演 Paused；其他人提出輸入、敵人移動、UI 點擊與 Timer。每個狀態必須回答允許或禁止。這能把抽象 enum 變成可觀察政策。

口語概念地圖

輸入先從硬體事件進入 Input Map，變成遊戲意圖。需要持續執行的意圖被迴路讀取，一次性意圖以事件觸發。物件若明確知道另一個物件並要求它執行公開行為，就直接呼叫方法；若只是宣布一件已發生的事，就發出 Signal。Group 把多個節點標記成共同身分。State 像一道閘門，決定此刻哪些輸入、方法與事件有效。

事件在物件間流動，資料則由明確所有者保存。當兩條流都能被說清楚，溝通就不再是一張黑盒子網路。

聽完後的自我檢查

1. Input Map 解耦了哪兩個層次？

2. 直接方法呼叫在什麼情況是清楚而合理的？

3. Signal 最適合表達命令，還是已發生的事件？

4. 事件流與資料流分別回答什麼？

5. Group 為什麼是標籤，而不是自動保證介面的型別？

6. 暫停為什麼不只是顯示一個面板？

章末金句

- 輸入裝置只是來源，遊戲動作才是規則真正關心的意圖。

- 直接呼叫不是原罪，穿透不該知道的內部才是風險。

- 訊號最適合說「事情已經發生」，而不是遠端命令所有人做事。

- 事件流決定何時通知，資料流決定誰擁有真相。

- HUD 可以顯示分數，卻不應成為分數的第二個主人。

- Group 是標籤，不是免費得到的介面合約。

- 狀態不是一個名字，而是一組此刻允許與禁止的行為。

- 降低耦合的目標是讓改變可控，不是把所有關係藏起來。
