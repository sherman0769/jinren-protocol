第十二章｜完成、匯出與教學：把一次開發變成可複製的方法

遊戲在你的電腦上成功跑起來，算完成了嗎？

如果目標只是驗證一個概念，能跑已經是一個重要里程碑。但若要交給別人玩、公開下載、放進課堂或當成可重複的示範，完成還包含另一組責任：錯誤是否可追蹤、效能是否經量測、檔案是否可重建、匯出是否在目標平台執行、素材授權是否清楚、教學者是否能從頭說明每個決策。

交付不是在開發結束後按一次 Export。它是從「我這裡能跑」轉成「別人在明確條件下也能取得、執行、理解與回報問題」的過程。

這一章會把除錯、版本控制、效能、匯出、驗收與教學串在一起，讓能量收集者從一個本機專案，成為可交付、可示範、可再製的學習成果。

除錯先從證據開始

錯誤大致可以分成幾類：

- 解析或編譯錯誤：腳本語法、型別、類別或資源無法被讀取。

- Runtime 錯誤：執行時取得 null、索引越界、檔案開啟失敗等。

- 邏輯錯誤：程式能跑，但結果不符合規則。

- 資源與場景錯誤：路徑失效、場景無法載入、碰撞形狀缺失、訊號未連接。

- 平台錯誤：只在特定作業系統、瀏覽器、輸入裝置或圖形驅動出現。

- 效能問題：幀率下降、記憶體成長、卡頓或載入時間過長。

分類的目的，不是替錯誤貼標籤，而是決定先看哪一種證據。解析錯誤先看錯誤行與類別文件；碰撞問題先看 Remote 樹、CollisionShape、Layer／Mask；邏輯問題要追蹤狀態變更；平台問題要保留環境資訊。

一個好的 Bug 回報至少包含：

1. Godot 版本、標準或.NET 版、目標平台。

2. 重現前置條件與逐步操作。

3. 預期結果與實際結果。

4. 完整錯誤訊息、堆疊與相關日誌。

5. 是否必然發生，或只在某些幀率／裝置發生。

6. 最近一次正常版本與相關 Git diff。

Codex 能從完整證據推理；只有「壞掉了」時，它只能廣泛猜測。

Output 與 Debugger：先看引擎已經告訴你什麼

Godot 的 Output 顯示程式輸出、警告與錯誤；Debugger 可查看錯誤、堆疊、變數、監視與其他執行資訊。發生錯誤時，先讀第一個與根因相關的訊息，不要只處理後面連鎖產生的十幾個錯誤。

例如主場景無法載入，後面可能出現 Player、HUD 與訊號都不存在。若只在每一處加 null 檢查，會把根因遮住。真正要修的是場景路徑或解析錯誤。

堆疊告訴你呼叫路徑：哪個函式呼叫了哪個函式，最後在哪裡失敗。把堆疊交給 Codex 時，保留檔名、行號與完整順序。不要只截最後一句。

警告也不應全部忽略。未使用參數、可能 null、型別不一致、碰撞形狀缺失或資源問題，可能是尚未爆發的風險。但不要為了讓警告數字歸零，機械地停用所有檢查。每個警告都要判斷是否有意、是否需修正、是否應以清楚方式標示。

日誌要記錄狀態轉換，不要淹沒每一幀

有效日誌應回答：什麼事件發生、關鍵狀態從什麼變成什麼、由哪個實例處理。

例如：

```text[GameState] phase: PLAYING -> PAUSED[Player] health: 3 -> 2, source=Enemy#17[Score] value: 9 -> 10, target=10```

這比每一幀列印 position 更容易追蹤。若要觀察每幀資料，可以用暫時監視、Debugger 或有節流的採樣，而不是長期向 Output 灌入數千行。

日誌也要避免洩漏個資、權杖、存檔內容或平台秘密。公開版本可以分級控制 debug 訊息；正式玩家不需要看到所有內部資料。

Codex 加日誌時，要求它說明每筆日誌對應哪個驗收條件，並在修正後移除或降低暫時性噪音。

Remote 場景樹與可觀察性

Runtime 問題常需要看「現在真正存在什麼」。Remote 場景樹能幫你確認：動態生成的 Pickup 是否加入正確容器、Enemy 是否被清理、PauseMenu 是否重複建立、Autoload 是否只有一份、節點屬性是否在執行時被意外改變。

可以把可觀察性分三層：

- 結構可觀察：Remote 場景樹、節點數量與層級。

- 狀態可觀察：Inspector 遠端屬性、日誌、監視變數。

- 流程可觀察：signals、狀態轉換、堆疊與時間線。

一個功能若完全沒有觀察點，Codex 與人都只能從最後畫面猜測。設計時就加入少量關鍵事件與狀態顯示，能讓除錯成本下降。

Profiler：不要用直覺替代量測

Godot Profiler 能協助觀察腳本、物理、渲染與其他效能資料。效能問題不能只靠「我覺得這段迴圈很慢」判斷，應先重現卡頓、擷取量測、找到耗時位置，再做最小改善。

小型能量收集者可能不會立刻遇到嚴重效能瓶頸，但仍可建立基本習慣：

- 不在每幀重複載入 Resource。

- 不在熱路徑反覆搜尋整棵樹。

- 離開畫面的動態物件要有清理策略。

- 粒子、音效與動畫實例數要可控。

- 量測 Debug 與 Release 的差異。

- 在目標低階裝置上測試，而不只看開發機。

優化前先設定目標。例如「在目標筆電的測試關卡，五十個 Enemy 時維持可接受的更新」；不要以抽象的「讓它更快」為任務。Codex 若沒有基準，也很容易把可讀性換成無法證明的微小優化。

Git：讓作品可重建，也讓教學可回放

版本控制不只是避免檔案遺失。它記錄每個概念如何進入專案，讓你可以回到「只有移動」「加入收集」「加入分數」「加入暫停」的不同節點。

對教學而言，這些 checkpoint 就是一條課程路線。學員若在第三步失敗，可以比較第二步與第三步 diff；講師可以準備每堂課的起始分支與完成分支；Codex 的每次修改也能被審查。

Godot 專案通常應提交場景、腳本、Resource、原始素材、project.godot、export_presets.cfg 與必要文件；忽略.godot/ 等可重建快取，以及秘密、憑證與本機特定設定。實際清單仍要依版本與外掛核對。

提交訊息應描述意圖，例如「新增分數事件與 HUD 同步」，而不是「update files」。若一次提交同時包含格式化、搬移、重構與新功能，之後很難教學與回退。

匯出之前，先區分專案與成品

Godot 編輯器能讀取完整專案來源；玩家成品則是由引擎與匯出設定打包出的執行內容。匯出通常需要對應平台的 Export Templates。你在 Project > Export 建立 preset，設定平台、架構、視窗、圖示、簽章、包含資源與其他選項。

export_presets.cfg 保存大部分匯出設定，通常可納入版本控制；敏感憑證與密碼不能以明文提交。匯出時 Godot 會依設定收集資源與場景依賴，再建立套件。

成功產生檔案不等於成功交付。必須在乾淨環境或另一台裝置執行，確認沒有依賴開發機絕對路徑、未提交素材、外部工具或只有編輯器才存在的檔案。

Windows 匯出的概念

Windows 匯出通常會產生可執行檔與專案資料封裝，也可依設定嵌入。需要考慮：

- x86_64、arm64 或其他目標架構。

- 圖示、版本資訊與產品名稱。

- 渲染方法與目標顯示硬體。

- 標準版或.NET 版對應的 export templates。

- 防毒誤判、程式簽章與散布方式。

- 存檔路徑與權限。

開發機能啟動不代表其他 Windows 環境都有相同驅動與執行元件。至少要在一個沒有 Godot 編輯器與專案來源的環境測試。

書中不提供固定的商店或簽章操作，因政策與工具可能更新。正式發布前應查 Godot 4.7 對應文件與散布平台最新規則。

Web 匯出的概念

Web 匯出使用 WebAssembly 與瀏覽器圖形能力。它的優點是使用者可透過瀏覽器進入，但也有不同限制：伺服器需以正確 MIME type 供應檔案，瀏覽器對音訊自動播放、滑鼠捕捉、剪貼簿、執行緒、檔案系統、網路與跨來源政策有自己的規則。

不能把匯出的 HTML 檔直接雙擊後成功與否，當成正式 Web 驗收。應透過本機或正式 Web 伺服器提供，並在目標瀏覽器、桌面與行動裝置測試。

Web 版本還要注意下載大小、首次載入、記憶體、觸控、橫直向與頁面嵌入。若使用 C#，平台支援要依當前 Godot 官方文件重新確認，不能假設與 GDScript 相同。

Android 匯出的概念

Android 匯出涉及 JDK、Android SDK、裝置與商店要求。Godot 官方文件會列出相符工具鏈與設定；這些版本高度時效性，應以 4.7 文件與當下商店政策為準。

Android 驗收至少包含：

- 不同螢幕比例與像素密度。

- 觸控按鈕、手勢與虛擬搖桿。

- 暫停、切到背景、回到前景。

- 音訊焦點、來電或系統中斷。

- 權限與儲存位置。

- APK／AAB、簽章與版本碼。

- 低階裝置效能、耗電與溫度。

若只是桌面鍵盤遊戲，成功匯出 APK 也不能稱為 Android 可玩。輸入與 UI 必須重新設計。

主機平台與「支援」的真正含義

Godot 可用於主機發行，但封閉主機平台涉及平台商核准、NDA、官方 SDK 與專用匯出方案。Godot 官方不能把受限制的主機 SDK 與範本像一般開源 export template 一樣公開散布；開發者可能使用第三方中介服務或自行維護移植。

因此，「Godot 能做主機遊戲」與「按一下就能公開匯出到所有主機」不是同一件事。若作品目標從一開始就是特定主機，工具、預算、認證與合作方案應在早期評估，不要等遊戲完成後才處理。

Release、Debug 與可重現建置

開發時 Debug build 提供較多診斷資訊；Release build 偏向正式效能與散布。兩者都要測，因某些問題只在最佳化、權限或缺少除錯功能時出現。

可重現建置至少需要：

- 記錄 Godot 精確版本與標準／.NET 版。

- 記錄 export templates 版本。

- 提交 export preset 與必要腳本。

- 鎖定外掛與外部工具版本。

- 說明素材與產出來源。

- 提供從乾淨 checkout 到匯出的步驟。

- 保留建置日誌與成品 checksum。

不一定要達成位元完全相同的學術式 reproducible build，但另一個人應能依文件產生功能相同的成品。

Codex 可以協助將匯出命令放進腳本或 CI，但簽章、商店上傳與秘密管理需要額外安全設計。

交付驗收矩陣

能量收集者可以用五個面向驗收。

功能

- 玩家可用定義的輸入移動。

- 能量只收集一次，分數正確。

- 接觸傷害、無敵與死亡符合規則。

- 開始、暫停、失敗、重來與完成狀態可到達。

- 存檔與讀取有明確成功與失敗行為。

結構

- 主場景、Player、Pickup、Enemy、HUD 責任清楚。

- 分數與生命沒有多份真相。

- 沒有未說明的巨大 Autoload 或深層 NodePath。

-.godot/ 與秘密未提交。

品質

- Godot 啟動無解析錯誤。

- 重要警告已處理或有說明。

- 目標幀率與裝置經量測。

- 動態節點不持續洩漏。

- 主要流程可重複執行十次。

平台

- Windows／Web／Android 依實際目標分別驗證。

- 輸入、解析度、音訊、暫停與存檔符合平台情境。

- 匯出成品在無開發環境的裝置可執行。

文件與授權

- README、版本、啟動與匯出步驟完整。

- Godot 授權文字依要求保留。

- 第三方素材與外掛有來源與授權登錄。

- 已知限制與待辦沒有被包裝成已完成。

從開發專案轉成教學專案

一個能玩的專案不一定能教。教學需要把成品拆成認知步驟，每一步只引入必要的新概念。

可以把能量收集者拆成六堂課：

1. 引擎與遊戲迴路：空場景、輸入與狀態。

2. 節點與場景：建立 Player 與 Pickup。

3. 訊號與資料流：收集、分數與 HUD。

4. 時間與物理：Enemy、受傷、無敵與動畫。

5. 架構與 Codex：狀態、重構、Resource 與存檔。

6. 除錯與交付：Git、Profiler、Windows／Web 匯出與成果發表。

每堂課都要有四個層次：講師示範、學員跟做、獨立挑戰、驗收與反思。只看示範容易形成「我看懂了」的錯覺；獨立挑戰才能暴露知識是否能遷移。

一堂 Godot＋Codex 課的基本節奏

可以採用以下節奏：

- 問題開場：今天要解決什麼玩家行為？

- 概念地圖：這件事位於五層模型哪裡？

- 人工規格：用八格規格單說清楚。

- Codex 執行：先讀、計畫、修改與檢查。

- Godot 驗證：SceneTree、Debugger、Runtime 與目標平台。

- 變化挑戰：改一個條件，驗證能否遷移。

- 口語回教：學員不用看筆記，說明輸入如何改變狀態。

真正的學習成果不是學員成功複製講師檔案，而是他能在條件改變時重新定義規格。

教學中如何使用 AI 而不讓學習消失

AI 可以替學員處理語法摩擦、產生測試場景、解釋錯誤與比較方案。但若學員把所有任務都交給 Codex，再只確認畫面有動，他學到的是操作代理，不是理解系統。

可以要求每次使用 Codex 前，學員先回答：

- 這次改哪個層次？

- 哪個物件擁有資料？

- 事件從哪裡到哪裡？

- 哪些行為不得改變？

- 我會用什麼證據驗收？

Codex 完成後，再讓學員指出實際 diff 與原計畫差異，並用自己的話解釋一個關鍵方法。AI 不是作弊工具，也不是自動學習；它是一面放大鏡，會同時放大清楚規格與模糊理解。

成果發表不是只播放遊戲

一個完整教學成果可以包含：

1. 三分鐘遊戲示範。

2. 一張五層全局模型圖。

3. 一棵主要場景樹。

4. 一條收集或受傷的事件／資料流。

5. 一份八格 Codex 規格與 diff。

6. 一個曾經遇到的 Bug、證據與修正。

7. 一份目標平台匯出與測試清單。

8. 一段「如果增加新敵人，我會改哪裡」的遷移說明。

這讓評量從畫面華麗程度，轉向系統理解與工程可說明性。

可以直接交給 Codex 的五個任務

任務一：交付前只讀審查

不新增功能。依功能、結構、品質、平台、文件與授權六類審查專案。每項問題附檔案、證據、嚴重度、最小修正與是否阻擋發布。不要把未實測平台寫成通過。

任務二：建立匯出矩陣

目標為 Windows x86_64 與 Web。根據 Godot 4.7 stable docs，列出必要 export templates、preset、資源包含、渲染、輸入、存檔、音訊、伺服器與瀏覽器測試。區分「可自動檢查」與「必須人工裝置驗證」。

任務三：產生可重建文件

依實際專案建立 README：精確 Godot 版本、取得方式、開啟專案、執行、測試、匯出、目錄責任、已知限制、授權來源。只使用專案中可證明的資訊，不猜測外掛或素材授權。

任務四：建立六堂課教材骨架

將目前專案拆成六個 Git checkpoint 與六堂課。每堂列唯一概念、起始狀態、講師示範、學員任務、Codex 使用邊界、驗收、延伸挑戰與常見錯誤。不得要求學員一次複製完整成品。

任務五：錯誤重現包

對目前指定 Bug 建立最小重現說明：環境、初始狀態、步驟、預期、實際、錯誤與相關最小檔案。若可行，建立獨立測試場景；不要把整個遊戲複製成重現包。

Codex 可能做錯什麼

第一，把匯出檔成功生成寫成「平台驗收通過」。

第二，為了消除錯誤訊息吞掉例外或移除警告，而沒有修根因。

第三，猜測素材授權、簽章狀態或商店規範。

第四，把 Debug 開發機的效能當成 Release 目標裝置效能。

第五，產生 README 卻與實際命令、版本與路徑不一致。

第六，把教學拆成六次功能清單，沒有認知推進、獨立挑戰與驗收。

第七，在交付前「順便升級」引擎、外掛或工具鏈，擴大變更風險。

如何把這一章教給別人

可以讓學員收到一份「能跑但不能交付」的專案：沒有 README、素材來源不明、.godot/ 被提交、Web 匯出直接雙擊、暫停後 Timer 繼續、錯誤面板有警告。請他們先列交付風險，不急著修。

接著使用交付驗收矩陣，一項一項取得證據。這能讓學員理解品質不是最後的美化，而是可重複的檢查。

最後讓學員教回其中一條流程，例如「收集能量」。他必須不用畫面，口述輸入、碰撞、訊號、分數資料、HUD 與完成狀態。若能說清楚，就證明知識已從操作遷移成結構。

口語概念地圖

開發完成後，先用 Output、Debugger、Remote 場景樹與日誌取得正確性證據，再用 Profiler 量測效能。Git 保存可回退、可教學的每一步。Export Templates 與 presets 把專案資源轉成平台成品；Windows、Web、Android 各自有輸入、權限、工具鏈與裝置驗收。最後，README、授權登錄、測試矩陣與課程 checkpoint，讓一次開發能被別人重建、理解與學習。

完成不是停止修改，而是你能說明這個版本在什麼條件下已通過什麼證據，還有哪些限制。

聽完後的自我檢查

1. 為什麼「我的電腦能跑」還不等於可交付？

2. 除錯時，解析錯誤、邏輯錯誤與平台錯誤需要哪些不同證據？

3. Profiler 的價值為什麼在量測，而不是替你自動優化？

4. Windows、Web 與 Android 匯出各有哪些不能互相代替的驗收？

5. 可重建建置至少要記錄哪些版本與步驟？

6. 一個能玩的專案要如何拆成可教的六堂課？

7. 使用 Codex 教學時，怎麼防止學員只得到成品而沒有得到理解？

章末金句

- 能在開發機啟動，是里程碑，不是交付證明。

- 除錯先分類，再找證據；不要用十種猜測換一個偶然消失的錯誤。

- 好日誌記錄狀態轉換，不用每一幀的噪音淹沒真相。

- 效能要量測，平台要實測，授權要有來源。

- 匯出檔存在不代表玩家能玩，玩家能玩也不代表作品可維護。

- Git 不只保存程式，也保存一條可以回放的學習路線。

- 可交付版本是一組有條件、有證據、有已知限制的承諾。

- 真正的教學成果，不是複製出同一個遊戲，而是能在條件改變時重新定義與驗收。
