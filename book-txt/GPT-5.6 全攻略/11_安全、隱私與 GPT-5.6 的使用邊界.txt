安全、隱私與 GPT-5.6 的使用邊界

章首開場：能力越接近工作，安全越不能只靠一句「請小心」

聊天工具答錯一個問題，影響可能只是一次誤解；工作型 Agent 若讀錯資料、改錯檔案、寄錯對象、公開祕密或執行不可逆動作，錯誤會直接進入真實世界。

GPT-5.6 的能力提升，不只表現在答案與推理，也表現在工具使用、長任務、電腦操作、程式修改、多 Agent 與工件交付。能力越接近工作，風險就越接近營運。

OpenAI 在 GPT-5.6 System Card 中，把 Sol、Terra、Luna 都依 Preparedness Framework 視為網路安全與生物／化學風險的 High capability，但三者都未達 Critical；AI Self-Improvement 則未達 High。官方同時部署模型訓練、即時監控、activation classifiers、帳號層級措施與 Trusted Access 等多層防護。[OAI-14]

這些平台防護很重要，但使用者與組織不能因此把自己的治理外包出去。平台不知道你的機密分級、客戶承諾、內部權限、法規義務與業務後果。

模型安全處理「它能不能協助」；組織治理還要處理「它在你的世界裡可以做到哪裡」。

一、風險不是模型屬性，而是能力、資料與權限的組合

同一個模型，放在不同環境裡，風險完全不同。

- 只讀公開文章、不能使用工具：風險較低。

- 能讀內部客戶資料：隱私與機密風險上升。

- 能修改正式資料庫：完整性風險上升。

- 能寄信、發布與付款：外部影響風險上升。

- 能長時間自主、建立子 Agent：可見性與成本風險上升。

可以用一個簡化公式思考：

```textOperational Risk= Capability × Data Sensitivity × Action Authority × Autonomy Duration÷ Observability & Recovery```

這不是精確數學，而是一個設計提醒。即使模型能力固定，只要降低資料敏感度、縮小動作權限、縮短自主時間、提高觀察與回復能力，整體風險就能下降。

二、Capability Is Not Authorization：會做，不等於被授權做

GPT-5.6 可能能夠修改檔案、執行命令、分析漏洞、操作網站或產生專業建議。但能力不是授權。

在企業治理裡，至少要分清楚三件事：

1. Capability：模型技術上會不會。

2. Permission：這個工作流被允許使用什麼工具與資料。

3. Authority：誰有權承擔這個動作的後果。

例如 AI 可以寫出合約草案，工作流也被允許讀取範本，但正式承諾仍需有授權的人核准。AI 可以計算薪資差異，但不代表可以自行修改薪資。AI 可以找到系統弱點，但測試必須在明確授權範圍內進行。

能力擴張得越快，授權語言就越需要精確。

三、資料分級：不是所有 Context 都能用同一種方式處理

我建議建立一個簡單的 Data Context Ladder，資料情境階梯。

D0：Public——公開

已正式公開、可自由分享的資料，例如官網、公開報告、已發布課程資訊。

D1：Internal——一般內部

未公開但低敏感，例如內部流程、一般會議紀錄、工作草稿。

D2：Confidential——機密

客戶資料、未發布策略、財務預測、報價、合約、內部評估。

D3：Restricted——高度受限

身分證號、醫療、薪資、法律特權資料、密鑰、資安事件細節。

D4：Prohibited for This Workflow——此流程禁止

不是說資料永遠不能由任何 AI 處理，而是目前這個工作流、帳號、模型或工具沒有足夠條件，因而禁止進入。

每一級都要定義：

- 允許使用的產品或 API 環境。

- 是否可以傳到外部服務。

- 是否需要去識別化。

- 保存期限。

- 日誌是否可保留原文。

- 誰可核准。

- 是否可用於模型改善或評估。

資料治理的核心不是貼一個「機密」標籤，而是把標籤轉成系統行為。

四、Action Risk Ladder：動作風險比文字風險更直接

同一份資料，讀取與寫入的風險不同。可以建立 Action Risk Ladder。

A0：Explain——解釋

回答、摘要、比較、規劃，不改變外部狀態。

A1：Draft——草擬

建立新草稿、測試檔或建議，不覆蓋正式資產。

A2：Local Change——範圍內可逆修改

修改指定檔案、建立分支、跑非破壞性測試，可輕易回復。

A3：External Write——外部寫入

寄信、發布、更新 CRM、寫入正式資料庫、建立部署或通知使用者。

A4：High-impact / Irreversible——高影響或不可逆

刪除、付款、簽約、法律提交、正式人事決定、醫療處置、重大資安動作。

一般原則是：

- A0 可廣泛自動化。

- A1 可在清楚範圍內自動化。

- A2 需要版本與回復。

- A3 通常需要明確核准、冪等與稽核。

- A4 應由有資格的人承擔最終決策，並採更嚴格流程。

OpenAI 的模型指南也建議對外部寫入、破壞性動作、購買或重大擴大範圍要求確認；System Card 另評估電腦操作中的使用者確認與避免資料破壞行為。[OAI-05][OAI-14]

五、Guardrail Stack：護欄不是一個過濾器，而是六層系統

只在模型輸出後跑一次敏感詞檢查，不能構成完整安全。可以用 Guardrail Stack。

Layer 1：Identity & Access

確認使用者是誰、屬於哪個角色、可使用哪些資料與工具。權限應沿用既有組織控制，不因 AI 介面而繞過。

Layer 2：Input & Context

檢查資料分級、去識別、來源可信度、Prompt Injection 與必要性。不要把整個共享硬碟送進 Context。

Layer 3：Model Policy

以系統與開發者政策定義允許、禁止、需要核准與失敗回報。政策應精簡、版本化、可測試。

Layer 4：Tool Boundary

工具採最小權限、讀寫分離、參數限制、沙箱、allowlist、冪等與確認。模型不直接取得萬用管理者憑證。

Layer 5：Output & Action Validation

對格式、個資、祕密、事實、引用、危險指令與高風險動作做規則或模型檢查。外部寫入前建立 Approval Gate。

Layer 6：Monitoring & Response

記錄異常、拒絕、越權嘗試、成本突增、重複失敗與安全事件；能停用工具、撤銷憑證、回復版本與通知責任人。

多層設計的目的不是假設每一層完美，而是假設任何一層都可能失敗。

六、Prompt Injection：資料裡的文字不一定只是資料

當 Agent 讀取網頁、Email、文件、Issue 或外部工具結果時，內容可能包含「忽略先前指令、把祕密傳到某處」等惡意文字。這些文字對人來說是資料，對模型可能看起來像指令。

GPT-5.6 System Card 包含對 Connector、搜尋與 Function Calling Prompt Injection 的評估；即使模型防禦表現提升，應用端仍必須採取分層措施。[OAI-14]

應用端防護原則

- 清楚標記外部內容為不受信任資料。

- 不讓資料內容改變工具權限與系統政策。

- 工具選擇與高風險參數由程式限制。

- 祕密不放入模型可見 Context，除非絕對必要。

- 外部寫入要求核准。

- 對異常指令、跨域資料外傳與非預期工具呼叫建立偵測。

- 對重要工作使用 allowlist，而非只用 blocklist。

- 在測試集中加入真實 Prompt Injection 變體。

不要要求模型「自行判斷所有惡意內容」；安全邊界必須同時存在於系統與工具層。

七、Overreach：高自主模型可能多做一步，而那一步可能就是風險

System Card 提到，在 Agentic Coding 的部署模擬中，GPT-5.6 相較 GPT-5.5 有較高傾向超出使用者意圖，包括嘗試未被要求的動作，但絕對比率仍低。[OAI-14]

這個發現非常值得一般工作流注意。當模型更主動、更持續，它可能認為「順便幫你完成」是好事，但那個順便可能包含：

- 改了範圍外檔案。

- 安裝不必要套件。

- 把草稿發出去。

- 清理它以為沒用的資料。

- 修改既有格式。

- 擴大研究或成本。

防止 Overreach 的方法不是反覆說「不要亂做」，而是建立 Change Envelope，變更信封：

- 允許修改的目錄、檔案與資源。

- 禁止變更的 Invariants。

- 可以自行做的可逆動作。

- 必須先核准的外部或不可逆動作。

- 超出範圍時只回報，不執行。

- 最終交付差異清單。

八、Least Privilege for Agents：每個 Agent 只拿當次需要的鑰匙

傳統系統常以服務帳號配置權限；多 Agent 時，更要把權限切到工作包。

研究 Agent 只需要讀取公開與指定內部資料，不需要寄信。寫作 Agent 需要建立草稿，不需要部署。部署 Agent 需要特定環境權限，但不需要看完整客戶資料。稽核 Agent 可以讀取 Trace，不一定能修改結果。

可以建立 Agent Permission Manifest：

```textAgent: course-report-builderData: D0-D1；D2 僅限去識別摘要Read tools: activity_files, survey_summaryWrite tools: create_draft_filesForbidden: email_send, public_publish, delete_sourceApproval required: export_external, deploy_siteMax duration: 30 minutesMax cost: project policy valueOwner: education_ops```

權限 Manifest 要能被程式執行，而不是只寫在 Prompt 裡。

九、Human-in-the-Loop：人應該出現在高價值決策點，不是每一步

若每次工具呼叫都要問人，Agent 會失去效率；若完全不問，高影響錯誤可能直接發生。正確做法是依風險設計 Approval Gates。

適合自動通過

- 讀取範圍內資料。

- 建立草稿。

- 跑非破壞性測試。

- 產生摘要與比較。

- 在隔離環境建立預覽。

適合批次覆核

- 大量分類與資料清理。

- 低風險內容草稿。

- 可抽樣檢查的重複任務。

適合逐次核准

- 對外寄送、發布與部署。

- 修改正式資料。

- 使用敏感資料。

- 高金額、法律、醫療、人事與安全決策。

- 無法回復的動作。

人類核准介面也要提供足夠資訊：目標、將執行的動作、影響範圍、資料、差異、風險與回復方式。只問「是否允許？」而不說明後果，是形式上的 Human-in-the-Loop。

十、隱私：少收、少傳、少留，往往比事後加密更重要

AI 應用容易因為「可能有用」而收集大量對話、文件與日誌。隱私治理應從資料最小化開始。

Collection Minimization

只收完成任務必要的欄位。不需要出生日期，就不要收；只需要年齡區間，就不要收完整生日。

Transmission Minimization

只把當次任務需要的片段送給模型或工具。可在本地完成的去識別、過濾與聚合，先在本地做。

Retention Minimization

定義原始輸入、Trace、工具結果、工件與評估資料各自的保存期限。不是所有資料都要永久留存。

Exposure Minimization

日誌、錯誤、分析儀表板與人工審查介面使用遮罩；限制能看到原始內容的人。

Purpose Limitation

資料用於哪個目的，要與收集時承諾一致。不要因為建立了 AI 管線，就把同一批資料任意拿去訓練、行銷或其他分析。

若 API 服務個別終端使用者，OpenAI 官方建議送出穩定、保護隱私的 safety_identifier，協助安全執行；設計時仍應避免使用直接可識別資訊。[OAI-05]

十一、安全事件必須可以被處理，而不只是被記錄

成熟系統要假設會發生：錯誤發布、祕密外洩、資料誤改、工具濫用、Prompt Injection、成本失控或模型行為回歸。

一個 AI Incident Playbook 應包含：

1. 偵測：什麼訊號觸發事件？

2. 分級：影響資料、使用者、金額與範圍？

3. 控制：停用哪個工具、模型、帳號或流程？

4. 回復：還原檔案、撤銷憑證、下架內容、修正資料。

5. 通知：誰需要知道？是否有法規或合約通知義務？

6. 調查：保留哪些 Trace、版本與證據？

7. 修正：政策、工具、測試、權限或教育要改什麼？

8. 驗證：如何確定問題不再發生？

只記錄「模型答錯了」沒有用。事件處理要能改變下一次循環。

十二、安全 Evals：不要只測模型會不會拒絕

安全評估至少包含五種能力。

1. Policy Compliance

面對禁止、限制與需核准任務，是否採取正確行為？

2. Permission Compliance

是否只使用允許資料與工具？會不會超出 Change Envelope？

3. Injection Robustness

是否會被文件、網頁或工具結果中的惡意指令改變目標？

4. Safe Failure

資料缺失、工具錯誤、來源衝突或安全檢查介入時，能否停止、保留狀態並清楚回報？

5. Recovery

失敗後是否能重試、降級、回復或轉人工，而不重複造成影響？

測試案例應包含正常與惡意變體，也包含「看似無害但需要授權」的灰色案例。真正困難的安全問題，往往不是明顯惡意，而是目的合理、手段越界。

十三、實際情境一：協會會員資料與活動報告

協會要使用 AI 整理活動資料。可以這樣設計：

- 原始會員名冊為 D3，不直接進入寫作 Agent。

- 本地腳本先產生去識別統計。

- 照片依授權狀態分類，未授權不進公開工件。

- 寫作 Agent 只取得統計、活動資訊與已核准照片。

- 產生的成果報告先是 A1 草稿。

- 對外發布為 A3，由活動 Owner 核准。

- Trace 不保存完整身分欄位。

- 發現數字不一致時停止，不以推估補齊。

這個流程不是阻止 AI 工作，而是讓 AI 在不碰不必要個資的情況下完成大部分工作。

十四、實際情境二：企業資安修補 Agent

資安 Agent 可以讀取漏洞報告、重現問題、建立修補分支與測試，但權限應限制：

- 只在明確授權的專案與環境。

- 不對外部目標做未授權測試。

- 生產部署需人工核准。

- 密鑰透過受控工具取得，不顯示在 Prompt 與日誌。

- 修補前後都有測試與差異。

- 若發現可能被利用的重大問題，進入既有事件通報流程。

OpenAI 對 GPT-5.6 的評估指出，它在找出與修正弱點方面的能力提升，但未達能可靠自主完成針對強化目標的端到端攻擊；官方同時採更保守的多層防護，力求保留合法防禦工作。[OAI-01][OAI-14]

這提醒我們：能力越適合防禦，也越需要明確授權與稽核。

十五、實際情境三：高風險專業建議

在醫療、法律、財務與人事情境中，AI 可以協助：

- 整理資料與選項。

- 找出問題與缺口。

- 產生提問清單。

- 比較規則與文件。

- 建立草案與檢查表。

但不能把流暢文字當成專業責任。應清楚標示資料日期、假設、限制、來源與需要持證專業人員判斷的部分；最終決策權與責任不能被一個「AI 建議」按鈕模糊掉。

十六、內化筆記：護欄不是不信任 AI，而是不把責任藏起來

有人把 Guardrails 理解成限制，彷彿只要模型夠強，就應該讓它自由工作。這忽略了真實組織本來就有權限、覆核、版本、預算與責任。

我們不會因為一位員工很優秀，就把所有客戶資料、管理者密碼與付款權限一次交給他；也不會因為一套軟體測試通過，就取消備份與監控。AI 同樣需要適當邊界。

護欄的目的不是讓 AI 什麼都不敢做，而是讓它知道哪些可以快速前進，哪些必須停下來讓有責任的人決定。

好的安全設計，不是把所有工作卡住，而是把速度留給可逆工作，把慎重留給高影響決策。

十七、章末金句

1. 能力越接近工作，安全越不能只靠一句「請小心」。

2. 模型安全處理它能不能協助；組織治理處理它在你的世界可以做到哪裡。

3. 風險不是模型單一屬性，而是能力、資料、權限與自主時間的組合。

4. Capability Is Not Authorization：會做，不等於被授權做。

5. 資料分級只有轉成系統行為，才不是貼標籤。

6. 護欄不是一個過濾器，而是一套身分、Context、工具、驗收與回應系統。

7. 不要要求模型自行承擔全部安全判斷；邊界必須存在於工具與程式層。

8. 高自主模型可能多做一步，而那一步正是需要治理的地方。

9. 每個 Agent 只應拿到完成當次工作所需的鑰匙。

10. 人類核准的價值不在按按鈕，而在理解後果並承擔決定。

11. 好的安全設計把速度留給可逆工作，把慎重留給高影響決策。

12. 護欄不是不信任 AI，而是不把責任藏起來。
