Codex：從寫程式進化成數位工作者

章首開場：程式碼只是它工作的語言，不是它工作的邊界

很多人聽到 Codex，第一個反應是：「那是工程師寫程式用的。」這個理解曾經合理，但已經不完整。

當一個 Agent 能閱讀專案、修改檔案、執行命令、查看結果、跑測試、使用 Git、連接工具、建立網站與反覆修正，它做的事情已經不只是產生程式碼。它是在一個受控工作環境裡，把意圖轉成可運作的成果。

程式碼仍然重要，因為程式碼是數位世界最精確的操作語言之一。但 Codex 的真正價值，是讓人不必逐行指揮，而能用任務、約束與驗收來驅動工作。

OpenAI 把 Codex app 定位為能同時管理多個 Agent、長時間任務、專案檔案、工作樹與版本控制的工作中心；同一套能力也延伸到 CLI、IDE 與雲端環境。[OAI-11][OAI-17]

因此，本章不把 Codex 當成「更強的自動補字」，而把它視為一個 Digital Work Runtime，數位工作執行環境。

一、從 Code Generator 到 Work Executor

早期 AI 寫程式常見的流程是：人在聊天視窗描述需求，AI 回傳一段程式碼，人複製到編輯器，遇到錯誤再把訊息貼回去。這其實還是 Copy-Paste Cliff，只是內容從文字變成程式。

真正的 Agent 工作方式至少多了六件事：

1. Inspect：先讀取現有專案、規範與相依性。

2. Plan：把需求拆成可執行步驟。

3. Edit：在正確檔案裡修改，而不是只回傳片段。

4. Run：執行建置、測試、腳本或應用。

5. Observe：讀取錯誤、畫面、日誌與測試結果。

6. Iterate：根據驗收反覆修正，直到通過或升級給人。

這六個動作形成 Codex Work Loop：

看懂現場 → 設計變更 → 實際執行 → 觀察結果 → 修正 → 交付差異。

人在這個循環裡，不必親自搬運每一段程式碼，但要定義工作範圍、不可破壞的條件、測試與核准點。

二、Codex 的四個工作表面

理解 Codex，不能只看單一介面。不同表面適合不同工作。

1. IDE：貼近當下編輯

適合閱讀一段程式、修改目前功能、解釋錯誤與協助小範圍重構。人仍在編輯器裡密切互動。

2. CLI：貼近命令與自動化

適合在終端機操作專案、執行腳本、檢查環境、批次處理檔案與串接既有開發流程。它對技術團隊特別自然，因為能和 shell、Git、測試工具共存。

3. Codex app：多任務控制台

適合同時啟動多個工作、監看進度、切換專案、管理工作樹、檢視差異與安排長任務。它把 Agent 從聊天分頁提升為可管理的工作組合。[OAI-11][OAI-17]

4. Cloud：隔離與委派

適合把任務交給隔離環境執行，讓 Agent 在不占用本機操作的情況下完成研究、修改、測試或建立成果，再回傳變更。

這四個表面不是互相取代，而是形成連續帶：當下協作、終端執行、多任務協調與遠端委派。

三、Repository as World：專案庫就是 Agent 的世界

對 Codex 而言，一個 repository 不只是程式碼儲存區。它可能包含：

- 產品需求與設計文件。

- 程式碼與測試。

- 資料庫結構。

- 部署設定。

- 品牌素材。

- 操作腳本。

- Agent 指令。

- 評估案例。

- 歷史變更與討論。

這些共同構成 Agent 的工作世界。我把這個觀念稱為 Repository as World。

當專案庫缺少規格、命名混亂、測試不足、敏感資訊散落，Agent 並不會神奇地補上組織記憶。它只會在不完整世界裡做出合理猜測。

因此，要讓 Codex 工作得好，第一步不是寫更長 Prompt，而是讓 repository 變得可理解：

- 根目錄有清楚 README。

- 開發、測試、建置與部署指令可重現。

- 重要規範寫進 AGENTS.md 或相應指令檔。

- 敏感資訊使用環境變數與祕密管理。

- 範例資料與真實資料分開。

- 測試代表重要行為。

- 目錄與命名反映領域概念。

整理專案給 Agent 使用，也是在整理專案給下一位人類使用。

四、Agent Contract：把工作委派給 Codex 前，要先寫契約

一個有效的 Codex 任務，不只包含功能描述。可以用 Agent Contract 定義七個部分。

1. Objective——目標

要解決的使用者問題是什麼？不要只說「新增按鈕」，要說按鈕支持哪個行為。

2. Scope——範圍

允許修改哪些目錄、模組與檔案？哪些部分不應動？

3. Invariants——不變條件

既有 API、資料格式、權限、品牌、效能或相容性中，有哪些不能被破壞？

4. Tooling——工具

要使用哪些建置、測試、瀏覽器、資料庫或設計工具？

5. Acceptance——驗收

哪些測試要通過？畫面要符合哪些狀態？失敗情境怎麼處理？

6. Authority——權限

可否安裝套件、修改資料庫、連網、部署、建立分支、提交或開 Pull Request？

7. Escalation——升級

遇到規格衝突、祕密缺失、測試不穩、需要不可逆變更時，何時停止並回報？

以下是一個實務範例：

```text目標：替課程報名系統新增候補機制；名額滿時可加入候補，取消名額後依順序通知。

範圍：可修改 registration、notification 模組與相關測試；不要改付款流程。

不變條件：既有報名 API 向後相容；不得在日誌寫入完整個資；通知失敗不得造成名額遺失。

驗收：- 正常報名、額滿候補、取消遞補、重複提交與通知失敗都有測試。- 所有既有測試通過。- 提供資料庫遷移與回復方式。

權限：可以建立新分支與安裝開發相依；部署與寄送真實通知前必須核准。```

這種契約能讓 Codex 自主規劃，又不會把自主誤解成無邊界操作。

五、工作樹不是技術細節，而是平行工作的安全空間

當多個 Agent 或人同時修改同一個專案，最常見的問題是彼此覆蓋。Git worktree 提供不同工作目錄，讓每個任務在獨立分支進行；Codex app 把這種隔離帶入多 Agent 工作流程。[OAI-11][OAI-17]

可以把 worktree 想成一張工作桌：

- 每個 Agent 有自己的材料與變更。

- 不會直接踩到主線。

- 完成後可檢視差異。

- 通過驗收才整合。

- 失敗時可以丟棄整張桌面，不污染其他工作。

這讓「同時委派三件事」不只是開三個聊天，而是建立三個可追蹤的變更空間。

但隔離不會自動解決所有衝突。若三個任務都修改同一核心介面，最後仍需要整合設計。平行化應該用在相對獨立的工作，不是把相互依賴的任務硬拆開。

六、Skills：把重複經驗封裝成可調用能力

每次都告訴 Agent 如何做簡報、如何跑測試、如何部署網站，會形成巨大的提示詞負擔。Skills 的價值，是把重複規則、步驟與資源封裝成可重用能力；Plugins 則能把技能、工具與整合一起帶入特定工作。[OAI-12]

一個 Skill 可以包含：

- 何時使用。

- 必要輸入。

- 標準步驟。

- 可使用工具。

- 輸出格式。

- 驗收方式。

- 範例與失敗處理。

例如「協會活動成果包」Skill，可以規定：讀取報名表、照片與問卷，產生成果報告、社群貼文、結案簡報與資料清單，並對個資遮罩、統計數字與圖片授權做檢查。

這不是把 Prompt 存起來而已。好的 Skill 是一個小型操作手冊，能被 Agent 在正確時機選用。

我把 Skill 的成熟度分成四層：

1. Instruction：只有文字說明。

2. Template：加入固定工件與格式。

3. Tool-enabled：能呼叫腳本、API 或軟體。

4. Evaluated：有測試案例與品質量測，能持續改進。

技能只有在被評估後，才真正從「經驗筆記」變成「可依賴能力」。

七、MCP 與工具：讓 Codex 碰到真實世界

沒有工具的 Agent，只能在文字世界裡推理。透過工具與 MCP，Codex 能查詢文件、讀取設計、操作資料、呼叫服務、建立部署或連接組織系統。

但「能接」不代表「都該接」。每增加一個工具，都增加：

- 可用能力。

- 權限風險。

- 錯誤模式。

- Context 噪音。

- 維護成本。

- 外部相依性。

因此，工具設計要遵守 Least Tool Principle，最少工具原則：讓 Agent 只看見完成當前任務所需的最小工具集合。

工具也應該有清楚契約：

- 名稱與用途單一。

- 參數有型別與限制。

- 回傳內容結構化。

- 錯誤能被辨認。

- 讀取與寫入分開。

- 不可逆動作要求核准。

- 認證資料不暴露給模型輸出。

工具越模糊，Agent 越容易選錯；工具越龐大，越難建立有效評估。

八、Codex 不只是工程師工具：非工程師可以做什麼？

非工程師未必要自己維護大型程式，但可以把 Codex 用在「建立小型數位工具」。

1. 資料整理器

批次重新命名檔案、合併 CSV、清理欄位、產生摘要與建立查詢介面。

2. 課程網站

把課綱、教材、影片、作業與常見問題整理成可瀏覽網站。

3. 內部表單與儀表板

建立報名、庫存、追蹤、評量或專案看板的原型。

4. 文件自動化

從資料來源產生固定格式的證書、報告、報價、會議紀錄與交付清單。

5. 個人工作助手

建立只服務自己工作習慣的小工具，例如講座資料打包器、章節字數檢查器、照片素材清單產生器。

非工程師使用 Codex 的關鍵，不是「完全不懂技術也能做任何產品」，而是把需求描述、驗收、資料責任與維護成本看清楚。原型很容易，長期可靠的系統仍需要架構、安全與維運。

九、Prototype Trap：原型成功，不等於系統可以上線

Codex 能快速做出有畫面的成果，也因此更容易掉進 Prototype Trap，原型陷阱。

原型通常證明「這個想法可以被展示」；正式系統則必須回答：

- 多個使用者同時操作會怎樣？

- 資料如何備份與刪除？

- 權限是否隔離？

- 服務中斷怎麼處理？

- 更新會不會破壞舊資料？

- 成本如何監控？

- 誰負責維護？

- 法律與隱私要求是什麼？

AI 把從零到一變快，卻沒有取消從一到穩定的工程。

可以用 Prototype-to-Production Bridge 檢查六個面向：

1. Architecture：架構與相依性。

2. Security：認證、授權、祕密與漏洞。

3. Data：資料模型、遷移、備份與保留。

4. Reliability：測試、監控、錯誤與復原。

5. Operations：部署、版本、成本與責任人。

6. Experience：可用性、無障礙、回饋與支援。

只有走過這座橋，AI 建立的工具才真正進入組織工作。

十、測試不是最後一道程序，而是 Agent 的方向感

人類工程師可以依經驗看出某個修改可能有問題；Agent 更需要明確回饋。測試提供可機器判讀的方向：通過或失敗、預期與實際、哪一個行為被破壞。

對 Codex 而言，好的測試同時扮演三個角色：

- Specification：描述系統應如何運作。

- Sensor：偵測修改造成的影響。

- Boundary：限制 Agent 不要跨越重要不變條件。

因此，委派任務時不要只要求「功能做完」，也要要求：

- 先閱讀既有測試，理解行為。

- 新增失敗案例與邊界案例。

- 執行完整或適當範圍的測試。

- 不得為了通過而刪除有效測試。

- 若測試與需求衝突，先說明而不是自行選邊。

對 Agent 而言，測試不是限制創造力，而是讓它知道自己是否仍在正確世界裡。

十一、Diff as Deliverable：真正的交付是可審查差異

傳統聊天式寫程式，最後交付一大段「建議程式碼」。Codex 工作更適合以差異為中心：改了哪些檔案、為什麼改、測試結果、已知限制、需要人工決定什麼。

一份成熟的交付摘要可以包含：

1. 目標與完成範圍。

2. 主要設計決策。

3. 變更檔案清單。

4. 測試與驗證結果。

5. 資料庫或部署影響。

6. 安全與隱私考量。

7. 未解問題與回復方式。

我把這稱為 Diff as Deliverable，差異即交付。它讓審查者不必重讀整個專案，只需理解這次改變。

十二、實際情境：替講師建立課程資料打包器

假設講師每次開課後，都要整理簽到表、照片、回饋、教材與證書。這個工作重複、容易漏檔，也很適合 Codex。

Agent Contract

- 目標：從一個活動資料夾產生標準成果包。

- 輸入：活動資訊 JSON、學員 CSV、照片、教材與問卷。

- 輸出：成果報告草稿、照片索引、證書、統計表、README 與 ZIP。

- 限制：個資不得出現在公開報告；照片需保留原檔；缺少欄位不得猜測。

- 驗收：同一輸入可重複產生相同結構；檔名無亂碼；所有文件可開啟；統計數字可回查。

Codex 工作循環

1. 先掃描資料夾與格式。

2. 建立資料模型與缺口報告。

3. 寫入處理腳本與模板。

4. 用匿名測試資料執行。

5. 檢查輸出 ZIP 與字型、圖片、統計。

6. 針對錯誤修正。

7. 交付原始碼、使用說明與樣本成果。

這個案例的價值不只是省下一次整理時間，而是把講師的隱性流程封裝成可重複工具。

十三、實際情境：讓多個 Codex Agent 平行完成改版

一個網站改版可以分成：

- Agent A：盤點現有頁面與內容缺口。

- Agent B：建立設計元件與版型。

- Agent C：改善無障礙與效能。

- Agent D：補測試與部署檢查。

每個 Agent 使用獨立工作樹，先在各自範圍修改。主 Agent 或人類架構師負責共同介面、優先順序與整合。

這不是讓四個 AI 隨意寫四份程式，而是建立一個 Agent Portfolio：每個工作有契約、邊界、狀態、成本與驗收。

多 Agent 的真正挑戰，通常不在同時啟動，而在最後誰負責整合。這會在第九章深入討論。

十四、內化筆記：會寫程式的人，角色會往「定義系統」移動

Codex 不會讓工程思維變得不重要。相反地，當產生與修改速度變快，錯誤也能更快擴散。架構、測試、資料責任、權限與觀察性因此更重要。

工程師的價值會逐漸從輸入每一行，轉向：

- 把模糊需求轉成可測試行為。

- 設計可讓 Agent 理解的專案世界。

- 建立安全工具與權限邊界。

- 判斷哪些任務可以平行、哪些必須整合。

- 審查差異與系統性風險。

- 把一次成功封裝成技能與評估。

非工程師的價值也不是被迫變成工程師，而是學會以更清楚的規格和驗收，與數位工作者合作。

程式碼只是 Codex 工作的語言；真正的產品，是一個可理解、可測試、可維護的改變。

十五、章末金句

1. 程式碼只是 Codex 工作的語言，不是它工作的邊界。

2. 從 Code Generator 到 Work Executor，差別在於能不能看懂、執行、觀察與修正。

3. Repository 不只是程式碼庫，而是 Agent 所處的世界。

4. 整理專案給 Agent 使用，也是在整理專案給下一位人類使用。

5. 自主不是沒有邊界，而是在清楚契約裡自行前進。

6. 工作樹替每個 Agent 提供一張不互相踩踏的工作桌。

7. Skill 只有被評估後，才從經驗筆記變成可依賴能力。

8. AI 把從零到一變快，沒有取消從一到穩定的工程。

9. 對 Agent 而言，測試是方向感，不只是最後一道程序。

10. 真正的交付不是一大段程式碼，而是一個可審查、可回復的差異。
