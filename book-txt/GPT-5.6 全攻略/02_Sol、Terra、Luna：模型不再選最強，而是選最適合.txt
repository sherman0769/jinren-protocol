Sol、Terra、Luna：模型不再選最強，而是選最適合

章首開場：最強模型，不等於最好的系統

當一家公司只有一種車，所有貨物都用同一台車運送，管理很簡單，效率卻未必好。送一份文件不需要貨櫃車，搬一整間倉庫也不能靠機車。模型也是如此。

GPT-5.6 不再只用一個名稱涵蓋所有工作。OpenAI 把它設計成三個模型：Sol、Terra、Luna。Sol 追求旗艦能力，Terra 在能力、速度與成本之間取得平衡，Luna 則面向高流量、成本敏感與結構清楚的任務。三者在 API 模型頁面上都支援文字與圖片輸入、文字輸出、多語與視覺能力，Context Window 都是 1.05M，最大輸出 128K Token；官方列出的知識截止日為 2026 年 2 月 16 日。[OAI-06]

真正重要的不是背下規格，而是建立一個新習慣：不要問哪個模型最強，要問這一段工作需要哪一種能力。

本章要把模型選擇從直覺與偏好，轉成可以被設計、測試與治理的 Model Routing。

一、為什麼「永遠用最強」通常不是好策略？

模型選擇看似只是技術設定，實際上同時影響四件事：品質、速度、成本與容量。

假設一個客服系統每天要處理十萬筆訊息。大部分工作只是分類、擷取訂單編號、判斷語言與套用標準回覆；少部分涉及退款爭議、法規、情緒風險與跨系統查證。如果全部交給最高能力模型，成本與延遲會被簡單任務拖高；如果全部交給最低成本模型，複雜案件的風險又會增加。

這就是模型路由存在的原因：讓模型能力跟任務難度對齊。

更精確地說，模型路由不是「先用便宜的，不行再換貴的」這麼簡單。它至少包括：

- 任務在一開始如何被分級。

- 哪些訊號代表需要升級。

- 升級後是否保留原始 Context。

- 不同模型的輸出如何用同一套標準驗收。

- 成本、延遲與失敗率如何被追蹤。

如果沒有這些機制，模型家族只是三個按鈕；有了這些機制，它才成為一套生產架構。

二、三個模型的實務定位

Sol：把能力放在最需要判斷的地方

Sol 是 GPT-5.6 的旗艦模型。官方把它定位為複雜專業工作、推理與程式任務的首選，API 的 gpt-5.6 alias 也會指向 gpt-5.6-sol。[OAI-05][OAI-06]

Sol 適合的，不只是「很難的題目」，而是以下幾種工作形狀：

1. 需求模糊：資料不完整，需要先理解真正目標。

2. 步驟很長：研究、規劃、執行、驗證必須連續進行。

3. 代價很高：錯誤會影響決策、合約、資安、財務或品牌。

4. 跨領域：需要同時處理商業、技術、設計與溝通。

5. 需要整合：多份文件、工具與子任務最後要形成一致成果。

Sol 的價值不是每一個句子都比其他模型華麗，而是在模糊與長程任務裡較能維持方向、做出判斷並完成驗證。

Terra：大多數正式工作的主力層

Terra 的官方定位是能力與成本的平衡。它不是「比較差的 Sol」，而是更適合日常規模化工作的模型。[OAI-02][OAI-05]

很多企業真正需要的主力，不是每次都使用旗艦模型，而是有一個能穩定處理大量正式任務的中間層。例如：

- 依模板產生週報與會議摘要。

- 整理研究資料並輸出初步比較表。

- 將課程逐字稿轉成教材初稿。

- 依既有規則審查文件缺漏。

- 在 Codex 中處理較輕量的子 Agent 工作。

- 進行日常資料分析與多步驟工作。

Terra 特別適合「規則已經清楚，但仍需要判斷」的任務。它是模型路由中最容易成為預設工作馬的角色。

Luna：高流量與結構化工作的效率層

Luna 是 GPT-5.6 系列中速度與成本效率最高的選項。它適合大量、重複、格式明確、可快速驗收的工作。[OAI-02][OAI-06]

例如：

- 內容分類、標籤與路由。

- 欄位擷取、格式轉換與資料清理。

- 依固定規則產生短摘要。

- 批次檢查檔名、標題、欄位與基本一致性。

- 對大量候選資料做第一輪篩選。

- 為多 Agent 系統處理低風險子任務。

Luna 的強項不是把每一個複雜問題都想透，而是用較低成本把大量明確工作做完。只要驗收條件清楚，這類模型往往能釋放整個系統的吞吐量。

三、Model Routing Triangle：用三角形，不用排行榜

我把模型選擇整理成 Model Routing Triangle，模型路由三角形。三個角分別是：

1. Ambiguity，模糊度：任務目標、資料與路徑有多不確定？

2. Impact，影響度：錯誤造成的損失有多大？

3. Volume，規模量：任務頻率、資料量與並行需求有多高？

路由原則

- 模糊度高、影響度高：優先 Sol。

- 模糊度中等、影響度中等、規模大：優先 Terra。

- 模糊度低、影響度低、規模極大：優先 Luna。

- 規模很小但影響度極高：仍然可能選 Sol。

- 規模很大且影響度高：通常採 Luna/Terra 前處理，加 Sol 做最後判斷。

這個模型提醒我們：成本不是唯一軸，能力也不是唯一軸。任務設計必須同時看「不確定性、風險與數量」。

四、不要把整份工作交給同一個模型

一份工作通常包含多種形狀。以「製作企業月報」為例：

1. 從多個來源擷取數字：Luna。

2. 清理欄位並找出缺漏：Luna 或 Terra。

3. 解讀異常與推論原因：Terra。

4. 判斷哪些議題需要主管注意：Sol。

5. 依公司模板產生簡報：Terra 或 Sol，視設計與複雜度而定。

6. 最後審查數字、敘事與風險：Sol。

這種設計叫做 Capability Placement，能力放置。不是讓最強模型從頭做到底，而是把高能力放在真正需要判斷的節點。

能力放置有三個好處：

- 降低簡單步驟消耗高價 Token。

- 讓高能力模型的 Context 更乾淨，不被大量雜訊塞滿。

- 讓每一段工作都能用適合的驗收方式測試。

五、GPT-5.6 API 規格與價格，應該怎麼看？

截至 2026 年 7 月 9 日，官方 API 模型頁列出的標準短 Context 價格如下，單位為每一百萬 Token 的美元價格：[OAI-06][OAI-07]

| 模型 | 輸入 | Cached Input | Cache Write | 輸出 ||---|---:|---:|---:|---:|| GPT-5.6 Sol | 5.00 | 0.50 | 6.25 | 30.00 || GPT-5.6 Terra | 2.50 | 0.25 | 3.125 | 15.00 || GPT-5.6 Luna | 1.00 | 0.10 | 1.25 | 6.00 |

長 Context 的價格較高；Batch、Flex 與 Priority 也有不同費率。價格會更新，真正導入前必須再查官方頁面。

比價格表更重要的是三個觀念。

第一，輸出 Token 通常比輸入昂貴

這代表「讓模型講很多」可能比「給它看很多」更貴。好的工作流不只壓縮輸入，也要避免無效的中間報告、重複解釋與過度冗長的輸出。

第二，便宜模型不一定代表總成本低

假如 Luna 需要重跑三次、人工修正兩次，最後仍要升級到 Sol，總成本可能比一開始使用 Terra 更高。要看的是 Cost per Successful Outcome，每一個成功成果的成本，不是單次呼叫價格。

第三，Context 長度不是免費記憶

1.05M Context Window 很大，但放入更多內容會影響費用、延遲與注意力分配。長 Context 的價值是能承載更完整工作，不是鼓勵把所有檔案無差別塞進去。

六、建立任務分級：S、M、L 不是模型名稱，而是工作等級

一個簡單的企業起步方式，是先建立三層任務分級。

S 級：結構化、低風險、高頻率

特徵：輸入固定、規則清楚、容易自動驗收、錯誤可逆。

建議：Luna 為主；必要時 Terra 抽查。

例子：分類、標籤、格式整理、欄位擷取、短摘要、初步去重。

M 級：需要判斷、中等風險、可用規則驗收

特徵：需要理解脈絡與做有限推論，但有模板、Rubric 或歷史案例。

建議：Terra 為主；高風險項目升級 Sol。

例子：週報、教材初稿、客服建議、文件缺漏審查、一般資料分析。

L 級：高度模糊、高影響、跨領域或長程

特徵：需求可能改變、需要多工具、多次驗證，錯誤成本高。

建議：Sol；必要時使用高推理、Pro 或 Multi-agent。

例子：策略規劃、架構評估、重大提案、深度研究、資安審查、正式產品交付。

這個分級可以再搭配「是否需要人核准」。模型層級與核准層級是兩件不同的事。即使用 Sol，付款與公開發布仍然可能需要人；即使用 Luna，低風險的格式轉換也可以完全自動。

七、Routing Policy：一份可被執行的模型路由規則

真正能上線的路由策略，不應只有「簡單用 Luna、困難用 Sol」。它需要具體條件。

以下是一個示範：

```text預設使用 Terra。符合以下任一條件，改用 Luna：- 任務只涉及分類、擷取、轉換或去重。- 輸出可由確定性規則自動驗證。- 單筆失敗可安全重試，不影響外部系統。

符合以下任一條件，升級 Sol：- 需要整合三種以上資料來源並做跨來源判斷。- 涉及公開對外、法務、財務、資安或重大品牌風險。- 需求模糊，需要先提出假設與執行計畫。- Terra 的信心不足、來源衝突或連續兩次未通過驗收。

任何模型都不得自行執行付款、刪除正式資料、公開發布或寄送大量郵件。```

這份規則的價值在於可觀察。當工作失敗時，你可以追問：分級錯了？模型不適合？Context 不足？驗收太鬆？還是工具故障？

沒有路由規則，失敗只能被解釋成「AI 不穩」；有了路由規則，失敗才能變成工程問題。

八、升級與降級：模型路由不是單向扶梯

很多系統只設計升級：失敗就換更強模型。成熟系統也要設計降級。

升級訊號

- 來源彼此衝突。

- 模型回報無法判斷。

- 驗收連續失敗。

- 任務影響度被重新評估為更高。

- 使用者要求更深證據或更多替代方案。

降級訊號

- 經過幾次執行後，流程已高度固定。

- 先前由 Sol 完成的工作已被整理成模板與規則。

- 評估顯示 Terra 或 Luna 品質無顯著下降。

- 大量工作中只有少數例外需要更高能力。

降級不是品質退步，而是把學習固化成流程。當 Sol 幫你理解問題、建立 Rubric 與處理例外後，穩定部分就可以交給 Terra 或 Luna。這正是 AI 系統從「一次性聰明」走向「可規模化能力」的關鍵。

九、企業導入案例：三層內容生產線

假設一個協會每週要產生：活動整理、社群貼文、講師簡報與月報。

第一層：Luna 做材料整備

- 將照片與文件依活動分類。

- 擷取日期、講師、課程、地點與人數。

- 將逐字稿切段、去除重複口頭語。

- 標出缺少欄位與可能重複檔案。

第二層：Terra 做內容組裝

- 依模板產生活動紀錄。

- 把逐字稿整理成課程摘要與社群草稿。

- 根據既有母片形成簡報初版。

- 產生不同平台需要的文字長度。

第三層：Sol 做觀點與審查

- 判斷哪些內容值得成為核心主張。

- 檢查事實、敘事與品牌一致性。

- 比較本月與過去活動的變化。

- 產生理事會可使用的決策摘要。

這套分層能把「每一篇都從零請最強模型寫」改成可重複的生產線。人的角色則集中在觀點、敏感內容、重大決策與公開核准。

十、不要忽略評估：模型路由要靠資料，而不是印象

最常見的錯誤，是用一兩次聊天經驗判斷模型優劣。真正的路由至少需要一組代表性任務集。

可以先選二十到五十個真實任務，對 Sol、Terra、Luna 分別測量：

- 任務成功率。

- 一次通過率。

- 人工修正時間。

- 來源與事實錯誤。

- 格式符合率。

- 總 Token 與實際成本。

- 延遲與使用者等待感受。

- 發生例外時的可恢復性。

最後不要只問「哪個模型分數最高」，而要問：「在哪一類任務上，哪個模型的品質、速度與成本最合理？」

這就是 Eval 驅動的 Model Routing。

十一、內化筆記：選模型，其實是在分配注意力

高能力模型像一位資深顧問。你不會叫他整天手動整理檔名，也不會把重大策略交給完全不了解背景的臨時工。好的管理，不是把所有工作丟給最厲害的人，而是讓不同能力在正確位置發揮。

模型家族讓這件事更明顯：AI 架構不再只是「接一個 API」，而是建立一個能力組合。當我們開始路由，才會真正看見任務結構：哪些工作只是搬運，哪些需要推論，哪些需要責任判斷。

因此，模型路由最後不只是成本優化，而是一面鏡子。它逼迫組織說清楚：什麼是簡單工作？什麼是高風險工作？哪些判斷不能外包？哪些流程已經成熟到可以自動化？

選模型的本質，不是挑一顆更大的腦，而是把有限的注意力放到最值得的地方。

十二、章末金句

1. 最強模型，不等於最好的系統。

2. 不要問哪個模型最強，要問這一段工作需要哪一種能力。

3. Sol 處理模糊與高影響，Terra 承接日常正式工作，Luna 放大高流量效率。

4. 模型路由不是省錢技巧，而是能力配置。

5. 真正應該比較的是每一個成功成果的成本，不是單次呼叫價格。

6. 長 Context 是工作容量，不是免費記憶。

7. 升級讓困難問題得到更強能力；降級讓已學會的工作得到規模。

8. 沒有路由規則，失敗只能被說成 AI 不穩；有了規則，失敗才會變成工程問題。

9. 把旗艦模型用在搬運工作上，是能力浪費；把低成本模型用在重大判斷上，是風險錯置。

10. 選模型的本質，是把有限的注意力放到最值得的地方。
