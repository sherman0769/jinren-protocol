Ultra 與 Multi-Agent：一個 AI 不再負責所有事情

章首開場：多開幾個 Agent，不會自動變成一個團隊

當單一模型愈來愈強，一個直覺問題會出現：為什麼還需要多 Agent？讓最強模型多想一點，不就好了嗎？

答案在於某些工作不是單純「更難」，而是同時包含多個相對獨立的工作面：研究不同市場、檢查不同風險、修改不同模組、產生不同版本、以不同觀點審查同一成果。這些工作若依序完成，時間很長；若由同一個 Context 全部承擔，資訊也容易互相干擾。

GPT-5.6 的 Ultra 會以多個 Agent 平行處理問題，再整合結果；官方說明其預設協調四個 Agent。API 的 multi-agent beta 則讓開發者透過根 Agent 與子 Agent，建立自己的委派與平行工作流程。[OAI-01][OAI-09]

但多 Agent 不是把同一個 Prompt 複製四次。若沒有工作拆解、角色契約、共享狀態、驗收與整合者，四個聰明 Agent 只會產生四份難以合併的答案。

多 Agent 的關鍵不是數量，而是協作結構。

一、單一 Agent 的三種壓力

1. Context Pressure——情境壓力

一個 Agent 同時讀取所有資料、規則、工具回傳與中間草稿，Context 會變得龐大。即使 Context Window 足夠，重要資訊也可能被噪音稀釋。

2. Cognitive Switching——認知切換

同一個 Agent 一下扮演研究員、一下扮演設計師、一下審查資安，容易把角色標準混在一起。它可能在創作時過度批判，也可能在審查時替自己的決定辯護。

3. Sequential Delay——序列延遲

相互獨立的任務若一個接一個完成，會浪費可平行時間。例如同時研究四個競爭者，不必等第一個做完才開始第二個。

Multi-Agent 的價值，就是讓不同工作擁有較乾淨的 Context、穩定角色與平行時間。

二、什麼任務適合多 Agent？

官方 multi-agent 指南建議把它用在可獨立、邊界清楚的工作流，並提醒不是所有任務都適合平行化。[OAI-09]

我把適合度整理成 PARA 判斷法。

P——Parallelizable，可平行

子任務能否同時進行？若 B 必須等待 A 的細節結果，就不是真正平行。

A——Autonomous，可自治

每個子任務能否在自己的 Context 與工具裡完成，而不必持續向其他 Agent 詢問？

R——Reviewable，可審查

每個輸出是否有清楚格式與驗收，讓根 Agent能判斷品質？

A——Aggregatable，可聚合

多份結果能否依共同結構合併，而不是彼此衝突的自由散文？

四項越高，越適合多 Agent。

高適合度任務

- 分別研究多個市場或公司。

- 對大量獨立文件做同一種抽取。

- 同時修改低耦合模組。

- 從不同觀點做紅隊與審查。

- 產生針對不同受眾的版本。

- 搜尋多個資料源後統一整理。

低適合度任務

- 需要連續推導的單一數學證明。

- 高度耦合的架構設計。

- 每一步都依賴上一個細節的流程。

- 成果很小，協調成本高於執行成本。

- 無法定義共同輸出格式的創作任務。

三、Root Agent 與 Subagents：不是主管與工讀生

在 multi-agent 架構裡，根 Agent 的工作不是「比較聰明」，而是承擔不同責任。

Root Agent 的責任

- 理解整體 Outcome Contract。

- 拆解工作與決定哪些可平行。

- 建立子 Agent 契約。

- 分配 Context、工具、預算與時間。

- 監看狀態與處理失敗。

- 驗證、去重、解決衝突與整合。

- 產生最終可負責任的成果。

Subagent 的責任

- 在界定範圍內完成一個工作包。

- 只使用必要 Context 與工具。

- 以指定結構回傳證據、結果、信心與限制。

- 遇到契約外問題時升級，而不是自行擴大範圍。

這不是「主管把雜事丟給工讀生」，而是 Control Plane 與 Execution Plane 的分工。根 Agent 是控制平面，子 Agent 是執行平面。

四、Agent Work Package：子 Agent 需要一個可交付工作包

一個子 Agent 任務至少應包含：

1. Question：要回答或完成的單一問題。

2. Inputs：可使用的資料與版本。

3. Tools：允許呼叫的工具。

4. Boundaries：不應延伸的範圍。

5. Output Schema：回傳格式。

6. Evidence：需要保留的來源或測試結果。

7. Confidence：對結果的信心與未知。

8. Budget：時間、Token、工具呼叫或成本限制。

9. Escalation：何時停止與回報。

例如，研究 GPT-5.6 三個模型時，不要給三個 Agent 同一句「分析模型」。可以分別定義：

```textAgent Sol：整理官方定位、能力、價格與適合任務。Agent Terra：使用相同欄位整理，禁止引用非官方價格。Agent Luna：使用相同欄位整理，特別說明高流量工作限制。

共同輸出：JSON，欄位固定為 model、positioning、context、output、price、best_for、cautions、sources。```

共同 Schema 讓結果可聚合，而不是三種不同文章風格。

五、Context Partitioning：不是每個 Agent 都要拿到所有資料

多 Agent 系統常見錯誤，是把完整 Context 複製給每個子 Agent。這會增加成本、噪音與資料暴露。

更好的方式是 Context Partitioning，情境分區。

Shared Context——共享情境

所有 Agent 都需要的目標、核心術語、版本、政策與共同輸出格式。

Local Context——局部情境

只有該工作包需要的文件、資料與工具結果。

Restricted Context——受限情境

只讓特定有權限的 Agent 使用，例如個資、財務、祕密或內部法律意見。

Derived Context——衍生情境

由上游 Agent 產生的摘要、結構化中間結果，而不是原始全量資料。

情境分區有三個好處：降低成本、減少干擾、縮小風險面。

Multi-Agent 不是把 Context 放大，而是把 Context 切得更精準。

六、Concurrency Budget：平行不是免費的

平行化可以縮短牆鐘時間，但通常增加總 Token、工具呼叫與整合成本。官方 API 指南提供並行子 Agent 控制，預設建議的最大同時子 Agent 數為三；實際設定仍要依任務、成本與系統限制調整。[OAI-09]

我把平行化成本分成四項：

1. Execution Cost：每個 Agent 的推理與工具成本。

2. Duplication Cost：多個 Agent 重複讀相同資料或做相同分析。

3. Coordination Cost：拆解、狀態、錯誤與通訊。

4. Synthesis Cost：根 Agent 去重、衝突處理與整合。

因此，需要一個 Concurrency Budget，並行預算。它不只設定「最多幾個 Agent」，還要設定：

- 哪些工作值得並行。

- 每個工作最多使用什麼模型。

- 是否允許建立第二層子 Agent。

- 何時取消低價值工作。

- 結果重複到什麼程度就停止。

- 總成本或延遲上限。

最強的多 Agent 系統，不是同時跑最多 Agent，而是在正確工作上使用最少必要協作者。

七、Fan-out、Map-Reduce 與 Debate：三種常見拓樸

1. Fan-out / Fan-in——分散後集中

根 Agent 把不同工作派出去，再收回整合。適合競爭者研究、文件抽取、模組修改與多受眾版本。

2. Map-Reduce——同規則批次處理

Map 階段讓多個 Agent 對獨立資料做同一操作；Reduce 階段合併統計、排序與摘要。適合大量文件、問卷、客服紀錄與內容分類。

3. Debate / Critique——辯論與批判

一個 Agent 提方案，其他 Agent 從資安、使用者、成本、法律或反方角度審查，再由整合者決定。適合高影響決策，但成本較高，也要避免「為辯論而辯論」。

還有更複雜的階層式、網狀與事件驅動架構，但一開始應選最簡單的拓樸。協作結構越複雜，觀察與除錯越困難。

八、Synthesis Is Work：整合不是把答案貼在一起

多 Agent 最容易被低估的工作，是最後整合。

四個 Agent 可能：

- 使用不同定義。

- 引用不同日期。

- 重複同一證據。

- 對同一數字產生衝突。

- 適用不同前提。

- 對信心表達方式不同。

根 Agent 必須做四層整合。

1. Normalization——正規化

統一欄位、單位、日期、術語與來源格式。

2. Deduplication——去重

辨認同一事實被不同語言重複，不把重複當成多重證據。

3. Reconciliation——調和

遇到衝突時回查來源、比較版本與前提；無法解決就保留分歧。

4. Composition——組成

依最終受眾與目的重新組織，不受子 Agent 回傳順序限制。

Synthesis 不是排版工作，而是一個新的推理任務。

因此，根 Agent通常需要更高能力模型或更明確的評估，而不應把所有預算都花在子 Agent。

九、Shared Memory 與 Blackboard：協作需要共同狀態

當任務持續時間長，Agent 不能只靠一次訊息傳遞。需要一個共享狀態，記錄：

- 工作包與負責者。

- 狀態：待辦、進行、阻塞、完成、失敗。

- 產出位置。

- 關鍵決策與理由。

- 已知風險。

- 版本與時間。

- 誰正在修改什麼。

這可以是一張結構化表、一個任務系統、一組檔案或資料庫。AI 領域常稱為 Blackboard；我更喜歡稱為 Loop Ledger，循環帳本。

帳本不是把所有對話永久保存，而是保留下一輪真正需要的狀態。沒有帳本，多 Agent 每次啟動都會重新猜測世界。

十、失敗不是例外：多 Agent 的八種常見故障

1. Duplicate Work——重複工作

拆解不清，兩個 Agent 做了同一件事。

2. Coverage Gap——覆蓋缺口

大家以為別人會做，最後沒有 Agent 負責。

3. Interface Mismatch——介面不合

輸出格式不同，無法整合。

4. Context Drift——情境漂移

子 Agent 使用不同版本或自行改變定義。

5. Tool Collision——工具碰撞

同時修改同一檔案、資料或外部狀態。

6. Error Amplification——錯誤放大

一個上游錯誤被多個下游當成事實。

7. Endless Delegation——無限委派

子 Agent 再建立子 Agent，成本失控而沒有增加價值。

8. Synthesis Collapse——整合崩潰

根 Agent 面對大量回傳，只做表面摘要，反而丟失證據與限制。

每一種故障都需要觀察訊號與處理政策。例如工具碰撞可用工作樹或鎖；情境漂移可用版本欄位；無限委派可限制深度與總預算。

十一、Multi-Agent Evals：不能只評最後答案

若只看最終成果，很難知道系統為何成功或失敗。多 Agent 評估至少分成四層。

Task Level——工作包層

每個子 Agent 是否完成指定問題、格式與證據？

Coordination Level——協調層

拆解是否完整？重複率多高？阻塞是否被處理？成本是否在預算內？

Synthesis Level——整合層

是否解決衝突、保留重要限制、正確引用來源？

Outcome Level——成果層

最終工件是否真的支持決策或使用者任務？

可以建立指標：

- Coverage：必要子題覆蓋率。

- Redundancy：重複工作比例。

- Conflict Resolution：衝突解決率。

- Evidence Retention：證據保留率。

- Cost per Accepted Outcome：每個通過成果的成本。

- Human Intervention Rate：需要人工介入的比例。

沒有這些量測，多 Agent 只是更昂貴的黑箱。

十二、實際情境一：四 Agent 完成一本技術書研究

一本 GPT-5.6 書稿可以有四條並行研究線：

- Agent A：產品與 ChatGPT 功能。

- Agent B：API、價格與技術參數。

- Agent C：Codex、Sites 與多 Agent。

- Agent D：安全、限制與版本風險。

共享 Context 包含書籍定位、日期、官方來源優先、引用格式與禁止杜撰。每個 Agent 只取得自己的文件集，回傳結構化 Facts Ledger：主張、來源、日期、信心、適用範圍與可能變動性。

根 Agent 不直接把四份報告拼成章節，而是先建立一致事實層，再由寫作 Agent 轉成白話觀點，最後由查證 Agent 對主張逐項核對。

這種分工把研究、寫作與驗證分開，降低作者同時「創作又替自己辯護」的偏誤。

十三、實際情境二：企業提案的多觀點審查

一份 AI 客服導入提案，可以由不同 Agent 審查：

- 使用者 Agent：流程是否真的更方便？

- 營運 Agent：人力、SLA、例外與交接是否可行？

- 資安 Agent：資料、權限、日誌與供應商風險。

- 財務 Agent：成本模型、敏感度與回收期。

- 反方 Agent：找出提案最可能失敗的理由。

根 Agent 必須要求每位審查者使用共同格式：風險、證據、嚴重度、可能性、緩解方式、Owner。最後不是投票決定，而是依組織風險偏好做整合。

十四、實際情境三：多 Agent 不是所有工作都更快

假設要修改一個只有三個檔案的小工具。若啟動五個 Agent，建立工作包、分配 Context、收回、解決衝突，可能比單一 Agent直接完成更慢。

這說明一個重要原則：

平行化的對象應該是工作，不是焦慮。

不要因為擔心模型做不好，就不斷增加 Agent。先改善單一 Agent 的 Context、工具與驗收；只有當任務真的具有可平行結構，再引入多 Agent。

十五、內化筆記：管理 AI 團隊，首先是在管理介面

人類團隊的協作常依賴默契、關係與臨場對話；Agent 團隊更依賴明確介面。誰負責什麼、拿到哪些資料、以什麼格式交付、怎麼判斷完成，不能只存在管理者腦中。

這會逼迫我們把管理經驗形式化。多 Agent 架構做得好，其實不是因為 Agent 很多，而是因為工作被看清楚：可平行的被分開，必須共同決定的留在整合層，風險被限制在局部，成果能被追溯。

未來管理者的重要能力之一，是設計 Agent Portfolio：知道何時用一個強 Agent、何時用幾個專業 Agent、何時根本不該交給 AI。

多 Agent 的成熟，不是讓更多 AI 同時說話，而是讓每一個工作都有邊界、介面、證據與負責整合的人。

十六、章末金句

1. 多開幾個 Agent，不會自動變成一個團隊。

2. 多 Agent 的關鍵不是數量，而是協作結構。

3. 適合平行化的是獨立工作包，不是所有複雜工作。

4. Root Agent 是控制平面，Subagent 是執行平面。

5. 共同 Schema 讓結果可以聚合，角色名稱本身不會。

6. Multi-Agent 不是把 Context 放大，而是把 Context 切得更精準。

7. 平行不是免費；節省的是時間，增加的可能是總成本。

8. Synthesis 不是排版工作，而是一個新的推理任務。

9. 沒有循環帳本，多 Agent 每次都在重新猜測世界。

10. 平行化的對象應該是工作，不是焦慮。

11. 管理 AI 團隊，首先是在管理介面。

12. 多 Agent 的成熟，是每個工作都有邊界、證據與整合責任。
