第八章｜從一個 Agent，走向企業證據基礎設施

一個 Agent 專案成功後，企業很快會出現第二個、第三個與第十個。

客服團隊建立回答與退款 Agent，採購團隊建立比價與補貨 Agent，人資建立履歷整理 Agent，研究團隊建立報告 Agent，行銷團隊建立內容 Agent。每個團隊都會遇到相似問題：資料從哪裡來、版本如何判定、哪些工具能呼叫、什麼情況送人工、最後如何追溯。

如果每個 Agent 都各自建立一套規則，企業不會得到十個可信系統，而會得到十種互不相容的可信定義。

同一份政策文件，在客服 Agent 裡被視為現行版本，在內容 Agent 裡可能仍使用舊版；同一種「高風險」在採購代表十萬元，在行銷卻代表對外發布；同一筆來源在某系統有 lineage，在另一個系統只剩一段複製文字。

因此，雙閘門證據迴路最終要建立可被多個工作流共用的企業證據基礎設施，不能停在替每個 Agent 各加兩個外掛。

企業真正要共享的是「判斷能力」

企業常先共享模型入口、向量資料庫與 Prompt 範本。這些能降低重複開發，卻仍不足以共享可信度。

更值得共享的是以下能力：

- 來源與版本的註冊。

- Metadata 與資料契約。

- 行動前 predicate 與政策規則。

- 受治理替代值與緩衝區。

- Agent run、工具與行動 Trace。

- 主張—證據帳本。

- 人工審核與例外路由。

- 評測、事件與 coverage gap 回饋。

當這些能力成為平台服務，每個 Agent 不必重新發明「什麼叫現行文件」「什麼叫可追溯」「什麼叫高風險主張」。團隊仍可依業務設定門檻，但共享共同語言與基礎控制。

八個基礎元件

企業證據基礎設施不一定要由單一產品提供，但責任上可以拆成八個元件。

一、來源登錄與權威層級

記錄資料源、Owner、更新頻率、適用範圍、權威程度、敏感等級與失效方式。

來源登錄回答：「哪些系統可以提供什麼類型的證據？」它也應區分官方主資料、業務工作檔、外部公開資料與未驗證輸入。

二、Metadata 與資料契約

定義必要時間戳、版本、單位、幣別、schema、lineage 與實體鍵。資料契約不是只為了 API 穩定，也為了讓 gate 擁有判斷訊號。

若某欄位缺失，契約應說明是拒絕、降級還是允許有限用途。

三、Policy／Predicate Engine

把 freshness、版本唯一性、完整性、金額門檻、權限與任務專屬條件寫成可執行規則。規則需要版本管理、測試、批准與回滾。

這一層要避免把所有治理寫進 Prompt。提示詞可以解釋規範，硬性控制仍應由模型無法任意覆寫的元件執行。

四、受治理緩衝區

保存已知良好、可版本化的替代資料。它支援 downstream-only remediation，但必須有來源、有效期限與使用範圍，不能成為另一個無人管理的暫存區。

五、Trace 與事件儲存

將來源、檢索、gate、Agent run、工具呼叫、行動、錯誤與人工決定串起來。它需要支援查詢與事件重建，而不只是保存大量文字日誌。

六、Claim／Evidence Ledger 服務

提供主張抽取、證據包、支持關係、路由、審核與釋出版本管理。不同內容系統可以使用共同 schema，讓研究報告、客服知識與教材都能被追蹤。

七、Review Queue 與角色權限

依資料、業務、內容、法遵與系統問題分流。介面呈現必要證據、失敗原因與可選方案，並記錄批准、拒絕、修改與 override。

八、Evals 與持續監測

追蹤 gate 偵測、false block、漏檢、路由召回、人工負擔、發布後更正與事件成本。評測不只看模型回答，還要看整條工作流是否在正確時刻阻擋與升級。

八個元件的共同目標，是讓 Agent 的可信能力不綁在某一個模型或某一組 Prompt 上。

Prompt 是資產，但不是最終證據資產

企業可以把 Prompt 版本化、測試與重用。這很重要，但當 Agent 進入正式流程，Prompt 只能回答「我們要求模型怎麼做」，不能完整回答「這次系統實際憑什麼做」。

同一個 Prompt 在不同資料版本、工具回傳與權限環境下，結果可能完全不同。真正能承擔稽核的資產，至少還包括：

- 輸入資料與 Metadata snapshot。

- 檢索與排序結果。

- Predicate 版本與判斷。

- 模型與工具版本。

- 實際行動參數與回傳。

- 主張—證據關係。

- 人工決定與釋出版本。

Prompt 是意圖的一部分；證據鏈才是單次行動的完整依據。

這個區分也有助於避免 vendor lock-in。當治理規則、evidence schema 與 Trace 全部封裝在單一模型供應商的專屬介面裡，企業很難替換模型或比較不同 Runtime。若證據基礎設施使用獨立識別、標準化事件與可攜資料結構，模型可以更換，責任鏈仍然存在。

多 Agent 的交接，不應只傳一段文字

在多 Agent 系統裡，一個 Agent 的輸出常成為下一個 Agent 的輸入。研究 Agent 找資料，分析 Agent 產生洞察，寫作 Agent 完成報告，審核 Agent 做檢查。

若每次交接只傳一段自然語言，前一個 Agent 的不確定性、來源與限制會逐步消失。第二個 Agent 看到的是結論，不知道它如何形成；第三個 Agent 再把結論寫得更肯定。

更可靠的交接單位應是 artifact，而不只是 message。至少包含：

- 內容或候選行動。

- 使用的來源與版本。

- 已通過與未通過條件。

- 尚未解決的風險。

- 主張與證據關係。

- 允許下一個 Agent 做什麼。

例如研究 Agent 不只交出「市場正在快速成長」，而要交出 claim、evidence packet、relation、範圍限制與查閱日期。寫作 Agent可以重新表達，但不能悄悄提高語氣強度。若要擴張主張，就必須補證據並產生新的 ledger record。

Agent 交接的品質，取決於證據狀態是否能隨內容一起移動。

權限必須與證據狀態連動

傳統權限管理回答「誰可以呼叫什麼工具」。Agent 系統還需要回答：「在什麼證據狀態下，可以呼叫到什麼程度？」

同一個 Agent 可能具有階段性權限：

- 資料未通過：只能搜尋與分析。

- 基本條件通過：可建立草稿或待審工單。

- 高風險條件通過：仍需人類批准。

- 批准完成：取得一次性執行權限。

- 執行後：權限自動收回。

這種設計比長期給 Agent 一個廣泛 API key 更安全。權限應被視為由任務、證據、風險與批准共同決定的短期能力，而非永久角色屬性。

企業證據基礎設施因此應與 Identity、Access Management、Secrets 與工具閘道整合。雙閘門負責判斷是否達到條件，權限系統負責強制執行。

隱私與證據保存之間的張力

可追溯常讓團隊傾向「全部保存」。但完整 Trace 可能包含個資、商業機密、內部意見與模型輸入。保存越多，不一定越安全，也可能增加隱私與資安風險。

證據基礎設施需要資料最小化與分層保存：

- 保存必要識別與雜湊，而非無限制複製原始敏感資料。

- 將來源權限沿用到 evidence packet 與 review queue。

- 對高敏感 Trace 設定較短保留期或更嚴格存取。

- 區分稽核需要的結構化事件與不必要的完整對話。

- 對外部模型傳輸內容建立遮罩與政策。

- 確保刪除與更正能傳遞到相關 ledger 與索引。

可信不等於監控一切。證據鏈也必須符合必要、適當與可治理的原則。

角色與營運責任

企業證據基礎設施不是純工程專案。至少需要以下角色共同工作：

業務流程 Owner

定義任務目標、風險、可逆性與人工批准門檻。

Data Steward

管理來源、Metadata、版本、資料契約與品質事件。

AI／平台團隊

實作 Runtime、policy engine、Trace、模型與工具整合。

研究編輯或領域專家

定義主張粒度、證據品質與釋出條件。

資安、法遵與隱私角色

管理敏感資料、權限、保留期與法規要求。

審核者與事件負責人

處理高風險例外、批准、override 與事故回顧。

各家公司不必設置完全相同的職稱；關鍵在於上述責任不能全落在一位「懂 AI 的人」身上。

企業級評測要從答案擴大到工作流

只用正確率評估 Agent，會漏掉很多系統問題。企業可以建立四類 Evals。

資料准入評測

注入過期、被取代、缺欄位、單位改變與跨來源衝突，觀察 gate 是否在正確位置攔截，以及 false block 是否可接受。

行動評測

觀察 Agent 是否遵守降權、阻擋與一次性權限，是否存在繞過 gate 的工具路徑。

主張—證據評測

建立支持、反駁、證據不足與混合證據測試集，分別量測 relation accuracy、macro-F1、review-needed recall 與額外送審率。

人類監督評測

測試審核者能否在介面中找到關鍵訊號、是否受到系統建議影響、override 是否合理，以及處理時間是否可持續。

這些評測共同回答的是「整條責任鏈在壓力下是否仍能工作」，範圍遠超過模型本身聰不聰明。

不同領域如何使用同一套基礎能力

雙閘門架構可以跨領域共享，但 predicate 與釋出條件必須在地化。

採購與供應鏈

重點在價格時效、單位、幣別、供應商實體、合約版本與金額權限。

客服

重點在政策現行版本、客戶身分、權益影響、敏感資料與可逆處理。

政策與公部門內容

重點在法規、公告版本、適用對象、地區、日期與正式發布批准。

教育與研究

重點在原始來源、研究範圍、因果語氣、版本與主張—證據對齊。

企業知識管理

重點在文件權威層級、過期機制、來源 Owner 與不同知識之間的衝突。

共享的是 Trace、身份、版本、路由與 Ledger；不同的是風險定義與條件。

九十天起步方案

大型基礎設施不必一次建成。可以用九十天建立第一個可驗證版本。

第 1 至 30 天：選一個高價值、可控範圍

- 選擇一個有明確工具呼叫或正式內容輸出的 Agent。

- 盤點來源、版本與現有人工審核。

- 建立 Agent run、source、tool call、claim 的共同 ID。

- 找出三到五個最重要風險，不追求全覆蓋。

第 31 至 60 天：建立最小雙閘門

- 在高風險行動前實作少數 deterministic predicate。

- 對數字、日期、版本與因果主張建立 Ledger。

- 設計人工 review card 與 route。

- 保存 gate、override 與釋出紀錄。

第 61 至 90 天：壓力測試與校準

- 注入已知缺陷，測試 placement 與 coverage。

- 建立支持、反駁、缺證據、混合證據案例。

- 量測人工負擔、誤攔、漏檢與處理時間。

- 根據結果調整自主等級與資料契約。

- 決定哪些能力值得平台化供其他 Agent 共用。

九十天的目標，是建立一條可以被測量、被挑戰、被改進的責任鏈；此時還不能宣稱「可信 Agent 已完成」。

Definition of Done：Agent 何時才算能進正式流程

一個企業 Agent 不應只因 Demo 成功就進入正式運作。最低完成條件可以包括：

1. 關鍵來源有 Owner、版本與失效方式。

2. 高風險工具呼叫前有可強制的 gate。

3. 已知 coverage gap 被記錄，而不是隱藏。

4. Agent 無法繞過阻擋或自行提升權限。

5. 重要主張有 evidence packet 與 release condition。

6. 人工審核者能看見足以判斷的資訊。

7. Override 有權限、理由、範圍與期限。

8. 每次行動與發布版本可以被重建。

9. 有壓力測試、事件處理與回滾機制。

10. 有人負責持續更新資料、規則與評測。

這些條件不保證零錯誤，卻能讓錯誤被看見、被控制、被追溯與被修正。

從 AI 工具走向思想與責任資產

企業導入 Agent 的早期，很容易把價值放在「能不能自動做完」。隨著系統進入更多流程，真正拉開差距的會是另一件事：組織能不能保存每一次自動化背後的證據與責任。

提示詞可以複製，模型可以更換，工具可以重新整合。若資料版本、主張關係、人工決定與事件回饋沒有被保存，組織每次升級都會重新失憶。

證據基礎設施讓 Agent 的產出不只是一次性答案，而是可以被教學、稽核、交接與持續改善的知識資產。它也讓企業有能力站在供應商與模型之上，知道自己真正依賴的是哪些資料、規則與責任。

走到這裡，我們已經從一個錯誤價格，走到一套企業級責任結構。最後要回答的問題，已從技術上能不能做到，推進到組織願不願意承認：當 AI 進入行動，可信是整個系統共同設計出的性質，不能歸因為模型的個人品德。

章末金句

1. 十個各自為政的 Agent，不會自動形成一個可信企業。

2. 企業真正要共享的，不只是模型入口，而是來源、規則、Trace、Ledger 與審核能力。

3. Prompt 記錄我們要求模型怎麼做，證據鏈記錄這一次系統實際憑什麼做。

4. 多 Agent 交接若只傳文字，不確定性與限制就會在接力中逐步消失。

5. 權限不應只是角色屬性，也應隨證據狀態與批准結果暫時產生。

6. 可追溯不等於全部保存，證據基礎設施也必須遵守資料最小化。

7. 企業級 Evals 要測整條責任鏈，而不只是模型答案。

8. Demo 證明 Agent 做得到，Definition of Done 才證明組織承擔得起。

9. 模型可以更換，責任鏈不能每次重新失憶。
