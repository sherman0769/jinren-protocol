第一章｜更聰明的模型，為什麼不一定更可信？

很多企業導入 AI 的第一個反應很直覺：如果結果不夠可靠，就換更強的模型。

這種思路並非全錯。更強模型通常能處理更複雜的指令、維持更長的推理鏈、改善工具選擇，也可能降低某些語言與邏輯錯誤。但它隱藏了一個前提：模型必須先擁有做出正確判斷所需要的資訊。

如果關鍵訊號根本沒有進入上下文，模型能力再高，也只能在一個資訊不完整的世界裡做出更完整的推理。

想像一位非常優秀的採購主管。你交給他一張表格，裡面列出產品、庫存、需求預測與單價。他依據這些數字做出精確計算，流程完全正確。事後才發現，單價其實是四個月前的版本，而你沒有把更新日期放在表格裡。這位主管的專業能力沒有幫助他識別過期，因為他從頭到尾都沒看到時間訊號。

把主管換成最先進的模型，結構問題仍然存在。

能力與證據完整性，是兩條不同的軸線

我們很容易把 AI 可靠度想成一條直線：小模型比較差，大模型比較好；便宜模型比較不穩，昂貴模型比較可信。這條線在某些任務成立，但對 Agent 系統來說，至少還有另一條軸線：證據完整性。

模型能力回答的是：

- 能不能理解複雜任務？

- 能不能規劃步驟？

- 能不能正確呼叫工具？

- 能不能在多個限制之間做推理？

證據完整性回答的是：

- 模型看見的資料是不是正確版本？

- 判斷所需的 Metadata 是否存在？

- 來源是否可信且能追溯？

- 資料之間是否衝突？

- 目前資訊是否足以支持這個行動？

兩條軸線可以同時高，也可以一高一低。高能力、低證據完整性的系統，往往特別危險，因為它能把錯誤資料轉換成更完整、更一致、更有執行力的決策。

這不代表能力越強越危險。更準確地說，能力會放大它所依賴的證據。輸入良好時，能力轉成價值；輸入有缺陷時，能力也可能更忠實地把缺陷傳遞到行動。

SARC-DQ 用「無能保護罩」（incompetence shield）描述一個反直覺現象。在研究的先導實驗中，一個能力較差、幾乎不根據價格調整決策的 Agent，反而沒有把錯誤價格轉成行動缺陷。它並未識別資料問題；它只是根本沒有把資料用好。能力較強的 Agent 更忠實地追蹤價格，因此也更忠實地繼承了錯誤。

這個現象不能被誤解成「用笨模型比較安全」。那個能力較差的 Agent 在乾淨資料情境中，本來就做得不好。它偶然避開錯誤，反映的是任務失能，稱不上可靠治理。

真正的教訓是：不能把沒有犯錯，直接解讀成系統有能力識別風險。

沒有懷疑，不代表有信心；有信心，也不代表有證據

人們常期待模型在資料可疑時表現出猶豫，例如說「我不確定」「資料可能過時」「建議人工確認」。問題是，模型的猶豫通常來自它能感知的衝突、模糊或缺漏。

如果一筆過期價格在數值上合理、格式上正確、語境上也沒有矛盾，模型可能沒有任何理由表現懷疑。從模型眼中看，這更像是「根據目前可見資訊完成任務」，未必是「在風險中仍然過度自信」。

SARC-DQ 的實驗把這件事量化。在其 Metadata-blind 的補貨情境裡，錯誤價格被轉成重大行動偏差時，模型文字中沒有可區辨的懷疑訊號，明確資料品質警告也為零。四個模型層級跨越約十五倍推理價格，這個現象沒有因模型層級提升而消失。

這項結果最值得記住的是「訊號位置」的概念，遠比某個模型名稱或百分比重要。

要判斷資料是否過期，你需要時間戳與允許時效；要判斷資料是否已被取代，你需要版本與 companion record；要判斷來源是否可信，你需要 provenance；要判斷單位是否一致，你需要明確單位欄位或可比較的規格。若這些訊號沒有被帶進判斷機制，要求模型更謹慎只是把責任交給一個看不見問題的人。

Context Engineering 的下一步，是 Evidence Engineering

當我們談 Context Engineering，通常關心要把哪些資料送入模型、如何壓縮、如何排序、如何避免上下文過長。這些都重要，但 Agent 系統還需要更前一步的問題：送進去的資料是否有資格成為行動依據？

這可以稱為 Evidence Engineering 的視角。重點轉向管理證據的准入條件，而非一味把更多資料塞進上下文。

同一份文件可能有三種狀態：

1. 可供參考，但不能支持自動行動。

2. 可支持低風險建議，但需要人工確認。

3. 可支持特定範圍內的自主執行。

這三種狀態不是由文件內容單獨決定，也與任務風險、資料時效、來源權威、可逆性與影響範圍有關。

例如，去年版本的旅遊資訊可以用來提供大方向，但不適合用來自動訂票；舊版法規可以用於歷史比較，卻不能支持目前資格審核；一份未確認的供應商報價可以進入情境分析，卻不應直接觸發採購。

可信系統需要把「可讀」與「可採用」分開。模型能讀懂一筆資料，不代表系統應允許它據此行動。

四種常被混在一起的可靠性

為了避免把所有問題都推回模型，本書建議把可靠性拆成四個層次。

一、模型可靠性

模型能否正確理解、推理、生成與使用工具。這是模型評測與提示設計經常處理的部分。

二、證據可靠性

資料是否新鮮、完整、一致、可追溯，且適用於目前任務。這是 SARC-DQ 所強調的系統軸線。

三、流程可靠性

工作流是否在正確位置檢查、處理失敗、保存狀態、限制權限，並在例外時正確路由。

四、責任可靠性

組織能否回答誰設定規則、誰批准例外、誰負責監測，以及事故發生時如何追溯與修正。

這四層彼此相連，卻不能互相替代。

更好的模型不能自動補上缺失的資料血緣；完整 Metadata 也不能保證模型不誤解任務；流程有閘門，若沒有人維護門檻，久了仍會失效；有人簽核，若看不到證據與 Trace，簽核只是形式。

真正的 Agent 架構，不是選一個最強模型，再把其他風險寫進使用須知。它要把四種可靠性分開設計，再在 Runtime 中重新接起來。

為什麼「再加一個批判 Agent」不一定有效

面對不可靠輸出，常見做法是建立多 Agent：一個負責產生，一個負責批判，一個負責裁決。這種設計在某些問題上有效，例如找出推理矛盾、格式錯誤或內容缺漏。但若所有 Agent 看見的是同一份不完整表示，它們可能共享同一個盲點。

第一個 Agent 看不到更新時間，第二個也看不到；第一個不知道有另一個版本，第三個也不知道。多一個模型只增加了對同一份資訊的不同語言處理，不會自動增加資料通道。

因此，在設計批判或驗證角色前，先問三件事：

- 驗證者是否看見不同於產生者的證據？

- 驗證者是否具備可執行的檢查條件，而不只是一般提示？

- 驗證結果是否能阻擋行動，還是只有建議權？

若三個答案都是「否」，這個驗證 Agent 很可能只是另一層文字，而不是治理機制。

假設情境：客服 Agent 的舊版退費規則

假設一家公司讓客服 Agent 自動回答退費問題，並在符合條件時建立退款申請。

知識庫裡有一份內容完整、條款清楚的退費規則，但它已在兩週前被新版取代。舊文件本身沒有錯字，規則也自洽。檢索系統因為語意相似度較高，把舊版放在最前面。

一個能力很強的 Agent 可能做到以下事情：

- 精確解讀舊條款。

- 正確比對客戶提供的日期與商品類型。

- 有條理地解釋判斷。

- 自動建立符合舊規則的退款流程。

從語言與邏輯看，它幾乎完美；從企業狀態看，它做錯了。

改用更強模型，未必能解決「版本已被取代」這件事。真正需要的是版本狀態、有效日期、權威來源與檢索後的准入檢查。當文件 superseded=true，系統就不該把它當作現行規則進入自主決策；若新舊版本衝突，應降權或送審。

這個例子說明：可信系統不要求模型隨時自行識破錯誤；它先避免把無法信任的材料當作既定事實交給模型。

重新理解「更強」

企業真正需要的強，不只是一個更大、更會思考的模型。

一個強的 Agent 系統，應該能：

- 知道自己使用了哪些資料版本。

- 在必要 Metadata 缺失時拒絕行動。

- 將風險分級，而不是只有成功與失敗。

- 把不確定性轉成明確路由。

- 保存足以讓人類重建決策的 Trace。

- 在新的錯誤模式出現後，擴充檢查條件。

這些能力有一部分來自模型，更多來自架構、資料契約、權限與治理。

當我們只把預算放在模型升級，就會忽略一個更便宜也更關鍵的問題：是否把正確訊號放在正確位置。SARC-DQ 的核心提醒可以濃縮成一句話：能力提升會改善模型如何使用證據，卻不會自動改善證據是否值得使用。

下一章，我們將進一步拆開那些最危險的資料錯誤。它們不一定混亂、不一定缺欄位，甚至可能比正確資料看起來更乾淨。真正的風險，往往藏在數字外面。

章末金句

1. 更完整的推理，無法彌補根本沒有進入上下文的訊號。

2. 高能力、低證據完整性的系統，會更有效率地放大錯誤。

3. 無能保護罩不是安全策略，只是任務失能偶然避開了風險。

4. 沒有表現懷疑，不代表資料可靠；可能只是模型看不到懷疑的理由。

5. 模型能讀懂資料，不代表系統應允許它據此行動。

6. 多一個批判 Agent，不等於多一條證據通道。

7. 可信度要拆成模型、證據、流程與責任四個層次。

8. 真正的升級，不只是換模型，而是把正確訊號放到能阻擋行動的位置。
