序章｜AI 最危險的時候，是它開始行動之後

一個聊天機器人拿到錯誤價格，最直接的後果可能是一句錯誤回答。它告訴你某項材料一公斤四十二元，但實際價格早已改變。你看見答案、產生懷疑、回頭查詢，事情還有修正空間。

同一個錯誤價格交給補貨 Agent，風險就改變了。它可能讀取庫存、預估需求、計算採購量，再透過企業系統送出訂單。錯誤不再停留在文字裡，而是被轉成數量、金額、物流、合約與責任。

這不是把 Chatbot 換個名字叫 Agent 而已。真正的差異是：系統開始對世界造成狀態改變。

只要 AI 還停留在回答問題，人們很容易把可信度理解成「它有沒有說對」。當 AI 開始呼叫工具、修改資料、發送通知、建立報表、核准流程或提出可直接採用的決策建議，可信度就必須被重新定義。問題不只剩下答案正不正確，而是：

- 它根據哪一筆資料行動？

- 那筆資料是不是最新版本？

- 來源與轉換過程能不能追溯？

- 如果資料有問題，系統會停下來，還是照樣完成任務？

- 它寫出的每一項重要主張，有沒有真的被證據支持？

- 最後是誰決定放行？為什麼放行？

這些問題共同指向一個轉變：AI 治理不能只留在模型周圍，也不能只寫成一份原則文件。它必須進入工作流，成為會在關鍵時刻發生作用的機制。

從「模型會不會犯錯」到「系統怎麼處理證據」

過去幾年，我們談生成式 AI，最常見的警告是幻覺。於是人們學會在提示詞裡加上「請勿捏造」「不確定就說不知道」「請附上來源」。這些做法有價值，但它們仍然把安全責任放在模型的自我約束上。

問題在於，模型只能懷疑它看得見的東西。

假設一筆價格資料的數字格式完全正確，欄位也沒有缺漏，唯一的問題是它已經一百二十天沒有更新。若系統只把價格數字放進模型上下文，卻沒有提供更新時間、版本狀態或來源血緣，模型看到的就只是一個看起來合理的數字。要求它「更仔細」並不會憑空產生缺失的資訊。

這正是 SARC-DQ 研究最有力量的地方。它把問題從「模型夠不夠聰明」移到「判斷所需的訊號究竟放在哪裡」。在該研究的補貨基準中，四個不同模型層級跨越約十五倍推理價格，面對 Metadata-borne defect 時，行動缺陷率仍維持在約六成，模型也沒有表現出可區辨的懷疑訊號。研究並未否定更強模型的價值；它指出的是一個結構事實：當關鍵訊號沒有進入模型可見的表示時，能力升級不能替代訊號供應與執行位置。

這個觀點會改變我們設計 Agent 的方式。原本的思路是把更多責任交給模型：請它自我反思、請另一個模型批判、再請第三個模型投票。新的思路則是先問：哪些條件根本不該交給自然語言推理？哪些條件應該在行動點以前，由可驗證、可設定、可記錄的規則直接執行？

「資料是否超過允許時效」通常不需要一場語言辯論。「版本是否已被取代」也不該靠模型猜測。這些問題更適合成為 Runtime 的檢查條件：通過才行動，未通過就阻擋、降權、隔離、替代或送交人工。

生成速度提高，驗證成為新瓶頸

輸入端只是問題的一半。

當 AI 能在幾分鐘內完成一篇研究摘要、一份政策說明或一組企業建議，真正稀缺的就不再是文字，而是驗證能力。人類作者可能需要數小時，才能逐項確認句子是否忠於來源。更麻煩的是，一段文字可以有漂亮的引用格式，卻仍然沒有被引用內容支持。

引用與支持是兩件不同的事。

一篇來源談的是「兩者相關」，AI 可能寫成「A 導致 B」；一份報告只涵蓋特定地區，AI 可能把結論擴張成全球現象；一項研究指出「在某些條件下有效」，AI 可能省略條件，留下更肯定、更好讀，卻更不可靠的句子。這些錯誤不像虛構文獻那麼醒目，因為文獻可能真的存在，問題出在主張與證據之間的關係。

Evidence-Ledger Adjudication 研究提供了另一個重要視角：不要只問文章有沒有來源，而要把每一項重要主張與一個證據包配對，明確判定目前證據是支持、反駁、缺少，還是混合。接著，把需要注意的主張路由回作者，而不是讓整篇內容一次性通過或一次性退回。

這個工作流的價值不在於創造一部自動真理機。研究自己的數據已經說明，它仍會漏掉問題，也會把一部分其實受到支持的主張送去複查；尤其混合證據類別的辨識表現明顯較弱。真正值得吸收的，是它把驗證從模糊的「請檢查一下」轉成可稽核的中間產物：主張、證據包、關係、信心、理由與處理路由。

一旦這些中間產物被保存，AI 產出的內容才開始具備可追溯性。你不只看見最後一句話，也能回頭知道它依據什麼、系統如何判斷、哪裡曾經有衝突，以及人類為什麼最後決定保留。

兩道閘門，守住同一條責任鏈

本書把兩篇研究放在同一條工作流上理解。

第一篇處理的是 Agent 行動以前的問題：資料是否足以支持行動？

第二篇處理的是 Agent 形成主張以後的問題：證據是否足以支持主張？

一前一後，形成兩道不同但互補的閘門：

```text資料來源→ 資料品質閘門→ Agent 推理、工具使用與行動→ 主張拆解→ 主張—證據帳本→ 人類審核與放行→ 發布、執行或退回修正→ 保存完整 Trace```

本書將這套整合框架稱為「雙閘門證據迴路」（Dual-Gate Evidence Loop）。這是根據兩篇研究延伸提出的工作概念，不是論文作者共同命名的模型，也不是既有國際標準。

它想解決的，不只是兩種錯誤，而是同一條責任鏈的兩個斷點。

第一個斷點發生在資料進入推理以前。資料可能過期、來源不明、版本被取代、單位不一致，卻因為格式正確而順利進入 Agent。

第二個斷點發生在內容離開系統以前。主張可能被過度延伸、缺少支持、忽略反證，卻因為文字流暢而順利發布。

如果只設第一道閘門，Agent 可能用乾淨資料寫出過度推論的結論；如果只設第二道閘門，系統可能在前面已經根據錯誤資料完成不可逆行動。可信工作流需要同時管理「證據如何進入」與「主張如何出去」。

治理不是在流程外面加一張表

很多組織談 AI 治理時，最容易做的是建立規範：哪些資料不能上傳、哪些內容需要人工審查、哪些情境不能完全自動化。這些規範必要，卻常在實際運作中失去力量，因為它們沒有被翻成 Runtime 的條件與路由。

一條真正有效的治理要求，至少要回答五件事：

1. 在哪個時間點檢查？

2. 檢查什麼訊號？

3. 判斷門檻是多少？

4. 未通過時系統做什麼？

5. 誰可以覆核、放行與事後追溯？

例如「高風險決策必須有人類審核」仍然太模糊。什麼叫高風險？是金額超過某數值、影響外部權益、資料來源衝突、模型信心低，還是主張屬於醫療與法律？人工審核要看整個任務，還是只看被路由出來的例外？審核者是否能看見資料版本與證據關係？

當這些問題沒有被回答，Human in the Loop 很容易退化成「有人在最後按了一個確認鍵」。人類在場，並不代表人類真正掌握了判斷所需的資訊。

本書更重視 Human on the Loop：人類不必逐筆重做 Agent 的工作，但要站在迴路之上，設定閘門、批准高風險例外、監看錯誤模式、調整條件覆蓋，並保留停止系統的權力。人類的價值從大量重複檢查，轉為設計與監督責任結構。

這本書怎麼讀

第一章先處理一個常見迷思：更強模型為什麼不一定更可信。第二章進一步拆解那些「看起來完全正確」的錯誤資料，說明 Payload、Metadata、來源鏈與可見性的差異。

第三章進入第一道閘門，討論 Runtime Data-Quality Gating 如何把抽象資料治理轉成行動前的可執行條件。第四章把視線移到輸出端：當 AI 寫得比人類查得快，驗證為什麼會成為新的系統瓶頸。

第五章拆解 Evidence Ledger，說明主張—證據關係與審核路由。第六章把兩道閘門接成完整迴路，建立本書主要工作框架。第七章重新安排人類的位置：不再要求人類檢查一切，而是讓人類負責最需要判斷與承擔的部分。

第八章則把單一 Agent 放回企業環境，討論資料版本、工具紀錄、主張帳本、權限與例外如何形成證據基礎設施。最後的結語會回到最根本的責任問題：AI 可以生成答案，但不能替組織生成責任。

這本書不保證提供一個放進任何產業都適用的萬能模板。兩篇核心研究都是新近公開的預印本，各自有明確實驗範圍與限制。本書真正想交付的，是一種看系統的方法：

當你準備讓 Agent 做更多事時，不要只問它能不能完成任務；還要問，系統有沒有能力在證據不足時不做事。

這個「不做事的能力」，可能比流暢生成、快速推理與自動操作更難設計，卻也是自主系統真正走入企業之前，最不能缺少的能力。

章末金句

1. Chatbot 的錯誤停在句子裡，Agent 的錯誤可能進入帳戶、流程與現實世界。

2. 模型只能懷疑它看得見的訊號，缺失的 Metadata 不會因為提示詞更嚴厲而出現。

3. 有資料，不代表有足以支持行動的資料。

4. 有引用，不代表引用真的支持主張。

5. 治理只有進入 Runtime，才會在關鍵時刻產生阻力。

6. 可信 Agent 的核心能力之一，是在證據不足時暫停行動。

7. 人類不必重做所有工作，但必須掌握放行、例外與停止的權力。

8. AI 可以生成答案，責任鏈必須由系統與人共同建立。
