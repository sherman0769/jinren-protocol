第二章｜錯誤資料為什麼看起來完全正確？

我們習慣把髒資料想成一眼就能看出問題的東西：欄位空白、日期亂碼、姓名重複、數字超出合理範圍、格式彼此不一致。這些錯誤確實存在，也相對容易成為資料清理的對象。

真正危險的資料，往往沒有那麼狼狽。

它可能欄位完整、格式正確、語意清楚，甚至曾經是權威答案。問題只是它已經失效、被取代、離開原本適用範圍，或在另一個系統裡代表不同單位。它看起來不像垃圾，反而像仍然有效的事實；實際上，它只是已經失效的舊狀態。

這類資料特別適合欺騙自動化系統，因為自動化通常獎勵格式穩定、可解析與可直接使用。資料越整齊，流程越容易放行；但整齊與可信從來不是同義詞。

Payload 正確，整筆資料仍可能錯

SARC-DQ 把證據紀錄分成兩個通道。

第一個是 Payload，也就是直接提供給使用者或模型的欄位值。價格是 42、庫存是 80、資格是符合、文件內容是一段完整政策文字。

第二個是 Metadata，也就是描述這筆資料所處狀態的資訊：它什麼時候建立、最後更新時間、來自哪個系統、經過哪些轉換、版本是否仍有效、是不是權威紀錄、適用範圍是什麼。

一筆資料的 Payload 可以完全正確，Metadata 卻顯示它不應再被使用。

例如：

```text價格：42幣別：新台幣單位：公斤最後更新：120 天前現行版本：否取代版本：price_v8```

如果 Agent 只收到前三行，它很可能正確理解每一個字，卻仍然做出錯誤決策。這種錯誤與語言理解、數學計算無關；根源在於系統把「資料內容」和「資料資格」混為一談。

資料內容回答「它說了什麼」；資料資格回答「它現在能不能被拿來做這件事」。

八種缺陷，八種不同的可見性

SARC-DQ 的基準涵蓋八類缺陷。這些分類不必被當作完整產業標準，但很適合幫助我們看見：資料風險不是只有一種形態。

1. 過期主資料

數值本身合理，問題藏在時間。沒有可靠時鐘與最大允許時效，就無法判斷。

2. 已被取代的黃金紀錄

系統同時存在舊版與新版權威紀錄，或舊紀錄沒有被正確標示失效。需要版本關係或 companion record 才能判斷。

3. Schema 漂移

欄位結構或型別改變。內容可能仍能被讀取，但原本的解讀方式已經不適用。這需要具型別的 schema 檢查，而不是只看文字是否順暢。

4. 必填欄位缺失

最典型的完整性問題。它在 Payload 中可見，但前提是系統真的有定義哪些欄位必填。

5. 跨來源矛盾

兩個資料來源對同一實體給出不同值。要看見矛盾，必須同時取得兩邊資料，而且能正確對齊同一個實體。

6. 重複供應商與衝突條件

同一供應商可能以不同名稱或不同鍵值出現，條款互相衝突。若系統沒有完成 entity resolution，單純逐列檢查可能看不出重複。

7. 靜默單位改變

數字仍然合理，但公斤變成磅、箱變成個、含稅變成未稅。若單位沒有被明確列印或保存，任何模型都只能猜。

8. 看似合理的離群值

數值不一定超出簡單門檻，卻與歷史脈絡、來源鏈或特定群體分布不一致。這需要更進一步的統計或 lineage-based 檢查。

這八類缺陷提醒我們，資料品質不能只靠一個「總分」。不同缺陷需要不同訊號、不同檢查，也會導向不同處理方式。

可見性不是資料的固定屬性

乍看之下，我們可能把錯誤分成 Payload-visible 與 Metadata-borne，然後以為每一類永遠固定。SARC-DQ 的結果反而提供了一個更精細的校正：可見性取決於機制實際拿到什麼表示，以及它實作了什麼檢查。

研究中，schema drift 被預先歸為 Payload 可見，但一般的 Payload-only critic 沒有抓到；具型別的 schema predicate 卻能抓到。相反地，某些已被取代的紀錄雖被歸為 Metadata-borne，因為 companion record 在內容層形成矛盾，critic 反而能看見。

因此，更準確的說法應該是：錯誤是否屬於 Metadata，取決於系統如何表示它。

一個缺陷是否可被偵測，取決於判斷機制能看見哪些表示、比較哪些 companion evidence，以及是否實作了對應條件。

這個觀點對架構設計很重要。團隊不能只在資料字典裡標記「這是 Metadata 問題」，就以為風險已被管理。真正要畫出的是「訊號—機制矩陣」：

- 哪個風險的辨識訊號在哪裡？

- 哪個元件可以讀取？

- 哪一條規則會執行？

- 沒有通過時，誰有權阻擋？

只有當四個問題都有答案，資料品質才從概念變成控制。

Metadata 也會錯

談到 Metadata，人們容易把它想成比較可信的管理資訊。實際上，Metadata 本身也可能缺失、過期、被錯誤產生或在系統轉換中遺失。

SARC-DQ 的壓力測試就指出，gate 的偵測能力取決於 Metadata 通道是否完整。當 Metadata 被退化，整體偵測率會下降；其中新鮮度檢查尤其依賴可靠時鐘。如果更新時間被刪掉或錯置，freshness predicate 也失去依據。

這表示「把 Metadata 接進來」只是開始，還需要管理 Metadata 的來源與品質。

一個成熟的資料契約至少要回答：

- 時間戳由誰產生？是來源時間、匯入時間，還是最後轉換時間？

- 版本狀態由哪個系統負責？

- lineage 是否在每次轉換後持續保留？

- 欄位單位與幣別是否強制存在？

- 權威來源變更時，舊版本如何失效？

- Metadata 缺失本身是否被視為風險訊號？

很多組織的資料平台保存了大量欄位，卻沒有明確說明哪些欄位是決策級必備。當 Agent 出現後，這個缺口會被放大，因為人類以前可能憑經驗知道「這張表要看更新日期」，Agent 卻只會依照系統真正提供的欄位與規則運作。

資料血緣不是為了畫一張漂亮的圖

資料血緣常被理解成資料平台裡的一張關係圖：某張表來自哪裡，經過哪些 ETL，再流向哪個報表。這對維運很重要，但在 Agent 系統裡，lineage 還要更靠近決策。

我們需要回答得更具體：這張表如何形成、經過哪些轉換、目前又是哪一個版本？

- 這一次行動實際用了哪幾筆紀錄？

- 每筆紀錄的內容與 Metadata 是哪個版本？

- 是否有替代值？替代值從哪個受治理緩衝區而來？

- 原始資料有沒有被修改？

- 行動完成後，能不能重建當時的證據集合？

SARC-DQ 的 downstream-only remediation 有一個值得注意的設計：當 gate 隔離並替代有問題的值時，它不回寫來源資料，而是在受治理、具版本的緩衝區建立替代紀錄，並把這次行動實際依賴的 evidence set 記錄下來。

這種做法的價值，是避免修正動作破壞原始歷史。若系統為了讓 Agent 繼續工作，直接把來源值改掉，事後就很難知道當時到底發生什麼。保留原始狀態、建立新版本並記錄使用關係，才能讓稽核者重建事件。

這也與 W3C PROV 的基本精神相通：來源追溯不只是附上一個網址，而是表示實體、活動、責任主體與生成關係。企業不一定要直接採用 PROV-O，但需要承認「答案從哪裡來」是一個可建模、可交換、可檢查的系統問題。

假設情境：舊版補助資格仍在知識庫

假設一個公部門服務 Agent 協助民眾查詢補助資格。知識庫裡同時有去年與今年的實施計畫。去年的文件標題完整、條文清楚，甚至因為被更多網站引用，檢索排序更高。

若系統只依語意相似度取回內容，Agent 可能引用舊版條文，產生一段看似專業的回答。它甚至可以逐項核對年齡、戶籍與所得條件，最後告訴民眾「符合資格」。

問題不在文字生成，而在文件准入。

這類系統至少需要：

- 生效日期與失效日期。

- 文件版本與取代關係。

- 發布機關與權威層級。

- 適用地區與對象。

- 檢索後的現行版本檢查。

- 若版本衝突，禁止自動下結論。

在這個情境中，最可靠的回答不一定是更長、更完整的答案。當版本狀態無法確認時，最可靠的行為可能是暫停判定，告知需要確認現行公告，並把問題送往人工或權威資料源。

可信系統不以「完成回答」為唯一成功，而以「在不適合回答時正確停下」作為成功的一部分。

從資料清理走向資料准入

傳統資料品質常著重上游：清理資料、修正主檔、建立唯一來源。這些工作仍然不可取代。SARC-DQ 也明確說明 Runtime gate 不是上游資料治理的替代品。

但 Agent 帶來另一個需求：即使上游治理不完美，系統在行動點仍要做最後一次針對任務的判斷。

同一筆資料對不同任務，准入條件可能不同。三十天前的價格可供趨勢分析，卻不能支持即時下單；缺少一個非必要欄位的客戶紀錄可以用於一般統計，卻不適合自動做權益判定；來源存在輕微衝突時可以生成比較報告，卻不應自動寫入主資料。

所以，資料品質無法只用「好或壞」概括。真正的問題是：在這個任務、時間點與風險水準下，它是否足以支持眼前行動。

這正是下一章要處理的問題。當我們已經知道錯誤可能藏在哪裡，就要把這些認知寫成 Runtime 中會真正執行的閘門，而不是留在資料治理簡報裡。

章末金句

1. 最危險的髒資料，往往看起來像一筆乾淨的事實。

2. Payload 告訴你資料說了什麼，Metadata 告訴你它現在有沒有資格被使用。

3. 格式正確，只能證明它容易被機器讀取，不能證明它值得被機器相信。

4. 錯誤是否可見，取決於訊號、表示與檢查機制的共同作用。

5. Metadata 不是天然可信，它也需要來源、契約與品質管理。

6. 資料血緣的價值，不在畫出流程，而在重建某一次行動實際依賴的證據。

7. 可信系統要把「可讀」與「可採用」分開。

8. 評估資料品質，最後都要回到它是否足以支持眼前行動。
