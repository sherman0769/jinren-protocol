第六章｜把兩道閘門接成一個可信迴路

單獨看第一道閘門，我們得到一個較安全的行動入口：資料不符合條件，就不能直接驅動工具。單獨看第二道閘門，我們得到一個較可稽核的內容出口：主張沒有足夠證據，就不能直接成為正式知識。

但企業真正運作的是一條連續工作流，兩張分開的檢查表不足以描述它。

Agent 先讀取資料，再形成計畫；計畫驅動工具，工具回傳新資料；系統根據結果產生摘要、理由與報告；人類可能批准、修改或重新執行。輸入與輸出之間沒有一道乾淨的牆，只有不斷流動的證據、狀態與決策。

因此，兩道閘門只有接在同一條 Trace 上，才真正形成治理能力。

本書把這個整合架構稱為：

雙閘門證據迴路

Dual-Gate Evidence Loop

這是本書根據 SARC-DQ 與 Evidence-Ledger Adjudication 整合提出的工作框架。它不是兩篇論文共同提出的正式模型，也不是已被標準組織採納的產業規範。

它的核心很簡單：

第一閘門決定資料能不能支持行動；第二閘門決定證據能不能支持主張。人類負責設定條件、處理例外與批准高風險釋出。

完整迴路

```text[資料來源與工具回傳]↓[第一閘門：資料品質准入]↓[Agent 規劃、推理與工具使用]↓[候選行動／候選內容]↓[主張拆解與證據包建立]↓[第二閘門：主張—證據裁決]↓[人工審核／例外處理]↓[發布、執行、降權或退回]↓[保存 Trace、監測結果、更新規則]└──────────────→ 回到資料與條件治理```

這不是一次通過就結束的管線。任何一個環節發現新問題，都可能回到前面：

- 第二閘門發現主張缺少證據，可能觸發新的資料搜尋。

- 人類發現來源版本錯誤，可能要求第一閘門新增條件。

- 事後稽核發現某類單位轉換經常漏掉，可能補上 unit consistency predicate。

- 新政策發布，可能使既有 Evidence Ledger 中的主張需要重新裁決。

可信是一種持續修正「什麼可以進、什麼可以出」的系統能力，不能濃縮成單一靜態分數。

第一閘門與第二閘門不能合併成一個問題

有人可能會問：既然都是證據檢查，為什麼不做一個總體「可信度評分」？

因為兩道閘門面對的對象、時間點與失敗成本不同。

第一閘門面對行動依據

它檢查資料紀錄與 Metadata，關心新鮮度、版本、完整性、一致性與 lineage。它通常要在工具呼叫以前快速、確定地做出決定。

第一閘門失敗的代價，是錯誤資料進入推理並造成外部狀態改變。

第二閘門面對知識主張

它檢查主張與證據包的語意關係，關心範圍、因果、強度、反證與混合情況。它需要較多語意判斷，也更常需要人工處理。

第二閘門失敗的代價，是缺乏支持的內容被當成正式知識、政策理由或決策依據。

一筆資料可以通過第一閘門，卻不足以支持 Agent 後來寫出的強烈結論。例如官方統計資料是最新且可追溯的，但 Agent 把觀察相關寫成因果；資料品質沒有問題，主張關係仍然有問題。

反過來，一項主張可能在文字上被證據支持，但證據來源其實已失效。若 Evidence Ledger 沒有接到版本 Metadata，就可能認定「來源內容支持句子」，卻忽略來源已被新版本取代。

所以兩道閘門不能互相替代，也不能只剩一個模糊總分。它們需要共享資料，卻保留各自的責任邊界。

共享 Trace：讓每一項主張回到每一次行動

整合架構的關鍵在於建立跨階段的識別關係；多畫兩個方框並不會自然產生治理。

至少需要連接以下物件：

```textsource_record_idsource_versionmetadata_snapshotretrieval_event_idagent_run_idtool_call_idaction_idclaim_idevidence_packet_idreview_idrelease_version```

這些 ID 讓系統可以回答：

- 某一項主張使用了哪些來源紀錄？

- 那些紀錄在當時是什麼版本？

- 哪一道 predicate 曾阻擋或替代資料？

- Agent 實際呼叫了哪些工具？

- 工具回傳又形成了哪些新主張？

- 人類修改了哪一句文字？

- 最後發布的是哪個版本？

沒有這種連接，第一道閘門的 log 與第二道閘門的 ledger 只是兩座孤島。出現爭議時，團隊仍要靠人工猜測它們是否屬於同一次任務。

共享 Trace 不必一開始就採用複雜圖資料庫。最小可用方式，是確保每次 Agent run 都有唯一 ID，所有來源、工具呼叫、行動、主張與審核都帶著這個 ID，並保存版本化關聯。

六層實作架構

雙閘門證據迴路可以拆成六個系統層次。

第一層：來源與證據層

包含資料庫、文件庫、API、搜尋結果、人工輸入與工具回傳。每項資料應盡量附帶版本、時間、來源、適用範圍與識別碼。

這一層要讓風險訊號可被後續元件讀取，並不假裝來源永遠乾淨。

第二層：資料准入層

執行 freshness、lineage、schema、completeness、consistency 與任務專屬 predicate。輸出不只 pass/fail，也包含風險、原因、替代紀錄與允許的自主程度。

第三層：Agent Runtime 層

負責規劃、推理、工具調用、狀態管理與候選行動。Runtime 必須尊重 gate 的決策，不能讓模型用自然語言覆寫硬性阻擋。

第四層：主張與證據層

從候選內容與決策理由中抽取重要主張，建立 evidence packet，判定支持關係與初步路由。

第五層：人類與權限層

依風險與例外分配審核角色。人類能看見 gate 結果、來源版本、主張關係與修改建議，而不是只看最後答案。

第六層：Trace 與治理層

保存事件、版本、規則、人工決定與結果指標。這一層也負責回饋：哪些 predicate 漏檢、哪些主張經常被誤路由、人工審核負擔是否過高、哪類來源最常失效。

這六層代表六種責任，不等於必須購買六個產品。小型系統可以用同一個服務完成多層，大型企業可能由不同平台負責。重點是不要讓責任消失。

風險路由矩陣

雙閘門不應讓所有問題走同一條人工流程。可以用兩個維度建立簡單路由矩陣：行動風險與證據狀態。

| 行動／內容風險 | 證據狀態良好 | 輕微缺口 | 明顯衝突或缺失 ||---|---|---|---|| 低 | 自動執行或釋出 | 降低語氣／標示提醒 | 退回修正 || 中 | 自動準備、抽樣審核 | 送人工確認 | 阻擋並升級 || 高 | 必須人工批准 | 阻擋、補證據 | 停止，不得覆寫 |

矩陣不企圖用三乘三表格解決所有情境；它只要明確表達：同一種證據缺口，在不同風險下應有不同結果。

例如一個過期一天的資料：

- 用於內部趨勢草稿，可能只需標示。

- 用於對外價格公告，可能需要人工確認。

- 用於大額自動交易，可能必須阻擋。

治理要把證據狀態與行動風險放在一起判斷，不能只替資料貼上單一好壞標籤。

假設情境：供應鏈 Agent 從下單到決策報告

假設一個 Agent 每天分析庫存與需求，提出補貨計畫，低金額項目可自動送單，並生成一份給主管看的決策摘要。

步驟一：資料進入

Agent 取得庫存、價格、需求預測與供應商條款。每筆資料帶有來源、更新時間、單位與版本。

步驟二：第一閘門

系統發現某供應商價格超過允許時效，且另一來源有更新版本。舊價格被隔離，受治理緩衝區提供新價格。這次替代與 evidence set 被記錄。

另一項商品缺少明確單位，gate 沒有可靠替代值，因此把自主程度降為「只能產生建議，不能送單」。

步驟三：Agent 規劃與行動

Agent 使用通過准入的資料計算採購量。低風險商品自動建立訂單；單位不明商品進入人工確認佇列。

步驟四：產生決策摘要

Agent 寫道：「本次調整可降低本月採購成本 12%，並避免所有缺貨風險。」

步驟五：第二閘門

系統拆出兩項主張：

1. 可降低採購成本 12%。

2. 可避免所有缺貨風險。

第一項有計算表與基準版本支持，但需要標示比較基準。第二項證據不足，因需求預測仍有不確定性，「所有」語氣過強。

Ledger 將第一項判為 Supports，route 為補上基準說明；第二項判為 Missing Evidence，route 為改寫成「降低預估缺貨風險」。

步驟六：人類批准

主管除了看見一份整理好的報告，也能看見：哪些資料被替代、哪項訂單被降權、兩項主張如何裁決，以及最後文字如何修改。

步驟七：結果回饋

月底系統比較預估與實際結果。如果單位缺失類問題反覆出現，資料治理團隊把 unit 欄位列為強制契約，並新增對應 predicate。

這個完整情境顯示，雙閘門的目的在於把不同種類的風險放到正確位置處理；流程中的必要摩擦不能簡化成「變慢」。第一閘門不負責判斷「避免所有缺貨」是否過度；第二閘門也不應替代價格版本檢查。兩者共享 Trace，各自完成唯一任務。

從日誌走向證據鏈

很多 Agent 平台已經保存 prompt、response、token、latency 與 tool call。這些 observability 資料很重要，但它們不等於證據鏈。

一段完整對話可以告訴你模型說了什麼，卻未必告訴你：

- 檢索到的文件是否為現行版本。

- 哪項 Metadata 曾被 gate 使用。

- 某句主張對應哪個來源段落。

- 人類修改了哪個關係判定。

- 最終釋出版本與草稿有何差異。

證據鏈需要把技術 Trace 與知識 Trace 接起來。前者記錄系統做了什麼，後者記錄系統憑什麼這樣做。

W3C PROV 提供了表示來源、活動與責任主體的通用思路；NIST AI RMF 則強調治理、量測與管理應貫穿生命週期。雙閘門證據迴路不取代這些框架；它補上一個較具體的 Agent 工作流視角：把資料准入、主張釋出與人類路由接成可執行鏈。

五階段導入路徑

企業不必一次完成所有層次。可以逐步建立。

階段一：先能追溯

替每次 Agent run、來源、工具呼叫與最終內容建立 ID，保存版本與時間。

階段二：先管高風險行動

只在不可逆或高影響工具呼叫前加入少數硬性 predicate，例如版本、時效、必要欄位與金額門檻。

階段三：建立主張級審核

針對數字、日期、因果、比較與外部發布內容建立 Evidence Ledger，不必一開始查核所有句子。

階段四：風險化自主權

讓系統依證據狀態在「自動執行、只產生草稿、送人工、阻擋」之間切換。

階段五：持續校準

用實際事件更新 predicate coverage、路由門檻、信心校準與人工審核配置。

這條路徑比一開始追求「全自動可信 Agent」更實際。可信來自逐步建立可追溯、可阻擋、可修改與可學習的責任結構，無法靠購買單一元件完成。

框架的邊界

雙閘門證據迴路也有明確邊界。

它不能保證來源本身永遠正確；不能自動發現所有未建模錯誤；不能取代資安、權限、隱私、偏見與模型安全控制；不能替組織決定所有風險容忍度；更不能把人工批准變成責任卸載。

它主要處理一條問題線：證據如何進入 Agent，主張如何離開 Agent，以及中間的判斷能否被追溯。

只有承認邊界，框架才不會變成另一個萬能口號。

下一章將把焦點移到人類。當系統已經能分流證據與主張，人類就不必被安排在每一步裡重做工作。真正需要設計的是：哪些決定必須由人承擔、什麼資訊要呈現給審核者，以及如何避免「有人按確認」卻沒有人真正監督。

章末金句

1. 兩道閘門只有接在同一條 Trace 上，才會形成完整責任鏈。

2. 第一閘門回答能不能行動，第二閘門回答能不能這樣主張。

3. 一個總體可信分數，無法取代兩種不同時間點與不同失敗成本的判斷。

4. 技術 Trace 記錄系統做了什麼，知識 Trace 記錄系統憑什麼這樣做。

5. 治理要讓不同風險走向正確角色，不能把所有風險一律推給人工。

6. 自主權應隨證據品質與行動風險改變。

7. 可信是系統持續修正准入與釋出條件的能力，無法用靜態分數完全表示。

8. 框架只有承認自己的 coverage gap，才有資格被持續改進。

研究基準

- [R01] SARC-DQ：資料准入、Runtime placement、predicate coverage 與 downstream-only lineage。

- [R02] Evidence-Ledger Adjudication：主張—證據關係、author route 與審核佇列。

- [R03][R04] NIST AI RMF / GenAI Profile：跨生命週期治理、量測與管理背景。

- [R05] W3C PROV：來源、活動與責任主體的可表示性背景。
