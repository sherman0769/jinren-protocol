第三章｜第一道閘門：Agent 行動前的資料品質治理

治理最容易失效，往往因為原則沒有在行動發生前出現，而非組織完全沒有原則。

一份政策可以寫著「重要資料必須確認版本」「高風險決策需要人工審核」「來源不明不得自動執行」。但當 Agent 準備呼叫採購 API、更新客戶資格或寄出正式通知時，如果系統沒有一個元件真的檢查這些條件，原則就只是一段背景文字。

Runtime Data-Quality Gating 的價值，在於把抽象治理轉成一個會做出「准入或不准入」決定的執行點。

它不要求 Agent 自己記得所有規範，而是讓系統在行動前回答一個具體問題：

目前這組資料，是否已經達到支持這項行動的最低證據條件？

這個問題看似簡單，實際上包含了檢查位置、訊號來源、門檻、失敗處理、替代資料、權限與追溯等完整設計。

閘門必須靠近「狀態改變點」

資料品質檢查可以發生在很多地方。資料進入倉儲時可以檢查，建立向量索引時可以檢查，Agent 檢索後可以檢查，工具呼叫以前也可以檢查。

上游檢查越完整越好，但對 Agent 而言，最不能缺少的是靠近狀態改變點的 Pre-Action Gate。

所謂狀態改變點，是指系統從「思考或建議」跨入「對外部世界造成效果」的瞬間，例如：

- 寫入主資料。

- 建立訂單或付款請求。

- 發送對外公告。

- 修改權限。

- 核准或拒絕申請。

- 將內容發布到正式平台。

閘門放得太早，資料可能在後續流程又被替換或污染；放得太晚，行動已經發生，只能事後補救。最實用的設計是讓 Agent 先完成規劃與候選行動，再由 gate 檢查這次行動實際要依賴的 evidence set。

換句話說，閘門關注的不是整個資料庫的平均潔淨度，而是這一次行動準備使用的資料，能否支撐眼前的工具呼叫。

六類檢查條件，代表六種治理問題

SARC-DQ 提出六類參數化 predicate。它們不一定涵蓋所有產業，但示範了如何把資料治理語言轉成可執行條件。

1. Freshness：資料夠不夠新

```textfreshness(max_age = 24h)```

它要求系統知道資料更新時間，也要求業務定義「多舊算太舊」。同一筆資料在不同任務中，max_age 可能完全不同。即時價格也許只有數分鐘有效，年度統計可能數月仍可使用。

2. Lineage Present：來源鏈是否存在

```textlineage_present = true```

這不要求每筆資料都附上一篇完整故事；最低要求是能追溯到可識別的來源、轉換與版本。若 lineage 缺失，系統無法判斷資料是否來自正式系統、人工輸入或未經批准的中間檔。

3. Golden Record Unique：權威紀錄是否唯一

```textgolden_record_unique(entity_id)```

當同一個客戶、產品或政策同時出現兩筆互相衝突的「權威版本」，Agent 不該自行挑一筆最像答案的資料。唯一性檢查把主資料治理的衝突轉成明確阻擋訊號。

4. Cross-Source Consistent：多來源是否一致

```textcross_source_consistent(tolerance = 2%)```

不是所有差異都代表錯誤，因此需要容許範圍、對齊鍵與比較規則。價格、數量、匯率與日期可能需要不同 tolerance。

5. Schema Conformant：結構與型別是否符合

```textschema_conformant(version = v3)```

這個檢查確保欄位名稱、型別、單位或列舉值符合目前契約。它特別適合攔截「程式仍能解析，但語意已變」的 schema drift。

6. Complete：必要欄位是否齊全

```textcomplete(required = [price, currency, unit, effective_at])```

完整性不能只看欄位是不是空白，也要看任務真正需要什麼。要自動下單，價格、幣別與單位可能都不可缺；只做商品名稱摘要，則不一定需要同樣條件。

這六類 predicate 的共同精神是：不要用「資料品質良好」這種無法執行的形容詞，而要寫出系統能判定真假的條件。

本書提出：行動前最低證據條件

為了把不同 predicate 與任務風險接起來，本書使用「行動前最低證據條件」（Minimum Evidence Condition for Action）這個工作概念。

它是一份任務級契約，不能退化成所有 Agent 共用的固定清單。設計時至少考慮四個因素：

一、影響程度

這次行動會影響多少金額、多少人、哪些權益？影響越高，證據條件越嚴格。

二、可逆性

寄出草稿通知可以撤回，實際付款或刪除資料可能難以逆轉。不可逆行動需要更多檢查與人工批准。

三、時間敏感度

有些情境允許等待人工，有些需要即時處理。系統可以在低風險時降權執行，在高風險時停止。

四、證據可替代性

資料有問題時，是否存在受治理替代來源？如果沒有，系統應升級或停止，而不是自行補猜。

例如，同一個補貨 Agent 可以設定三個層級：

```text建議採購量：允許資料 24 小時內、來源可追溯建立待審訂單：允許資料 4 小時內、幣別與單位完整、來源一致自動送單：允許資料 30 分鐘內、黃金紀錄唯一、金額低於門檻、無衝突```

這樣一來，自主性不再是「全開或全關」，而是依證據條件動態調整。

閘門不是只有阻擋

很多人一聽到 gate，就想到 pass 或 fail。實際系統需要更豐富的回應。SARC-DQ 提到四類方向：block、degrade autonomy、escalate、quarantine-and-substitute。

阻擋

當資料不具備基本條件，且行動風險高或不可逆，直接禁止工具呼叫。

降低自主權

Agent 仍可完成分析、產生建議或準備草稿，但不能直接執行。這是企業導入中很實用的中間狀態。

升級處理

將項目送到人工、資料管理者或特定風險角色。升級時不應把整個任務原封不動丟給人；系統要連同失敗原因、相關資料與候選方案一起送出。

隔離並替代

將有問題的紀錄排除，從受治理的緩衝區取用已知良好值。這需要嚴格版本與 lineage，不能由模型隨意「猜一個合理數字」補上。

這四種回應把治理轉成可運作的路由，避免它只剩下更高的失敗率。好的 gate 追求讓不同風險走向合適的處理路徑，並非盡量擋住所有事情。

Downstream-only remediation：修正但不改寫歷史

SARC-DQ 強調 downstream-only remediation。它的設計原則是：gate 對來源資料保持唯讀，發現問題時不直接修改 source store，而是在下游受治理緩衝區建立替代紀錄，並記錄這次行動使用了哪些原始與替代資料。

這個原則解決一個常見矛盾：系統需要在 Runtime 繼續工作，但又不能為了方便而改寫證據。

假設舊價格為 42，新價格為 48。若 gate 直接把來源資料從 42 改成 48，事後只剩一個看似從來沒有出錯的資料庫。你無法解釋 Agent 為什麼曾準備下錯單，也無法驗證偵測與修正是否真的發生。

若採 downstream-only：

1. 原始紀錄保留不變。

2. 舊紀錄被標記隔離。

3. 受治理緩衝區提供新版本 48。

4. 此次行動記錄同時包含舊紀錄、替代紀錄、gate 判斷與採用理由。

5. 上游資料問題另開流程修正。

這使 Runtime 補救與資料治理責任分開，又透過 lineage 接在一起。

Gate 也需要被治理

閘門不是裝上去就永遠正確。SARC-DQ 的結果清楚顯示，gate 只會處理 predicate 覆蓋的問題。研究中的 silent unit change 與 plausible outlier 沒有對應 predicate，因而無法恢復整體 portfolio 損失。

這個限制非常重要。它提醒我們不要把 gate 當成完整安全層，而要持續管理 coverage。

一個成熟的 gate 應該有自己的登錄表：

- 目前有哪些 predicate？

- 各自依賴哪些訊號？

- 對哪些行動生效？

- 門檻由誰批准？

- 最近一次校準時間？

- 已知 coverage gap？

- false block 與漏檢情形？

- 當 Metadata 不完整時如何降級？

如果沒有這些資訊，gate 可能從治理機制變成另一個不可解釋的黑盒。

四個執行位置，不只一道牆

SARC-DQ 把資料品質 predicate 放在四個 SARC enforcement sites：Pre-Action Gate、Action-Time Monitor、Post-Action Auditor、Escalation Router。

本書以 Pre-Action Gate 為第一道核心閘門，但完整系統仍需要其他位置互補。

Pre-Action Gate

在工具呼叫前檢查 evidence set，防止可預見問題進入行動。

Action-Time Monitor

行動執行過程中監測參數、回傳值與環境狀態。例如下單 API 回傳的幣別與預期不同，就應中止後續步驟。

Post-Action Auditor

行動後檢查實際結果是否符合批准內容，並保留對帳與事件發現能力。它不能取代事前阻擋，但能發現未預期模式。

Escalation Router

根據失敗類型與風險，把項目送給正確角色。資料過期可能送資料管理者，金額過高送主管，來源衝突送業務負責人。

這四個位置形成一個「預防—監測—稽核—處理」結構。只做事後稽核，成本已經發生；只做事前檢查，也可能錯過執行中的環境變化。

假設情境：活動場地預約 Agent

假設一個組織讓 Agent 自動安排課程場地。系統讀取教室容量、設備、空檔與租金，選擇最適合的場地並送出預約。

某間教室資料顯示可容納八十人、有投影機、當日下午空檔。Payload 完整，但設備資訊最後更新於一年前，且場地最近整修，投影設備已拆除。

若 Agent 只負責推薦，資料仍可被標示風險後提供；若它要直接簽訂租約，最低證據條件就應提高：

- 空檔資料更新不超過一小時。

- 設備清單更新不超過三十天。

- 租金版本為現行。

- 場地狀態沒有維修標記。

- 超過一定金額需人工批准。

設備 Metadata 過期時，gate 不一定要完全停止任務。它可以降低自主權：保留候選場地，但把「投影設備待確認」送給承辦人；或改選一個設備狀態已驗證的次佳場地。

這就是可用的治理：不要求系統永遠只有最理想答案，而是讓它在證據不足時改變行為模式。

第一閘門的真正價值

資料品質閘門不是用來證明資料永遠正確。它的價值是建立一個制度化的拒絕條件：當某些證據要求沒有被滿足，Agent 不得假裝一切正常。

這道閘門會讓系統偶爾變慢，也可能增加人工審核。這種摩擦是把原本隱藏的風險成本提前顯示，不能直接視為缺陷。沒有 gate 時，流程看似順暢，只是把成本延後到錯誤訂單、客訴、權益爭議與事後追查。

然而，即使輸入資料通過第一道閘門，Agent 仍可能在推理與寫作中過度延伸證據。資料乾淨，不代表結論必然被支持。

下一章，我們將進入工作流的另一端：當 AI 生成速度遠超過人類查證速度，為什麼「寫得出來」逐漸失去稀缺性，而「證明這句話站得住」成為新的瓶頸。

章末金句

1. 治理若沒有出現在行動以前，就很容易只剩事後說明。

2. 閘門聚焦於這一次行動實際依賴的證據集合，不做整個資料庫的籠統評分。

3. 好的規範必須能被翻成可判定真假的條件。

4. 自主性不必全開或全關，可以依證據品質動態降級。

5. 隔離並替代，不等於改寫來源與抹去錯誤歷史。

6. Gate 只會攔住它被設計去看見的問題。

7. 已知的 coverage gap，比假裝完整的安全承諾更有價值。

8. 可信系統的價值，在證據不足時能正確改變行為，不在於永遠順利完成。
