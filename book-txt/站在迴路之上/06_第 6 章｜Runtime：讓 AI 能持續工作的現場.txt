第 6 章｜Runtime：讓 AI 能持續工作的現場

回答發生在對話裡，工作發生在 Runtime 裡

一個 Chatbot 可以在幾秒內完成回覆。

一個 Agent 的工作卻可能持續數分鐘、數小時，甚至跨越多天。它需要等待外部資料、呼叫多個工具、產生檔案、請求人類核准、從失敗中恢復，也可能被另一個 Agent 接手。

這時，工作已經超出單一模型呼叫。

模型可以決定下一步，卻不會自己提供檔案系統、工作佇列、權限管理、狀態保存、錯誤重試、秘密金鑰、執行隔離與人工核准介面。

這些事情發生的地方，就是 Runtime。

在本書中，Runtime 指的是：

讓 Agent 的目標、Context、工具、狀態、事件、規則與人工介入能夠在真實環境中持續運行的執行現場。

OpenAI Agents SDK 將 agent loop、tools、handoffs、sessions、human-in-the-loop 與 tracing 放在同一套高階執行框架中，正是 Runtime 思維的具體表現。[R03]

Runtime 不一定是一個產品，也不一定只有一台伺服器。它可以是本機開發環境、雲端工作服務、企業內部平台、瀏覽器自動化系統，或由多個服務共同構成的運行層。

重點不在名字，而在它是否能承受工作的現實。

一次模型呼叫與長任務的差別

一次模型呼叫通常有清楚輸入與輸出：送出 Context，取得回覆。

長任務則會出現時間與狀態。

例如，Agent 要完成一份供應商評估：

1. 讀取需求。

2. 找到候選名單。

3. 查詢公開資料與內部紀錄。

4. 等待財務系統回傳。

5. 發現其中一家公司資料衝突。

6. 暫停並請採購人員確認。

7. 第二天取得核准。

8. 繼續評分與產生報告。

9. 送交主管審核。

10. 將決策與證據寫回系統。

這個過程中，至少有三個不同時間尺度：模型思考的秒、工具執行的分鐘、人類決策的天。

若 Runtime 不能保存狀態，任何中斷都可能迫使任務重頭開始；若只靠聊天歷史恢復，Agent 容易把舊狀態與新狀態混淆。

因此，Runtime 的第一責任是：讓工作不因單次模型呼叫結束而消失。

Runtime 的十二個核心能力

1. 任務身份

每個任務都需要唯一識別、建立時間、擁有者、風險等級、目前狀態與正式成果位置。

沒有任務身份，日誌、檔案、工具呼叫與人工核准很難被正確連接。

2. 狀態保存

Runtime 要保存已完成步驟、當前 Context 摘要、工具結果、錯誤、決策與下一步。

狀態不應只存在模型輸出的自然語言裡，重要欄位應結構化，讓系統與人都能查詢。

3. Checkpoint 與恢復

長任務應在關鍵節點建立 checkpoint。若執行失敗，可以從最近安全狀態恢復，而不是重做全部工作。

Checkpoint 也能支援人工核准：系統先保存暫停狀態，核准後再繼續。

4. 工具執行

Runtime 負責真正呼叫 API、程式、資料庫、瀏覽器與外部服務，並處理認證、參數、回傳與錯誤。

模型提出工具意圖，Runtime 才決定是否允許、如何執行與留下什麼紀錄。

5. 隔離與沙箱

Agent 執行程式、開啟檔案或操作瀏覽器時，需要隔離環境。

暫存區、分支、容器、唯讀掛載與網路限制，都能降低錯誤影響。沒有隔離，試驗與正式行動的邊界會消失。

6. 秘密與身份管理

API Key、帳號、憑證與權限不應直接放進 Prompt。Runtime 應根據任務與角色提供最小必要授權，並記錄使用情況。

Agent 可以知道「有一個寄信工具」，不必看見真正密碼。

7. 事件與佇列

任務可能由新檔案、表單提交、排程、錯誤、核准或外部訊息觸發。Runtime 需要接收事件、排入佇列、控制優先序與避免重複執行。

8. 併發與鎖定

多個 Agent 可能同時修改相同資料。Runtime 必須處理鎖定、版本衝突、合併與重試。

否則，平行處理帶來的不是速度，而是互相覆蓋。

9. 成本與資源控制

模型用量、工具費用、執行時間、儲存與平行數都要被計量與限制。

Runtime 應能在超過預算時停止、降級模型、縮小範圍或請求人類決定。

10. 人工介入

人工介入需要介面與狀態，不只是一封「請確認」訊息。

核准者應看見：Agent 想做什麼、依據什麼、可能影響、可選方案、目前信心，以及核准後的下一步。

11. 可觀測性

Runtime 應記錄模型、工具、Agent、規則、錯誤、延遲與結果。OpenTelemetry 的生成式 AI 可觀測性工作，正嘗試用 spans 表示 invoke_agent、模型呼叫與工具執行，使跨服務的延遲、重試與錯誤更容易被定位。[R26]

12. 成果與回寫

工作完成後，正式檔案、資料庫狀態、決策紀錄與新知識必須被寫回正確位置。Runtime 不只負責「跑完」，還要負責讓下一次任務看到更新後的世界。

Runtime 是狀態機，不是一個會一直聊下去的視窗

對話介面容易讓人以為 Agent 的連續性來自聊天紀錄。

但真正的 Runtime 更接近狀態機。

以內容發布為例：

```textidea_received→ sources_ready→ draft_generated→ fact_check_failed→ draft_revised→ awaiting_editor→ approved→ scheduled→ published→ metrics_written_back```

每個狀態都有清楚責任。

draft_generated 不代表可以發布。

approved 不代表已成功上線。

published 也不代表任務完全結束，還可能需要保存網址、記錄版本與更新內容歷史。

狀態機讓系統避免把「做過一個動作」誤認為「完成一個結果」。

它也讓失敗更容易恢復。若發布失敗，只需要從 approved 重試，不必重新研究與寫作。

Durable Execution：長任務需要可持續執行

Durable execution 的核心不是讓程式永遠不斷，而是讓任務即使中斷，也能保留確定狀態並安全繼續。

常見情境包括：

- 外部 API 暫時失效。

- 人工核准要等到明天。

- Agent 達到用量上限。

- 工作節點重啟。

- 網路中斷。

- 子任務其中一個失敗。

- 新版資料在執行中到達。

一套耐久 Runtime 需要區分：

可重試錯誤：例如暫時網路失敗。

不可重試錯誤：例如權限被拒、輸入格式根本不合法。

需要人類錯誤：例如來源衝突或高風險決策。

需要重新規劃的錯誤：例如原方法多次失敗，必須改變策略。

若所有錯誤都只做同樣重試，系統會浪費成本；若所有錯誤都立刻停下，人類又會被大量低價值事件淹沒。

Runtime 的成熟，體現在錯誤分類與恢復策略。

Idempotency：重做一次，不能把事情做兩次

長任務最危險的問題之一，是重試造成重複影響。

寄信工具超時，不代表信沒有寄出；付款 API 沒有即時回應，不代表交易失敗；建立行事曆事件後連線中斷，重新執行可能產生兩個活動。

因此，高影響工具需要 idempotency，也就是同一個操作重試時，不會重複造成效果。

常見做法包括：

- 使用唯一請求鍵。

- 先查詢目前狀態再執行。

- 將建立與提交分成不同步驟。

- 對外行動保存交易識別。

- 重試前確認上一輪是否已成功。

這些都是 Runtime 工程，不能只靠模型說「請不要重複」。

沙箱：讓 Agent 有地方犯可恢復的錯

人類學習需要練習場，Agent 也一樣。

程式 Agent 應在分支或暫存工作區修改，而不是直接碰正式版本。

資料 Agent 可以先寫入 staging table，再通過檢查後合併。

內容 Agent 可以先建立草稿，不得直接公開。

瀏覽器 Agent 可以在測試帳號操作，不應拿正式管理員帳號做探索。

沙箱的價值，是把「能不能嘗試」與「能不能造成正式影響」分開。

高自主性若沒有沙箱，等於把探索成本轉嫁給真實世界。

MCP 與 Runtime：標準接口不是執行現場

MCP 讓 AI 應用用標準方式連接外部 Resources、Tools 與 Prompts。它能降低整合成本，也讓工具與脈絡提供者有更一致的接口。[R15]

但 MCP 不等於 Runtime。

MCP 可以描述一個工具如何被呼叫，Runtime 還要決定：

- 哪一個任務可以呼叫。

- 使用哪一個身份與權限。

- 是否需要核准。

- 呼叫前後如何保存狀態。

- 失敗是否重試。

- 成本如何計量。

- 回傳是否可信。

- 結果如何進入下一步。

- 完成後如何稽核與回寫。

因此，MCP 更像標準化插座；Runtime 是整棟建築的電路、保險、配電、監控與操作規則。

只裝很多插座，不代表建築就安全運作。

A2A 與 Runtime：Agent 能溝通，不代表能互相信任

Agent2Agent Protocol 的目標，是讓獨立、可能使用不同框架的 Agent 系統進行能力發現、訊息交換與任務協調。[R16]

這對企業很重要，因為未來不會只有一個大型 Agent，而可能有採購 Agent、客服 Agent、研究 Agent、程式 Agent 與外部供應商 Agent。

但互通只解決「能不能說話」，不解決「該不該相信」。

Runtime 仍要處理：

- 對方 Agent 的身份。

- 它宣告的能力是否經驗證。

- 能分享哪些資料。

- 任務是否跨越權限。

- 回傳結果是否帶證據。

- 失敗與爭議如何處理。

- 最終責任屬於誰。

一個外部 Agent 說「已完成」，不能自動改變內部正式狀態。需要驗證與接收條件。

多 Agent 世界不只需要協定，也需要信任邊界。

Control Plane：人類應該看見什麼

當 Agent 數量增加，人不可能閱讀每一段內部推理或每一行日誌。

Runtime 需要一個 control plane，也就是讓人掌握任務、風險、成本與例外的控制面。

一個好的控制面應顯示：

- 正在執行哪些任務。

- 每個任務目前狀態與責任人。

- 哪些任務等待人工核准。

- 哪些工具或資料發生錯誤。

- 哪些任務成本或時間異常。

- 哪些輸出信心低或證據不足。

- 哪些任務已完成但尚未回寫。

- 哪些系統指標正在偏移。

OpenAI 的 Symphony 經驗把工作看板轉成 Agent control plane，讓持續運作的 Agent 接取工程任務，人類則審查成果與處理高層問題。[R30] 這種做法最值得借鏡的，不是特定軟體，而是把人的注意力集中到狀態與例外，而不是逐步監看所有動作。

Runtime 與人的三種互動

1. Request

Agent 主動請求人類提供缺少資訊或核准行動。

好的 request 應精簡而完整，不應只說「請確認」。它要說明選項、依據、影響與建議。

2. Override

人類在發現風險時可以暫停、修改或終止任務。

Override 必須留下原因，否則下一輪系統無法學習。

3. Review

人類對結果、過程或例外進行審查。審查不一定逐項執行，也可以採抽樣、風險分流或事後稽核。

三種互動共同形成 Human-in-the-Loop 與 Human-on-the-Loop 的實作基礎。

Runtime 的安全邊界

一個 Agent Runtime 至少應有五種邊界。

資料邊界

只讀取任務需要的資料；敏感資料分級；成果不得把內部資訊帶到外部。

工具邊界

工具依任務與角色授權；高影響工具需要額外核准。

網路邊界

限制可連接的服務與網域；下載內容先掃描與驗證。

執行邊界

程式、檔案與瀏覽器操作在隔離環境進行；原始檔與正式環境受到保護。

成本邊界

每個任務與團隊都有用量上限、異常警示與降級策略。

這些邊界若只存在政策文件中，卻沒有落實在 Runtime，就只是期望。

一個假設案例：跨日研究 Agent

假設一個研究 Agent 要在三天內完成法規與產品比較。

第一天，它建立研究計畫，搜尋官方來源，發現其中一份規格即將更新。Runtime 保存目前來源、版本與未決問題。

第二天，外部規格更新事件到達。系統觸發重新檢查，只更新受影響部分，而不是重做所有研究。

接著，Agent 發現兩個官方來源對適用日期表述不同。它把任務狀態改為 awaiting_human，附上衝突、影響與建議，請領域負責人判斷。

第三天，取得核准後，Agent繼續撰寫，執行引用檢查與版本檢查，產生正式報告。完成後，Runtime 將來源、查閱日期、限制與下次更新條件寫入研究登錄。

這個案例中，模型能力只是一部分。真正讓任務可持續的，是事件、狀態、checkpoint、人工介入與回寫。

一個假設案例：預約 Agent 的現實問題

預約看起來是簡單工作：找空檔、建立活動、寄出通知。

正式 Runtime 卻需要處理：

- 不同時區。

- 服務前後緩衝。

- 多個行事曆衝突。

- 重複提交。

- 建立成功但通知失敗。

- 使用者改期與取消。

- 外部 API 暫時無回應。

- 個資保存期限。

- 人工封鎖時段。

若 Agent 只看行事曆畫面，可能做出局部正確、整體錯誤的決定。Runtime 必須把建立事件、同步狀態、失敗補償與通知結果連成一個可恢復流程。

這再次說明，工作不只是一個工具呼叫，而是一個有狀態的交易。

Runtime Thinking：把工作看成可運行系統

Runtime Thinking 是一種工作觀。

它要求我們在交辦 Agent 之前先問：

- 任務從哪裡啟動？

- 狀態放在哪裡？

- 誰可以讀取與修改？

- 外部工具失敗時怎麼辦？

- 任務中斷後如何恢復？

- 哪些行動可逆，哪些不可逆？

- 人類在哪裡接收例外？

- 如何知道任務真的完成？

- 完成後哪些狀態必須回寫？

這些問題看似技術，其實也是管理問題。

因為 Runtime 決定工作如何被分配、例外如何被升級、責任如何被看見，以及組織能不能從一次執行中累積能力。

把 Runtime 當成服務來營運：Agent 也需要可靠性工程

當 Agent 從一次性任務走向長時間運作，它就不再只是功能，而像一項服務。服務會有尖峰、有中斷、有版本、有依賴、有事故，也需要有人值守與改善。若團隊只關心模型回答品質，卻沒有 Runtime 的營運視角，系統最終會在狀態、重試、成本與例外上失控。

先定義服務目標，而不是追求永不中斷

Runtime 不需要所有任務都達到相同可靠度。內部草稿 Agent 可以容許延遲與人工重跑；付款、醫療、權限或公共通知則需要更嚴格的可用性、正確性與審查。

可用的服務目標至少包括：

- 任務在多久內開始執行。

- 多久沒有進度就視為卡住。

- 多少比例能在不需人工救援下完成。

- 哪些錯誤可以自動重試，最多幾次。

- 成本與工具呼叫的預算上限。

- 高影響行動必須留下哪些證據。

- 事故發生後多久能停止、恢復與通知。

這些目標讓團隊知道何時系統只是「偶爾不順」，何時已經不適合繼續自動運作。

事故分類要指向不同處理方式

Agent 失敗不應全部歸類為「模型錯了」。Runtime 可以把事故分為：

狀態事故：checkpoint 遺失、任務重複、狀態不一致。處理重點是恢復與去重。

工具事故：外部 API 中斷、回傳格式改變、權限過期。處理重點是降級、重試與介面契約。

資料事故：資料過期、來源衝突、欄位缺失。處理重點是閘門、補充與停止。

規劃事故：Agent 選擇錯誤路徑、陷入循環、消耗過多步數。處理重點是限制、評測與重新分解。

安全事故：越權、敏感資料外洩、提示注入或不當外部行動。處理重點是立即隔離、保存證據與人工調查。

責任事故：沒有人知道誰能批准、誰應接手、誰要通知。處理重點不是改模型，而是修正治理。

分類的價值，在於每種事故都有不同擁有者與改善路徑。

重試之前先確認可重做

自動重試看似是最簡單的可靠性策略，卻可能放大錯誤。讀取資料重試通常風險較低；寄信、付款、建立訂單、修改正式紀錄若沒有 idempotency，就可能重複造成影響。

Runtime 在重試前應檢查：上一次行動是否真的失敗，還是只沒有收到回覆？工具是否支援冪等鍵？是否能查詢目前狀態？重做會不會覆蓋他人的更新？

若無法證明安全，系統應暫停並交給人，而不是以「再試一次」賭運氣。

併發與排隊是工作設計問題

當多個 Agent 同時處理同一客戶、同一文件或同一資源，就會產生競爭。沒有鎖定與版本控制，後完成的任務可能覆蓋前一個結果；沒有優先級，低價值工作可能佔滿資源，讓緊急任務等待。

Runtime 應管理任務佇列、優先級、併發上限、資源鎖與取消。更重要的是，組織要決定哪種 Outcome 值得搶占資源，哪些可以延後，哪些在資料更新後應重新啟動。

這些決定不是模型可以單獨推理出的偏好，而是業務政策。

成本也要成為執行狀態

長任務可能不斷檢索、呼叫工具、產生子 Agent 或重試。若成本只在月底報表出現，控制就太晚了。

Runtime 應在執行中追蹤 Token、工具費用、時間、儲存、外部服務與人工介入。當接近預算時，可以降低搜尋範圍、改用較便宜模型、要求人工確認是否值得繼續，或保存目前進度後停止。

預算不是單純限制花費，也是一種價值檢查：這個 Outcome 是否值得繼續投入？

Kill Switch 不應只存在紙上

任何能造成外部影響的 Agent，都需要實際可用的停止機制。停止不只是關閉模型 API，還可能需要撤銷工具權限、清空佇列、凍結進行中任務、阻止下游自動化、保存 trace，並通知相關人員。

Kill Switch 要定期演練。若只有少數人知道位置、需要臨時找權限，或關閉後無法確認哪些行動已執行，它就不是可靠的安全機制。

Runbook 讓接手者不必從零猜測

Runtime 應為常見事故建立 Runbook：如何確認任務狀態、如何安全重啟、如何回復 checkpoint、如何撤銷工具 token、如何查找最後一次外部行動、如何通知 DRI，以及什麼情況不得自行恢復。

Runbook 的重點不是把所有情況寫死，而是讓值守者在壓力下知道先做什麼、不該做什麼，以及需要保存哪些證據。

一個跨日研究 Agent 的營運方式

假設 Agent 每晚蒐集市場資料、隔天早上產出摘要。它需要知道資料截止時間、來源失敗時的降級策略、相同文章如何去重、摘要生成失敗是否重跑、前一天任務未完成是否阻止新任務、成本超標時如何縮小範圍，以及早上幾點前若仍未完成要通知誰。

若某個來源更新格式，Runtime 應把錯誤分類成工具或資料事故，暫停使用該來源，保留其他已完成結果，並在報告中誠實標示缺口。它不應為了準時而悄悄用過時資料填滿。

把 Runtime 當成服務來營運，會改變我們看待 Agent 的方式。真正可靠的系統，不是從不失敗，而是失敗可被看見、影響可被限制、狀態可被恢復、責任可被接手，而且每次事故都能讓下一次更好。

災難恢復與營運持續：Agent 停下來時，工作不能一起消失

當 Agent 進入正式營運，組織必須接受一件事：模型服務、工具、網路、資料源與身份系統都可能中斷。可靠 Runtime 不是承諾永遠不中斷，而是預先決定中斷時哪些工作要停、哪些可以降級、哪些必須由人接手。

首先要定義兩個時間問題。恢復時間目標回答：服務中斷後，最晚多久要恢復到可接受狀態？恢復點目標回答：最多可以遺失多少已完成狀態？對每日摘要，晚一小時可能可接受；對付款、預約或權益變更，任何狀態遺失都可能造成重複執行，因此需要更嚴格的 checkpoint 與對帳。

接著要設計降級模式。研究 Agent 在部分來源失效時，可以產出「資料不完整」的限定版報告；客服 Agent 若無法存取帳務，不應猜測答案，而可以建立待辦並告知回覆時間；公開發布 Agent 若無法確認來源版本，就應停止，而不是用快取內容填滿。降級的原則是縮小承諾，不是掩飾失敗。

營運持續還需要人工接管包。接手者要看見任務目前狀態、最後一次成功行動、已取得鎖定、等待中的外部回應、不可重做步驟、剩餘期限與建議下一步。若 Agent 倒下後，人只能從零閱讀全部對話，代表 Runtime 沒有把狀態設計成可交接資產。

對外部行動，必須有對帳機制。付款 API 超時，不代表付款失敗；郵件工具回傳錯誤，也不代表信件一定沒寄出。Runtime 應先查詢外部世界的最終狀態，再決定重試。災難恢復的核心不是「再跑一次」，而是防止未知狀態被重複行動放大。

備份也不只備份資料庫。系統還需要保存 Harness 版本、工具設定、權限矩陣、Eval 資料集、重要 trace 與 Runbook。若只有任務資料，卻無法還原當時的工作契約與執行環境，就很難重現事故，也無法可靠地在替代環境恢復。

組織應定期演練幾種情境：模型供應商暫時不可用、主要資料源延遲、工具憑證失效、錯誤版本已發布、任務佇列重複，以及關鍵 DRI 無法聯絡。演練目的不是表演系統完美，而是找出權限拿不到、通知送錯人、狀態看不懂與手動流程從未真正跑過的缺口。

營運持續也包含對人的溝通。當服務降級或暫停，使用者需要知道哪些功能受影響、資料是否安全、已提交工作是否會重複、何時更新。沉默會把技術事故變成信任事故；過度承諾則會迫使團隊在不安全狀態下匆忙恢復。

Agent 停下來並不可恥。真正危險的是，系統停下時沒有人知道工作走到哪裡，也沒有人知道如何安全接續。Runtime 的成熟，最後會表現在最壞的一天：它能否讓影響被限制、承諾被縮小、證據被保存，而且工作仍有一條可負責的回來之路。

本章收束：Runtime 是 Agent 的真實世界

模型可以在對話中展現聰明。

Agent 要在 Runtime 裡證明自己能工作。

Runtime 把目標變成任務，把任務變成狀態，把工具變成受控行動，把失敗變成可恢復事件，把人工介入變成正式節點，也把完成結果寫回組織的真實系統。

沒有 Runtime，Agent 只能完成短暫示範。

有了 Runtime，AI 才可能跨時間、跨工具、跨人員地承接責任。

但能持續運行還不夠。系統若只是反覆執行，可能把錯誤反覆放大。下一章，我們要處理如何把流程變成真正的改善循環：Loop Engineering。

章末金句

1. 回答發生在對話裡，工作發生在 Runtime 裡。

2. Runtime 的第一責任，是讓工作不因一次模型呼叫結束而消失。

3. 長任務的關鍵不是永不中斷，而是中斷後能從安全狀態繼續。

4. 模型提出工具意圖，Runtime 才決定是否允許、如何執行與留下什麼證據。

5. 沙箱讓 Agent 有地方犯可恢復的錯，而不是拿真實世界當練習場。

6. 標準接口讓 Agent 能連接，Runtime 才讓連接變成可治理的工作。

7. Agent 能互相溝通，不代表它們能互相信任。

8. 人不必看完所有動作，但必須看得見狀態、風險、成本與例外。

9. 工作不是一次工具呼叫，而是一個有狀態、可恢復、可追責的交易。
