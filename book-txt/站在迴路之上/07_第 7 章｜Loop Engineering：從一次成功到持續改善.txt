第 7 章｜Loop Engineering：從一次成功到持續改善

會做一次是作品，能穩定重複才是系統

一個 Agent 成功完成一次任務，很容易讓人興奮。

它讀完資料、使用工具、修正錯誤，最後交付成果。展示現場看起來像是未來已經到來。

可是第二次輸入稍微不同，它失敗了。

第三次工具回傳格式改變，它走錯路。

第四次資料缺了一欄，它沒有停下，而是自行補出合理內容。

第五次雖然成功，成本卻是預期的五倍。

這時我們才會發現：一次成功只能證明能力可能存在，不能證明系統已經可靠。

真正的工作需要重複。

每一次輸入不會完全相同，每一個錯誤也不會照劇本出現。系統必須在變化中維持方向，能觀察結果、取得回饋、修正策略、處理例外，並在必要時停止。

這就是我使用「Loop Engineering」這個詞的原因。

必須先說清楚：截至本書研究校準日，Loop Engineering 更像 2026 年 AI 實務社群正在形成的產業語言，而不是已完成學術定義的成熟學門。它背後的零件並不新：ReAct 的推理與行動、Tool Use、Reflexion、evaluator-optimizer、Agent Workflow、DevOps、CI/CD、observability、human-in-the-loop 與 guardrails，都早已提供重要骨架。[R09][R20][R22]

本書使用這個詞，不是為了把舊概念重新包裝，而是要把一個正在發生的工作轉變說清楚：

AI 的競爭不再只是哪一句 Prompt 寫得漂亮，而是誰能把目標、環境、工具、驗證、回饋、監督與交接設計成可持續工作的迴路。

Workflow 與 Loop 的差別

Workflow 重視路徑。

Loop 重視回饋。

一個工作流可以是：收到檔案、抽取資料、生成報告、寄出結果。

一個工作迴路則會問：

- 報告是否通過驗證？

- 若不通過，錯在哪一類？

- 要回到哪個步驟？

- 修正後如何避免重複錯誤？

- 哪些失敗應更新規則或工具？

- 哪些例外必須由人處理？

- 下一次執行是否真的比這一次更好？

Workflow 可以把事情做完。

Loop 的目標，是讓事情在回饋中變好。

但 Loop 也不是無限重試。沒有停止條件的循環，只是消耗。

真正的 Loop 必須同時有：

- 目標。

- 觀察。

- 判準。

- 修正。

- 記憶。

- 停止。

- 責任。

缺少其中任何一項，循環都可能變成繞圈。

本書提出：七環工作迴路

為了把分散技術整理成一般工作者、主管與技術團隊都能使用的共同語言，我提出「七環工作迴路」。

它不是既有標準，而是本書的作者整合框架。

七個環節是：

```text目標 Goal→ 脈絡 Context→ 工具 Tools→ 驗證 Validation→ 回饋 Feedback→ 監督 Oversight→ 交接 Handoff↺ 回到下一輪目標與脈絡```

這七個環節不是七個固定步驟。有些任務會平行，有些會反覆，有些只需要其中幾個簡化版本。它們更像七個必須被回答的責任問題。

第一環：目標 Goal

沒有目標的 Agent，只會把「持續活動」誤認為工作。

目標應包含 Outcome、成功條件、優先順序與不可犧牲的邊界。

例如，「提升客服效率」太模糊。更可用的目標可能是：

- 在不增加錯誤承諾與客訴升級率的前提下，縮短一般案件首次回覆時間。

- 高風險案件在十分鐘內轉交有權責的人。

- 每一個對外承諾都能追溯到規則與授權。

目標也要分層。

北極星目標回答為什麼做。

任務目標回答這一輪要完成什麼。

步驟目標回答下一個行動要解決什麼不確定性。

Agent 可以在任務中動態調整步驟目標，但不應在沒有授權時改寫北極星目標。

目標的成熟，不只是明確，也包含知道什麼不能用效率交換。

第二環：脈絡 Context

目標確定後，系統要準備足以行動的世界。

Context 包含正式來源、當前狀態、歷史決策、工具能力、權限、風險與輸出規格。

這一環的關鍵不是資料量，而是訊號品質。

每一輪 Agent 行動後，Context 都會改變。工具結果、錯誤、人工決策與新資料都必須被納入；過期內容、已被取代的版本與不再相關的歷史則要被壓縮或移除。

因此，Context 不是前置準備，而是迴路的持續維護。

一個常見錯誤，是任務開始時提供很多文件，之後卻不更新狀態。Agent 仍然依照初始世界工作，卻不知道現實已經改變。

第三環：工具 Tools

目標與脈絡若不能產生外部影響，Agent 仍停在回答層。

工具讓 Agent 查詢、計算、建立、修改、執行與溝通。

但工具不是越多越好。每一個工具都帶來能力，也帶來權限與故障面。

工具環應回答：

- 這個工具解決哪一種行動？

- 輸入與輸出是否清楚？

- 是否可逆？

- 使用哪個身份與權限？

- 失敗如何辨認？

- 是否會造成重複影響？

- 結果如何進入下一輪 Context？

Agent 最好不要直接接觸過度寬泛的「超級工具」。工具越接近具體責任，越容易權限分級與驗證。

第四環：驗證 Validation

驗證回答：「這一步或這個結果真的符合條件嗎？」

它可以發生在行動前、行動中與行動後。

行動前驗證檢查資料、權限、參數與風險。

行動中驗證檢查工具回傳、狀態變化與異常。

行動後驗證檢查 Outcome、證據與副作用。

驗證也要區分「形式通過」與「實質通過」。

檔案存在，不代表內容正確。

測試通過，不代表需求被滿足。

信件寄出，不代表寄給正確的人。

報告有引用，不代表引用真的支持主張。

因此，驗證應盡量靠外部訊號與可觀察結果，而不是讓 Agent 自己宣告成功。

第五環：回饋 Feedback

驗證只說通過或失敗，回饋則要指出下一步如何改進。

高品質回饋具有四個特徵。

具體

不是「內容不好」，而是「第二段主張缺少來源，第三段與正式規格版本衝突」。

可行

指出可修改的部分與可使用的證據，而不是只給抽象評價。

對應目標

回饋應與 Outcome 相關，不是迎合個人風格偏好。

能被回寫

若同一錯誤可能重複出現，回饋應轉成規則、工具、測試、範例或評測資料。

Anthropic 的 evaluator-optimizer 模式，就是由一個模型或機制產生結果，另一個根據明確標準評估並提供回饋，再反覆修正。[R09]

但回饋者也可能錯。重要任務需要多種回饋來源：程式測試、資料規則、模型評分、人類審查與真實使用結果。

第六環：監督 Oversight

監督不是人盯著 Agent 每一秒。

監督是讓有責任的人能看見系統狀態、風險、成本、例外與偏移，並在適當位置介入。

監督可以分成三層。

即時監督

高風險行動前核准，或異常發生時立即停止。

週期監督

定期檢查成功率、成本、錯誤類型、人工介入與資料偏移。

制度監督

檢查目標本身是否仍合理、規則是否公平、權限是否過度、責任是否清楚。

很多系統只做第一層：Agent 要寄信時請人按確認。但真正重要的問題往往在第三層：我們是否讓 Agent 追求了錯誤指標？是否因效率而犧牲不該犧牲的價值？

第七環：交接 Handoff

一個迴路若不能交接，就無法跨時間、跨人與跨 Agent 延續。

交接包含兩種方向。

橫向交接：從一個 Agent 或角色交給另一個。

縱向回寫：把本輪學習寫回正式系統，影響下一輪。

高品質交接要保留：

- 目標與當前狀態。

- 正式來源與版本。

- 已完成與未完成。

- 已知錯誤與風險。

- 人工決策與理由。

- 成果與證據位置。

- 下一步與停止條件。

若沒有縱向回寫，下一輪會重複同樣錯誤；若沒有橫向交接，每個節點都要重新讀完整歷史。

交接是迴路從一次執行變成組織能力的關鍵。

七環不是流水線，而是責任網

七環看起來像一條線，實際上是一張網。

驗證可能在工具使用前發生。

監督可能在目標設定時就介入。

交接可能改變下一輪 Context。

回饋可能要求重寫目標，而不是只修正內容。

因此，設計迴路時，不應機械地要求每一步都走一遍，而要問每一環的責任由誰承擔、用什麼機制完成。

例如，一個低風險摘要任務可以非常簡化：

- 目標：產生五點摘要。

- Context：指定文件。

- 工具：無。

- 驗證：字數與關鍵主題檢查。

- 回饋：不合格則重寫一次。

- 監督：抽樣人工檢查。

- 交接：存入草稿區。

而一個高風險採購任務則需要完整版本、資料品質、權限、雙重核准、交易紀錄與事後稽核。

框架的價值不是讓簡單事情複雜，而是讓複雜事情不再靠運氣。

迴路的四種失敗

1. 空轉 Loop

Agent 不斷搜尋、反思與重寫，卻沒有新的外部證據。文字愈來愈完整，問題沒有真正前進。

解法：要求每一輪必須降低一個明確不確定性；沒有新證據時停止。

2. 局部最佳 Loop

系統不斷優化某個容易衡量的指標，卻損害整體 Outcome。

例如為了提高回覆速度，犧牲準確與信任。

解法：建立多維成功條件與禁止邊界，不只追求單一分數。

3. 自我引用 Loop

Agent 用自己的前一版輸出當成新證據，逐輪強化錯誤。

解法：區分原始來源、衍生內容與已核准知識，重要主張必須回到外部證據。

4. 無限修正 Loop

評分器永遠能找到小問題，系統無法完成。

解法：設定可接受門檻、最大迭代、成本上限與人工決策點。

Loop Engineering 的核心不是鼓勵更多迴圈，而是設計「什麼回饋值得再跑一輪」。

Stop Condition：停止是迴路的一部分

一個成熟迴路至少有五種停止方式。

成功停止

Outcome 與品質條件通過，成果已寫回正式位置。

可接受停止

仍有已知限制，但在風險與成本範圍內可交付，並清楚標示限制。

資源停止

達到時間、成本、步數或重試上限。

風險停止

資料、權限、證據或影響超出自動化邊界。

人工停止

責任人決定方向改變、任務取消或需要另行處理。

停止不是失敗的同義詞。能在不確定性過高時停下，是可信系統的重要能力。

Feedback Debt：沒有回寫的修正會變成債

很多團隊每天都在修正 Agent，卻沒有讓系統變得更好。

使用者發現錯誤，口頭提醒一次；下次換一個人，又發生相同錯誤。工程師在執行時手動補上一個檔案，卻沒有更新文件與工具。主管否決某種輸出，但原因沒有被轉成標準。

這些沒有被回寫的修正，就是 Feedback Debt。

它會造成：

- 同一錯誤反覆出現。

- 人工依賴持續增加。

- Agent 看似需要「更懂公司」，實際上公司沒有正式記錄。

- 每次換模型或人員都重新學習。

要償還 Feedback Debt，可以建立簡單分類：

```text錯誤屬於：A. 目標不清B. Context 缺漏或過期C. 工具／權限問題D. 驗證不足E. 模型能力限制F. 例外只能由人判斷G. 交接或回寫失敗```

接著決定修正位置，而不是只改當次答案。

從 DevOps 看 Loop Engineering

軟體工程早已熟悉回饋迴路。

開發者寫程式，執行測試，讀取錯誤，修正，再次測試；CI/CD 把建置、測試、部署與監控串成循環；observability 讓系統在正式環境中的行為可被看見。

Agent 的新之處，不是發明循環，而是讓語言模型進入循環的多個位置：

- 讀懂模糊需求。

- 規劃下一步。

- 選擇工具。

- 解釋錯誤。

- 生成修正。

- 整理交接。

這使過去只有工程團隊熟悉的回饋式工作，開始進入內容、研究、行政、客服與管理。

但也帶來新的非確定性。程式測試的結果相對明確，文字品質、策略判斷與資料可信度往往沒有單一答案。這就是為什麼 Agent Loop 必須結合 Evals、Guardrails、人類監督與證據。

Improvement Loop：系統要改善什麼？

一個 Agent 的改善可以發生在四個層次。

輸出層

修正這一次答案或成果。

流程層

改變步驟、順序、路由與驗證。

Harness 層

增加或刪除工具、規則、權限、停止條件與評測。

組織層

重新定義目標、責任、資料來源與決策權。

很多團隊只在輸出層改善：「這段再寫好一點。」

真正有複利的改進，會往後三層移動。

OpenAI 的 Harness Engineering 經驗就是這種思路：當 Agent 反覆失敗，團隊不只修當次程式，而是建立它缺少的工具、文件、測試與防護，讓未來所有任務受益。[R07]

這就是從使用 AI 走向設計 AI 工作系統的分界。

一個假設案例：每日內容迴路

假設一個內容系統每天要根據真實近況產生社群草稿。

七環可以這樣設計：

目標

產生一篇符合作者觀點、真實、安全、與近期內容不重複的草稿；發布仍需人工核准。

脈絡

讀取長期人物資料、近七日狀態、已發布內容、可公開素材與隱私規則。

工具

檔案搜尋、行事曆唯讀、圖片資產、文字生成、圖像生成與內容檢查。

驗證

姓名、日期、活動狀態、來源、隱私、重複、語氣與圖文一致性。

回饋

編輯修改原因、發布後成效、讀者問題與錯誤紀錄。

監督

人工核准發布，高風險或私人內容自動阻擋。

交接

保存正式貼文、使用圖片、主題、開場、結尾與成效，更新下一次避免重複的 Context。

若系統每天只生成文章，沒有最後的回寫，它不是內容迴路，只是每日重來的生成器。

一個假設案例：Agent 修正流程

一個程式 Agent 修改功能後測試失敗。

第一輪，它讀錯誤訊息並修正。

第二輪，另一個測試失敗。若它只繼續改，可能造成連鎖破壞。

Loop Engineering 會要求：

1. 先分類錯誤是否與原需求相關。

2. 檢查修改範圍是否超出計畫。

3. 若連續兩次出現新回歸，停止局部修補，重新評估架構。

4. 保存每輪變更與測試證據。

5. 超過三輪或需要重大重構時，交由人類決策。

6. 完成後把新的測試加入回歸套件。

這樣，迴路不只是「失敗就重試」，而是「失敗改變下一輪的判斷與系統」。

Loop Review：每個月應檢查什麼

一個正式 Agent 系統可以定期做 Loop Review：

- 哪些任務成功率最低？

- 哪些錯誤最常重複？

- 哪一環造成最多人工介入？

- 哪些 Context 經常過期或衝突？

- 哪些工具回傳最難使用？

- 哪些驗證與真實 Outcome 無關？

- 哪些停止條件太早或太晚？

- 哪些人工決策可以轉成規則？

- 哪些規則應保留給人，不該自動化？

- 哪些學習沒有被回寫？

Loop Review 的目的不是消滅所有人工，而是把人的注意力放在真正需要判斷的地方。

迴路成熟度：不是有回圈就叫會學習

很多系統都能重試，也能根據錯誤訊息再做一次，但這不代表它已經形成成熟迴路。若目標模糊、驗證薄弱、回饋沒有回寫，重複只會讓系統更快地做同一件錯事。

可以把 AI 工作迴路分成六個成熟層級。這不是產業標準，而是本書用來診斷系統的工作模型。

Level 0｜單次生成

使用者提出要求，模型產出結果，工作在對話結束時停止。沒有明確狀態、驗證或交接。這適合低風險創意草稿與即時腦力激盪，但不適合需要持續責任的工作。

這一層最大的風險，是把一次看起來成功的示範，誤認成可重複能力。

Level 1｜可重複流程

任務被拆成固定步驟，輸入與輸出格式較一致，工具與交付位置明確。系統可以重跑，但仍主要依靠理想路徑。

此時應先確保每一步有清楚責任，不要急著增加自主性。若流程本身不穩定，Agent 只會放大變異。

Level 2｜可測量迴路

系統開始記錄 trace、成本、錯誤、驗證結果與 Outcome。團隊能回答哪一步失敗、失敗多久被發現，以及不同版本是否真的改善。

這一層的關鍵不是收集更多資料，而是建立可用的判斷訊號。若指標與真實 Outcome 無關，可觀測性只會形成新的儀表板噪音。

Level 3｜可恢復迴路

系統具有 checkpoint、狀態機、冪等設計、停止條件與高品質 Handoff。工具失敗或人工介入後，不必從頭開始，也不會重複造成外部影響。

可恢復讓 Agent 能承擔更長任務，卻也要求 Runtime 更成熟。此時「完成率」不再只是模型能力，而是狀態、依賴與例外治理的總和。

Level 4｜可學習迴路

錯誤被分類並轉成 eval case；人工修正被回寫到資料、工具、Harness 或政策；模型升級會重跑回歸測試；重複出現的例外逐步被系統吸收。

真正的學習不是 Agent 在一次執行中說它反思了什麼，而是組織能證明：同類錯誤發生率下降、恢復時間縮短、人工注意力更集中，而且新的修正不會破壞舊能力。

Level 5｜可治理迴路

系統不只會改善，還知道哪些方向不能只由效率決定。它有清楚 DRI、權限分層、證據保留、風險分級、申訴與停止機制；不同利害關係人的權益被納入，而不是只追求任務完成。

這一層的人類角色最少微管步驟，卻承擔最高層的方向與責任。Human Above the Loop 在此不是口號，而是制度化配置。

升級成熟度前，先問是否真的需要

不是所有工作都要走到 Level 5。一次性的創意任務可能停在 Level 0；固定內部報表可能只需要 Level 2 或 Level 3；涉及客戶權益、金錢、公共資訊與長期自主行動的系統，才需要更高治理。

成熟度的目的不是追求複雜，而是讓系統能力與影響相稱。若低風險任務被過度治理，成本會高到沒人使用；若高風險任務停在單次生成，組織則把責任交給偶然。

四種常見的假迴路

第一種是無驗證重試。系統反覆產生不同答案，最後選一個看起來最好，卻沒有外部標準。

第二種是只記錄不學習。Trace 很完整，事故報告很多，但修正沒有回到正式系統，同類問題持續發生。

第三種是只優化局部指標。為了提高完成率，系統降低拒絕與升級人工的比例，結果反而讓高風險錯誤增加。

第四種是人類永遠救火。每次例外都由同一群人手動處理，系統看似穩定，實際上靠隱形勞動維持。

建立三種節奏

成熟迴路需要不同時間尺度的回顧。

每次執行後，記錄結果、錯誤、成本與未解問題。這是運行層。

每週或每批次，檢查重複失敗、資料缺口與人工介入，決定哪些應回寫 Harness、Context 或工具。這是改善層。

每月或每季，重新檢查 Outcome 是否仍值得、自主性是否過高或過低、指標是否造成錯誤誘因，以及責任人是否仍適當。這是治理層。

三種節奏不能互相取代。只做即時修復，系統永遠沒有方向；只做季度策略，日常錯誤又會不斷累積。

迴路的終點不是零錯誤，而是更快接近真實

真實世界會改變，模型也不可能一次處理所有例外。成熟系統追求的不是永遠正確，而是能早點發現偏離、限制影響、保存證據、正確交接，並把經驗寫回下一輪。

這也解釋了為什麼 Loop Engineering 不是讓 Agent 一直跑。好的迴路有停止、有遺忘、有重設，也會在發現目標本身錯誤時結束。系統真正學會的，不只是如何完成任務，而是如何在不確定世界裡持續修正自己與目標之間的距離。

迴路治理：防止系統學會追逐錯誤獎勵

一個迴路只要持續收到回饋，就會逐漸朝回饋指標靠近。問題是，指標未必等於價值。當團隊獎勵完成數，系統可能拆出更多容易完成的小任務；獎勵點擊率，內容可能愈來愈刺激；獎勵快速結案，例外可能被過早關閉。

因此，Loop Engineering 除了設計回饋，還要治理回饋。第一步是區分代理指標與最終價值。代理指標可以快速量測，例如格式通過率、處理時間與工具成功率；最終價值則可能是問題真正解決、決策品質、公平、信任與長期學習。代理指標可以導航，不能取代最終價值。

第二步是為每個主要指標配一個反指標。追求速度時，同時看重做與申訴；追求自動完成率時，同時看人工救火與錯誤釋出；追求成本下降時，同時看資料品質與人員負荷。反指標不是拖慢改善，而是防止迴路在單一數字上愈跑愈偏。

第三步是建立停止改善的條件。不是所有小幅提升都值得更多複雜度。若新增規則只改善極少案例，卻增加大量延遲、維護與誤攔，團隊應接受目前的可接受邊界。Loop 的目標不是無限最佳化，而是在風險、價值與成本之間維持可說明的平衡。

第四步是設計終止條件。當 Outcome 已不再重要、資料基礎長期不足、事故超過容忍、使用者權益受到不可接受影響，或人工負荷持續高於替代方案，系統應被縮小、重做或下線。能停止一個錯誤迴路，和能改善一個正確迴路同樣重要。

第五步是讓受到影響的人進入回饋。內部 Metrics 可能顯示流程順暢，使用者卻感到無法申訴、理由不透明或被不公平分類。真正的治理需要把客服紀錄、申訴、撤回、專業人員觀察與受影響者意見，轉成可以被分析的訊號，而不是只相信系統自己的成功紀錄。

第六步是避免改善權集中在單一角色。工程團隊知道系統限制，業務知道現場例外，法務與治理角色知道責任邊界，使用者則知道真實影響。重大迴路的季度 Review 應讓不同角色共同檢查：目標是否仍正確？指標是否被操弄？例外是否集中在某些人？自動化收益由誰得到，風險又由誰承擔？

假設一個招募 Agent 的目標是提高面試到場率。它可能學會優先聯絡回覆快的候選人，短期數字變好，卻忽略需要更多時間、無法隨時上線或語言表達較慢的人。若只看到場率，迴路會把可及性問題誤認為低意願。加入族群分布、申訴、人工抽查與長期錄用結果，才能看見這個偏差。

好的迴路會學習，成熟的迴路還會質疑自己正在學什麼。治理不是在改善之後附加一道審核，而是讓目標、指標、反指標、停止與終止條件從一開始就進入迴路。

本章收束：迴路不是讓 AI 更忙，而是讓工作更會學

Loop Engineering 最容易被誤解成讓 Agent 一直跑、一直改、一直自我反思。

真正的核心不是次數，而是回饋品質。

一個好迴路，每一輪都應該降低不確定性、改善結果、補上系統缺口，或清楚知道何時該停。

七環工作迴路提供一個共同語言：目標讓系統知道往哪裡去；Context 提供當前世界；工具產生行動；驗證連接外部現實；回饋形成修正；監督保留人類責任；交接把一次經驗變成下一次能力。

但要讓迴路真正改善，我們必須看見它發生了什麼，也要有方法衡量它是否變好。

下一章，我們將進入 Tracing、Evals 與 Observability：看得見，才改得動。

章末金句

1. 一次成功只能證明能力可能存在，穩定重複才證明系統開始成立。

2. Workflow 重視路徑，Loop 重視回饋。

3. 沒有停止條件的循環，不是自律，而是消耗。

4. 七環工作迴路不是產業標準，而是把目標、脈絡、工具、驗證、回饋、監督與交接放進同一張責任圖。

5. 迴路的價值不是跑更多次，而是每一輪都降低一個真實不確定性。

6. 能在證據不足時停下，是可靠性的一部分。

7. 沒有被回寫的修正，會變成下一次仍要償還的 Feedback Debt。

8. 真正有複利的改善，不只修輸出，也修流程、Harness 與組織。

9. 迴路不是讓 AI 更忙，而是讓工作更會學。
