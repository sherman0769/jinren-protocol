第 5 章｜Harness Engineering：模型之外的工作契約

模型很強，為什麼系統還是常常做錯？

當 Agent 失敗，我們最直覺的反應通常是換一個更強模型，或把提示詞寫得更長。

有時這確實有效。但很多失敗並不發生在模型「不夠聰明」，而是發生在模型之外。

工具名稱太相似，Agent 選錯。

輸入參數沒有清楚限制，Agent 把日期格式填錯。

搜尋工具回傳一大段噪音，真正重要的錯誤藏在最後。

系統允許直接修改正式檔，卻沒有暫存區與測試。

任務沒有完成條件，Agent 做到一半就宣布成功。

錯誤後無限重試，成本不斷增加。

權限設得太寬，低風險任務也能碰到高影響工具。

這些問題不是單靠模型升級就能消失。它們屬於模型之外的工作契約與支架。

在本書中，我把這一層稱為 Harness，也可譯為駕馭層或工作支架。這不是要宣稱產業已有唯一標準定義，而是用來指稱：

包圍模型、引導模型、限制模型，並把模型能力轉成可執行工作的那一整套設計。

OpenAI 在 Harness Engineering 的工程分享中，強調當 Agent 暴露缺少的工具、文件、防護欄與驗證時，團隊應把這些缺口回寫到環境，讓下一輪工作更穩定；人的工作因此往更高抽象層移動。[R07] Anthropic 對長時間應用開發的研究也提醒，每一個 Harness 元件都隱含對模型能力的假設，而模型進步後，舊支架可能變得多餘、脆弱或反而妨礙表現。[R14]

Harness 的核心不是控制模型說每一句話，而是建立一個模型能夠被安全使用的工作契約。

Context、Harness 與 Runtime 到底差在哪裡？

這三個詞很容易混在一起。

Context 回答：AI 此刻知道什麼、看到什麼、記得什麼。

Harness 回答：AI 被要求如何工作、能用什麼、必須遵守哪些契約。

Runtime 回答：這套契約在哪裡真正執行、保存狀態、處理事件與恢復失敗。

可以用廚房做比喻。

Context 是今天要做的菜單、食材狀態、客人需求與過敏資訊。

Harness 是食譜、器具標示、衛生規則、權限、品質標準與出菜流程。

Runtime 是實際的廚房：爐火、冰箱、工作台、排單、庫存、計時、清潔與現場人員。

三者互相依賴，但不能互相取代。

只有 Context，AI 知道很多，卻不一定知道怎麼安全行動。

只有 Harness，規則很完整，卻可能缺少最新狀態。

只有 Runtime，系統能跑，卻可能在錯誤脈絡與模糊規則中穩定做錯。

Harness 的九個核心元件

一套實用 Harness，通常包含以下九類元件。

1. 指令層：角色、任務與優先序

指令不是堆疊人格設定，而是建立決策優先序。

例如：

1. 保護原始資料與個資。

2. 遵守正式來源與版本規則。

3. 完成 Outcome Contract。

4. 在不確定時先求證，不得自行補造。

5. 只在授權範圍內使用工具。

6. 無法安全完成時停止並回報。

好的指令層能讓 Agent 在規則衝突時知道如何排序。差的指令層只會塞入大量「務必專業、完整、準確」之類無法驗證的形容詞。

2. 工具層：能做什麼與不能做什麼

工具名稱、描述、參數、回傳格式與錯誤訊息，會直接影響 Agent 的行為。

Anthropic 把工具視為確定性系統與非確定性 Agent 之間的契約，強調工具應有清楚邊界、高訊號回傳、可驗證輸入輸出，並用評測反覆改善。[R11]

例如，一個工具若叫 manage_customer，可以新增、修改、刪除與退款，Agent 很難判斷風險；拆成 read_customer_profile、draft_refund_request、approve_refund，就能給予不同權限與審核條件。

工具設計的第一原則是：讓最小權限成為最容易的路。

3. 路由層：哪種任務交給誰

不是所有工作都該由同一個模型或 Agent 處理。

簡單分類可以交給便宜模型或規則；高風險推理使用更強模型；數值計算交給程式；最新資訊交給搜尋；法律判斷轉交專業人員。

路由層需要根據任務類型、資料敏感性、成本、延遲、信心與風險選擇處理路徑。

若沒有路由，團隊常用最強模型處理所有事情，成本高、速度慢，也不一定更可靠。

4. 輸出層：結果必須長成什麼樣子

自然語言彈性高，系統整合卻需要結構。

Harness 應定義：

- 必填欄位。

- 資料型別。

- 狀態值。

- 來源與信心。

- 錯誤與警告。

- 是否需要人工審查。

- 成果與附件位置。

結構化輸出不是為了讓文字變死板，而是讓下游系統知道如何驗收與分流。

5. 驗證層：怎麼知道做對了

驗證可以分成四類。

語法驗證：格式、欄位、型別、檔案是否存在。

語意驗證：內容是否回答問題、是否完整、是否前後一致。

行為驗證：工具是否真的執行、狀態是否正確改變。

結果驗證：使用者或系統的最終 Outcome 是否達成。

Harness 的重要工作，是把「看起來不錯」轉成可檢查的條件。

6. 權限層：能力不等於許可

模型知道怎麼刪檔，不代表有權刪檔；知道怎麼發信，不代表能代表公司承諾。

權限應依行動影響分級：

- 讀取。

- 建立草稿。

- 修改暫存。

- 提交審查。

- 執行可逆行動。

- 執行不可逆或外部行動。

越高影響的權限，越應有更嚴格身份、條件、日誌與人工核准。

7. 預算與時間層：Agent 不能無限思考

Agent 可能因不確定而持續搜尋、重試、分派子任務。沒有上限的 Agent，不是更努力，而是不可運營。

Harness 應定義：

- 最大步數。

- 最大模型或工具成本。

- 單步與總任務超時。

- 重試次數與退避策略。

- 可平行子任務數。

- 達到上限後的降級與交接方式。

預算是技術規格，也是管理選擇。它迫使團隊說清楚，這個 Outcome 值得花多少資源。

8. 停止與升級層：知道什麼時候不要再做

Agent 的成熟，不只在於能繼續，也在於能停。

應停止或升級的情況包括：

- 正式來源互相衝突。

- 關鍵資料缺少日期或版本。

- 權限不足。

- 驗證連續失敗。

- 成本超限。

- 風險等級提高。

- 需要價值判斷或專業責任。

- 行動不可逆且未核准。

「不知道」若能被正確識別，是可靠性的開始。

9. 版本與學習層：把失敗變成系統改進

Harness 不應只是一份固定提示詞。每次失敗都應被分類：

- 是 Context 缺漏？

- 工具描述不清？

- 驗證規則不足？

- 路由錯誤？

- 模型能力限制？

- 權限或停止條件不合理？

然後把可重複的修正回寫。

如果每次都靠人臨時提醒 Agent，系統沒有學習；如果修正成為工具、規則、測試、文件或評測，下一輪才真正變好。

工具設計：Agent 看見的按鈕，決定它如何理解工作

人類使用軟體時，會從介面與按鈕理解系統。Agent 也一樣，只是它看到的是工具名稱、描述、參數與回傳。

假設有一個工具：

```textsend_email(to, subject, body)```

它看起來很簡單，卻隱藏許多問題：

- 能寄給外部地址嗎？

- 是否需要先建立草稿？

- 收件者含個資時如何處理？

- 寄送前是否檢查附件？

- 是否有品牌簽名與法律聲明？

- 群發時會不會洩露地址？

- 什麼情況需要主管核准？

更安全的工具設計可能拆成：

```textcreate_email_draftvalidate_recipientsscan_sensitive_contentrequest_send_approvalsend_approved_email```

有人會覺得這樣很麻煩，但麻煩不是工具造成的，而是原本工作就包含這些責任，只是以前由人默默補上。

Harness 的價值，就是把隱性責任變成顯性接口。

高訊號回傳：不要把整個世界丟回 Context

工具回傳內容若過長、過亂，Agent 會浪費 Context 重新找重點。

一個測試工具不應只回傳數千行日誌；它可以同時提供：

- 是否通過。

- 失敗測試名稱。

- 最可能相關檔案。

- 精簡錯誤摘要。

- 完整日誌位置。

一個搜尋工具可以提供：

- 來源標題與角色。

- 日期與版本。

- 相關片段。

- 是否為官方或原始來源。

- 完整連結。

工具回傳越高訊號，Agent 越能做下一個正確決策。

這也說明 Harness 與 Context 的關係：Harness 不只決定能用哪些工具，也決定工具如何塑造下一輪 Context。

驗證應靠外部世界，不只靠模型自我感覺

讓同一個模型問自己「你確定嗎？」有時能發現問題，但不能作為主要驗證。

模型可能用更流暢的語言重複原本錯誤，也可能為錯誤結果產生看似合理的解釋。

更可靠的驗證應盡量接到外部訊號：

- 程式測試與編譯結果。

- 資料庫查詢與一致性檢查。

- 文件版本與數位簽章。

- 多來源交叉核對。

- 模擬環境。

- 規則與 schema。

- 人類專業審查。

Reflexion 類研究顯示，Agent 可以把環境回饋轉成文字反思，改善下一次嘗試；但自我反思仍可能產生錯誤歸因，因此需要外部評分與驗證支撐。[R22]

回饋的價值，取決於它是否真的與結果相連。

「更長的提示詞」不是 Harness

當 Agent 表現不穩，團隊常把所有規則都塞進 system prompt。久而久之，提示詞變成數千行混合文件：角色、工具說明、例外、格式、風險、產品知識、版本歷史全在一起。

這種做法有三個問題。

第一，規則難以測試。你不知道哪一段真的有效，哪一段互相衝突。

第二，規則難以維護。工具更新後，舊說明仍留在提示詞中。

第三，規則難以執行。某些限制應由權限與程式保證，不該只靠模型遵守文字。

Harness 應把不同問題放到最適合的層：

- 穩定原則放指令。

- 結構限制放 schema。

- 權限限制放工具與身份系統。

- 數值規則放程式。

- 品質要求放 eval。

- 高風險決策放人工核准。

- 執行狀態放 runtime。

能由系統保證的事情，不要只靠提醒。

Harness 的脆弱性：為今天的模型設計，明天可能變成障礙

Harness 會隨模型能力變化。

早期模型可能需要非常細的步驟分解，較新的模型能處理更高層目標。若仍強迫它走過度僵硬的細節，反而限制表現。

早期模型可能需要大量範例，較新的模型可能只需要清楚規格。過多範例會占用 Context，甚至把舊模式固定下來。

早期模型無法穩定使用複雜工具，團隊可能建立許多中間轉譯；能力提升後，這些轉譯成為新的故障點。

因此，Harness Engineering 不只是加規則，也包含刪規則。

每一次模型、工具或協定升級，都應重新問：

- 這個元件原本補的是哪個能力缺口？

- 缺口還存在嗎？

- 它是否造成延遲、成本或資訊損失？

- 能否用更簡單、可測試的方式取代？

- 移除後的風險能否被 eval 驗證？

好的 Harness 不是最厚，而是剛好足以讓系統可靠工作的最小支架。

一個假設案例：程式 Agent 的 Harness

假設一個 Agent 被要求修正網站錯誤。

沒有 Harness 時，它可能直接讀取錯誤訊息、修改正式檔案，看到頁面能開就宣告完成。

有基本 Harness 後，工作可以變成：

1. 只在新分支修改。

2. 先讀取專案規範與相關測試。

3. 不得改動機密與部署設定。

4. 修改前建立計畫與影響範圍。

5. 完成後執行 lint、test、build。

6. 驗證失敗時最多重試三次。

7. 若需要新增高風險依賴，先停止並請求核准。

8. 最後輸出變更摘要、測試證據、已知限制與回滾方式。

這套 Harness 不保證 Agent 永遠正確，卻把錯誤限制在可觀察、可回滾、可審查的範圍。

真正的價值不只是「它比較不會犯錯」，而是「犯錯時，我們知道錯在哪裡，也知道如何恢復」。

一個假設案例：內容 Agent 的 Harness

內容 Agent 也需要 Harness。

它可能有以下契約：

- 只根據指定正式來源與已公開資料寫作。

- 未確認資訊標示為待查，不得補造。

- 私人行程、健康、家庭與學員個資不得進入公開內容。

- 文章與圖片必須表達同一個核心觀點。

- 生成後先做事實、語氣、重複與敏感內容檢查。

- 發布只能由人核准，不得自行公開。

- 核准後記錄標題、主題、圖片與發布日期，供下一次避免重複。

這些規則若只寫在一句「請謹慎」，幾乎沒有治理作用。要把它們拆成資料存取、內容檢查、發布權限與紀錄回寫，才真正形成 Harness。

Harness Canvas：建立工作契約的十個問題

你可以用以下十個問題快速盤點一個 Agent 的 Harness：

1. 它的任務與完成條件是什麼？

2. 哪些原則永遠優先？

3. 它有哪些工具，每個工具的最小權限是什麼？

4. 哪些工作應交給程式、模型、其他 Agent 或人？

5. 輸出必須有哪些結構與證據？

6. 哪些驗證可以自動執行？

7. 哪些行動需要人工核准？

8. 成本、時間、重試與平行數上限是多少？

9. 哪些情況必須停止、降級或轉交？

10. 失敗後要把哪一項修正回寫到工具、文件、規則或 eval？

若這十個問題都沒有答案，Agent 可能仍能做出精彩展示，但很難成為穩定工作系統。

Harness 的版本化與測試：模型升級之前，先知道工作契約會不會失效

Harness 把模型能力包進一個可工作的契約，但契約不是寫完就固定。模型能力會變、工具介面會變、政策會變、資料會變，連組織對品質的期待也會變。若 Harness 沒有版本與測試，任何一次更新都可能在看似無關的地方造成退步。

先把隱含假設寫出來

每一個 Harness 都對模型做了假設。例如：模型能穩定遵循某種輸出格式、能從工具錯誤中找到原因、能在長 Context 中記住最高優先規則、能判斷何時停止、能正確選擇多個相似工具。

這些假設若沒有被記錄，團隊就會把它們當成自然能力。直到模型更換、任務複雜度增加或輸入分布改變，系統才突然失效。

因此，Harness 文件應明確列出：依賴的模型能力、可接受的失敗率、工具回傳格式、最大步數、必要驗證、人工介入點與已知限制。這不是為了增加文件，而是讓系統能被測試與交接。

建立四類測試

第一類是契約測試。它檢查工具名稱、參數、schema、權限與輸出格式是否符合預期。模型再聰明，也不應被要求猜測已經改名的欄位。

第二類是黃金任務測試。挑選一組代表性任務，保存輸入、必要行動、可接受結果與關鍵證據。每次模型、Prompt、工具或政策改版，都重新執行，確認沒有破壞核心能力。

第三類是負面測試。刻意提供缺資料、衝突資料、越權要求、提示注入、工具失敗與不可逆行動，確認系統會拒絕、停止、降級或升級人工。只測成功情境，無法證明邊界存在。

第四類是長任務測試。檢查 Context 壓縮、checkpoint、重試、交接與成本控制。許多 Harness 在三步內運作良好，到了三十步就開始遺忘目標、重複呼叫或耗盡預算。

工具介面要為 Agent 設計，不只是為人包裝

傳統 API 常把大量欄位一次回傳，假設呼叫者會自行閱讀文件、理解錯誤碼與處理例外。Agent 工具需要更高訊號的契約。

好的工具應有清楚而互斥的用途，避免多個工具名稱相近卻行為重疊；輸入參數應限制範圍，敏感操作必須顯式標示；回傳不只說成功或失敗，也要說明下一步可以採取什麼行動；錯誤訊息要能區分暫時性失敗、權限不足、資料不存在與輸入不合法。

工具也應提供可驗證的結果。例如，建立檔案後回傳路徑、版本與摘要；更新紀錄後回傳變更前後差異；發送前提供預覽與對象清單。如此，Harness 才能在行動後檢查，而不是只能相信工具說「完成」。

權限矩陣應與任務狀態連動

權限不一定在整個任務中固定。研究階段可能只需要讀取公開資料；草稿階段可寫入暫存區；審核通過後才允許寫入正式系統；外部發佈則需要另一個角色核准。

把權限與狀態連動，可以減少 Agent 一開始就持有全部能力。即使模型受到錯誤指示，仍無法直接跨越工作階段。這比在 Prompt 裡寫「請小心」可靠得多。

權限矩陣也要包含時間、金額、對象與頻率限制。例如一天最多發送多少訊息、單筆交易上限、只能聯絡已同意的對象、只能在工作時段執行。這些限制應由確定性系統執行，而不是交給模型自行遵守。

模型升級不是替換一個零件，而是重新驗證整份契約

新模型可能更會推理，卻也可能更主動使用工具；可能更能處理長文，卻改變輸出格式；可能更少犯某類錯誤，卻在另一類邊界上表現不同。不能因為整體能力評測更高，就假設既有 Harness 一定更好。

升級流程應包含平行測試、代表性任務回放、風險情境測試、成本與延遲比較，以及小流量觀察。若新模型需要大量補丁才能維持舊行為，團隊要判斷問題在模型、Harness，還是原本的工作契約過度依賴偶然行為。

避免 Harness 愈補愈厚

每次失敗都加一條指令，最後會形成互相衝突的規則森林。成熟的修正不是永遠增加文字，而是找出責任應該落在哪一層。

若問題是資料缺失，就修正 Context 或資料契約；若問題是工具輸入模糊，就改 schema；若問題可被確定性檢查，就加 validator；若是風險決定，就設人工核准；只有真正需要模型理解的行為，才放進指令。

定期進行 Harness 瘦身，可以刪除已被工具或系統吸收的規則、合併重複指令、移除過時假設，並重新測試最小可行契約。薄並不等於簡陋，而是讓每一條規則都有明確責任。

Harness 是組織工作方法的可執行版本

當一套 Harness 被長期使用，它其實會逐漸承載組織如何定義完成、如何分配權限、如何處理例外與如何留下證據。這些內容不能只存在某位工程師的腦中，也不能只依賴模型供應商的預設。

版本化、測試與變更紀錄，讓 Harness 成為可審核的工作契約。模型可以更新，工具可以替換，但組織仍能知道：這個系統為什麼被允許工作、它承諾什麼，以及哪一次改變讓責任邊界發生了變化。

Harness 變更治理：每一條規則都應有理由、擁有者與退路

Harness 會隨著事故、模型更新與業務需求持續改變。若變更只靠某位工程師直接修改提示詞、工具 schema 或權限設定，系統很快會失去可說明性：大家知道現在能跑，卻不知道為什麼這樣設計，也不知道哪一次改動造成新的行為。

成熟做法可以建立一個輕量的 Harness Change Record。每次重要變更至少記錄：要解決的問題、受影響 Outcome、原始失敗證據、修改哪一層、預期改善、可能副作用、測試案例、核准人、發布範圍與回復方法。

「修改哪一層」尤其重要。若錯誤來自資料版本，就不應只補一句提示詞；若工具參數容易誤用，就應改 schema 或加入確定性驗證；若屬於高影響價值判斷，就應調整 Review Route。變更紀錄迫使團隊先找正確責任層，避免所有問題都堆進指令。

發布可以採四個階段。第一階段在離線資料集回放，確認舊能力沒有明顯退步。第二階段使用影子模式，讓新 Harness 在真實流量上產生結果但不執行。第三階段只開放小範圍或低風險任務，觀察退回率、人工負荷、成本與例外。第四階段才逐步擴大，同時保留可快速回復的舊版本。

回復不是把程式碼退回就結束。若新版本已經建立檔案、寄出通知或寫入狀態，Runtime 還要知道哪些外部影響需要補償。Harness 變更計畫應同時寫清楚「設定回復」與「業務回復」，否則系統版本回去了，真實世界卻還留在錯誤狀態。

不同變更需要不同核准。文案語氣微調可以由內容 owner 決定；工具權限、付款、個資、法規或正式對外行動，則應由相應責任人與安全角色共同核准。不是所有規則都要走同一套官僚程序，而是讓核准強度和影響相稱。

團隊也要防止「緊急修正」永久化。事故發生時，臨時關閉工具或加上限制是合理的；但事後必須回顧：這個補丁是否仍需要？是否造成其他任務退步？能否改由更穩定的資料、工具或驗證機制承擔？沒有期限的臨時規則，往往是 Harness 膨脹的主要來源。

最後，Harness 必須有明確 owner。Owner 不代表獨自決定一切，而是確保版本、測試、變更紀錄與責任路由有人維護。當一套工作契約沒有擁有者，它就會在多次局部修補後變成任何人都不敢刪、也沒有人真正理解的遺留系統。

模型可以被供應商更新，Harness 卻是組織自己的工作方法。對它建立變更治理，不是增加文件負擔，而是保留一條重要能力：知道系統為什麼能被信任，也知道信任失效時如何退回安全位置。

本章收束：Harness 是把能力變成可用責任的橋

模型提供能力，Harness 把能力放進契約。

它決定 Agent 能看到哪些工具、能採取哪些行動、如何輸出、怎麼驗證、何時停止，以及失敗如何成為下一輪改進。

沒有 Harness，模型像一位非常聰明、卻不知道公司規則、工具邊界與交付標準的新同事。

過度 Harness，則像把一位能處理複雜任務的人綁在僵硬腳本裡，讓每一次模型進步都無法發揮。

真正的工程，不是規則越多越好，而是把責任放在最合適的層，並持續用證據刪除多餘支架、補上真實缺口。

下一章，我們要把這份工作契約放進真正的執行現場：Runtime。因為規則寫得再完整，若系統不能保存狀態、處理事件、隔離權限與恢復失敗，Agent 仍然只能在理想世界裡工作。

章末金句

1. 模型能力很強，不代表模型之外的工作契約已經完整。

2. Harness 的工作，是把能力放進可執行、可驗證、可限制的責任結構。

3. 能由系統保證的事情，不要只靠提示詞提醒。

4. 工具是 Agent 看見的按鈕，工具設計會直接塑造它對工作的理解。

5. 最小權限應該是最容易走的路，而不是最後才補上的限制。

6. Agent 的成熟不只在於能繼續，也在於知道何時應該停止。

7. 每一次重複失敗，都應被回寫成工具、規則、文件或評測。

8. 好的 Harness 不是最厚的支架，而是足以讓系統可靠工作的最小支架。
