第 8 章｜看得見才改得動：Tracing、Evals 與可觀測性

最危險的不是失敗，而是不知道怎麼失敗

一個 Agent 交付錯誤結果，團隊通常會問：「它為什麼這樣做？」

如果系統只能看到最後輸出，答案往往只能靠猜。

也許它讀錯文件。

也許搜尋工具回傳過期資料。

也許路由選了不適合的模型。

也許工具呼叫失敗，但 Agent 把錯誤訊息當成正常結果。

也許中途 Context 被壓縮，遺漏重要限制。

也許評分器偏好流暢文字，讓內容看起來完整卻缺少證據。

若看不見過程，就無法把錯誤轉成工程修正。團隊只能不斷調 Prompt、換模型、加人工，卻不知道真正問題在哪裡。

因此，Agent 系統第一個信任條件不是「永遠不錯」，而是「錯了能被看見」。

Tracing、Evals 與 Observability 的工作，就是把不可見的工作變成可分析的訊號。

Log、Trace、Metric 與 Outcome

這四種資訊常被混在一起。

Log：發生了什麼事件

例如：工具呼叫失敗、檔案已建立、使用者已核准、API 回傳 403。

Log 適合保存具體事件與錯誤訊息。

Trace：一次任務如何走過系統

Trace 把模型呼叫、工具呼叫、Agent 交接、規則檢查與狀態變化連成一條執行軌跡。OpenAI Agents SDK 的 tracing 能記錄 generations、tool calls、handoffs、guardrails 與自訂事件，支援開發、除錯與監控。[R05]

Trace 回答：「這個結果是怎麼形成的？」

Metric：系統整體表現如何

例如成功率、平均成本、P95 延遲、人工介入率、重試率、資料品質失敗率、工具錯誤率。

Metric 回答：「這個系統是否正在變好或變壞？」

Outcome：真實結果是否達成

例如預約是否真的成功、客戶問題是否解決、程式是否通過正式測試、報告是否支持決策。

Outcome 回答：「工作真正完成了嗎？」

四者缺一不可。

只有 Log，事件很多卻看不出因果。

只有 Trace，能看見流程卻不知道整體趨勢。

只有 Metric，知道數字異常卻不知道哪一步造成。

只有 Outcome，知道成功或失敗，卻無法定位與改善。

Trace 不是模型的私密思考全文

談到 tracing，有人會以為要保存模型所有內部推理。這既不必要，也不一定可行。

對工作系統真正有用的 Trace，重點是可觀察行為與狀態，例如：

- 收到哪個任務版本。

- 使用哪個模型與設定。

- 取得哪些 Context 來源。

- 選擇哪個工具與參數。

- 工具回傳什麼結構化結果。

- 哪個規則通過或失敗。

- 任務狀態如何改變。

- 是否發生人工核准。

- 最後交付什麼成果。

我們不需要取得模型的隱藏思考，才能知道它用了哪份過期資料或哪個工具回傳錯誤。

這個區分也能降低隱私與安全風險。Trace 應保存足以除錯、稽核與評測的資訊，不應無限制記錄所有敏感內容。

一條好 Trace 應該能回答什麼

一條可用 Trace 至少要回答七個問題。

1. 任務是誰啟動的？

2. 使用哪個目標、版本與成功條件？

3. Agent 看見哪些關鍵 Context？

4. 它做了哪些外部行動？

5. 在哪些節點通過或未通過驗證？

6. 人類在哪裡介入、作出什麼決策？

7. 成果、成本、時間與最終狀態是什麼？

若 Trace 只能告訴你模型輸入與輸出，仍不足以理解整個 Agent Runtime。

OpenTelemetry 對生成式 AI 的語意慣例，嘗試把 invoke_agent、模型 chat 與 execute_tool 等 spans 放進分散式追蹤，讓一個跨服務的 Agent 任務仍能被連接。[R26]

這對企業非常重要，因為錯誤可能不在模型，而在身份服務、資料庫、工具 API、佇列或人工核准介面。

Observability：不只看見，還要能推論系統內部狀態

可觀測性不是把很多日誌放在儀表板。

真正的 observability，是從外部訊號推論系統內部發生什麼。

例如：

- 成功率下降，是模型變差、資料來源改版，還是工具延遲造成？

- 人工介入率上升，是風險增加，還是停止條件設得太敏感？

- 成本增加，是任務變難、重試增加，還是路由錯把簡單任務交給昂貴模型？

- 某類客戶結果變差，是 Context 偏差、規則不公平，還是輸入分布改變？

因此，Agent observability 應同時觀察四個面向。

品質

成功率、準確、完整、引用支持、一次通過率、返工率。

效率

Token、工具成本、延遲、步數、平行度與重試。

風險

權限拒絕、敏感內容、資料品質、未經核准行動、異常路徑。

學習

哪些錯誤被轉成修正、哪個 Harness 版本變好、哪些人工決策仍反覆出現。

若只看品質，系統可能用無限成本取得高分；若只看成本，系統可能變快卻不可信。

Evals：把「感覺不錯」變成可重複測量

Evals 是 Agent 工程中最容易被簡化的詞。

有人把一次人工試用叫 eval，有人用另一個模型打分，有人只看最終答案是否相似。這些都可能有價值，但完整評測需要清楚的單位。

Anthropic 將 Agent eval 拆成 task、trial、grader、transcript／trace、outcome、evaluation harness 與 agent harness，並強調非確定性系統需要多次試驗，而不是只看單次輸出。[R12]

可以這樣理解：

- Task：要評測的任務與環境。

- Trial：同一任務的一次執行。

- Grader：判斷某項條件的評分機制。

- Transcript／Trace：執行過程。

- Outcome：最終環境或成果狀態。

- Evaluation Harness：批次執行、收集與比較評測的系統。

- Agent Harness：Agent 真正工作的工具、規則與 Runtime。

若沒有區分這些元素，團隊很容易拿一個漂亮示範代表整體品質。

為什麼 Agent 需要多次試驗

模型與環境都可能帶有非確定性。

相同任務可能因抽樣、搜尋結果排序、外部 API 狀態、工具延遲與 Context 差異走出不同路徑。

因此，不能只問「這次有沒有成功」，還要問：

- 十次中成功幾次？

- 失敗集中在哪些路徑？

- 成功是否依賴偶然工具結果？

- 平均與最差成本是多少？

- 哪些失敗具有高影響？

- 重新執行是否造成不同副作用？

一個 Agent 可能平均表現很好，卻偶爾做出不可接受行動。這時「平均分數」會掩蓋尾端風險。

高影響系統應看成功分布、最差案例與風險暴露，而不是只看平均。

評測什麼：結果、過程與邊界

Agent eval 至少應有三個層次。

1. 結果評測

最終 Outcome 是否達成。

例如，程式是否通過測試，資料是否正確寫入，報告是否包含必要證據。

2. 過程評測

Agent 是否使用合理路徑。

例如，是否先查正式來源、是否在必要時使用工具、是否避免無效重試、是否正確交接。

過程評測不能要求只有一條正確路徑。Agent 的價值之一就是能動態選擇。因此應檢查必要約束與明顯危險，而不是把它變成僵硬腳本。

3. 邊界評測

是否遵守權限、安全、隱私、成本與人工核准規則。

一個 Agent 即使結果正確，若透過未授權資料或越權工具完成，也不能算合格。

這三層共同避免「只要結果對，過程都可以」的危險想法。

Grader：評分器也需要被評估

評分器可以是程式、規則、模型或人。

確定性 Grader

適合檢查格式、欄位、數值、測試、檔案與狀態。優點是穩定、可重複；缺點是難處理開放語意。

Model Grader

適合檢查完整性、相關性、語氣、論證與風險訊號。優點是彈性；缺點是可能偏誤、受提示影響，也可能把流暢誤認為正確。

Human Grader

適合高層判斷、例外、倫理、策略與專業責任。優點是能理解情境；缺點是成本、速度與一致性。

好的 eval 通常混合三者。

更重要的是，Grader 本身也要校準。可以用人類標註樣本檢查模型評分是否一致，分析不同評分器的分歧，並保留反例。

若評分器獎勵錯誤行為，Agent 會更有效率地學會迎合錯誤指標。

建立一個有用的 Eval Dataset

評測資料不應只包含順利案例。

一個實用資料集需要多種難度與風險：

- 一般成功案例。

- 欄位缺漏。

- 來源衝突。

- 過期版本。

- 工具暫時失敗。

- 權限不足。

- 惡意或誘導輸入。

- 高成本路徑。

- 需要人工決策的例外。

- 看起來合理、實際錯誤的 silent failure。

資料集也要反映真實分布。若正式環境多為模糊、髒亂輸入，測試卻只用乾淨範例，eval 會高估系統。

最有價值的 eval 案例，往往來自真實失敗。每一次重大錯誤都應問：能不能匿名化後加入回歸測試？

這樣，系統不只修正一次，也避免未來版本重犯。

Offline Evals 與 Online Monitoring

離線評測在上線前或版本更新時執行，能快速比較模型、Prompt、工具與 Harness。

線上監測則觀察正式環境，因為真實使用者、資料、工具與時間條件永遠比測試複雜。

兩者不可互相取代。

Offline Evals 適合：

- 回歸測試。

- 模型與版本比較。

- 安全與邊界測試。

- 成本與延遲估算。

- 新工具或新 Harness 驗證。

Online Monitoring 適合：

- 輸入分布改變。

- 資料來源品質下降。

- 工具 API 改版。

- 長期成功率與人工介入趨勢。

- 新型攻擊與例外。

- 真實 Outcome 與使用者回饋。

Palantir 的企業 Agent 文件把 metrics、tracing、logs、execution history 與模擬式 eval 放在同一可觀測層，顯示正式系統需要把離線測試與線上運行連起來。[R28]

從 Trace 到改進：錯誤分類比責怪模型有用

一次失敗可以用以下方式分類。

Goal Error

目標或成功條件不清，Agent 完成了錯誤的事。

Context Error

資料缺漏、過期、衝突或權威順序錯誤。

Tool Error

工具描述、參數、回傳或外部服務失敗。

Planning Error

Agent 選擇不合理路徑、過早停止或無效循環。

Validation Error

檢查規則不足，錯誤結果仍被判定通過。

Permission Error

越權、權限不足或身份錯置。

Handoff Error

交接遺漏狀態、限制或已知風險。

Human Decision Error

人工核准建立在不完整資訊上，或責任人選錯。

這種分類能把「模型很笨」轉成可修正的系統問題。

可觀測性也會帶來風險

記錄愈完整，不代表愈安全。

Trace 可能包含：

- 客戶個資。

- 內部文件內容。

- API 參數與回傳。

- 敏感決策理由。

- 未公開策略。

- 模型輸入中的機密。

因此，可觀測性也需要治理：

- 敏感欄位遮罩。

- 最小化保存。

- 分級存取。

- 保存期限。

- 加密與稽核。

- 不把秘密寫入模型 Context 或一般日誌。

- 對訓練與分析用途另行取得合法依據。

NIST 的 AI 風險管理框架以 GOVERN、MAP、MEASURE、MANAGE 組織全生命週期治理，提醒測量本身必須被治理，而不是單純增加監控。[R17]

監控 Agent，不等於讀懂 Agent 的「心」

更自主的 Agent 需要持續監控風險訊號。OpenAI 對內部 coding agents 的監測經驗，也把分層緩解、風險訊號與持續監控放在重要位置。[R29]

但監控不應被理解成能百分之百知道模型真正意圖。

工程上更實際的做法是監測可觀察行為：

- 是否嘗試存取不需要的資源。

- 是否繞過正常工具。

- 是否隱藏錯誤或宣告未驗證成功。

- 是否反覆嘗試被拒絕的行動。

- 是否出現與任務無關的資料外傳。

- 是否在沒有新證據時改變高影響結論。

系統不必理解所有內在原因，仍能對危險行為設置邊界。

一個假設案例：報告 Agent 的 Eval 設計

假設 Agent 要根據十份文件產生董事會報告。

可建立以下評測：

結果

- 所有必要章節存在。

- 財務數字與原始報表一致。

- 每個重要主張有可追溯來源。

- 風險與未決問題沒有被省略。

過程

- 優先使用正式來源。

- 遇到版本衝突有標示與升級。

- 沒有把衍生摘要當成唯一證據。

- 沒有在來源不足時補造數字。

邊界

- 未讀取不必要的個資。

- 未對外發布。

- 成本與步數未超限。

- 高風險主張已送人工審查。

Robustness

- 對缺漏文件、過期版本、格式變動與工具失敗進行多次試驗。

這樣的 eval 不只評估文字，而是在評估一個工作系統。

一個假設案例：模型升級，系統反而變差

假設團隊更換更強模型後，單次內容品質提高，但整體成本與失敗率反而上升。

Trace 顯示，新模型更願意主動探索，呼叫更多搜尋工具，也更常重寫完整檔案。原本為較弱模型設計的細緻 Harness，與新模型的高層規劃發生衝突，造成重複工作。

若只看最終文字，團隊可能以為問題是「新模型不穩」。透過 Evals 與 Trace，才發現真正問題是舊 Harness 假設已經失效。

修正可能不是退回舊模型，而是：

- 簡化步驟指令。

- 收斂工具回傳。

- 調整探索預算。

- 增加差異修改工具，避免重寫整檔。

- 更新停止條件與回歸測試。

可觀測性讓模型升級不再靠感覺，而能看見系統層的影響。

Evals 應該服務決策，不是製造分數

評測最終要支持決策，例如：

- 這個版本能不能上線？

- 哪種任務可以提高自主性？

- 哪種風險必須保留人工？

- 應選哪個模型與路由？

- 哪一個工具最需要改造？

- 成本增加是否換到足夠品質？

- 哪些錯誤已被修正，哪些仍未知？

若一個分數不能影響任何決策，就可能只是儀表板裝飾。

OpenAI 的 Agent eval 文件將 datasets、graders、traces 與 eval runs 放進持續改善流程，重點正是讓評測形成工程迴路，而不是一次性考試。[R06]

從事故回顧建立 Eval 飛輪

Evals 最有價值的來源，往往不是實驗室裡想像出的題目，而是系統在真實工作中留下的失敗與猶豫。每一次錯誤、人工改寫、升級處理與客訴，都可能成為下一輪評測案例。若這些訊號只停在聊天紀錄或個人記憶裡，組織就會重複支付同一筆學費。

事故回顧要先重建事實

回顧不應從「模型為什麼這麼笨」開始，而應重建時間線：收到什麼輸入、載入哪一版 Context、呼叫哪些工具、工具回傳什麼、在哪一步做出關鍵選擇、何時第一次出現異常、何時被人發現、哪些外部行動已執行。

Trace 能提供過程，但仍要和真實 Outcome、外部系統紀錄與人工決策對照。只看 Agent 自己留下的敘述，可能把錯誤原因誤寫成一個聽起來合理的故事。

用錯誤分類取代責怪

一個實用分類可以包括：

- Goal Error：任務目標或完成條件錯誤。

- Context Error：缺資料、舊資料、衝突資料或錯誤記憶。

- Tool Error：工具選錯、參數錯、外部服務失敗。

- Planning Error：步驟順序不當、過度搜尋、陷入循環。

- Validation Error：沒有檢查、檢查標準太弱或 grader 錯判。

- Permission Error：越權或權限不足。

- Handoff Error：狀態、證據與未解問題沒有交接。

- Human Decision Error：人工核准缺乏資訊、角色不對或受到錯誤介面誘導。

分類不是為了找到唯一責任，而是讓改善落到正確層。Context Error 不應只用更強模型解決；Tool Error 不應只加 Prompt；Human Decision Error 也不能假裝與系統設計無關。

把事故轉成可重放案例

一個好的 eval case 應保存最小必要輸入、關鍵 Context 版本、工具模擬、預期 Outcome、不可接受行為與評分理由。涉及個資與機密時，要去識別化或建立安全測試替代品。

重放案例不是要求每次輸出逐字相同，而是檢查關鍵責任是否維持。例如：是否引用正確版本、是否在資料不足時停止、是否避免越權、是否提供必要證據、是否把例外交給正確的人。

建立黃金案例，也建立邊界案例

黃金案例代表常見且重要的成功路徑；邊界案例則故意測試系統最容易自信犯錯的地方。兩者缺一不可。

若資料集只包含正常輸入，模型升級看起來總是進步；一旦遇到衝突、缺件、提示注入、工具超時或價值判斷，真正風險才出現。邊界案例也應隨事故持續增加，而不是一次建立後永久不變。

Grader 也需要校準

評分器可能偏好長答案、特定措辭或表面格式，也可能無法判斷真實世界結果。團隊應定期抽樣比較 grader 與人類判斷，檢查哪些錯誤被漏掉、哪些正確結果被誤判。

高風險任務可以使用多層評分：確定性規則先檢查 schema、來源、權限與必填欄位；模型 grader 評估語意品質；人類處理爭議與價值判斷。不要讓一個分數承擔所有真相。

Offline Eval 與 Online Monitoring 要形成閉環

離線評測適合比較版本、重放歷史案例與測試失敗邊界；線上監測則能看見真實輸入分布、成本、延遲、人工介入與新型錯誤。

兩者的循環是：線上發現異常，經去識別化後轉成離線案例；離線驗證修正有效，再以小流量上線；上線後持續觀察是否出現副作用。若只做離線測試，資料會逐漸與現實脫節；若只做線上監控，修正又缺乏可重複驗證。

指標要能驅動決策

評測不是為了產生更多分數。每個指標都應對應一個可能行動：低於門檻是否阻止部署？某類錯誤增加是否降低自主性？成本上升是否調整工具與模型？人工介入過多是否代表 Context 或 Harness 有缺口？

若團隊看到指標變差卻不知道該做什麼，這個指標可能只是裝飾。

設定錯誤預算

並非所有失敗都需要立即停止系統。可以依風險設定錯誤預算：低影響格式問題容許一定比例，並排入改善；高影響越權、錯誤付款或不實對外發布則可能採零容忍。一旦超過預算，系統自動降低權限、切換人工或暫停新任務。

錯誤預算讓可靠性與迭代速度可以被討論，而不是在「永遠不能錯」與「先上線再說」之間擺盪。

不需要保存所有內容，仍要保留可追溯性

Trace 可能包含個資、機密與大量模型內容。可觀測性設計應採最小必要原則：保存事件類型、時間、版本、工具、結果摘要與證據指標；敏感內容可遮罩、雜湊或存入受控環境；不同資料有不同保存期限。

可追溯不等於無限制監控。系統應讓人知道哪些資料被記錄、用途是什麼、誰能存取，以及何時刪除。

一個報告 Agent 的 Eval 飛輪

假設報告 Agent 曾把舊數據當成當期資料。事故回顧發現，原因不是模型不會比較日期，而是檢索同時回傳新舊文件，摘要又移除了版本資訊。修正不應只加一句「請使用最新資料」，而要保留 metadata、建立 freshness gate、更新 Context Pack，並把這個案例加入回歸資料集。

下一次模型升級時，團隊可以重放：系統是否仍選到正確版本？若資料日期不明，是否停止？輸出是否標示截止時間？這樣，事故才真正轉成組織能力。

Eval 飛輪的核心不是更頻繁地考模型，而是讓真實失敗能被結構化、重放、修正與驗證。當每一次事故都讓系統多一個可測試的邊界，可靠性才不是運氣，而是累積出來的資產。

可觀測性架構：在看得見、付得起與守得住之間取捨

Trace 愈完整，除錯與追溯通常愈容易；但保存所有提示、文件、工具回傳與中間推論，會迅速帶來成本、隱私與權限問題。可觀測性不是把一切留下來，而是設計一個足以回答重要問題、又不超出責任範圍的訊號系統。

可以先把事件分成四層。第一層是營運事件：開始、結束、延遲、重試、成本與錯誤碼。第二層是決策事件：選了哪個路由、為何停止、哪條 Guardrail 觸發。第三層是證據事件：使用哪些來源、版本與判定。第四層是內容事件：實際輸入、輸出與工具內容。層級愈高，診斷價值可能愈大，敏感性也愈高。

不是每個任務都要保存第四層。低風險大量工作，可以保留結構化事件與抽樣內容；高影響決策則可能需要完整證據包，但應進入受控儲存，限制存取並設定期限。分層讓團隊不必在「完全看不見」與「永久保存所有內容」之間二選一。

採樣策略也要有目的。一般流量可以按比例採樣，所有錯誤、越權、人工介入與低信心案例則全量保留；新模型、新 Harness 或新資料源上線期間提高採樣；穩定後再降低。採樣不是偷懶，而是把有限儲存與審查能力用在高訊號區域。

敏感資料應在靠近來源的地方處理。能以事件類型、雜湊、遮罩欄位或摘要完成診斷，就不要把原始個資送進中央日誌。需要完整內容時，要記錄誰能讀取、用途、保存多久與如何刪除。可觀測性若沒有存取治理，本身就會成為新的資料風險。

成本也要被觀測。某次任務可能在模型上花費不高，卻產生大量 trace、長期儲存與查詢費用；或為了追蹤每一步，引入明顯延遲。團隊應把可觀測性成本和事故價值一起評估，保留真正能支援決策的訊號，刪除沒有人使用、也無法觸發行動的紀錄。

Dashboard 不應只顯示平均值。平均延遲可能很正常，但少數高影響任務已經嚴重超時；總錯誤率很低，卻集中在某一類使用者或某一個工具。分位數、任務類型、風險層級與版本切片，往往比一個整體數字更能看見真實問題。

每一個指標都應有「看見後做什麼」的答案。若人工介入率上升，誰調查？若某工具錯誤增加，是否自動降級？若證據缺失，能否阻止發布？如果一個 Dashboard 沒有 owner、門檻與處置路由，它只是漂亮的牆面，不是控制系統。

可觀測性最終服務的是人的注意力。它不要求人監看所有 Agent，而是讓少數重要偏差能被提早看見，讓事故能被重建，讓版本能被比較，也讓組織知道哪些資料不應被無限保存。看得見是一種能力，知道不該看什麼、何時刪除，同樣是一種治理能力。

本章收束：看見不是為了監控一切，而是把注意力放對地方

Agent 系統不可能零錯誤。

真正的分水嶺是：錯誤是否可見、可分類、可重現、可限制，並能轉成下一輪改進。

Tracing 讓我們看見一次任務如何形成。

Metrics 讓我們看見系統長期趨勢。

Evals 讓我們在版本與設計之間做可重複比較。

Outcome 讓所有測量回到真實工作結果。

人的工作不是閱讀每一條 Trace，而是設計正確訊號、看見例外、調整邊界，並確保評測沒有把錯誤目標變成更精密的自動化。

下一章，我們要深入一種特別危險的失敗：資料本身帶著模型看不見的缺陷。若 Agent 在行動前沒有資料品質閘門，再好的推理也可能建立在錯誤世界上。

章末金句

1. 最危險的不是 Agent 失敗，而是失敗之後只能靠猜。

2. Trace 告訴你結果如何形成，Metric 告訴你系統如何變化，Outcome 告訴你工作是否真的完成。

3. 可觀測性不是保存更多日誌，而是能從訊號推論系統內部狀態。

4. Agent eval 不能只看一次漂亮輸出，必須看多次試驗、執行軌跡與最終環境狀態。

5. 評分器也會犯錯；錯誤指標會訓練出更會迎合錯誤的系統。

6. 每一次真實失敗，都應該有機會成為下一版的回歸測試。

7. 監控不是讀懂模型的心，而是對可觀察的危險行為建立邊界。

8. 看見不是為了監控一切，而是把人的注意力放到真正需要判斷的地方。
