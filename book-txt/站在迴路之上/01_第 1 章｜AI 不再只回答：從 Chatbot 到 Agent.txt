第 1 章｜AI 不再只回答：從 Chatbot 到 Agent

真正改變的，是動詞

生成式 AI 剛走進大眾生活時，我們最常用的動詞是「問」。

問它一段文字怎麼改，問它一個觀念怎麼解釋，問它能不能整理會議紀錄、寫一篇貼文、做一張圖片。這些應用讓很多人第一次感受到，語言不只是表達，也可以成為操作電腦的新介面。

但從 Chatbot 走向 Agent，真正改變的不是模型名稱，而是動詞。

我們開始不只「問」，而是「交辦」。

不是請 AI 告訴我如何整理報告，而是請它找到相關檔案、確認版本、整理證據、建立報告、檢查格式並交付。

不是請 AI 建議網站怎麼修改，而是讓它讀取程式碼、定位問題、修改檔案、執行測試、看錯誤訊息，再根據結果修正。

不是請 AI 幫忙想一個研究方向，而是讓它拆解問題、搜尋來源、比較觀點、追蹤缺口、分派子任務，再把結果整合回來。

Chatbot 的核心是語言回應；Agent 的核心是目標導向的行動。

這個差別看起來只多了一個「做」，實際上卻把 AI 從內容層推進到工作層。

Chatbot、Copilot、Workflow 與 Agent

很多產品都會使用 Agent 這個名稱，但名稱本身不足以判斷系統真正的自主程度。比較實用的做法，是先看人與系統如何分工。

Chatbot 主要接收訊息並回應。它可以寫得很好、推理得很深，甚至在對話中使用搜尋或程式工具，但工作通常仍以一輪或幾輪回覆為中心。

Copilot 是副駕。人掌握主要流程，AI 在局部步驟提供建議、補全、檢查或產出。它可能很強，卻不一定負責決定下一步。

Workflow 是工作流。系統事先安排好步驟，例如先分類，再查資料，再生成，再驗證。模型可以參與每個節點，但整體路徑主要由程式決定。

Agent 則在一定邊界內，根據目標、當前狀態與工具結果，動態決定下一步。它可以規劃、行動、觀察結果、改變策略，直到完成、失敗、超時或遇到需要人類決策的情況。

Anthropic 的工程文件特別提醒，workflows 與 agents 應被分開理解：前者依照預先定義的程式路徑編排模型與工具，後者讓模型動態決定流程與工具使用；實務上應從最簡單可行的方法開始，只有在任務需要時才增加代理自主性。[R09]

這個提醒非常重要，因為「看起來很 Agent」不一定比較好。

假設一個公司每天要把固定格式的訂單匯入系統、檢查欄位、產生確認信。若規則穩定、例外很少，一套明確工作流可能比自由規劃的 Agent 更便宜、更容易測試，也更容易追責。

相反地，若任務是研究一個全新市場，資料來源不確定、問題會隨發現而改變，固定工作流可能太僵硬，Agent 才有價值。

所以，選擇 Agent 的理由不應是「這個詞比較新」，而是任務本身具有足夠的不確定性，需要系統根據環境動態調整。

Agent 的基本循環

若把不同產品的介面拿掉，Agent 常可被理解為一個循環：

```text接收目標→ 讀取當前脈絡→ 選擇下一個行動→ 呼叫工具或產生內容→ 觀察結果→ 更新狀態→ 判斷繼續、重試、改路、交接或停止```

ReAct 研究早期就把推理與行動交錯，讓模型不只在內部推演，而能根據外部觀察更新後續步驟。[R20] Toolformer 探索了模型如何決定何時使用 API、帶入參數，再把工具結果納回後續處理。[R21] 後來的 Agent SDK 與工程框架，則把工具、交接、session、人工介入與 tracing 逐漸整合為可運行的系統元件。[R03]

這裡最重要的不是歷史名詞，而是理解：Agent 不等於一個模型。

一個能工作的 Agent 至少同時依賴：

- 模型：理解、推理、產生選擇。

- 目標：知道什麼結果才算完成。

- Context：知道此刻相關的資訊與狀態。

- Tools：能對外部世界產生影響。

- Runtime：讓行動真正執行、保存與恢復。

- Rules：限制權限、成本、時間與風險。

- Feedback：讓系統知道行動是否有效。

- Human：處理例外、核准高風險行動並承擔責任。

只把模型接上兩個工具，並不會自動得到可靠 Agent。那只是把語言模型放到更接近真實世界的位置，也同時放大了它做對與做錯的影響。

會使用工具，和會完成工作，是兩件事

很多 Agent 示範令人驚豔：它能開瀏覽器、操作試算表、執行程式、寄出郵件、建立檔案。可是「會呼叫工具」只是能力，不是成果。

要完成一份可交付的工作，至少還要回答五個問題。

第一，它是否理解真正的完成條件？

「幫我整理資料」可能只需要一份摘要，也可能需要可追溯來源、欄位完整、版本正確、格式可匯入的正式交付。若完成條件沒有被說清楚，Agent 很容易在看起來合理的地方提早停止。

第二，它是否使用正確的資料？

搜尋到一份文件，不代表那是最新版；資料庫有一筆紀錄，不代表仍然有效；兩個來源內容一致，也不代表它們不是從同一個錯誤來源複製而來。

第三，它是否有適當權限？

能讀不代表能改，能改不代表能刪，能建立草稿不代表能公開發布。Agent 的便利往往來自權限，而最大的風險也常來自權限。

第四，它是否知道什麼情況應該停止？

如果付款資料不一致、合約版本衝突、來源缺少日期、成本超過預算，可靠系統應該停止或升級，而不是「盡力完成」。

第五，它的結果能否被驗證？

若只能看到最後一段漂亮文字，卻不知道它使用哪些資料、呼叫哪些工具、在哪一步改變策略，錯誤就很難被發現，更難被修正。

因此，我們不能用「工具呼叫成功」來代表「工作完成」。

工具呼叫只是動作；工作完成需要結果、證據與責任。

自主性不是一個開關

人們常把 Agent 分成「自主」與「不自主」，彷彿只要打開某個開關，AI 就能自己工作。實際上，自主性更像一組可分配的權限。

系統可以被允許自主選擇資料來源，但不能自主公開結果。

可以自主重試測試，但不能自主提高預算。

可以自主修改暫存分支，但不能直接部署正式環境。

可以自主建立採購建議，但必須由人核准付款。

可以自主回覆常見問題，但遇到法律、醫療、財務或個資情境時必須轉交。

這表示設計 Agent 時，真正要問的不是「要不要自主」，而是：

在哪一個範圍、哪一種行動、哪一個風險層級，允許它自主到什麼程度？

我會把自主性拆成六個面向：

1. 目標自主：能否自行重寫或選擇子目標。

2. 規劃自主：能否決定步驟與順序。

3. 資料自主：能否自行搜尋、選擇與捨棄來源。

4. 工具自主：能否選擇並呼叫外部工具。

5. 影響自主：能否對真實世界做不可逆行動。

6. 停止自主：能否自行判定完成、失敗或轉交。

低風險任務可能在前四項給予高度自由，卻仍限制第五項。高影響任務則可能連資料選擇都必須受規則約束。

這樣看，Human-in-the-Loop 也不是簡單地「每一步都要人按確認」。真正合理的設計，是把人放在影響最大、證據最不完整、例外最難規則化的位置。

能力、可靠、責任與價值

Agent 時代最容易混淆四個層次。

能力回答：它能不能做？

可靠回答：它能不能在不同情境下穩定做對？

責任回答：它做錯時，誰能看見、介入與承擔？

價值回答：這件事是否值得做，是否符合組織與人的目的？

一個系統可能很有能力，卻不可靠。它可以在十次中完成八次，但兩次失敗會造成重大損失。

它也可能可靠，卻沒有清楚責任。流程穩定執行，但沒有人負責監看資料是否偏移、權限是否過期、規則是否仍合適。

它甚至可能可靠又可追責，卻做了錯誤的事。比如系統非常有效率地提高點擊率，卻犧牲使用者信任；非常準確地篩掉「高風險」申請者，卻延續不公平的歷史模式。

因此，模型能力提升不會自動完成後面三層。

這也是本書不把重點放在「哪個 Agent 最強」的原因。真正長期有價值的問題，是如何把能力放進可靠、責任與價值的結構裡。

一個假設案例：從會寫報告到能交付報告

假設一位專案經理每週要製作進度報告。

在 Chatbot 階段，他把各部門訊息貼進對話，請 AI 摘要。結果很快，但每週都要重新收集、複製與校正。

在 Copilot 階段，AI 進入文件工具，協助補寫段落、統一格式與整理表格。人仍負責找資料與判斷狀態。

在 Workflow 階段，系統固定讀取任務看板、會議紀錄與風險表，依模板產生草稿，再執行欄位檢查。

在 Agent 階段，系統可以發現某項任務狀態衝突，回頭查詢原始紀錄，要求相關責任人補充，或把無法判定的項目標示為待確認。

可是，若沒有進一步設計，它仍可能犯錯：

- 把測試環境的完成狀態當成正式上線。

- 使用過期風險表。

- 將沒有來源的推測寫成確定事實。

- 看到資料缺漏時自行補出合理數字。

- 在主管審核前就把報告寄給外部客戶。

要讓這個 Agent 真正可用，還需要 Context 版本、權限、資料來源優先序、驗證規則、人工核准點、執行紀錄與回寫機制。

也就是說，真正的升級不是從「AI 幫忙寫」跳到「AI 自己寫」。

真正的升級是從一次生成，走向一套可以說明、可以停止、可以驗收、可以持續改進的工作系統。

Agent 對工作的真正衝擊

Agent 最深的影響，不只是把某些步驟自動化，而是改變工作的最小單位。

過去，我們常把工作拆成人的行為：打電話、填表、整理檔案、寫信、更新系統。

未來，工作會更多地被描述成結果：完成客訴處理、完成候選供應商評估、完成一份可發布的研究報告、把一個功能從需求推到通過測試。

當結果成為交付單位，人類的價值也不再只看「親自做了多少步」，而會看：

- 能不能定義好結果。

- 能不能設計必要的脈絡與工具。

- 能不能辨認風險與例外。

- 能不能建立驗證與回饋。

- 能不能讓不同的人與 Agent 接手。

- 能不能對最終影響負責。

這不是說執行不重要。執行永遠重要，只是執行開始被重新分配。

有些動作交給程式，有些判斷交給模型，有些例外交給人，有些高風險決策保留給正式責任人。工作的設計能力，會逐漸成為新的基本能力。

從功能採購到責任設計：Agent 導入前必須說清楚的四件事

很多組織第一次接觸 Agent，會從功能清單開始：能不能上網？能不能讀檔？能不能寄信？能不能修改系統？能不能自己規劃？這些問題都重要，卻不是最先該回答的問題。功能只能描述它「可能做什麼」，不能說明它「為什麼被允許做、做到哪裡、錯了誰負責」。

真正成熟的導入，應該先完成四場對話。

第一場對話：誰擁有這個 Outcome

每一個 Agent 都應該有一個真實世界的結果負責人。這個人不一定是工程師，也不一定是提出需求的人，而是能回答以下問題的人：

- 這項工作真正要改善什麼？

- 什麼狀態才算完成？

- 哪些結果即使看起來漂亮，也不能接受？

- 當速度、品質、成本與風險衝突時，優先順序是什麼？

沒有 Outcome Owner，Agent 最容易被要求「盡量做得好」。這句話對展示很方便，對正式工作卻極度危險。因為「好」可能代表更完整、更快速、更便宜、更有創意，也可能代表更保守、更準確、更符合規範。若沒有一個能為取捨負責的人，系統就只能把價值判斷偷偷交給模型。

第二場對話：它要在哪一個環境中行動

相同的模型，放進不同環境，會成為完全不同的 Agent。讀取公開網頁與讀取客戶資料，不是同一種工作；產生草稿與直接更新正式資料庫，也不是同一種權限。

因此，導入前要先畫出「影響半徑」：

第一圈是可讀資訊。Agent 看得到哪些資料？哪些只能看摘要？哪些必須經過去識別化？

第二圈是可寫範圍。它能建立草稿、寫入暫存區、修改測試資料，還是可以改動正式系統？

第三圈是外部影響。它能不能寄出訊息、建立訂單、發佈內容、移動金錢、改變權限，或對外代表組織？

第四圈是連鎖效應。一次錯誤只影響一份文件，還是會觸發後續自動化、通知大量人員、產生法律或財務後果？

影響半徑愈大，自主性就不應該只用「開或關」表示，而要用權限、金額、時間、資料類型、對象與可逆性逐項分配。

第三場對話：哪些決定必須留在人手上

人類介入點不應只放在流程最後。若前面的資料來源、工具選擇或任務解讀已經偏離，最後再按一次同意，往往只是替錯誤蓋章。

比較好的做法，是先辨識三種不可輕易外包的決定。

第一種是價值決定。例如是否值得聯絡某個人、是否應該拒絕一項申請、是否要犧牲少數人的便利換取整體效率。這些問題不是資料愈多就自然有答案。

第二種是不可逆決定。只要行動難以撤回、會造成重大外部影響，或需要由特定角色依法承擔責任，就應保留明確核准。

第三種是爭議決定。當資料彼此衝突、規則無法涵蓋、不同利害關係人有合理但相反的主張時，模型可以整理證據，卻不能取代制度化的裁決。

第四場對話：失敗時誰接手

Agent 系統最常被忽略的，不是成功路徑，而是失敗後的接手路徑。系統應事先知道：工具無法使用時要不要等待？資料過期時要向誰索取？連續重試幾次後要停止？超出預算時誰能延長？遇到敏感內容要交給哪個角色？

一個沒有接手設計的 Agent，看起來很自主，實際上只是把例外堆到某個無人看見的角落。真正的自主，不是永遠不求助，而是知道何時求助、向誰求助，並把已完成的工作、目前狀態、風險與下一步清楚交接。

自主性也需要預算

我們可以把自主性理解成一種有限資源，而不是愈多愈先進。每一項自主權都會換來速度，同時帶來新的失敗模式。組織應為不同任務設定「自主性預算」：

- 低影響、可逆、可自動驗證的工作，可以給更高自主性。

- 高影響但規則明確的工作，可以讓 Agent 準備完整行動包，再由人核准。

- 高度模糊、涉及價值衝突的工作，Agent 適合整理選項與證據，而不適合獨立做最後決定。

- 一旦系統累積足夠 trace、eval 與真實結果，才逐步擴大權限，不應先把權限全開再等待事故教訓。

假設有一個採購 Agent。它可以搜尋供應商、整理報價、檢查規格、產生比較表，甚至根據既定門檻提出建議。但是否直接下單，要看金額、供應商風險、合約條款與可撤回性。若金額很小、品項標準化、供應商已核准，系統可以自動完成；若涉及新供應商、長期合約或個資處理，就應把證據與風險送到正確的人，而不是只在最後跳出一個「是否同意」。

這就是從功能採購走向責任設計。你不是先問 Agent 能做多少，而是先決定哪些結果值得交付、哪些權力可以分配、哪些證據必須留下，以及哪一個人會在系統做錯時真正接住它。只有完成這些設計，Agent 才從有趣的功能變成可以進入工作的角色。

用三軸決定自主性：影響、可逆性與不確定性

「這個 Agent 可以自動做到哪裡？」通常不是一個功能問題，而是一個風險配置問題。只用任務類型分類不夠，因為同一個動作在不同情境中的後果可能完全不同。寄出一封草稿給自己，和代表公司寄出正式承諾，技術動作相似，責任重量卻差很多。

比較實用的做法，是用三個軸一起判斷。

影響回答：做錯一次，會影響多少人、多少金額、多少權利，或多長時間？影響不只看直接損失，也包括信任、法規、品牌與後續補救成本。

可逆性回答：錯誤發生後，能否迅速恢復？草稿可以刪除，錯誤分類可以重算；已匯款、已公開、已通知大量對象或已改變個人權益的行動，通常比較難完全撤回。

不確定性回答：系統是否擁有足夠規則、資料與可驗證條件？任務看似簡單，若依賴模糊語意、快速變動政策、未結構化資料或多方利益判斷，不確定性仍然很高。

三軸交叉後，可以形成四種授權方式。低影響、可逆、低不確定的工作，適合直接執行並事後抽查。低影響但高不確定的工作，適合讓 Agent 探索、提出假設，卻不要把猜測寫回正式系統。高影響但低不確定的工作，可以採「準備完成、等待核准」：Agent 蒐集資料、跑完檢查、形成行動包，人只負責最後決定。高影響、高不確定的工作，則應讓 Agent 成為分析與證據助手，而不是決策主體。

這個判斷還要再加入暴露量。單次可逆的小錯，若每分鐘執行一萬次，總風險仍可能很高。因此，初次導入不應立刻開放全部流量，而要從影子模式開始：Agent 做出決定但不執行，先和人工結果比較；接著只開放小範圍、低金額、內部使用；通過真實資料與事故回顧後，再逐步擴大。

授權也不應永久固定。系統的自主性可以像信用額度一樣，根據證據升降。當錯誤率、例外量、資料品質或人工撤回率超出門檻，權限自動收縮；當長期結果穩定、可觀測性完整、回復流程經過演練，才擴大可執行範圍。

這樣做的好處，是組織不必在「全部自動」與「完全不敢用」之間選邊。自主性被拆成可以討論、測試與回收的授權。真正成熟的 Agent 導入，不是一次宣布它成為數位員工，而是讓每一項權力都有取得條件、使用證據與撤回機制。

最後，三軸仍不能取代價值判斷。某些行動即使容易撤回，也可能傷害尊嚴或公平；某些決定即使規則明確，也可能依法或依治理原則必須由人負責。矩陣的用途是幫助看見風險，不是替組織逃避責任。

本章收束：不要急著問 Agent 能做多少

當我們第一次看到 Agent 能自己操作工具，很容易立刻想像一個「全自動」未來。

但更成熟的問題應該是：

它正在完成哪一個結果？

它依據什麼脈絡？

它能使用哪些工具？

它怎麼知道做對了？

它在什麼情況下會停止？

誰能看見它的過程？

誰在最後負責？

這些問題會把我們從功能展示帶到系統設計。

下一章，我們要再往前一步：當 AI 不再只完成一個小任務，而開始承接整段 Workflow，甚至被要求對 Outcome 負責時，工作的邊界會怎麼改變？

章末金句

1. 從 Chatbot 到 Agent，真正改變的不是介面，而是動詞：從問問題走向交辦工作。

2. 會呼叫工具是能力，能交付可驗收結果才是工作。

3. 自主性不是一個開關，而是一組必須逐項分配的權限。

4. 能力不等於可靠，可靠不等於可負責，可負責也不代表值得做。

5. Agent 不只會放大效率，也會放大組織原本沒有說清楚的模糊。

6. 選擇 Agent 的理由不是它比較新，而是任務真的需要根據環境動態調整。

7. 真正的升級，不是 AI 自己寫完，而是整個工作能被說明、停止、驗收與改善。

8. 當執行開始被重新分配，工作設計就會成為新的基本能力。
