第 2 章｜從 Task 到 Workflow，再到 Outcome

把一個動作交給 AI，和把一個結果交給 AI

請 AI 寫一封信，是一個 Task。

請 AI 讀取客戶問題、查找訂單、判斷原因、草擬回覆、必要時建立退款申請，再把需要人工決策的部分送給主管，這已經是一段 Workflow。

請系統把「客訴被正確處理，客戶得到清楚回覆，金流與庫存同步，風險個案被升級，處理紀錄可追查」作為完成條件，則開始接近 Outcome。

這三者的差別，不只在步驟多少，而在責任範圍。

Task 把一個動作交出去。

Workflow 把一段流程交出去。

Outcome 則要求系統對一個可驗收的結果負責到某個邊界。

很多 AI 導入卡住，正是因為組織口頭上想要 Outcome，實際上只提供了幾個零散 Task 的提示詞。

主管說：「我們要用 AI 提升客服效率。」

團隊做出自動摘要、自動回信與知識庫問答。每一個功能都能展示，卻沒有回答：客訴是否真的縮短處理時間？錯誤承諾是否增加？需要重複聯繫的比例是否下降？高風險個案是否更快被升級？

做了很多功能，不等於完成一個結果。

Task：最容易自動化，也最容易高估

Task 的優點是邊界清楚。

輸入一段內容，輸出一份摘要；讀取一張發票，抽取欄位；根據模板，產生一封信。這些任務容易測試，也容易比較人工與 AI 的速度。

因此，Task 是導入 AI 的好起點。

問題是，單一 Task 的效率提升，未必會轉化成整體工作的效率提升。

假設原本製作報告需要四小時，其中寫摘要只占二十分鐘。AI 把摘要縮短到兩分鐘，看起來快了十倍，但整體工作可能只節省十八分鐘。若資料收集、版本確認、主管等待與格式返工仍然不變，真正的瓶頸沒有移動。

更常見的情況是，AI 讓上游產出變快，卻把更多檢查負擔推到下游。

以前一天產生十份草稿，編輯能仔細檢查；現在一天產生一百份，表面產能提高，實際上審核變成新的堵塞點。若組織只看「生成量」，就可能把擁塞誤認為生產力。

Task 自動化最適合處理三種情況：

1. 輸入與輸出相對清楚。

2. 錯誤容易被發現、可逆且成本低。

3. 成功可以用明確規則或樣本檢查。

當任務涉及多個系統、長時間狀態、例外處理與責任交接時，就不能只用 Task 思維。

Workflow：工作的真正形狀開始出現

Workflow 不是把很多 Task 排成一列而已。

一段能運作的工作流，至少要處理：

- 先做什麼、後做什麼。

- 哪些步驟可以平行。

- 哪些資料是共同基準。

- 哪些條件會改變路徑。

- 哪些錯誤可以重試。

- 哪些例外必須升級。

- 哪個狀態代表完成。

- 中途失敗後從哪裡恢復。

Anthropic 將 prompt chaining、routing、parallelization、orchestrator-workers 與 evaluator-optimizer 等模式整理為不同工作流圖樣，目的不是鼓勵所有系統都變複雜，而是讓架構與任務的真實需要對齊。[R09]

例如，一份研究報告可能包含：

```text定義問題→ 建立研究子題→ 搜集多類來源→ 來源去重與分級→ 建立主張清單→ 配對證據→ 撰寫草稿→ 反例檢查→ 事實與引用審核→ 形成正式版本```

其中某些步驟適合平行進行，某些必須等前一步完成；某些可以由固定程式處理，某些需要模型判斷；某些結果不合格可以自動重做，某些衝突需要人決定。

Workflow 的價值，是把原本只存在熟練工作者腦中的做法，轉成可以被看見、被分工、被測試的結構。

但這裡也有一個陷阱：流程畫得很完整，不代表結果就會好。

若目標本身錯了，流程只會更穩定地做錯事。

若驗收條件只檢查格式，系統就可能交付格式完美、內容空洞的成果。

若每個步驟都通過，卻沒有人檢查跨步驟的一致性，局部正確仍可能組成整體錯誤。

因此，Workflow 還需要一個更高的方向：Outcome。

Outcome：先定義「什麼改變才算完成」

Outcome 不是「輸出一個檔案」。

檔案只是 Artifact，成果物。Outcome 是這份成果物在真實工作中要造成的可驗收改變。

一份招募報告的 Artifact 是 PDF；Outcome 可能是決策者能在限定時間內比較候選人、理解風險、追溯證據，並作出符合規則的選擇。

一個預約系統的 Artifact 是網站與資料庫；Outcome 是使用者能成功預約、避免衝突、收到確認、能改期或取消，而管理者可以看到正確狀態。

一個內容 Agent 的 Artifact 是貼文；Outcome 可能是內容符合品牌定位、沒有虛構事實、能被人工審核、在核准後進入發布流程，並把成效與修正回寫到內容系統。

因此，Outcome 必須包含至少四種條件：

1. 結果條件：真正要達成什麼。

2. 品質條件：做到什麼程度才算合格。

3. 邊界條件：哪些不能被犧牲或越過。

4. 證據條件：如何證明已經達成。

我把這種定義稱為「成果合約」或 Outcome Contract。它不是法律合約，而是一份讓人、Agent 與系統對齊的工作規格。

一份可用的 Outcome Contract

一份簡潔但有效的成果合約，可以回答八個問題。

1. 目標是什麼？

不要只寫「完成市場研究」，而要說明這份研究要支持哪一個決策。沒有決策用途，研究很容易變成資料堆積。

2. 誰是使用者？

同一份內容給技術主管、財務主管與一般客戶，深度、格式與證據要求都不同。

3. 什麼算完成？

完成不應只由 Agent 自己宣告。需要可觀察狀態，例如必要欄位齊全、測試通過、引用可開啟、責任人核准、成果已寫入正式位置。

4. 有哪些禁止條件？

例如不得改動原始檔、不得使用未授權資料、不得直接寄出、不得揭露個資、不得在來源衝突時自行猜測。

5. 需要哪些證據？

例如每一項財務主張要對應原始報表與日期；每一個程式變更要有測試結果；每一個公開資訊要有可查證來源。

6. 何時必須停下？

當成本超過上限、資料過期、權限不足、來源衝突、測試失敗、風險等級升高時，系統應該停止、降級或轉交。

7. 誰能核准？

不是所有人工確認都一樣。內容編輯可以核准文案，不代表能核准法律承諾；財務人員可以確認金額，不代表能核准品牌聲明。

8. 結果要寫回哪裡？

若完成後只留在聊天紀錄，下一次任務仍會從舊狀態開始。Outcome 必須包含正式成果位置與狀態回寫。

從步驟管理，走向狀態管理

人類工作常以活動描述：「我寄了信」、「我開了會」、「我做了報告」。

Agent 系統更需要以狀態描述：「資料已驗證」、「風險待核准」、「草稿通過內容檢查但未通過法務」、「部署已完成且監控正常」。

活動只告訴你做過什麼，狀態才告訴你現在能不能往下走。

這也是為什麼長任務不能只靠一串對話。當任務可能中斷、跨人員、跨 Agent 或跨系統，就需要明確狀態，例如：

```textreceived→ scoped→ context_ready→ executing→ validation_failed→ awaiting_human→ approved→ delivered→ written_back```

每個狀態都應定義：

- 進入條件。

- 可執行行動。

- 責任角色。

- 離開條件。

- 失敗與恢復路徑。

這樣，Agent 不必靠猜測理解「接下來怎麼辦」，人也不必每次重新翻聊天紀錄找進度。

Handoff：交接不是把文字貼給下一個人

從 Task 走向 Workflow，交接會變得愈來愈重要。

一個 Agent 搜集資料，另一個 Agent 寫作，第三個 Agent 查證；或一個人定義需求，Agent 執行，主管核准，工程團隊部署。每一次交接，都可能丟失脈絡。

低品質交接通常只有一句：「前面已經處理好了，請接著完成。」

高品質交接則至少包含：

- 已完成什麼。

- 使用哪些正式來源。

- 已做哪些決策。

- 哪些項目被排除，以及原因。

- 目前狀態與成果位置。

- 已知風險與未決問題。

- 下一個責任人的任務與完成條件。

- 哪些內容不可重做或覆寫。

交接的目的不是讓下一個節點知道更多，而是讓它不必重新猜測。

在多 Agent 系統中，獨立 Context 可以降低資訊污染，卻也會增加協調與壓縮成本。Anthropic 的多 Agent 研究系統採用 orchestrator-worker 與平行子 Agent，顯示這種架構在開放式研究中有價值，但也需要更精細的任務分工、結果整合與成本控制。[R13]

多 Agent 不是把同一件事丟給更多模型，而是把責任邊界與交接設計得更清楚。

Task、Workflow、Function 與 Department

近年的產業敘事常把 AI 能力演進說成：從完成單一任務，到承擔工作流，再到承擔一種企業職能，甚至形成「AI 部門」。這種說法很有啟發性，但也容易過度擬人化。

一個 Agent 系統可以承擔客服分類、回覆草擬、資料查詢與流程更新，不代表它真的成為客服部門。

部門除了產出，還包含：

- 對外與對內承諾。

- 人員培養與知識傳承。

- 例外協商。

- 法規與倫理責任。

- 預算與資源取捨。

- 跨部門政治與信任。

- 長期策略與文化。

因此，比較準確的說法是：AI 可以承擔某些職能中的可定義工作包，並逐步擴大其責任邊界；但組織責任仍需要由正式角色承擔。

這個區分非常重要。

若我們把 Agent 叫做「AI 員工」，很容易忘記它沒有法律人格、職業倫理、組織忠誠或真正的責任感。它能模擬回覆，卻不能承擔後果；能執行規則，卻不會因為規則不公而自發承擔道德責任。

所以，當 Agent 從 Task 走向 Workflow，人類責任不是減少，而是從操作責任轉向系統責任。

自動化邊界應由不確定性與影響決定

要決定一段工作能不能交給 Agent，可以用兩個軸來看：不確定性與影響。

低不確定、低影響

例如整理格式、分類一般文件、建立草稿。適合高度自動化，重點是效率與基本驗證。

高不確定、低影響

例如探索創意方向、蒐集初步資料。可以讓 Agent 自由嘗試，但成果應標示為候選，不直接成為正式決策。

低不確定、高影響

例如依明確規則產生付款批次。流程可以自動化，但權限、雙重核准、資料品質與稽核必須非常嚴格。

高不確定、高影響

例如醫療、法律、重大投資、裁員決策或公共安全。Agent 可以協助分析與整理，但不應在證據不足時自行完成不可逆行動。

這個矩陣提醒我們：越值得用 Agent 的開放任務，通常越難驗證；越容易完全自動化的任務，通常越接近固定工作流。

真正成熟的系統，不會把「自主程度最高」當成成功，而會把自主性配置在最能創造價值、又能被治理的位置。

一個假設案例：活動報名流程

假設一個協會要辦一場公開課。

Task 層可以讓 AI 寫活動文案、整理報名名單或產生提醒訊息。

Workflow 層可以串接表單、名單去重、資格檢查、錄取通知、行前提醒、現場簽到與活動後回饋。

Outcome 層則要定義：

- 符合資格的人能正確報名。

- 名額不超賣。

- 個資被妥善處理。

- 未錄取者收到清楚說明。

- 時間與地點一致。

- 重要變更能通知到人。

- 現場名單可使用。

- 活動後資料依規則保存或刪除。

此時，單純「寄信成功」並不代表 Outcome 成功。寄錯對象、寄出過期地點、重複寄送、洩露收件人名單，都可能是流程執行成功、結果卻失敗。

因此，Outcome Contract 必須把成功、風險與證據一起定義。

工作真正的最小單位，正在從步驟變成責任包

在 Agent 時代，最有價值的工作拆解，不再只是把流程切得更碎，而是建立一個個可交付、可驗收、可交接的責任包。

每個責任包應該包含：

- 清楚目標。

- 必要 Context。

- 可用工具與權限。

- 驗證方法。

- 失敗與升級條件。

- 交付位置。

- 明確責任人。

Agent 可以執行其中的大部分行動，但責任包的定義與最終歸屬仍然是組織問題。

這也會改變管理者的工作。過去管理者常追蹤活動：「做了沒？寄了沒？開會了沒？」未來更需要追蹤狀態與證據：「結果是否達成？哪個條件未通過？目前風險在哪裡？誰有權處理？」

管理工作的核心，會從催促動作，轉向設計結果與解除阻塞。

Outcome Contract 的進階版：從理想流程走進例外世界

許多流程圖只畫出「事情順利時會怎樣」。資料完整、工具正常、每個人準時回覆，Agent 依序完成步驟，最後交出成果。這種流程適合簡報，卻不足以支撐正式工作。真實世界的工作價值，往往不是展現在順利路徑，而是展現在缺資料、時間延誤、規則衝突、需求變更與責任交接時，系統仍知道下一步怎麼辦。

因此，一份成熟的 Outcome Contract，不能只定義完成，還要定義「無法完成時，怎麼保持誠實」。

先從結局反推，而不是從第一步開始畫

設計流程時，人很容易從「先做什麼」開始。但更有效的方法，是先列出可能的結局：

- 成功完成，而且證據充分。

- 部分完成，仍有缺件或待確認事項。

- 因條件不足而暫停。

- 因風險過高而拒絕執行。

- 因外部系統失敗而等待重試。

- 因權限或責任問題而升級人工。

- 因需求已變更而取消。

每一個結局都應有狀態名稱、必要證據、負責人與下一個動作。這樣，Agent 才不會把所有不順利都包裝成「已完成」，也不會在無法前進時無限重試。

完成條件要能被第三方驗收

「報告寫完了」不是好的完成條件，因為它只描述檔案存在。「報告涵蓋三個指定市場、所有數據標示來源與日期、結論逐項連結證據、風險段落通過人工審查，並存入指定資料夾」才接近可驗收的 Outcome。

一個實用的測試是：把完成條件交給沒有參與過程的人，他能不能只看成果與證據，判斷是否完成？若判斷仍依賴「我覺得差不多」「模型看起來很有信心」，條件就還不夠清楚。

完成條件也需要分層。最低門檻回答「可不可以交付」，品質目標回答「做到什麼程度比較好」，卓越條件回答「哪些額外價值值得追求」。若把所有期待都混在一起，Agent 可能為了追求更完整而拖延，也可能為了趕時間而犧牲不可妥協的底線。

把依賴關係寫進契約

Outcome 並不只由 Agent 自己決定。它可能依賴上游資料、外部 API、他人回覆、審批時間、庫存、法規或實體世界事件。若依賴沒有被顯式化，失敗就會被錯誤歸因給模型。

契約至少要說明：

- 哪些輸入由誰提供，最晚何時提供。

- 哪些來源是正式來源，哪些只能作參考。

- 外部服務中斷時，允許等待多久。

- 依賴版本改變時，是否必須重新驗證。

- 上游輸入不符合條件時，是補充、退回、降級還是停止。

這不只是技術規格，也是合作關係。當上游知道下游會依據什麼行動，資料品質才有改善的責任入口。

例外不是附註，而是流程的一部分

一個常見錯誤，是把例外處理寫成最後一行：「如有特殊情況，轉人工。」這句話沒有說明什麼叫特殊、轉給誰、對方會看到什麼、多久要處理，也沒有說明人工處理完之後是否回寫系統。

更好的方式，是把例外分類。

資訊例外：資料缺失、衝突、過期或來源不明。系統應先嘗試補充，無法補充再升級。

權限例外：需要更高權限、特殊身份或敏感資料。系統不得用替代路徑偷偷繞過。

價值例外：規則無法涵蓋的公平、倫理、品牌或關係判斷。Agent 應呈現選項與可能後果。

執行例外：工具失敗、網路中斷、重複請求、併發衝突。Runtime 應負責重試、鎖定與恢復。

責任例外：無法判定誰有權核准，或多個角色意見相反。這時需要制度性的裁決路由，而不是把問題交給最有空的人。

Handoff 必須保留「為什麼」

交接包不能只有已產生的文字。下一個人或 Agent 需要知道：目標是什麼、已採取哪些步驟、使用哪些來源、哪些判斷仍不確定、哪些行動已執行、哪些不可重做，以及下一步的建議。

高品質 Handoff 最重要的不是長，而是可接續。它應該讓接手者不必重新猜測整段歷史，也不會因為缺乏狀態而重複寄信、重複下單或覆蓋他人的修改。

用假設的活動報名流程看差異

若只畫理想路徑，流程可能是：收到報名、檢查資格、寄出通知、建立名單。進階版 Outcome Contract 會再定義：資料不全時寄出補件通知；名額額滿時進入候補；重複報名時合併紀錄；付款失敗時保留名額多久；特殊身分需要人工確認時由誰處理；活動取消時如何通知並留下回覆紀錄；個資在活動後何時刪除。

這些設計不會讓流程看起來更簡單，卻會讓系統更真實。工作不是一條從起點走到終點的直線，而是一組有狀態、有例外、有證據、有責任的承諾。當 Outcome Contract 能描述這個世界，Agent 才知道何時前進、何時停下，以及無法完成時如何不假裝完成。

Outcome 的反指標：別讓漂亮數字把工作帶往錯誤方向

Outcome Contract 不只要定義成功，也要定義哪些「看起來成功」其實不能接受。當團隊只設定正向指標，Agent 很容易把局部數字最佳化，卻犧牲了工作真正要保護的價值。

例如客服 Agent 的目標若只有縮短處理時間，它可能更快結案，卻留下更多沒有真正解決的問題；招生流程若只追求報名數，可能吸引不適合的對象，讓現場退費與抱怨增加；內容系統若只看發文量，會把重複、薄弱與難以查證的內容大量推出。

因此，每一份 Outcome Contract 都應搭配至少三類反指標。

品質反指標記錄被退回、撤回、重做、申訴或人工大幅改寫的比例。它提醒團隊，快速產出若需要更多下游修復，就不是完整的改善。

風險反指標記錄越權、錯誤通知、資料外洩、引用失真、權益受損或高影響例外。這類事件即使發生率很低，也不能被平均分數掩蓋。

人類負荷反指標記錄審查排隊時間、每件任務所需注意力、夜間救火、認知疲勞與責任人的壓力。若 Agent 省下操作時間，卻把人變成全天候例外處理器，組織只是把工作移到看不見的地方。

完成條件還可以分成三個層次。第一層是單件驗收：這一個結果是否符合格式、資料、證據與權限要求。第二層是服務水準：一段期間內，有多少比例能在時限、成本與品質範圍內完成。第三層是營運結果：客戶、員工、收入、風險或任務週期是否真的改善。

這三層不能混為一談。單件報告寫得很好，不代表整個流程能準時交付；系統每天準時完成，也不代表報告幫助了真正決策。Outcome Contract 應把「作品好不好」「服務穩不穩」「工作有沒有變好」分開衡量。

在高量工作中，不一定需要人工逐件驗收，但要設計抽樣。隨機抽樣可以看一般品質；風險抽樣專看高金額、新資料、新供應商、低信心或規則邊界；事故抽樣則追蹤所有被撤回與申訴的案例。三種抽樣合在一起，才能避免系統只在平均案例上表現漂亮。

抽樣結果必須能回到權限。若某類任務連續通過，可以降低人工比例；若新版本造成退回率上升，就恢復較高審查，甚至退回影子模式。這讓人類審查不再是永久固定成本，而是一個隨證據調整的控制機制。

最重要的是，指標必須定期被質疑。當團隊開始為了過指標而改變行為，就要重新問：這個數字是否仍代表我們真正想要的結果？Outcome Contract 不是把目標寫死，而是讓目標、反指標、抽樣與責任形成可以被檢查的承諾。

本章收束：先把 Outcome 說清楚，Agent 才有地方前進

Task 讓我們看見 AI 的速度。

Workflow 讓我們看見 AI 的協作能力。

Outcome 才讓我們開始談真正的生產力。

若一家公司只把更多小任務交給 AI，卻沒有重做資料、狀態、驗收與責任，它得到的可能只是更多輸出，而不是更好的結果。

章末金句

1. Task 把一個動作交出去，Workflow 把一段流程交出去，Outcome 才把可驗收結果說清楚。

2. 做了很多 AI 功能，不等於完成一個真正的結果。

3. 產出變快，可能只是把瓶頸從生成移到審核。

4. 活動告訴你做過什麼，狀態才告訴你能不能往下走。

5. 交接不是把文字貼給下一個人，而是讓下一個責任人不必重新猜測。

6. 多 Agent 的價值不在數量，而在責任邊界與交接品質。

7. AI 可以承擔工作包，最終責任仍必須有正式的人與組織角色承接。

8. 自動化的邊界，應由不確定性與影響決定，而不是由技術展示決定。

9. 真正的生產力不是產出更多，而是讓正確結果更穩定地發生。
