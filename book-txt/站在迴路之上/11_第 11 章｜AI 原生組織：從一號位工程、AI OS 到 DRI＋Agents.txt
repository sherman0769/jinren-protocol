第 11 章｜AI 原生組織：從一號位工程、AI OS 到 DRI＋Agents

公司裡到處都有 AI，不代表公司已經變成 AI 公司

一家公司可以有很多 AI 工具。

行銷用 AI 寫文案，客服用 AI 摘要對話，工程用 coding agent，財務用模型整理報表。每個部門都有自己的帳號、Prompt、資料夾與小型 PoC。

表面上，AI 已經無所不在。

但客戶資料仍然分散，版本仍然衝突，跨部門仍靠人工搬運，主管仍然等到月報才知道問題，AI 產出的結果也沒有共同驗證與責任規則。

這種狀態可以叫「很多人使用 AI」，卻不能叫 AI 原生組織。

AI 原生不在於工具覆蓋率，而在於組織是否重新設計了：

- 結果如何被定義。

- 資料如何成為共同現實。

- 權限如何被分配。

- 工作如何在 Agent 與人之間流動。

- 例外如何被升級。

- 決策如何留下證據。

- 學習如何回到系統。

- 最終責任如何被承擔。

若這些沒有改變，AI 只是被插進既有組織；組織本身沒有變。

為什麼是「一號位工程」

零一萬物在「一號位工程」方法論中，主張企業 AI 轉型應由 CEO／CAIO 直接承擔，以財務與營運結果定義成功，而不是只看做了多少 Agent 或 PoC；其企業 AI 決策中樞被描述為模型、Ontology 2.0、即時 Context 與作業系統的組合。[R02]

這個觀點的管理價值，在於它把 AI 從資訊工具拉回經營責任。

AI 導入常被交給資訊部門，是因為需要模型、資料、API 與安全。但真正決定成敗的問題往往不是技術部門能單獨回答的：

- 哪一個結果最值得被重設？

- 哪些資料應被視為正式來源？

- 哪些權限能交給 Agent？

- 哪一種錯誤公司無法接受？

- 哪些部門必須改變責任與流程？

- 成本節省是否傷害客戶或員工？

- 誰有權跨部門解決阻塞？

這些都是一號位問題。

但一號位工程也不能被理解成 CEO 親自寫每一個 Prompt。CEO 的責任是定義方向、授權跨部門改造、設定不可犧牲邊界，並要求結果進入真正的營運指標。

技術、資料、風險與業務團隊則把方向轉成可運行系統。

從 AI 專案到 AI 作業層

傳統 IT 系統常以應用為單位：CRM 管客戶、ERP 管資源、HR 系統管人事、文件系統管知識。

Agent 的工作會跨越這些邊界。

一個「完成客戶續約」的 Outcome，可能需要讀取 CRM、合約、使用紀錄、付款狀態、支援案件與產品資料，最後產生提案、安排會議、更新預測並交給業務責任人。

若每個 Agent 都用自己的方式連接資料、權限與工具，組織會得到一片新的自動化孤島。

因此，需要一個共同 AI 作業層，把以下能力連起來：

- 模型與路由。

- 企業資料與 Ontology。

- Context 與記憶。

- Tools、MCP 與 A2A 接口。

- Harness 與 Runtime。

- 身份、權限與秘密。

- Tracing、Evals 與監控。

- Data Quality 與 Evidence Ledger。

- Human Review 與 DRI。

- 成本、版本與治理。

本書把這個廣義層次稱為 AI OS。它不是特定產品名稱，也不是另一套作業系統品牌，而是「企業讓模型、資料、流程、權限、證據與責任共同運作的作業層」。

AI OS 的八層架構

第一層：Model Layer

提供不同能力、成本、延遲與風險的模型，並依任務路由。模型是大腦資源，但不是整個系統。

第二層：Ontology and Data Layer

把企業資料映射到真實業務物件、關係、狀態與行動。

Palantir 將 Ontology 描述為組織的 operational layer，連結資料與 objects、properties、links、actions、functions 與 security，使資料能直接支援決策與行動。[R27]

本書採用這個案例，是為了說明 Ontology 不只是知識圖譜，而是「企業如何定義自己的現實與可行動關係」。

第三層：Context Layer

根據任務與角色，提供最小必要的正式來源、當前狀態、歷史決策與限制。

第四層：Tool and Interoperability Layer

以 API、MCP、A2A 或內部接口連接工具與其他 Agent。互通不等於授權，仍要經身份與政策判定。[R15][R16]

第五層：Harness and Runtime Layer

執行任務、保存狀態、管理佇列、權限、重試、沙箱、人工核准與成果回寫。

第六層：Evidence and Quality Layer

在行動前檢查資料品質，在主張釋出前檢查證據關係，並保存 provenance、approval 與 trace。

第七層：Observability and Improvement Layer

追蹤品質、成本、延遲、風險與真實 Outcome，透過 eval 與真實失敗改善系統。

第八層：Governance and Responsibility Layer

定義一號位、CAIO、平台團隊、業務擁有者、資料擁有者、審查者與 DRI 的權責。

缺少第八層，前七層再完整，仍可能形成責任空洞。

Ontology：讓 AI 理解公司的「真實物件」

企業資料常以表格與系統欄位存在。

customer_id、ticket_status、contract_value、inventory_qty 對系統有意義，但對真實工作而言，它們代表客戶、問題、承諾與可行動狀態。

Ontology 的價值，是把資料放回業務世界。

例如，「客戶」不只是資料列，而可能連結：

- 合約。

- 聯絡人。

- 使用產品。

- 服務案件。

- 付款。

- 風險。

- 可執行 actions。

- 哪些角色有權看見與修改。

當 Agent 被要求「處理高風險客戶」，它需要知道什麼叫高風險、依據哪些關係、可採取哪些行動、哪一個狀態需要人工核准。

若沒有共同 Ontology，不同 Agent 可能各自理解「客戶狀態」，造成語意衝突。

AI 決策中樞不是一個更大的聊天框

企業 AI 決策中樞容易被想像成 CEO 專用 Chatbot：打開畫面，什麼都可以問。

真正有價值的中樞，應該不只回答，也能：

- 看見公司當前狀態。

- 連結資料與業務物件。

- 比較假設與影響。

- 追蹤承諾與執行。

- 發現異常與證據缺口。

- 把決策轉成受控行動。

- 留下理由、核准與後續結果。

也就是從「資訊檢索」走向「可追溯決策與執行」。

這需要的不只是大模型，還需要前面十章的所有基礎。

如果 Context 不可靠，決策中樞只會快速回答錯誤現況。

如果 Runtime 不完整，決策無法真正落地。

如果沒有 Tracing 與 Evals，主管看不到系統長期偏移。

如果沒有 Evidence Ledger，漂亮分析可能缺少支持。

如果沒有 DRI，AI 建議最後只會留在會議裡。

DRI：直接責任人不是流程管理員

DRI 是 Directly Responsible Individual，直接責任人。

它不只是「負責開會的人」，而是對特定 Outcome 有清楚責任、決策權與交接義務的人。

在 Agent 時代，DRI 的價值反而更高，因為執行者可能從一群人，變成人與多個 Agent 的組合。

DRI 要負責：

- 定義 Outcome。

- 確認 Context 與正式來源。

- 配置 Agent、工具與權限。

- 決定驗收與風險門檻。

- 處理跨部門例外。

- 看見成本、品質與證據。

- 核准高影響決策。

- 對外承擔結果。

Agent 可以替 DRI 執行大量動作，卻不能替 DRI 成為責任主體。

這也是為什麼「一個人帶一群 Agent」不是簡單的一人公司幻想。真正能放大產能的人，必須具備工作拆解、Context、驗證、協調與判斷能力。

DRI＋Agents 的工作單元

一個 AI 原生工作單元，可以長成這樣：

```textDRI├─ Research Agent├─ Data Agent├─ Drafting Agent├─ Validation Agent├─ Operations Agent└─ Human Specialists```

DRI 不需要微管每一個步驟，而是管理責任包。

每個責任包包含：

- 子目標。

- Context 邊界。

- 工具與權限。

- 完成條件。

- 證據要求。

- 升級條件。

- 交接格式。

這與傳統分工的差別，是 Agent 可以快速建立、平行執行與動態調整；但若責任包不清楚，多 Agent 只會產生更多需要整合的內容。

Anthropic 的多 Agent 研究展示 orchestrator-worker 在開放研究上的可能性，也同時指出協調、Context、成本與結果整合的複雜度。[R13]

多 Agent 的經濟性，不來自模型數量，而來自是否能讓各自獨立工作減少干擾，又能在交接時保持共同真相。

Orchestrator 不是永遠正確的主管

多 Agent 系統常有一個 orchestrator，負責分派與整合。

但 orchestrator 也是模型或軟體，也會出錯。

它可能：

- 把任務拆錯。

- 分派重複工作。

- 遺漏重要領域。

- 偏好某個子 Agent 的流暢結果。

- 在成本超限時仍繼續擴張。

- 整合時刪掉反證與限制。

因此，orchestrator 需要自己的 Harness、Evals 與監督。

評估多 Agent 不能只看最後答案，也要看：

- 任務分解品質。

- 重複與覆蓋。

- 子 Agent 來源獨立性。

- 衝突是否被保留。

- 整合是否符合 Outcome。

- 成本是否值得。

多 Agent 不應成為複雜性的預設答案。

從職位管理走向 Outcome Portfolio

傳統組織用部門與職位分配工作。

AI 原生組織可能更多以 Outcome Portfolio 管理：每一個重要結果有 DRI、資源、Agent、資料、風險與指標。

例如，不只是「行銷部負責內容」，而是：

- 新產品上市認知。

- 既有客戶留存。

- 高價值名單轉換。

- 品牌風險管理。

每一個 Outcome 可以跨部門組成工作單元，也可以配置不同 Agent。

這種結構的優點是結果清楚，缺點是若共同平台、Ontology 與治理不足，會形成大量短期隊伍與重複系統。

所以，AI 原生組織需要同時強化兩端：

- 中央平台提供共同能力、標準與治理。

- 邊緣 DRI 擁有接近業務的決策與責任。

中央不能把所有流程管死，邊緣也不能各自建立不可治理的 Agent 孤島。

平台團隊與業務團隊如何分工

AI 平台團隊

負責模型接入、Runtime、身份權限、工具標準、觀測、Evals、安全、成本與共同元件。

資料／Ontology 團隊

負責正式資料、業務語意、資料品質、lineage 與變更管理。

業務 DRI

負責 Outcome、風險、例外、使用者價值與正式核准。

風險／法務／合規

定義高影響邊界、審查與稽核。

主管與一號位

負責優先順序、資源、跨部門阻塞與不可犧牲價值。

這些角色不是把責任分散，而是把不同責任說清楚。

AI 導入的三種錯誤組織形態

1. 工具市集型

每個人自由選工具，快速試驗，但沒有共同資料、權限與治理。適合探索，不適合高影響正式流程。

2. 中央管制型

所有 AI 需求都排隊給單一中心，安全一致，但速度慢、不了解業務，也容易成為瓶頸。

3. 自動化幻覺型

高層宣布全面 Agent 化，卻沒有資料、Runtime、Evals 與責任設計。成果多為展示，正式環境仍靠人救火。

比較成熟的方向，是「平台化能力＋分散式責任＋共同治理」。

AI 原生組織的成熟階梯

Level 1｜個人工具

員工自行用 Chatbot 或 Copilot。價值在個人生產力，風險是資料與版本分散。

Level 2｜部門 Workflow

固定流程加入模型與工具，開始有模板與驗證。

Level 3｜受控 Agent

Agent 在 Runtime 中工作，有狀態、權限、Trace、Evals 與人工核准。

Level 4｜跨部門 AI 作業層

共同 Ontology、資料、工具、身份、證據與治理，Agent 能跨系統完成 Outcome。

Level 5｜自我改善的 AI 原生組織

真實失敗、人工決策與營運結果持續回寫，組織能調整 Harness、流程、責任與策略。

成熟不是自主性愈來愈高，而是組織能在更大範圍內保持可控、可證明與可負責。

指標：不要只看 Agent 完成多少任務

AI 原生組織應觀察四組指標。

Business Outcome

收入、成本、週期、留存、品質、風險、使用者結果。

System Performance

成功率、延遲、成本、重試、工具錯誤、資料品質與模型路由。

Human Load

人工介入率、審核時間、例外類型、員工認知負擔與技能轉移。

Learning Rate

重複錯誤是否下降、真實失敗多久被轉成 eval、規則與工具多久更新、過期 Context 多快被清理。

若只看完成任務數，Agent 可能用更多步驟製造更多活動。

組織真正需要的是結果與學習速度。

人才：未來不是每個人都要變成工程師

AI 原生組織需要的新能力，不只程式能力。

不同角色可能要學會：

- 把模糊需求轉成 Outcome Contract。

- 整理正式來源與 Context。

- 設計驗收、例外與停止條件。

- 讀懂 Trace 與評測。

- 與 Agent 協作並判斷何時不該使用。

- 建立可交接的責任包。

- 對決策留下證據與理由。

這些能力可以出現在主管、顧問、編輯、教師、行政、客服與技術人員身上。

真正的差距不只是「會不會用某個 AI 工具」，而是「能不能把自己的專業轉成 AI 可協作、可驗證、又保留人類責任的系統」。

一個假設案例：從分散 PoC 到共同 AI 作業層

假設一家公司有三十個 AI PoC。

客服 Agent 有自己的知識庫，行銷 Agent 有另一份產品資訊，業務 Agent 使用個人試算表，法務 Agent 讀取共享硬碟。四個系統對「最新價格」與「可承諾功能」定義不同。

第一階段不是再做第三十一個 Agent，而是盤點共同真相：

- 哪些業務物件最重要？

- 正式來源在哪裡？

- 誰擁有資料？

- 哪些 actions 可以標準化？

- 哪些權限必須集中管理？

- 哪些 Trace 與 Evidence 必須共同保存？

第二階段建立共同 Runtime 與工具層，讓部門仍能快速建立 Agent，但使用相同身份、權限、資料品質與觀測能力。

第三階段選擇一個跨部門 Outcome，例如縮短續約週期，由 DRI 帶領人與 Agent 工作單元，直接以客戶結果與風險衡量。

第四階段把真實失敗與人工決策回寫到共同平台。

這樣，組織才從 PoC 集合走向 AI 作業層。

一個假設案例：DRI 變成微型 CEO

一位產品經理負責某項新功能的上市 Outcome。

他可以調度研究 Agent 分析需求、資料 Agent 整理使用行為、程式 Agent 建立 prototype、測試 Agent 驗證、內容 Agent 準備說明。

表面上，他像帶領一個小型數位團隊。

但真正讓他成為「微型 CEO」的，不是能叫很多 Agent，而是他要：

- 在資料衝突時決定優先順序。

- 在速度與安全之間取捨。

- 在多個版本中選擇方向。

- 對外承諾上市日期。

- 承擔結果與學習。

Agent 放大了他的執行能力，也放大了他的判斷責任。

若他只會交辦，不會定義、驗證與承擔，Agent 數量越多，失控越快。

AI OS 不是把公司交給 AI

「AI OS」這個詞容易讓人想像公司將由一個中央智能自動管理。

本書主張相反：AI OS 的成熟，不是讓 AI 取得無限權力，而是讓權力、資料、行動與責任被更清楚地編排。

它應該讓人更容易知道：

- 哪個 Agent 正在做什麼。

- 依據哪些資料。

- 具有什麼權限。

- 哪個結果等待誰決定。

- 哪個風險正在升高。

- 哪個學習已回寫。

AI OS 不是公司的新老闆，而是讓人與 Agent 能在共同真相、共同規則與共同證據上工作的作業層。

九十天建立 AI 作業層：不要從「全公司都要用」開始

AI 原生轉型最容易失敗的方式，是一開始就宣告全面導入，購買大量工具，要求每個部門提出 Agent 點子。這會快速產生熱鬧的 PoC，卻不一定形成共同資料、責任與作業能力。

比較穩健的做法，是用九十天建立一個可驗證的 AI 作業層。目標不是完成整間公司的 AI OS，而是證明一個高價值 Outcome 可以在共同 Context、Harness、Runtime、Evidence 與 DRI 責任下穩定運作。

第 1–30 天：畫出 Outcome 與責任地圖

第一個月不急著選最多功能，而是選一個足以產生價值、又能控制風險的工作。好的候選通常具有：需求明確、資料可取得、目前痛點可測量、人工仍能接手、外部影響可限制。

團隊先回答：

- 現在的基準線是什麼？週期、品質、等待、成本與錯誤如何？

- 真正要改善的 Outcome 是什麼？

- 哪些步驟是固定流程，哪些需要 Agent 動態判斷？

- 哪些資料是正式來源，誰擁有？

- 哪些行動可自動，哪些需要核准？

- 誰是 DRI，誰負責平台、資料、風險與營運？

這個月的交付不是 Agent demo，而是一份 Outcome Contract、責任圖與風險邊界。

第 31–60 天：建立共同工作契約

第二個月開始打造最小作業層。重點不是把所有系統整合，而是讓選定工作有一致的執行方式。

Context：建立正式來源、版本、適用範圍與最小 Context Pack。

Tools：只開放必要工具，定義 schema、權限、回傳與可逆操作。

Harness：明確指令、輸出格式、驗證、預算、停止與人工介入。

Runtime：建立任務身份、狀態、checkpoint、重試、成本追蹤與 Handoff。

Evidence：重要行動與主張保存來源、版本、trace 與審查結果。

Evals：從歷史案例與邊界情境建立小型回歸資料集。

此時平台團隊與業務團隊必須一起工作。平台團隊提供可重用能力，業務 DRI 定義 Outcome、例外與真實驗收。若任何一方單獨主導，系統都可能失去另一半。

第 61–90 天：受控進入正式工作

第三個月以有限範圍上線。可以先採 shadow mode：Agent 產生建議，但不直接行動，與人工結果比較；接著開放低影響、可逆行動；只有當 trace、eval 與人工審查顯示穩定，才擴大權限。

上線期間要觀察：

- Outcome 週期是否縮短，而不只是模型回應更快。

- 錯誤在哪裡發生、多久被發現。

- 人工介入是否集中在高價值判斷。

- 資料與工具缺口是否可被修正。

- 成本是否在預算內，尖峰是否造成排隊。

- 使用者是否理解系統限制與申訴方式。

- DRI 是否能看見整體，而不是只收到成功摘要。

九十天結束時，應由 DRI 決定擴大、維持、重設或停止，而不是因為已投入資源就必須繼續。

平台團隊要交付積木，不要接管所有業務

平台團隊的責任，是提供身份、權限、工具連接、Runtime、trace、eval、資料治理與 guardrail 等共同能力。它不應替每個部門決定業務 Outcome，也不應成為所有例外的永久客服。

業務團隊則負責真實流程、資料語意、完成條件、風險、人工審查與成果採用。兩者的接口可以用模板化契約表達：Context Pack、Harness Canvas、Data Contract、Eval Dataset、Approval Packet 與 Runbook。

當接口清楚，新的 Agent 才能重用平台而不必從零開始；平台也能從多個業務案例中找出共通能力。

DRI 要擁有 Outcome Portfolio

一個 DRI 不只管理單一 Agent，而是管理一組為 Outcome 服務的能力：人工角色、資料來源、流程、Agent、工具、成本與風險。他需要知道哪些任務適合自動、哪些仍由人執行、哪些正在測試，以及哪個瓶頸才是真正限制結果。

這種管理方式不同於計算 Agent 完成多少任務。若任務量增加卻沒有改善 Outcome，DRI 應有權停止無效自動化、調整流程或重新分配資源。

用少量共同指標取代工具排行榜

九十天試點可以使用五組指標：

- Business Outcome：週期、轉換、品質、成本或服務結果。

- System Performance：完成、恢復、延遲、成本與工具失敗。

- Human Load：審查時間、例外量、認知負擔與滿意度。

- Learning Rate：多少錯誤轉成 eval、規則、工具或資料改善。

- Trust and Risk：越權、錯誤釋出、申訴、撤回與重大事故。

這些指標比「用了幾個模型」「有多少 Prompt」「建立幾個 Agent」更接近轉型成效。

不做大爆炸式導入

AI 作業層應從可驗證責任迴路逐步擴張。每成功一個 Outcome，就沉澱可重用的資料契約、工具、Runtime 模組、測試與治理；下一個團隊在此基礎上前進，而不是複製一套孤立 PoC。

AI OS 最終不是一個可以一次購買完成的產品，而是公司對資料、行動、證據、責任與改善方式的共同作業協議。九十天的真正成果，不是宣告公司已經 AI 原生，而是建立第一條能被重複、被審查、被擴張的責任迴路。

組織改造的難題不在工具，而在誘因、身份與參與方式

AI 作業層即使技術完整，也可能在組織中失敗。原因常不是員工抗拒新科技，而是導入方式讓人看見明確風險，卻看不見自己的位置：工作被重新分配，績效標準沒有更新，錯誤責任仍由人承擔，節省下來的時間又立刻被更多任務填滿。

首先，轉型要說清楚為什麼改造這個 Outcome。若只用「公司要跟上 AI」作為理由，團隊很難判斷該保留什麼、犧牲什麼。更具體的說法可能是縮短客戶等待、降低重複輸入、讓專業人員多花時間處理例外，或讓決策留下可查證證據。目的愈清楚，員工愈能參與設計，而不是只被要求使用工具。

第二，參與者應在流程設計前期進場。真正做工作的人知道資料在哪裡不完整、哪些例外無法寫進 SOP、哪些承諾不能只靠速度衡量。若平台團隊先完成 Agent，再請業務「提供意見」，常會把現場知識變成上線前最後一輪抱怨。共同畫出狀態、例外與責任，才是把隱性知識轉成系統資產。

第三，績效與責任要同步調整。若員工被要求讓 Agent 承擔更多工作，卻仍以手動產量評分，他們自然會保留舊流程；若 Agent 犯錯由第一線承擔，而權限與設計由其他單位決定，組織會形成責任與控制分離。DRI 必須同時擁有足夠決策權、資源與升級管道。

第四，要建立安全回報文化。員工指出 Agent 的錯誤，不應被視為妨礙自動化，而是提供高價值 Eval 資料。對發現資料缺口、越權風險與不公平結果的人給予肯定，會比單純獎勵自動完成率更能建立長期可靠性。若大家害怕讓專案看起來不好，問題只會被移到私下修補。

第五，節省下來的時間要有去向。若每一分鐘效率提升都立刻變成更高工作量，人不會把 AI 視為能力放大，而會視為新的壓力來源。組織應明確分配一部分時間給訓練、例外處理、流程改善與專業判斷，讓效率收益能轉成品質與學習，而不是只有更多產量。

第六，要為角色轉變提供學習路徑。有人從執行者轉成審查者，有人負責 Context、工具或 Eval，有人擔任 DRI。這些都需要新的能力：定義 Outcome、閱讀 Trace、判斷證據、設計例外、說明決策。不能只給一堂工具課，就假設人已能承擔新的責任。

第七，對可能受到工作重設影響的人，要有透明與尊重。組織應說明哪些任務會改變、決策依據、過渡安排與可申訴管道。人的尊嚴不能被包裝成「文化溝通」後略過；AI 轉型的品質，也要看權力、風險與收益如何分配。

AI 原生組織不是把每個人變成 Agent 管理員，而是讓不同專業在共同作業層上重新合作。技術提供新的可能，真正決定轉型能否成立的，是組織是否願意把目的、誘因、責任與人的位置一起重做。

本章收束：組織的基本單位，正在從部門走向責任迴路

AI 原生組織不會只是把人換成 Agent。

它會重新設計工作的基本單位：從職位與步驟，走向 Outcome、DRI、Agents、Runtime、Evidence 與 Improvement Loop。

一號位負責方向與跨部門改造。

平台提供共同能力與治理。

DRI 擁有結果與決策權。

Agent 執行可定義的責任包。

專業人員處理例外、價值與高影響判斷。

所有行動透過共同資料、權限、Trace 與證據連接。

這樣的組織不是少了人，而是人的位置改變了。

章末金句

1. 公司裡到處都有 AI，不代表公司已經成為 AI 原生組織。

2. 一號位工程不是 CEO 親自寫 Prompt，而是 CEO 對方向、邊界與營運結果負責。

3. AI OS 不是一個更大的聊天框，而是模型、資料、權限、Runtime、證據與責任共同運作的作業層。

4. Ontology 讓企業資料不只是一堆欄位，而成為真實物件、關係、狀態與可行動責任。

5. Agent 可以執行責任包，DRI 仍要承擔 Outcome。

6. 多 Agent 的價值不在數量，而在獨立工作、共同真相與高品質交接。

7. 成熟不是自主性愈來愈高，而是在更大範圍內仍能可控、可證明、可負責。

8. AI OS 不是把公司交給 AI，而是讓人與 Agent 在共同真相與共同證據上工作。

9. 組織的基本單位，正在從部門走向責任迴路。
