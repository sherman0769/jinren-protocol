第 9 章｜行動前先過閘門：Runtime Data-Quality Gating

模型可能完全不知道，資料已經不能用了

一份資料看起來內容完整、語句合理，卻可能因為 metadata 而失效。

它可能是昨天被取代的價格表。

可能來自測試環境，不是正式系統。

可能欄位名稱沒變，定義卻已經更新。

可能數字本身正確，卻不適用目前地區、客戶或時間。

可能兩份來源互相一致，只因為都複製自同一個錯誤上游。

人類熟練工作者看到檔名、日期、來源或狀態，可能會多問一句；模型若只取得內容本文，根本不知道這些缺陷存在。

這是一種特別危險的錯誤：silent evidence defect，沉默的證據缺陷。

它不一定讓資料看起來壞掉，也不一定讓模型產生低信心。相反地，內容越流暢、欄位越完整，Agent 越可能自信地採取行動。

SARC-DQ 預印本以高成本行動情境研究這類問題，核心洞見是：若缺陷存在於模型看不見的 metadata，模型能力提升不會自動帶來資料懷疑；pre-action gate 的效果取決於檢查條件覆蓋了哪些缺陷，以及閘門是否部署在真正能阻止行動的位置。[R24]

這篇研究的實驗範圍有限，不能把結果比例直接外推到所有產業。但它指出一個非常重要的系統軸：

Agent 的推理品質，不能補償它根本看不見的資料品質問題。

內容正確，不代表資料可用

資料品質常被簡化成「有沒有錯字、空值或異常數字」。對 Agent 而言，資料可用性至少包含八個面向。

1. Freshness｜新鮮度

資料是否仍在有效時間內？

昨天的庫存、上個月的法規、去年的人員權限，都可能在內容上完全正確，卻不適合現在行動。

2. Lineage｜血緣與來源鏈

資料從哪裡產生，經過哪些轉換，誰修改過？

若只看到最後值，無法判斷它是否來自正式系統、人工匯出、測試資料或二手整理。

3. Schema｜結構與語意版本

欄位名稱、型別、單位與定義是否符合目前系統？

price 可能是未稅價、含稅價、折扣後價或建議售價。欄位存在不代表語意一致。

4. Consistency｜跨來源一致性

不同資料是否互相衝突？

一致性檢查不只是找相同，也要辨識來源是否獨立。三份報告都寫同一數字，不一定是三重證據。

5. Completeness｜完整性

完成此行動需要的必要欄位是否齊全？

缺少一個低影響欄位可以降級處理；缺少核准狀態或收款帳號，則可能必須停止。

6. Authority｜權威與適用性

來源是否有權定義這件事？

同事的整理表可能很方便，卻不能取代正式合約；產品部落格可以解釋功能，卻不能取代法規。

7. Integrity｜完整性與未被竄改

資料是否在傳輸、儲存或轉換中被改變？是否有校驗、簽章或稽核紀錄？

8. Scope｜範圍

資料適用哪個地區、產品、版本、客戶與情境？

一項規則在 A 市場有效，不代表可直接套到 B 市場。

這八個面向共同說明：資料品質不是資料清洗的附屬工作，而是 Agent 行動的前置條件。

為什麼不能只把 metadata 丟給模型判斷

看到資料品質問題，有人會說：那就把 metadata 也放進 Prompt，請模型自己判斷。

這可以補充語意理解，卻不應成為唯一防線。

原因有四個。

第一，模型可能忽略。Context 很長時，關鍵日期或狀態可能被稀釋。

第二，模型可能誤解。deprecated、superseded、draft、effective_from 等欄位若沒有明確規則，模型可能用常識猜。

第三，模型可能為了完成目標而合理化。當系統強烈要求「務必完成」，模型可能把品質缺口當成可接受風險。

第四，某些條件本來就應由確定性系統保證。例如檔案已過期、schema 版本不符、數位簽章失敗，不需要模型自由判斷。

因此，資料品質閘門的基本原則是：

能用確定性 predicate 檢查的條件，先由 Runtime 在行動前檢查；需要語意判斷的部分，再交給模型或人。

模型可以解釋風險，閘門負責真正阻止行動。

本書提出：行動前最低證據條件

在「雙閘門證據迴路」中，第一個閘門是行動閘門。

我把它的通過標準稱為：Minimum Evidence Condition for Action，行動前最低證據條件。

這不是要求所有資料完美，而是根據行動影響，定義足以安全前進的最低條件。

例如，一個一般內容草稿可以容許部分資料待查，只要明確標示且不公開。

一個付款 Agent 則可能要求：

- 收款對象已驗證。

- 金額與幣別完整。

- 發票與採購單一致。

- 核准狀態有效。

- 資料未過期。

- 沒有重複付款紀錄。

- 權限與雙重核准通過。

若其中任何關鍵條件不滿足，系統就不能以「模型覺得合理」為由繼續。

最低證據條件應與風險成比例，而不是全公司只有一套固定門檻。

資料品質閘門的五種結果

閘門不一定只有通過與失敗。

Pass｜通過

所有必要條件滿足，可進入下一步。

Warn｜警告

存在低影響缺口，但可在標示限制後繼續。例如非關鍵欄位缺漏。

Enrich｜補充

系統可以自動查詢更可靠來源、更新 metadata 或要求上游補欄位，再重新檢查。

Escalate｜升級

需要有權責的人判斷，例如兩份正式來源衝突。

Block｜阻擋

高風險條件失敗，不得行動。例如簽章失敗、權限不足、資料已被撤銷。

這五種結果能避免兩種極端。

若所有缺口都直接阻擋，系統會被低價值例外拖住。

若所有缺口都只警告，閘門就只是儀表板裝飾。

Fail-Open 還是 Fail-Closed

當閘門本身無法判定時，系統要繼續還是停止？

Fail-open 表示檢查失敗或資料不足時仍繼續。適合低影響、可逆、重視可用性的任務。

Fail-closed 表示無法證明安全就停止。適合高影響、不可逆或受法規約束的行動。

真正的設計通常是分層。

例如，客服 Agent 在查不到完整歷史時，仍可產生「待人工確認」草稿，但不能自動承諾退款。

研究 Agent 在找不到某項次要數字時，可以標示缺口繼續；若核心結論沒有來源，則不能發布。

系統必須明確定義哪些條件失敗時採哪種策略，不能交給每一輪模型臨時決定。

閘門要部署在真正能阻止行動的位置

品質檢查做得再完整，若只在報表中提醒，Agent 仍可能先完成高影響行動。

有效閘門必須位於行動路徑上。

例如：

- 付款工具在執行前驗證資料，不是付款後才產生風險報告。

- 發布工具只接受已通過審核的 artifact ID，不是讓 Agent 直接提交任意文字。

- 刪除工具需要版本、備份與核准 token。

- 合約簽署流程在送簽前檢查正式版本與核准鏈。

這就是「部署位置」的重要性。

一個閘門若不能阻止行動，就只是觀察器。

Predicate Coverage：閘門能看見哪些缺陷

資料品質閘門不可能檢查所有問題。它的效果取決於 predicate coverage，也就是檢查條件涵蓋哪些已知缺陷。

常見 predicate 包括：

```textfreshness_within_limitschema_version_supportedsource_is_authoritativelineage_completerequired_fields_presentcross_source_consistentsignature_validapproval_not_expirednot_supersedednot_duplicate_transaction```

每一個 predicate 都應有：

- 適用行動。

- 輸入欄位。

- 通過標準。

- 失敗嚴重度。

- 失敗處理。

- 責任人。

- 測試案例。

若閘門只檢查「欄位非空」，卻不檢查版本與來源，表面覆蓋率很高，實際仍可能漏掉最危險缺陷。

真正的覆蓋應從風險與真實失敗事件建立，而不是從容易寫的規則開始。

Provenance：資料血緣是信任的骨架

Provenance 回答一筆資料如何形成。

W3C PROV-O 提供跨系統表示 entity、activity 與 agent 關係的語意基礎，讓資料來源與轉換可以被交換與整合。[R19]

在 Agent 系統中，provenance 至少可以記錄：

- 原始來源。

- 擷取時間。

- 轉換步驟。

- 使用工具與版本。

- 修改者或系統。

- 核准狀態。

- 衍生成果。

例如，一個財務數字不是只存 1,250,000，而是能追到：來自哪份報表、哪個欄位、哪個期間、是否經匯率轉換、由誰核准、被哪些報告引用。

沒有 provenance，資料品質檢查只能看表面值；有 provenance，系統才能判斷來源鏈是否可靠。

資料品質不是單一分數

把資料品質濃縮成一個 0 到 100 分，很方便，卻可能掩蓋關鍵風險。

一份資料完整度 98%，但缺少的 2% 是付款核准欄位，不能因總分高就通過。

另一份資料新鮮度稍低，卻只是用來產生內部歷史趨勢，可能仍可使用。

因此，品質應該與行動綁定。

同一份資料對不同任務有不同可用性。

昨天的價格對即時報價不可用，對月度趨勢分析可能足夠。

匿名資料對內容分析可用，對個人通知不可用。

草稿政策對腦力激盪可用，對正式合規判定不可用。

資料品質不是資料本身的絕對屬性，而是「資料、任務、時間與風險」之間的關係。

Semantic Gate：規則之外的語意品質

有些缺陷無法靠簡單 predicate 判斷。

例如：

- 來源雖是官方，但回答的是相近而非相同問題。

- 兩段文字表面一致，前提卻不同。

- 資料完整，但因樣本偏差不適合外推。

- 一份政策仍有效，卻只適用特定身分類別。

這時可以加入 semantic gate，由模型、規則與人共同判斷。

但 semantic gate 應輸出結構化理由，例如：

```textstatus: mixedreason: 來源 A 支持一般情況，來源 B 顯示本案屬例外missing: 本案身分類別的正式認定route: domain_owner_review```

不要只輸出一個「可信度 78%」。數字若沒有可解釋條件，很難支持責任判斷。

Data Contract：讓上游知道下游要靠什麼行動

資料品質不能只由 Agent 下游補救。

若上游系統沒有日期、版本、來源、核准與失效欄位，下游再聰明也無法可靠判斷。

Data Contract 可以明確定義：

- 欄位與語意。

- 必填與選填。

- 單位與格式。

- 更新頻率。

- 資料擁有者。

- 來源與 lineage。

- 有效與失效條件。

- 品質服務等級。

- 變更通知。

當 Agent 成為資料消費者，Data Contract 更重要，因為它不會像熟練員工一樣靠默契補洞。

AI 導入會迫使組織把「大家都知道」變成正式契約。這是一項成本，也是一項長期資產。

一個假設案例：庫存補貨 Agent

假設 Agent 根據庫存、銷量與供應時間提出補貨。

若只看數字，它可能認為某商品庫存不足，立即下單。

資料品質閘門應先檢查：

- 庫存時間戳是否在允許範圍。

- 是否包含門市調撥中的數量。

- 銷量資料是否排除退貨與測試訂單。

- 供應商交期是否仍有效。

- 商品是否已進入停售或改版。

- 是否已有未入庫採購單。

- 單位與包裝規格是否一致。

- 來源是否為正式系統。

若停售狀態存在，應直接 Block。

若交期資料稍舊，可以 Warn 或 Enrich。

若兩個倉庫數字衝突，應 Escalate。

模型可以分析需求，Runtime gate 必須確保分析建立在可行動資料上。

一個假設案例：活動通知 Agent

Agent 要向已錄取者發送行前通知。

資料品質閘門可以檢查：

- 名單是否為最終核准版本。

- 是否已去重。

- 收件方式是否有有效同意。

- 活動時間與地點是否來自正式來源。

- 是否有取消或更改狀態。

- 個資欄位是否只提供任務需要部分。

- 是否已發送過同版本通知。

如果活動地點來源衝突，系統不應「選一個看起來較新的」直接寄出，而要升級給活動責任人。

很多錯誤不是模型寫不好，而是資料在進入模型以前就沒有通過責任檢查。

資料品質閘門也需要 Evals

閘門若設計錯誤，可能產生兩種傷害。

False Negative

有問題的資料被放行，造成風險。

False Positive

可用資料被阻擋，造成大量人工與流程延遲。

因此，閘門本身要評測：

- 對已知缺陷的偵測率。

- 不必要阻擋率。

- 不同風險等級的表現。

- metadata 缺漏時的策略。

- 規則更新後的回歸。

- 人工覆核的分歧與理由。

還要監測「繞過閘門」的行為。例如 Agent 是否改用另一個工具完成相同行動，或人員是否因流程麻煩而直接從旁路操作。

治理不能只建立門，也要確認工作真的經過門。

從資料品質走向證據基礎設施

資料品質閘門解決的是：行動前，輸入是否達到最低條件。

但 Agent 產生報告、建議或公開主張時，還有另一個問題：資料存在，不代表它真的支持那一句主張。

一份研究可能引用很多來源，卻把相關誤當因果；一個模型可能找到官方文件，卻引用了不適用本案的段落；不同證據可能一部分支持、一部分反駁。

因此，第一閘門通過後，仍需要第二閘門：主張與證據的關係判定。

這就是下一章的 Evidence Ledger。

資料閘門的治理：規則也會錯，例外也需要責任

資料品質閘門常被想像成一組客觀規則：日期太舊就阻擋、欄位缺失就拒絕、來源不明就警告。但任何規則都可能誤判，也可能在不同業務情境中需要不同門檻。若閘門沒有治理，系統可能從「放任錯誤資料通過」走到另一個極端：大量正當工作被阻塞，最後使用者想辦法繞過所有控制。

每一個 predicate 都要有擁有者

一條資料規則至少要說清楚：誰提出、依據什麼、適用哪些任務、何時檢查、失敗後怎麼辦、誰能修改，以及多久重新檢視。

例如「資料不得超過三十天」看似明確，但市場價格、員工名冊、法規文件與年度統計的合理時效完全不同。沒有 owner 的規則，會在原始情境消失後繼續阻擋工作。

擁有者也不應只由工程團隊擔任。資料生產者、使用資料做決策的人、風險角色與系統營運者都需要參與，因為品質門檻本質上是「這份資料是否足以支持某項行動」的共同承諾。

閘門要區分資料錯誤與資料未知

有些資料確定不正確，例如 schema 不符或簽章無效；有些則只是尚未確認，例如來源日期缺失。兩者應採不同結果。

確定錯誤可以 Block；未知可能先 Enrich、要求補件或降低可執行範圍。若所有不確定都直接阻擋，系統會失去彈性；若所有未知都當成可用，又會讓缺乏證據的行動偷偷發生。

好的閘門會把「不知道」變成明確狀態，而不是逼迫系統假裝知道。

管理誤攔與漏攔

閘門有兩種基本錯誤。False Positive 是把可用資料誤判為不可用，造成延遲與額外人工；False Negative 是讓有問題的資料通過，造成錯誤行動。

不同任務對兩種錯誤的成本不同。低風險內部摘要可以容許較多漏攔，由人工在使用時發現；高影響付款或公共通知則應更重視漏攔，即使增加一些人工確認。

評測閘門時，不能只看通過率或攔截率，還要看被攔截後的真實判定、漏掉的事故、處理時間與使用者繞過行為。

例外放行要有期限、有範圍、有理由

真實工作一定會遇到規則無法完全涵蓋的情況。例外機制不是閘門失敗，而是治理的一部分。但例外不能只是管理者口頭說「這次先過」。

一個可審核的 waiver 應包含：申請人、原因、影響範圍、替代控制、批准者、生效與失效時間，以及是否需要事後補資料。期限到達後自動失效，不應變成永久後門。

若同一類例外頻繁發生，代表規則、資料流程或業務設計需要修正，不能永遠依賴人工放行。

閘門延遲也是成本

每多一個檢查，就可能增加查詢、等待與外部依賴。設計時要區分哪些 predicate 可在本地快速檢查，哪些需要查詢來源系統，哪些只在高風險行動前執行。

可以採分層策略：先做低成本確定性檢查，再做需要外部查詢的權威性與血緣檢查，最後才使用語意模型處理規則難以涵蓋的問題。不是所有資料都要走最昂貴的路徑。

閘門結果也應可快取，但快取必須受版本與時效控制。否則，昨天通過的資料可能在今天仍被錯誤視為有效。

讓上游看見下游需求

資料品質不應只由下游 Agent 被動檢查。Data Contract 應把最低條件回傳給資料生產者：哪些欄位必填、版本如何標示、更新頻率、允許值、權威來源、錯誤回報與責任窗口。

當上游能看見哪些資料缺口造成下游 Block，組織才有機會從根本改善，而不是每次由 Agent 臨時補救。

這也會改變績效討論。資料團隊的價值不只是提供更多資料，而是提供足以支援行動、可被理解與可被追溯的資料。

閘門決定要可解釋

被阻擋的人需要知道原因與修復方式。只回傳「品質不足」會造成挫折，也讓使用者無法判斷規則是否合理。

一個好的結果應說明：哪個 predicate 未通過、檢查到什麼、最低要求是什麼、可以採取哪些補救、是否可申請例外，以及若繼續行動可能承擔什麼風險。

解釋也能協助監測規則品質。若大量使用者都在同一條規則上卡住，團隊可以檢查是上游資料問題，還是規則與現實脫節。

一個庫存補貨 Agent 的治理例子

假設補貨 Agent 需要銷售、庫存、交期與促銷資料。某供應商交期資料已超過門檻，但採購人員知道近期沒有變動。系統可以允許具權限的人申請七天例外，同時限制訂購金額、要求保留理由，並建立補更新任務。

若例外在三個月內重複出現，系統應把問題升級到資料 owner，而不是讓採購人員每週按一次放行。反過來，若某欄位雖然缺失卻從未影響決策，團隊也應檢查它是否真的是必要 predicate。

資料品質閘門的成熟，不在規則愈多，而在每一條規則都有明確目的、可測試效果、例外責任與改善路徑。它不只是阻止 Agent，而是讓組織知道自己憑什麼行動。

讓資料閘門安全上線：影子、金絲雀與分層放行

資料品質規則一旦部署在行動前，就可能同時阻止錯誤與阻止工作。若團隊直接把新 predicate 以 Fail-Closed 方式套到全部任務，常見結果是大量正常案例被誤攔，使用者轉而尋找旁路，最後整套治理失去信任。

比較安全的方式，是先用影子模式。閘門照常評估，但不真正阻擋，只記錄它原本會 Warn、Degrade 或 Block 的案例。團隊將結果和人工判斷、後續 Outcome、事故與申訴比對，確認規則看見的是實際風險，而不是單純偏離理想資料格式。

第二階段是金絲雀部署。只選小比例、低金額、內部使用或有明確人工接手的任務啟用阻擋。觀察指標不只看攔截率，也看誤攔、漏攔、處理延遲、人工例外、上游修復時間與使用者繞路行為。若某條規則讓工作大量移到私下試算表，它雖然技術上生效，治理上卻失敗。

第三階段是風險分層。同一個缺陷在不同任務中不必有相同處置。資料稍舊，對內部趨勢探索可以 Warn；對自動補貨可能 Degrade 並限制金額；對法規申報則 Block。閘門應讀取 Outcome、影響與可逆性，而不是只讀欄位是否通過。

第四階段是例外路徑演練。正式上線前，要實際測試誰能申請例外、需要提供什麼理由、期限如何到期、系統是否限制範圍，以及例外是否能被追蹤。若正常工作一被阻擋，大家只能找管理員私下改資料，代表例外制度尚未成立。

第五階段是回復與熔斷。若新規則造成異常大量 Block、關鍵流程停擺或資料 owner 無法在時限內修復，系統應能暫時退回 Warn、縮小適用範圍或停用單一 predicate，而不是關閉整個資料治理。回復動作必須留下版本、原因與後續 Review 時間，避免緊急降級變成永久漏洞。

閘門上線後還要做規則漂移監測。上游 schema、業務季節、產品組合與政策都會變，原本有效的門檻可能逐漸失真。團隊可定期重算 false positive、false negative，查看哪些規則從未觸發、哪些規則總被例外，以及哪些事故發生在所有規則都通過之後。

假設活動通知 Agent 要求名單中的聯絡方式在三十天內確認。影子模式可能發現，許多固定會員雖超過三十天仍有效，而新加入資料的錯誤反而較多。團隊可以把規則從單純日期門檻，改成來源、驗證方式與變更歷史的組合；高風險大量發送仍 Block，低量內部提醒則允許 Warn 前進。

閘門不是一次寫完的法律，而是一個需要用真實結果校準的控制系統。安全上線的目標，是讓規則逐步取得阻止行動的正當性：它必須證明自己能看見重要風險、能解釋決定，也能在規則出錯時被限制與更正。

本章收束：先判斷資料能不能用，再讓模型判斷要怎麼用

模型能力愈強，我們愈容易相信它會自己發現資料有問題。

但若缺陷藏在模型看不見的 metadata、來源鏈與版本狀態中，再強的推理也無從懷疑。

Runtime Data-Quality Gating 的價值，是把「資料是否足以支持行動」從模型的臨場感覺，提升為系統的正式條件。

它不要求資料完美，而要求風險與證據相稱。

低影響工作可以帶著警告前進；高影響行動在無法證明資料可用時就必須停止。

真正可信的 Agent，不只是會找資料，而是知道哪些資料不能拿來行動。

章末金句

1. 模型可能完全不知道，眼前內容正確的資料已經不能用了。

2. Agent 的推理品質，不能補償它根本看不見的資料品質問題。

3. 能用確定性規則檢查的條件，先由 Runtime 檢查，不要只靠模型自律。

4. 行動前最低證據條件，不要求資料完美，而要求風險與證據相稱。

5. 一個不能真正阻止行動的閘門，只是觀察器。

6. 資料品質不是單一分數，而是資料、任務、時間與風險之間的關係。

7. Provenance 讓我們不只看見一個值，也看見這個值如何形成。

8. 真正可信的 Agent，不只是會找資料，而是知道哪些資料不能拿來行動。
