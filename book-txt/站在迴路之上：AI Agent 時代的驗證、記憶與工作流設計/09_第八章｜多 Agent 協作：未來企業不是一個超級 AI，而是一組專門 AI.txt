第八章｜多 Agent 協作：未來企業不是一個超級 AI，而是一組專門 AI

核心問題：企業到底應該打造一個什麼都會的超級 Agent，還是一組能協作的專門 Agent？

核心觀點：未來企業 AI 架構更可能是一組有權限邊界、能安全交接的專門 Agent，而不是一個全能 Agent。

本章比喻：企業不是找一個萬能員工做所有事，而是建立一個分工清楚、能交接、能稽核的 AI 組織。

一、這一章要解決的問題

企業到底應該打造一個什麼都會的超級 Agent，還是一組能協作的專門 Agent？

這個問題表面上是技術問題，實際上是工作方法問題。當 AI 還停留在聊天視窗裡，我們只需要追問答案是否好用；但當 AI 開始進入任務、工具、資料、流程與組織權限，問題就會變成：這個系統能不能被信任、被追蹤、被修正、被放行。

二、章首開場

很多企業一開始想做 AI，很容易想像一個超級 Agent：什麼都知道、什麼都能做、所有問題都問它。這個想像很誘人，因為它簡單。但真正的企業流程，通常不是靠一個萬能員工完成，而是靠分工、權限、交接與審核。

未來企業更可能擁有一組專門 Agent：客服 Agent、財務 Agent、文件 Agent、程式 Agent、教育訓練 Agent、品牌內容 Agent。每一個 Agent 有自己的資料、工具、權限與責任，然後透過協議互相交接。

三、現象觀察

現在很多人看 AI，還是習慣從單點能力開始看：會不會寫、會不會查、會不會畫、會不會改程式、會不會整理資料。這些能力當然重要，但它們只是節點，不是系統。真正的工作發生在節點之間：資料如何進來、任務如何拆解、工具如何被呼叫、結果如何被驗證、錯誤如何被回報、人如何決定是否放行。

以「Agent Organization Chart：Agent 組織圖」來看，本章真正要處理的不是單一功能，而是把功能放回工作迴路。只要沒有迴路，AI 再會做，都可能只是一次漂亮的展示；只要迴路設計得好，AI 的能力才有機會變成可累積的工作產能。

四、用白話講清楚核心技術

Google 的 A2A 文章把 agent-to-agent collaboration 放在一個重要位置。它強調 Agent 之間需要共同語言來協作與安全交接任務，也提到 specialized agents 可以在資料邊界或企業流程邊緣工作，再把符合條件的洞察或任務交給下游流程。

這裡要清楚區分 MCP 與 A2A。簡化來說，MCP 比較像讓 Agent 接工具與資料；A2A 比較像讓 Agent 接另一個 Agent。前者處理「我能用什麼」，後者處理「我可以把什麼任務交給誰」。

多 Agent 架構的好處，是權限邊界可以更清楚。財務 Agent 不需要知道客服所有對話，客服 Agent 不需要碰程式碼 repo，品牌 Agent 不需要讀員工薪資資料。每個 Agent 專注在自己的工作現場，再透過協議交換必要的任務與結果。

五、這個技術為什麼重要

把所有任務塞進一個超級 Agent，有三個風險：上下文污染、權限過大、責任不清。它可能把不相關資料混在一起，也可能擁有太多工具，導致一個錯誤影響太多流程。

多 Agent 架構則比較接近組織設計。它讓每個 Agent 有職務說明、工具清單、記憶範圍、驗證標準與交接規則。這不是技術花樣，而是企業治理需求。AI 越進入組織，越需要像組織一樣被設計。

七、實際情境

在企業內訓中，可以請學員畫出自己的 Agent 組織圖。例如一家教育公司可能需要招生 Agent、課程 Agent、講師 Agent、客服 Agent、行銷 Agent、學習成效 Agent。每一個 Agent 的資料來源、工具權限與人工審核點都不同。

對內容自動化團隊來說，也可以把一個全能寫作 AI 拆成：研究 Agent、章節 Agent、標題 Agent、金句 Agent、審稿 Agent、發佈 Agent。這樣每個 Agent 的任務更清楚，也更容易驗證。

十四、三個常見誤解

誤解一：只要模型更強，這個問題自然會消失。

模型變強會改善表現，但不會自動產生工作流。企業到底應該打造一個什麼都會的超級 Agent，還是一組能協作的專門 Agent？ 這類問題通常不是單純智力不足，而是資料、工具、流程、權限、驗證與責任沒有被設計。真正的關鍵是把模型能力放進可追蹤的迴路。

誤解二：工具接越多，Agent 就越成熟。

工具越多，能力邊界也越大；但如果沒有權限、驗證、日誌與人工放行，工具越多反而風險越大。Agent Organization Chart：Agent 組織圖 的目的，就是讓工具不只是被接上，而是被放進有邊界的工作系統。

誤解三：Human on Loop 是把人拿掉。

Human on Loop 不是無人化，而是讓人從每一步的救火者，變成整個迴路的設計者與監督者。人仍然負責標準、風險、倫理、責任與最後放行，只是不再被迫卡在每一個微小步驟裡。

十九、章末收束

這一章最後要留下的不是一個名詞，而是一個位置感：AI 不只是工具，AI 開始成為工作迴路裡的行動者。當 AI 成為行動者，人就不能只當提問者。人要成為設計迴路、設定標準、檢查結果、決定放行的人。這就是《站在迴路之上》真正想建立的思考方式。

一個超級 Agent 會造成上下文污染、權限混亂、責任不清與難以審計。這句警告，是本章最適合拿來開場的衝突。因為大多數人剛接觸 AI 時，會自然地被產出能力吸引；等到真正要交付、上線、導入、對客戶負責時，才發現問題不在於 AI 會不會生成，而在於它生成之後是否能被理解、被檢查、被追蹤、被修改與被承擔。

十七、四個應用情境：從自讀到企業內訓

個人知識工作

如果把這一章放回我自己的工作，第一個場景不是大型企業，而是每天的寫作、備課、閱讀與顧問整理。未來企業 AI 架構更像一組專門 Agent 的組織圖，而不是一個什麼都塞進上下文的超級大腦。這句話對我最大的提醒，是不要只追求一次輸出，而要追問輸出之前的資料從哪裡來，輸出之後如何被檢查，又如何變成下一次可重用的資產。

企業內訓現場

在企業內訓裡，學員最常問的不是理論，而是「明天能不能用」。所以這一章必須被翻成流程語言：誰提出需求，誰提供資料，AI 可以動用哪些工具，結果交給誰審，錯了如何回報。只有把Agent Organization Chart：Agent 組織圖放進這些問題裡，技術才會從名詞變成方法。

內容與社群輸出

對 FB 貼文與短影音來說，這一章不能只變成資訊整理，而要變成一個有衝突、有轉折、有金句的觀點。開場可以先說常見誤解，再用多 Agent 協作像企業組織，不是叫一個員工做客服、財務、工程、法務與行銷，而是讓不同角色安全交接。降低門檻，最後收束到一句可記住的話：未來企業不是養一個什麼都管的 AI，而是設計一組能安全交接、各自負責的專門 AI。

商業提案與顧問服務

如果這一章要轉成商業提案，重點不是告訴客戶「這個技術很新」，而是告訴客戶「這個技術會改變你的哪一段工作」。企業應該先畫 Agent 組織圖，再決定 MCP、A2A、API 與內部工具如何串接。這句話可以直接成為提案頁面的核心論述，後面再接上評估表、導入步驟與風險控管。

十八、常見誤解與修正

誤解 1：把技術當成答案，而不是問題的放大鏡

很多人看到How A2A is Building a World of Collaborative Agents這類新研究或新工具，會急著問「我要不要馬上導入」。但更好的問法是：它揭露了哪一個舊問題？它讓我們看見哪一個過去被忽略的流程缺口？在本章裡，真正值得內化的不是新名詞本身，而是它把「企業到底該打造一個全能 Agent，還是一組能協作的專門 Agent？」這個問題推到檯面上。

誤解 2：只看最炫的能力，忽略最笨的邊界

AI 最容易讓人興奮的地方，是它突然做出一個看似很完整的結果。但系統真正會出事的地方，通常不是展示時最亮的地方，而是權限、資料、例外、驗證與責任交界處。一個超級 Agent 會造成上下文污染、權限混亂、責任不清與難以審計。這不是保守，而是讓 AI 可以長期工作的基本條件。

誤解 3：把一次成功誤認為系統成熟

一次成功常常只是剛好資料乾淨、任務明確、工具可用、風險很低。要判斷是否成熟，不能只問這一次結果好不好，而要問十次、一百次、跨部門、跨資料版本、跨使用者語氣時，它是否仍然能留下可檢查的軌跡。

誤解 4：把人放回每一步，卻說自己完成自動化

很多導入表面上叫自動化，實際上是把人工檢查藏在後面。真正的 Human on Loop 不是讓人每一步救火，而是把規則、標準、例外與放行點設計在迴路上方，讓人看系統，而不是一直替系統補洞。

十九、課堂練習：把本章變成一個 60 分鐘工作坊

1. 請選一個你最近真正做過的任務，例如寫文章、做簡報、查資料、整理客戶需求或規劃企業內訓，先不要問 AI 怎麼做，而是畫出這個任務原本的人工作業流程。

2. 在流程上標出三種節點：資料節點、判斷節點、交付節點。資料節點回答「資訊從哪裡來」，判斷節點回答「誰說可以」，交付節點回答「結果要送到哪裡」。

3. 把Agent Organization Chart：Agent 組織圖套到流程上，逐一檢查主控 Agent、專門 Agent、工具層、權限層等環節是否存在。如果某個環節不存在，不要急著補工具，先補標準。

4. 設計一個最小迴路：只讓 AI 負責一小段任務，但要求它輸出來源、理由、風險、待人工確認事項與下一步建議。這個最小迴路比一個漂亮 demo 更接近真實導入。

5. 最後把這個流程改寫成三個版本：給學員看的課堂練習、給企業主管看的導入提案、給自己看的內化筆記。這就是本書要培養的轉化能力。

這個練習的重點，不是讓學員立刻做出完整 Agent，而是讓他們第一次意識到：AI 導入不是從工具開始，而是從任務迴路開始。只要能把一個任務畫清楚，很多技術選型就會變得比較簡單；如果任務本身畫不清楚，再好的模型也只是把混亂放大。

二十、李詩民自讀版補充筆記

我讀這一章時，真正想提醒自己的，是不要被「最新」牽著走。最新的論文、最新的平台、最新的 benchmark、最新的協議，當然都值得追，但它們不是目的。目的還是把 AI 變成我能理解、能教學、能導入、能負責的工作方法。

所以我在讀How A2A is Building a World of Collaborative Agents, Google Developers Blog, 2026-06-18這類資料時，會刻意問四個問題：第一，它解決的是哪一種真實工作痛點？第二，它暴露了哪一種舊方法的天花板？第三，它能不能變成一個課堂模型？第四，它能不能放進企業導入的檢查表？如果答案都能說清楚，這個技術才不只是新聞，而是可以沉澱成方法論。

多 Agent 課要教的是角色分工、交接契約、安全邊界與協作協議。這句話，應該成為未來課程設計的底層提醒。AI 教學不能只停留在讓學員驚訝，而要讓學員離開教室後，有能力回到自己的部門、專案、內容流程與客戶情境中，重新設計一個更可信的工作迴路。

二十一、可直接拆成演講的三段話

第一段可以這樣說：過去我們學 AI，重點是怎麼問；接下來我們學 AI，重點是怎麼讓它進入流程。這不是否定提示詞，而是承認提示詞只是入口。當 AI 開始讀資料、用工具、做判斷、交付結果，真正的問題就變成：誰來驗證？誰來追蹤？誰來放行？誰來負責？

第二段可以這樣說：多 Agent 協作像企業組織，不是叫一個員工做客服、財務、工程、法務與行銷，而是讓不同角色安全交接。如果我們只看它最會表演的一面，就會錯把展示當成部署。真正成熟的 AI 系統，不是一次回答很漂亮，而是每一次任務都能留下證據、暴露風險、接受審查，並把回饋帶回下一輪。

第三段可以這樣說：未來企業不是養一個什麼都管的 AI，而是設計一組能安全交接、各自負責的專門 AI。這句話是我希望聽眾帶走的核心。因為未來的競爭，不只是模型之間的競爭，也是人類是否有能力設計工作迴路的競爭。

二十二、本章小結：從能力崇拜到迴路設計

本章最後要收回到一個簡單但重要的轉換：不要只崇拜能力，要開始設計迴路。能力會進步，模型會更新，平台會改版，但一個可靠工作系統需要的問題意識不會消失。AI 只要進入真實工作，就必須面對資料、工具、記憶、驗證、權限、追蹤與責任。

這也是《站在迴路之上》這本書想建立的內在節奏：每一章都談一個技術訊號，但每一章最後都回到同一個位置。人不是站在 AI 前面等待答案，也不是站在 AI 後面收拾錯誤；人要站在迴路之上，設計它、觀察它、修正它，讓 AI 的能力變成可以被組織吸收的工作方法。

二十三、擴充案例包：把「多 Agent 協作」放進一個真實專案

如果這一章只停在概念，我讀完會覺得有道理，卻未必知道明天怎麼用。所以我需要把它放進一個真實專案裡看：假設我要替一家中型企業設計一套 AI 導入工作坊，第一步不是介紹模型，而是請每個部門拿出一個最痛的任務。客服拿出客訴分類，行銷拿出社群內容，工程拿出程式碼審查，主管拿出跨部門報告。接著我不急著示範工具，而是把每個任務放進「Agent Organization Chart：Agent 組織圖」裡，要求他們說清楚資料從哪裡來、AI 做哪一段、人審哪一段、錯誤如何被發現、結果如何被更新。

這時候，第八章｜多 Agent 協作：未來企業不是一個超級 AI，而是一組專門 AI的價值就會從一個章節主題，變成一種工作坊方法。學員會開始發現，原本他們以為 AI 導入是「買工具」或「學 prompt」，但真正困難的是把任務講清楚，把權限畫清楚，把驗證標準寫清楚。當這些事情沒有被說清楚，AI 不是不能用，而是只能停在個人效率工具；當這些事情被畫出來，AI 才有可能變成組織的工作能力。

我也可以把這個案例改成自己的內容生產系統。假設我要把一場演講變成書稿、投影片、FB 貼文、短影音腳本與企業內訓講義，我不能只對 AI 說「幫我整理」。我必須先定義輸入素材、輸出格式、審稿標準、引用檢查、章節一致性、金句抽取、社群語氣與後續回饋。這其實就是同一個模型在不同場景的應用：不是讓 AI 生成更多，而是讓 AI 生成的東西能夠被放進下一個環節。

這個案例也提醒我，真正好的架構不是只適合技術團隊，而是能讓非技術部門也開始問對問題。業務不需要懂所有模型細節，但他要知道客戶資料能不能交給 AI；行銷不需要懂底層推理，但他要知道品牌視覺如何驗收；主管不需要寫程式，但他要知道哪些任務可以自動放行，哪些任務一定要留下人工審核。從全能幻想走向角色分工，其實就是把 AI 從少數人的工具，變成組織共同討論的工作語言。

二十四、企業內訓檢查表：導入前先問的十個問題

第一，這個任務是否真的需要 AI，還是只是因為大家想嘗試新工具？很多導入失敗不是因為 AI 不夠強，而是任務本身沒有明確價值。第二，這個任務的輸入資料是否穩定？如果資料來源混亂、格式不一、版本不明，就不能期待 AI 自動解決所有混亂。第三，這個任務的成功標準是否能被寫下來？如果人類自己都說不清楚什麼叫好，AI 也只能產生看似合理的猜測。

第四，AI 可以使用哪些工具？工具是否有權限邊界？第五，AI 做完後，誰來驗證？驗證是抽查、全查，還是依風險分級？第六，錯誤如何回報？錯誤是直接覆蓋、人工修正、還是進入下一輪訓練與流程改善？第七，哪些資訊需要被記住？哪些資訊因為隱私、法規或過期風險不應被記住？這些問題看似瑣碎，其實才是 AI 能否進入真實工作的關鍵。

第八，這個任務是否需要跨 Agent 或跨部門交接？如果需要，交接格式、責任邊界與上下文清理機制是什麼？第九，是否留下足夠的 trace，讓後續可以回看 AI 在哪一步使用了什麼資料、做了什麼判斷、產生什麼版本？第十，這個流程是否會隨著使用次數增加而改善？如果每次都從零開始，AI 只是在加速單次產出；如果每次都能留下回饋，才算真正進入迴路。

這十個問題可以直接做成企業內訓講義。我的教法會是：先不要讓學員開 AI 工具，而是讓他們拿自己的工作任務填表。填到一半，他們通常就會發現，真正卡住的不是 prompt，而是任務定義、資料邊界、審核標準與責任歸屬。這一刻很重要，因為它會讓 AI 課從「技巧課」轉成「工作設計課」。

二十五、自我追問：我如何避免把這章寫成空泛趨勢？

第一個追問是：這一章有沒有讓我多一個可以使用的模型？如果沒有，它就只是資訊。第二個追問是：這一章有沒有讓我多一個可以教人的比喻？如果沒有，它很難進入課堂。第三個追問是：這一章有沒有讓我多一張可以畫在白板上的圖？如果沒有，它很難變成企業工作坊。第四個追問是：這一章有沒有讓我多一組可以拿去問客戶的問題？如果沒有，它很難變成顧問服務。

我也要提醒自己，不要把「技術深度」誤解成「術語密度」。一本真正能被我拿來內化、授課與演講的書，不是英文名詞越多越好，而是每一個重要名詞都能被翻成一個工作場景。當我說 多 Agent 協作，我必須能接著說：它在企業裡會卡在哪裡、在課程裡要怎麼教、在社群貼文裡要怎麼講、在顧問案裡要怎麼問。這樣的技術才會從閱讀變成能力。

第三個提醒是，不要為了追新而失去主線。這本書的主線不是某一篇論文或某一個平台，而是從 Prompt Engineering 走向 Loop Engineering。每一章都只是主線上的一個支點。只要我能把每一章拉回「人如何站在迴路之上」這件事，書稿就不會散掉；如果每一章都只追逐自己的新名詞，全書就會變成技術剪報。

二十六、本章可拆成三種商品化內容

第一種，是一篇 FB 長文。標題可以用衝突句，例如「AI 真正難的不是會不會做，而是能不能被放進工作」。內文先講一個常見誤解，再用本章比喻切入，最後放上三個檢查問題。這種貼文的目的不是教完技術，而是讓讀者開始意識到自己目前用 AI 的天花板。

第二種，是一段 20 分鐘演講。演講架構可以固定成四段：痛點、比喻、模型、案例。痛點讓聽眾感覺「這是在說我」，比喻讓聽眾聽得懂，模型讓聽眾帶得走，案例讓聽眾知道明天可以怎麼做。Agent Organization Chart：Agent 組織圖在這裡就不是書裡的圖，而是現場可以互動討論的工具。

第三種，是一堂企業工作坊。工作坊不以工具展示為主，而以任務重設為主。讓每組學員選一個部門任務，先畫現在流程，再畫 AI 介入點，最後標出驗證、追蹤、記憶、治理與人工放行點。只要能完成這件事，學員就會理解：AI 導入不是從更會問開始，而是從更會設計工作開始。

二十七、章末再收束：把這章留在身體裡

如果我要把這一章留在身體裡，而不是只留在筆記裡，我會把它縮成一個動作：每次看到 AI 的新能力，都先畫迴路。不要先問它多強，不要先問它能不能取代誰，不要先問它是否熱門，而是先問它進入哪一段工作、需要什麼資料、會動用什麼工具、如何驗證、如何追蹤、如何回到下一輪。

這個動作會讓我不容易被新技術牽著走。因為只要我開始畫迴路，我就會回到人的位置：人不是追在 AI 後面補洞，也不是站在 AI 前面等奇蹟，而是站在迴路之上，決定什麼可以交給 AI，什麼必須保留人類判斷，什麼要被記錄，什麼要被禁止，什麼要在下一輪改善。
