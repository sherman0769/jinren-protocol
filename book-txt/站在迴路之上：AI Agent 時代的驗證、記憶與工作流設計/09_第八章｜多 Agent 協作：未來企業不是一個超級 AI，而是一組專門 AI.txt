第八章｜多 Agent 協作：未來企業不是一個超級 AI，而是一組專門 AI

核心問題：企業到底應該打造一個什麼都會的超級 Agent，還是一組能協作的專門 Agent？

核心觀點：未來企業 AI 架構更可能是一組有權限邊界、能安全交接的專門 Agent，而不是一個全能 Agent。

本章比喻：企業不是找一個萬能員工做所有事，而是建立一個分工清楚、能交接、能稽核的 AI 組織。

本章校準來源：

- How A2A is Building a World of Collaborative Agents（Google Developers Blog 官方文章，2026-06-18）URL：https://developers.googleblog.com/how-a2a-is-building-a-world-of-collaborative-agents/用途：用於說明 A2A 如何讓專門 Agent 安全協作、交接任務、保持 secure boundary 與減少 context pollution。提醒：若來源為 arXiv 預印本，本書將它視為最新研究趨勢與觀念校準，不把它寫成已定型的產業標準。

一、這一章要解決的問題

企業到底應該打造一個什麼都會的超級 Agent，還是一組能協作的專門 Agent？

這個問題表面上是技術問題，實際上是工作方法問題。當 AI 還停留在聊天視窗裡，我們只需要追問答案是否好用；但當 AI 開始進入任務、工具、資料、流程與組織權限，問題就會變成：這個系統能不能被信任、被追蹤、被修正、被放行。

二、章首開場

很多企業一開始想做 AI，很容易想像一個超級 Agent：什麼都知道、什麼都能做、所有問題都問它。這個想像很誘人，因為它簡單。但真正的企業流程，通常不是靠一個萬能員工完成，而是靠分工、權限、交接與審核。

未來企業更可能擁有一組專門 Agent：客服 Agent、財務 Agent、文件 Agent、程式 Agent、教育訓練 Agent、品牌內容 Agent。每一個 Agent 有自己的資料、工具、權限與責任，然後透過協議互相交接。

三、現象觀察

現在很多人看 AI，還是習慣從單點能力開始看：會不會寫、會不會查、會不會畫、會不會改程式、會不會整理資料。這些能力當然重要，但它們只是節點，不是系統。真正的工作發生在節點之間：資料如何進來、任務如何拆解、工具如何被呼叫、結果如何被驗證、錯誤如何被回報、人如何決定是否放行。

以「Agent Organization Chart：Agent 組織圖」來看，本章真正要處理的不是單一功能，而是把功能放回工作迴路。只要沒有迴路，AI 再會做，都可能只是一次漂亮的展示；只要迴路設計得好，AI 的能力才有機會變成可累積的工作產能。

四、用白話講清楚核心技術

Google 的 A2A 文章把 agent-to-agent collaboration 放在一個重要位置。它強調 Agent 之間需要共同語言來協作與安全交接任務，也提到 specialized agents 可以在資料邊界或企業流程邊緣工作，再把符合條件的洞察或任務交給下游流程。

這裡要清楚區分 MCP 與 A2A。簡化來說，MCP 比較像讓 Agent 接工具與資料；A2A 比較像讓 Agent 接另一個 Agent。前者處理「我能用什麼」，後者處理「我可以把什麼任務交給誰」。

多 Agent 架構的好處，是權限邊界可以更清楚。財務 Agent 不需要知道客服所有對話，客服 Agent 不需要碰程式碼 repo，品牌 Agent 不需要讀員工薪資資料。每個 Agent 專注在自己的工作現場，再透過協議交換必要的任務與結果。

五、這個技術為什麼重要

把所有任務塞進一個超級 Agent，有三個風險：上下文污染、權限過大、責任不清。它可能把不相關資料混在一起，也可能擁有太多工具，導致一個錯誤影響太多流程。

多 Agent 架構則比較接近組織設計。它讓每個 Agent 有職務說明、工具清單、記憶範圍、驗證標準與交接規則。這不是技術花樣，而是企業治理需求。AI 越進入組織，越需要像組織一樣被設計。

六、模型整理

Agent Organization Chart：Agent 組織圖

1. 主控 Agent

2. 專門 Agent

3. 工具層

4. 權限層

5. 記憶層

6. 驗證層

7. 交接協議

這個模型可以作為上課、演講與企業訪談時的白板框架。它的用途不是讓聽眾背名詞，而是讓聽眾看到：AI 工作流不是一段 prompt，而是一組需要被設計、檢查與更新的關係。

七、實際情境

在企業內訓中，可以請學員畫出自己的 Agent 組織圖。例如一家教育公司可能需要招生 Agent、課程 Agent、講師 Agent、客服 Agent、行銷 Agent、學習成效 Agent。每一個 Agent 的資料來源、工具權限與人工審核點都不同。

對內容自動化團隊來說，也可以把一個全能寫作 AI 拆成：研究 Agent、章節 Agent、標題 Agent、金句 Agent、審稿 Agent、發佈 Agent。這樣每個 Agent 的任務更清楚，也更容易驗證。

十四、三個常見誤解

誤解一：只要模型更強，這個問題自然會消失。

模型變強會改善表現，但不會自動產生工作流。企業到底應該打造一個什麼都會的超級 Agent，還是一組能協作的專門 Agent？ 這類問題通常不是單純智力不足，而是資料、工具、流程、權限、驗證與責任沒有被設計。真正的關鍵是把模型能力放進可追蹤的迴路。

誤解二：工具接越多，Agent 就越成熟。

工具越多，能力邊界也越大；但如果沒有權限、驗證、日誌與人工放行，工具越多反而風險越大。Agent Organization Chart：Agent 組織圖 的目的，就是讓工具不只是被接上，而是被放進有邊界的工作系統。

誤解三：Human on Loop 是把人拿掉。

Human on Loop 不是無人化，而是讓人從每一步的救火者，變成整個迴路的設計者與監督者。人仍然負責標準、風險、倫理、責任與最後放行，只是不再被迫卡在每一個微小步驟裡。

十五、企業導入檢核表

1. 這個任務的原始需求是否已經被清楚定義？是否存在模糊、衝突或隱含假設？

2. AI 需要讀取哪些資料？資料是否最新、完整、可追溯？

3. AI 會使用哪些工具？每個工具的權限、限制與風險是否清楚？

4. 本章模型「Agent Organization Chart：Agent 組織圖」中的每一步是否都有對應的輸入、輸出與驗收標準？

5. 如果 AI 做錯，錯誤會停在哪裡？誰會收到通知？誰可以決定重跑或放行？

6. 哪些結果可以自動通過？哪些結果必須人工審核？

7. 過程是否留下日誌、版本、引用、工具呼叫與人工修改紀錄？

8. 這次任務的回饋，如何進入下一輪流程改善？

十六、課程設計練習

如果把這一章設計成 30 分鐘企業內訓，可以安排三段練習。第一段，請學員寫下自己部門一個真實任務，並回答：企業到底應該打造一個什麼都會的超級 Agent，還是一組能協作的專門 Agent？ 第二段，請學員把任務套進「Agent Organization Chart：Agent 組織圖」，找出目前缺少的步驟。第三段，請學員設計一個最小可行迴路：只改一個流程、只接一個工具、只建立一個驗證點，先讓 AI 從 demo 走向小規模真實使用。

如果把這一章設計成社群內容，可以拆成三篇。第一篇用比喻破題：企業不是找一個萬能員工做所有事，而是建立一個分工清楚、能交接、能稽核的 AI 組織。 第二篇解釋技術趨勢，但提醒來源若為預印本就只能當趨勢校準。第三篇轉成實務建議：不要打造一個什麼都管的超級 Agent，而是打造一組能互相交接、各自有權限邊界的專門 Agent。

十八、給未來自己的備忘

未來重讀這一章時，不要只看技術名稱是否還流行，而要看它背後解決的結構問題是否仍然存在。工具、模型、平台都會變，但「企業到底應該打造一個什麼都會的超級 Agent，還是一組能協作的專門 Agent？」這類問題，只要 AI 要進入真實工作，就不會消失。

真正值得累積的，是把這章轉成自己的方法論：能上台講，能帶企業討論，能讓學員做練習，能變成一張圖，能拆成一系列貼文，也能回到書稿裡成為一段有深度的文字。

十九、章末收束

這一章最後要留下的不是一個名詞，而是一個位置感：AI 不只是工具，AI 開始成為工作迴路裡的行動者。當 AI 成為行動者，人就不能只當提問者。人要成為設計迴路、設定標準、檢查結果、決定放行的人。這就是《站在迴路之上》真正想建立的思考方式。
