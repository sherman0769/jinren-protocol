第七章｜Coding Agent 從寫程式，走向資安、盤點與技術債整理

核心問題：Coding Agent 的價值，只是幫工程師寫新功能嗎？

核心觀點：Coding Agent 的企業價值，正在從寫程式擴展到理解舊系統、找出風險、整理技術債。

本章比喻：Coding Agent 像程式碼考古隊，不只是蓋新房子，也能挖出老房子的裂縫、管線與未標記危險區。

一、這一章要解決的問題

Coding Agent 的價值，只是幫工程師寫新功能嗎？

這個問題表面上是技術問題，實際上是工作方法問題。當 AI 還停留在聊天視窗裡，我們只需要追問答案是否好用；但當 AI 開始進入任務、工具、資料、流程與組織權限，問題就會變成：這個系統能不能被信任、被追蹤、被修正、被放行。

二、章首開場

很多人第一次理解 Coding Agent，是從「幫我寫一段程式」開始。這當然很直覺，因為程式碼看起來就是工程師的產出。但企業真正的痛點，往往不是沒有新功能，而是不知道舊系統裡藏了什麼。

一家公司跑了十年、二十年的系統，裡面可能有沒人敢碰的模組、沒人看懂的註解、過期套件、未修漏洞、只存在老員工腦中的部署流程。Coding Agent 的下一個價值，不只是寫新 code，而是幫組織理解自己累積下來的系統風險。

三、現象觀察

現在很多人看 AI，還是習慣從單點能力開始看：會不會寫、會不會查、會不會畫、會不會改程式、會不會整理資料。這些能力當然重要，但它們只是節點，不是系統。真正的工作發生在節點之間：資料如何進來、任務如何拆解、工具如何被呼叫、結果如何被驗證、錯誤如何被回報、人如何決定是否放行。

以「Codebase Archaeology：程式碼考古學」來看，本章真正要處理的不是單一功能，而是把功能放回工作迴路。只要沒有迴路，AI 再會做，都可能只是一次漂亮的展示；只要迴路設計得好，AI 的能力才有機會變成可累積的工作產能。

四、用白話講清楚核心技術

Anthropic 公布的 Alberta 政府案例提供一個很好的觀察點。官方說明提到，Alberta 自 2025 年起使用 Claude Code 搭配 Opus 與 Sonnet 模型審查政府系統、找出漏洞並修補。其團隊在 20 小時內掃描 4.66 億行程式碼，約 50 個 agents 並行，涵蓋 27 個省級部會、約 1,280 個應用與 3,400 個 repositories。

這個案例的重點，不是要把它當成所有企業都能複製的保證，而是看見 Coding Agent 的角色轉變。它不只是一個幫你 autocomplete 的工具，而是可以參與大規模程式碼審查、漏洞定位、文件補全與修補建議的工作者。

尤其官方案例提到的流程包含規則引擎先標記已知模式，再由 Claude Code 檢視並引用具體檔案與行數，讓開發者可以驗證。這裡再次回到本書主軸：Agent 的價值不是只做，而是做完後能被人驗。

五、這個技術為什麼重要

企業的程式碼庫其實是一種組織記憶。每一段程式碼都記錄了某個時代的決策、限制、權宜之計與技術債。問題是，這些記憶常常沒被整理，直到出事時才被看見。

Coding Agent 可以降低盤點門檻。它可以快速閱讀大量 repo，整理風險清單，產生技術文件，協助工程師看見跨系統依賴。但這同時需要嚴格治理，因為資安掃描與漏洞修補涉及高風險，不能把 AI 建議直接自動部署。

六、模型整理

Codebase Archaeology：程式碼考古學

1. 掃描

2. 分類

3. 找風險

4. 追來源

5. 產修補建議

6. 產技術文件

7. 建立持續巡檢迴路

這個模型可以作為上課、演講與企業訪談時的白板框架。它的用途不是讓聽眾背名詞，而是讓聽眾看到：AI 工作流不是一段 prompt，而是一組需要被設計、檢查與更新的關係。

七、實際情境

企業內訓可以把 Coding Agent 分成三層教：第一層是寫新功能，第二層是讀懂舊系統，第三層是建立持續巡檢迴路。真正成熟的企業，不只問 AI 能不能寫，而問 AI 能不能幫我們看見多年累積的風險。

對非工程主管來說，這章也能轉成管理語言：技術債不是工程部的小問題，而是組織風險。Coding Agent 讓技術債第一次有機會被規模化盤點，並轉成決策者看得懂的風險報告。

八、李詩民自己的閱讀筆記

我讀這個案例最大的啟發是：Coding Agent 不應該只被放在工程師個人生產力裡。它應該被放在組織治理、資安、維運與技術債管理裡。

如果未來我要對企業主管講 Coding Agent，我不會從「幫工程師寫得更快」開始，而會從「讓企業看懂自己的舊系統」開始。這更接近高層真正關心的風險、成本與可維護性。

十四、三個常見誤解

誤解一：只要模型更強，這個問題自然會消失。

模型變強會改善表現，但不會自動產生工作流。Coding Agent 的價值，只是幫工程師寫新功能嗎？ 這類問題通常不是單純智力不足，而是資料、工具、流程、權限、驗證與責任沒有被設計。真正的關鍵是把模型能力放進可追蹤的迴路。

誤解二：工具接越多，Agent 就越成熟。

工具越多，能力邊界也越大；但如果沒有權限、驗證、日誌與人工放行，工具越多反而風險越大。Codebase Archaeology：程式碼考古學 的目的，就是讓工具不只是被接上，而是被放進有邊界的工作系統。

誤解三：Human on Loop 是把人拿掉。

Human on Loop 不是無人化，而是讓人從每一步的救火者，變成整個迴路的設計者與監督者。人仍然負責標準、風險、倫理、責任與最後放行，只是不再被迫卡在每一個微小步驟裡。

十五、企業導入檢核表

1. 這個任務的原始需求是否已經被清楚定義？是否存在模糊、衝突或隱含假設？

2. AI 需要讀取哪些資料？資料是否最新、完整、可追溯？

3. AI 會使用哪些工具？每個工具的權限、限制與風險是否清楚？

4. 本章模型「Codebase Archaeology：程式碼考古學」中的每一步是否都有對應的輸入、輸出與驗收標準？

5. 如果 AI 做錯，錯誤會停在哪裡？誰會收到通知？誰可以決定重跑或放行？

6. 哪些結果可以自動通過？哪些結果必須人工審核？

7. 過程是否留下日誌、版本、引用、工具呼叫與人工修改紀錄？

8. 這次任務的回饋，如何進入下一輪流程改善？

十六、課程設計練習

如果把這一章設計成 30 分鐘企業內訓，可以安排三段練習。第一段，請學員寫下自己部門一個真實任務，並回答：Coding Agent 的價值，只是幫工程師寫新功能嗎？ 第二段，請學員把任務套進「Codebase Archaeology：程式碼考古學」，找出目前缺少的步驟。第三段，請學員設計一個最小可行迴路：只改一個流程、只接一個工具、只建立一個驗證點，先讓 AI 從 demo 走向小規模真實使用。

如果把這一章設計成社群內容，可以拆成三篇。第一篇用比喻破題：Coding Agent 像程式碼考古隊，不只是蓋新房子，也能挖出老房子的裂縫、管線與未標記危險區。 第二篇解釋技術趨勢，但提醒來源若為預印本就只能當趨勢校準。第三篇轉成實務建議：Coding Agent 不只是寫新功能，而是幫企業理解舊系統、資安風險、技術債與維護成本。

十八、給未來自己的備忘

未來重讀這一章時，不要只看技術名稱是否還流行，而要看它背後解決的結構問題是否仍然存在。工具、模型、平台都會變，但「Coding Agent 的價值，只是幫工程師寫新功能嗎？」這類問題，只要 AI 要進入真實工作，就不會消失。

真正值得累積的，是把這章轉成自己的方法論：能上台講，能帶企業討論，能讓學員做練習，能變成一張圖，能拆成一系列貼文，也能回到書稿裡成為一段有深度的文字。

十九、章末收束

這一章最後要留下的不是一個名詞，而是一個位置感：AI 不只是工具，AI 開始成為工作迴路裡的行動者。當 AI 成為行動者，人就不能只當提問者。人要成為設計迴路、設定標準、檢查結果、決定放行的人。這就是《站在迴路之上》真正想建立的思考方式。
