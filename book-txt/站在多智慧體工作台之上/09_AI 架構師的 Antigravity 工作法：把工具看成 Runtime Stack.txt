AI 架構師的 Antigravity 工作法：把工具看成 Runtime Stack

章首開場

如果只把 Antigravity 當成新開發工具，你會得到一套功能清單；如果把它當成 Runtime Stack，你會看到一種未來工作系統的雛形。桌面應用是控制中心，IDE 是近身編輯面，CLI 是終端調度器，SDK 是可程式化控制層，企業平台是權限與部署場域，Skills 是可重複能力，Hooks 是安全攔截，Artifacts 是驗收證據。這不是一個工具，而是一組工作堆疊。

現象觀察

資料頁面中列出的生態系組件很值得重讀。桌面應用、IDE、CLI、SDK、企業級平台各自負責不同層次，這讓我們看見 Agentic AI 不再只是單一 app。真正的變化，是 AI 開始需要自己的執行環境、權限模型、技能系統、證據輸出、背景排程與組織治理。這正是你過去談 Runtime Thinking 時需要的具體案例。

問題指出

很多企業導入 AI 仍把問題簡化成「買哪個帳號」或「訓練員工下 Prompt」。但 Agentic AI 進入工作後，帳號與 Prompt 只是入口。真正的問題包括：代理在哪裡執行？資料從哪裡來？可調用哪些工具？誰批准高風險動作？怎麼留下證據？哪些能力要封裝成 Skill？怎麼把成功流程推給整個團隊？若這些沒設計，導入只會停在示範。

新觀念提出

本章提出「AI Runtime Stack」。AI 架構師要把每個工具拆成層：任務層、代理層、工具層、技能層、證據層、治理層、學習層。當你用 Stack 看工具，就不會被單點功能吸走，而能判斷它在整個工作系統中扮演什麼角色。

模型整理：AI Runtime Stack 七層

1. Task Layer：任務如何被定義、拆解、排程與驗收。

2. Agent Layer：哪些代理負責規劃、執行、測試、瀏覽、整理與合併。

3. Tool Layer：代理能使用哪些 IDE、CLI、瀏覽器、MCP、API 與本地腳本。

4. Skill Layer：哪些流程被封裝成可重複技能。

5. Evidence Layer：代理交出哪些 Artifacts、Diff、截圖、測試與報告。

6. Governance Layer：權限、Hooks、沙箱、批准、稽核與回滾。

7. Learning Layer：成功案例如何沉澱成知識庫、技能與團隊標準。

實際情境

你可以把這章直接改成企業顧問簡報。先畫出客戶現有流程，再把 AI Runtime Stack 疊上去：任務從哪裡進來，代理在哪裡工作，工具怎麼接，成果怎麼證明，風險怎麼擋，經驗怎麼沉澱。這會讓客戶明白：導入 Agentic AI 不是裝外掛，而是設計一套新型工作作業系統。

內化筆記

給自己讀的重點：這章是整本書最接近你個人方法論核心的地方。你可以把 Antigravity 當案例，但不要讓書停在 Antigravity。真正要留下的是 Runtime Stack 這套語言。未來不管工具換成哪個品牌，你都可以用同樣架構分析。

延伸提醒

這裡還有一個必須補上的判斷：任何新工具都會有版本、價格、跑分與功能限制的變動，因此本書不把單一數字當成永久結論，而把它轉化為可遷移的方法。換句話說，我們關心的不只是某個功能今天支援幾個代理、哪個模型預設啟用、哪個訂閱方案比較划算；我們真正關心的是，這些功能背後反映了什麼工作設計。只要抓住這一層，你就能在工具更新後快速重構自己的講法，而不會被產品細節牽著走。

案例拆解

案例拆解：如果你要幫一家公司設計 Agentic AI 導入藍圖，可以先畫 Runtime Stack。最上層是公司想交給 AI 的任務；下一層是不同代理角色；再下一層是可用工具與資料；接著是 Skill 封裝；再來是 Artifacts 證據；最後是治理與學習。這張圖能讓董事長、IT、法務、工程與業務在同一張地圖上討論，而不是各講各的工具需求。

給自己的三個問題

- 我能否把一個 AI 導入案畫成七層 Runtime Stack？

- 目前缺的是模型、工具、技能、證據還是治理？

- 成功流程是否能被沉澱成組織資產？

演講提煉

演講時可以說：當 AI 只是聊天，Prompt 就夠了；當 AI 開始工作，Runtime Stack 才是重點。AI 架構師的工作，不是把模型接上去，而是替 AI 建立一個能安全工作的現場。

章末金句

- 當 AI 只是聊天，Prompt 就夠了；當 AI 開始工作，Runtime Stack 才是重點。

- 工具是入口，Runtime 才是工作現場。

- Agentic AI 的導入，不是裝外掛，而是設計作業系統。

- AI 架構師不是接模型的人，是設計 AI 工作現場的人。

- 成功流程若不能沉澱成 Skill，就只是一次漂亮展示。
