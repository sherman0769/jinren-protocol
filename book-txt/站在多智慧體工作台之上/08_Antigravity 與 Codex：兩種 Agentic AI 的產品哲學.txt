Antigravity 與 Codex：兩種 Agentic AI 的產品哲學

章首開場

當市場出現多個 Agentic AI 工具，最容易犯的錯是問「哪一個最強」。更好的問題是：它們各自假設了什麼樣的工作方式？Antigravity 與 Codex 的差異，不只是功能清單，而是兩種產品哲學。一種強調本地優先、實時監控、富媒體產出物；另一種強調雲端沙盒、非同步派發、以 Pull Request 交付結果。

現象觀察

資料中的對比很清楚：Antigravity 更像與開發者並肩工作的本地調度台，適合快速原型、UI/UX 高頻迭代、需要瀏覽器視覺驗證與即時回饋的任務；Codex 則更像結果導向的雲端工作者，適合長時間後端重構、複雜邏輯修復、雲端編譯測試與 PR 自動化。兩者不是簡單取代關係，而是對不同工作節奏的回答。

問題指出

如果團隊只用品牌或跑分選工具，容易把工具放錯場景。需要頻繁視覺互動的前端任務若交給只輸出 PR 的系統，人類會補很多驗證工作；需要長時間雲端沙盒執行的後端重構若硬放在本地工具，可能拖慢電腦、卡住工作流。工具錯配不是小問題，它會讓團隊誤判 AI 能力。

新觀念提出

本章提出「工具哲學對位」。選擇 AI 工具時，不先問模型多強，而要問四件事：工作是在本地還是雲端？需要即時互動還是非同步結果？信任依靠富媒體證據還是乾淨 Diff？任務偏 UI 迭代還是後端重構？當你用這些維度來看，就會知道不同工具其實對應不同工作流。

模型整理：Agentic Tool Selection Matrix

1. Local + Real-time：適合 UI、前端、跨目錄聯調與需要人快速回饋的任務。

2. Cloud + Async：適合大型重構、測試、PR、長時間後台工作與本機資源有限情境。

3. Artifact-rich：適合需要理解設計動機、可視化驗證與團隊審批的任務。

4. Diff-minimal：適合工程團隊已有成熟 PR review，偏好乾淨結果訊號的任務。

實際情境

作為顧問，你可以把這章做成企業選型工作坊。不要問客戶「你要不要導入 Antigravity 或 Codex」，而是先盤點任務組合：哪些工作需要即時 UI 驗證？哪些適合雲端跑一整晚？哪些需要 Artifacts 給主管審？哪些只需要 PR？最後再選工具。工具選型其實是工作流選型。

內化筆記

給自己讀的重點：不要成為工具品牌推銷員，要成為工作流架構師。不同工具的差異，應該被你轉譯成一般人懂的場景語言：本地調度台、雲端工人、視覺驗證、PR 交付、即時協作、背景執行。當你能把技術差異轉成工作情境，企業才聽得懂。

延伸提醒

這裡還有一個必須補上的判斷：任何新工具都會有版本、價格、跑分與功能限制的變動，因此本書不把單一數字當成永久結論，而把它轉化為可遷移的方法。換句話說，我們關心的不只是某個功能今天支援幾個代理、哪個模型預設啟用、哪個訂閱方案比較划算；我們真正關心的是，這些功能背後反映了什麼工作設計。只要抓住這一層，你就能在工具更新後快速重構自己的講法，而不會被產品細節牽著走。

案例拆解

案例拆解：同一個「重構會員系統」任務，在不同工具下應該有不同路線。若重點是後端邏輯重構、測試與 PR，雲端非同步代理更適合；若重點是會員頁面互動、表單驗證與前端視覺調整，本地即時瀏覽器代理更合適。這個案例可以教企業主管：不要把 AI 工具當單一答案，而要建立任務分類。工具策略的成熟度，取決於任務分流能力。

給自己的三個問題

- 這個任務需要本地即時互動，還是雲端非同步結果？

- 信任建立靠 Artifacts 還是 Diff？

- 團隊現在是不是用同一工具處理所有場景？

演講提煉

演講可以這樣收：Antigravity 問的是「你要如何看著 AI 一起工作」；Codex 問的是「你要如何把工作交到雲端等結果」。兩者都不是終點，真正的問題是你的團隊需要哪一種工作節奏。

章末金句

- 工具選型其實是工作流選型。

- 不要問哪個 AI 最強，要問哪個工作流最對。

- Antigravity 像本地調度台，Codex 像雲端工作者。

- 富媒體 Artifacts 建立理解，乾淨 Diff 追求交付效率。

- AI 架構師不推銷品牌，而是配置工作節奏。
