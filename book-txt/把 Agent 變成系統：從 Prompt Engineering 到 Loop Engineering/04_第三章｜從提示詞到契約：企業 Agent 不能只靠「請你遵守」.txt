第三章｜從提示詞到契約：企業 Agent 不能只靠「請你遵守」

提示詞是要求，程式契約才是保證。企業不能只拜託 AI 守規矩，而要讓系統真的攔得住它。

一、這一章要解決的問題

企業 Agent 的 Prompt 常寫得非常完整：只能使用公司核准的資料、不得洩漏內部推理、所有數字必須附來源、不能提供投資建議、輸出必須符合指定格式、遇到高風險情況要請主管批准。

看起來什麼都寫了。

問題是，寫在 Prompt 裡的規則仍然只是模型收到的文字。模型可能理解不完整、在長上下文中忽略、換一個模型後表現改變，也可能在輸出格式錯誤時把內部資訊直接吐給使用者。

這就像公司把門禁規則寫在牆上：「非相關人員請勿進入機房。」如果沒有門鎖、識別證、權限系統與稽核紀錄，牆上的文字只能表達期待，不能形成保證。

本章要處理的問題是：

哪些規則可以交給模型理解，哪些規則必須由系統執行？

二、用白話講清楚核心技術

《From Prompts to Contracts》提出 Harness Engineering，Harness 工程。Harness 原本有「繫具、控制裝置」的意思；放在 Agent 系統裡，可以理解成包圍模型、控制資料與行動流動的工程層。（R03）

模型仍然負責語言理解、組合與表達，但企業不可妥協的行為被移到模型外面：程式碼、Manifest、Schema、Validator、Trace 與輸出契約。

模型像引擎，Harness 像整台車

一顆引擎再強，也不能單獨上路。車子還需要方向盤、煞車、安全帶、儀表板、車門鎖與事故紀錄。

同樣地，大模型可以生成答案，但企業系統還需要：

• 哪些資料可以進入模型

• 問題應路由到哪個實體或公司

• 哪些來源被允許作為事實依據

• 輸出必須包含哪些欄位

• 哪些語句或資訊不得給使用者看到

• 哪些操作需要批准

• 每次執行留下哪些 Trace

• 驗證失敗時如何回退

Prompt 可以告訴引擎「請安全駕駛」，Harness 則真的提供煞車。

什麼是 Contract

這裡的 Contract 不是法律合約，而是系統可以檢查的行為契約。

例如一份企業研究答案可以定義：

1. entity_id 必須屬於允許清單。

2. 每個主要數字都必須連到已選定的來源識別碼。

3. 對外輸出不可包含內部 Trace 欄位。

4. 結果必須符合固定 JSON Schema。

5. 若資料不足，不得以推薦語氣補出結論。

6. 驗證未通過時，答案不得直接送給讀者。

這些條件可以被程式檢查，因此不必完全相信模型「自覺遵守」。

Harness 的幾個核心零件

1. Source Boundary：來源邊界

哪些資料是允許的權威來源？哪些資料只可參考？哪些資料完全不可讀？

來源邊界不應只寫成「請只使用可靠資料」，而要用資料清單、版本、授權與存取控制限制。

2. Entity Routing：實體路由

使用者問的是哪家公司、哪個客戶、哪個產品或哪個法域？如果路由錯誤，即使引用內容本身正確，也可能把甲公司的資料回答給乙公司。

實體辨識可以由模型提出候選，但最終路由應經過明確識別碼與程式驗證。

3. Schema：資料結構

輸出一定要包含哪些欄位？日期格式為何？來源如何表示？風險等級有哪些允許值？

Schema 把「請用這個格式」從禮貌要求，變成機器可以拒絕的不合格輸出。

4. Validator：驗證器

Validator 負責檢查契約。它可以檢查欄位完整、型別、來源連結、敏感字串、權限、禁止語言與其他可程式化條件。

5. Manifest：版本化規格

Manifest 記錄資料來源、模型、政策、規則與元件版本。當系統行為改變時，可以追溯是哪個版本造成差異。

6. Trace：可稽核軌跡

Trace 不是把模型所有內在思考暴露出來，而是保存必要的執行證據：輸入版本、來源選擇、工具呼叫、驗證結果、回退路徑、批准事件與輸出版本。

7. Composition Boundary：模型組合邊界

模型被放在一個可替換的位置，負責把已經過來源選擇與結構化的資訊組合成答案。邊界外的資料、規則、驗證與 Trace 由程式擁有。這樣換模型時，企業保證不必跟著全部重寫。

論文怎麼驗證 Harness

研究以五個韓國企業集團、二十五家上市公司的一個公開資料切片建立系統，並用三個 hosted models 執行共 270 次 composition-boundary runs。（R03）

需要精確理解結果：

• 程式擁有的檢查，包括 Trace、避免內部 Trace 洩漏、來源連結、後續問題品質與禁止推薦語言，在 270 次執行中全部維持。

• 模型負責組合的部分仍有失敗：第一輪有效結構為 234/270，最終整體 Harness 契約通過為 198/270。

• 失敗被檢查機制偵測並留下紀錄，沒有讓特定安全或洩漏違規直接穿透給讀者。

• 只用提示詞時，推薦語言與內部 Trace 洩漏仍可能抵達讀者；程式層 Harness 能攔截。

• 外掛式通用 Guardrail 也能阻擋部分違規，但在該消融實驗中出現較多過度拒絕，效用低於專門設計的 Harness。

所以，論文不是證明「有 Harness 後所有答案都正確」，而是證明：某些可程式檢查的企業保證，可以跨模型保持，而且模型失敗能在輸出邊界被發現。

三、論文真正想提醒我們什麼

論文提出什麼

它提出一種工程重構方式：把原本藏在 Prompt 與 Retrieval Context 裡的企業行為，轉成版本化、可檢查、可稽核的系統成分。模型保持可替換，來源與規則由 Harness 擁有。

論文沒有證明什麼

研究檢查的是程式可驗證契約能否維持，不是所有事實是否正確，也不是投資判斷品質。資料範圍是有限的公開資料切片，場景與契約也經過明確界定。不能因此宣稱任何企業只要加 Validator，就能消除幻覺或自動合規。

Harness 能保證的是它有能力檢查的條件。若契約本身漏寫規則、來源資料錯誤、驗證器有 Bug，系統仍可能失敗。

本書的核心推論

企業規則應按照「可執行程度」分類：

1. 意圖規則：適合寫進 Prompt，例如語氣、解釋深度、摘要風格。

2. 結構規則：適合寫進 Schema，例如必填欄位、型別、輸出格式。

3. 邊界規則：適合寫進程式與權限，例如可讀資料、可用工具、可寫位置。

4. 責任規則：適合設置人工批准，例如付款、發布、刪除、高風險建議。

越接近安全、法規、金錢、個資與不可逆行動，就越不能只依賴 Prompt。

四、這個技術如何改變 AI 教學

企業 Agent 課程不應只讓學生練習「寫一個很完整的系統提示詞」。更好的作業，是請學生把同一組規則分配到不同控制層。

例如建立一個企業文件問答 Agent：

• 「回答要白話」可以放在 Prompt。

• 「所有主要主張要附來源 ID」應放進輸出 Schema 與 Validator。

• 「只能讀指定部門文件」應放進存取權限與檢索範圍。

• 「不得顯示內部 Trace」應在回應組合層移除並驗證。

• 「涉及人事處分必須主管批准」應設人工 Gate。

學生最後要展示兩種測試：正常測試與故障注入。故意讓模型輸出缺欄位、引用錯誤來源、夾帶內部註記，確認系統是否真的攔住。

這比請學生在 Prompt 裡多寫十次「務必」更接近企業工程。

五、這個技術如何改變企業導入

企業可以從一份「不可只靠 Prompt 的規則清單」開始。

資料邊界

• 部門、客戶與租戶資料不得混用。

• 未授權資料不得進入模型上下文。

• 來源版本必須可追溯。

輸出邊界

• 必填欄位與格式必須通過 Schema。

• 未附來源的高影響主張不得發布。

• 內部 Trace、系統提示與機密欄位不得出現在外部答案。

行動邊界

• 讀取、寫入、刪除、付款、發布使用不同權限。

• 高風險工具使用前必須取得明確批准。

• 不可逆行動要有預覽與回復方案。

稽核邊界

• 每次執行記錄模型、規格、來源、驗證與批准版本。

• 驗證失敗不得被「靜默修掉」而不留紀錄。

• 模型替換要重跑固定測試集。

真正的企業 Agent，不是把 Prompt 放得更長，而是把保證放到模型外面。

六、連到李詩民的實際場景

企業內訓：把「請遵守」改成「系統會檢查」

可以讓學員拿一份公司規則，逐條回答：

• 這條只是風格要求，還是硬性規則？

• 可以自動檢查嗎？

• 如果違反，應重試、拒絕、升級還是人工批准？

• 哪個元件擁有這條規則？

這會讓企業知道，AI 治理不是寫一份漂亮政策，而是把政策轉成執行元件。

內容自動化：發布不是模型說完成就完成

一條社群發布流程可以設契約：

• 標題、摘要、平台標籤不得缺漏。

• 影片與字幕檔案必須存在且可開啟。

• 技術數據必須連到研究來源。

• 含「保證、治療、一定有效」等高風險字詞時必須人工複核。

• 發布前顯示預覽，取得批准後才呼叫平台 API。

創意仍由模型負責，發布資格由系統決定。

健身與健康 AI：建議語言需要分級

AI 可以提供一般運動教育，但涉及傷病診斷、疾病飲食、用藥或醫療處置時，不能只靠 Prompt 說「請不要給醫療建議」。系統可以依問題類型、使用者狀態與輸出語言觸發限制：

• 一般知識：允許回答並附範圍說明。

• 個人化訓練：要求確認健康狀態與教練審查。

• 疾病或急性症狀：不產生處方，改為安全引導與專業轉介。

這裡的重點不是把所有回答都拒絕，而是把不同風險放進不同契約。

美髮 AI：配方可以建議，實際施作需要專業 Gate

模型可以根據顧客偏好產生候選色彩與溝通稿，但過敏、頭皮狀況、漂染歷史與化學品用量不能只靠語言模型自由組合。系統應要求必填資料、限制可用產品、標示資料缺口，並把最終配方交由專業人員確認。

七、可以轉成課程的一句話

公司規則若只存在 Prompt 裡，就只是期待；能被程式檢查、阻擋與留下證據，才是系統保證。

八、可以轉成 FB 貼文的一段話

企業導入 AI 最危險的錯覺，是以為把規則寫進 Prompt，就等於建立了治理。你可以叫模型「不要洩漏內部資訊、所有數字要附來源、不要給高風險建議」，但這些仍只是文字要求。真正的企業 Agent，要把來源邊界、輸出格式、權限、敏感資訊、批准節點寫進程式、Schema、Validator 與 Trace。Prompt 負責表達意圖，Contract 負責提供保證。不要只拜託 AI 守規矩，要讓系統真的攔得住它。

九、這章的延伸問題

1. 哪些企業規則可以被完全程式化，哪些仍需要語意判斷？

2. Validator 自己出錯時，如何測試與監控？

3. 模型替換後，哪些固定測試必須重新執行？

4. 過度嚴格的 Guardrail 如何避免把正常需求一起拒絕？

5. Trace 應保留哪些證據，又如何避免保存機密或不必要的內部推理？

6. 誰有權修改契約？修改後是否需要重新批准與版本化？

7. 當 Prompt 與程式契約衝突時，哪一層具有最高權威？

李詩民式總結

我會把這一章濃縮成一句很直接的話：企業不要把規則寫在 Prompt 裡，然後祈禱模型照做。

Prompt 可以告訴 AI 我們希望它怎麼表現，但只要牽涉資料權限、來源、敏感資訊、對外發布與高風險行動，就要有真的門鎖、真的煞車、真的驗收。

我不是不要 Prompt，而是不要讓 Prompt 承擔它做不到的責任。模型可以被替換，企業的邊界不能跟著消失。

章末金句

1. Prompt 是要求，Contract 才是保證。

2. 寫在牆上的門禁規則，不等於門上真的有鎖。

3. 模型可以犯錯，系統不能讓所有錯誤直接穿透。

4. 可稽核不是保存更多文字，而是保存可驗證的責任證據。

5. 能換模型而不失去邊界，才算真正的企業架構。

6. 越接近金錢、個資與不可逆行動，越不能只依賴語言模型自律。

7. 治理不是提醒 AI 小心，而是決定它做不到什麼。
