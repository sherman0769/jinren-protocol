第四章｜讓 Agent 探索，讓系統接手：成功流程的漸進式固化

不是讓 Agent 永遠參與每一步，而是讓它發現一條路，再把這條路變成系統。

一、這一章要解決的問題

第一次面對未知任務時，我們需要 Agent 的彈性。它可以閱讀環境、嘗試工具、提出計畫、處理例外，甚至在原本方法失敗後換一條路。

但如果同一種任務已經成功十次、二十次，系統仍讓大模型每次重新理解、重新規劃、重新選工具，就會出現一個奇怪現象：流程愈成熟，成本卻沒有下降；經驗累積愈多，系統仍像第一次上班。

這就像每次沖咖啡都召開一場專家會議，重新討論水溫、比例與杯子。第一次研發配方需要探索，但配方穩定後，真正合理的做法是把可重複部分寫成標準流程，只把豆況、客人偏好與例外情況留給人的判斷。

Agent 很會探路，但不應永遠當同一條路上的全職嚮導。

本章要回答：

一條由 Agent 探索成功的路，如何逐步變成便宜、穩定、可重現的系統？

二、用白話講清楚核心技術

《Progressive Crystallization》提出 漸進式固化。Crystallization 原意是結晶：原本流動、可變的東西，在條件成熟後形成較穩定的結構。（R04）

論文把執行方式分成三類，從最固定到最自由：

Type 1：Deterministic Workflow，確定性工作流

流程由程式、規則與固定工具執行，不需要每次呼叫 Agent 規劃。輸入相同、環境相同時，結果具有高度可重現性。

例如：

• 依命名規則建立資料夾

• 轉換音訊格式

• 驗證字幕檔案

• 將通過核准的素材發布到指定位置

• 執行固定測試與報表

這類流程成本低、速度快，也容易稽核。

Type 2：Hybrid Workflow，混合工作流

穩定步驟由程式處理，仍需要判斷、創意或例外處理的部分交給 Agent。

例如內容流程中：檔案建立、格式轉換、版本命名與發布驗證固定化；主題提煉、文案方向與例外修正仍由模型處理。

這通常是最實用的中間狀態。

Type 3：Agent-Orchestrated Workflow，Agent 編排工作流

Agent 根據當下環境決定步驟、工具與順序。它適合新問題、未知環境、一次性任務與高度變動的情境。

這三類不是能力高低，而是適用問題不同。最自由不一定最成熟，最固定也不一定最聰明。成熟的系統會把不同工作放在合適執行型態，而不是追求全部 Agent 化。

Promotion：用證據升級，而不是憑感覺寫死

漸進式固化不是某位工程師看到流程成功兩次，就直接把它硬寫成腳本。論文強調以證據為基礎的升級機制：

1. 從多次 Agent 執行軌跡找出重複模式。

2. 抽取穩定的步驟、條件、工具與輸出。

3. 建立可驗收的測試與成功標準。

4. 先轉為混合流程，觀察是否仍能處理變化。

5. 證據足夠後，再轉成確定性流程。

也就是說，固化的對象不是「Agent 說它學會了」，而是「在可觀察案例中，這條路反覆通過驗收」。

Demotion：環境變了，流程要能退回

真正重要的是，論文不只設計升級，也設計降級。

如果外部 API 改版、資料格式改變、測試失敗、成功率下降，確定性流程不應假裝一切正常。它要能退回混合或 Agent 編排模式，重新探索。

這像高速公路與山路。路況穩定時，開啟定速巡航；遇到施工、濃霧或封路，就把控制權收回來。成熟不是永遠自動，而是知道何時取消自動。

從軌跡抽取流程

Agent 執行時留下的 Trace，會成為固化原料。系統可以分析：

• 哪些工具總是按相同順序被呼叫

• 哪些參數已經穩定

• 哪些分支其實很少發生

• 哪些驗收條件可以程式化

• 哪些步驟仍需要語意判斷

• 失敗時通常如何修復

這也說明第一章為什麼要保存工作流。沒有結構化 Trace，就沒有足夠材料判斷什麼可以固化。

生產案例中的結果

論文報告一個雲端網路維運 AIOps 生產案例。系統每月處理數萬起事件，八個月內，確定性流程的執行占比從 0% 增加到約 45%，混合流程約 30%，Agent 編排約 25%。同期事件量約增加一倍，但每起事件的 Agent 成本下降超過 70%。（R04）

這是很有力的案例，但必須保留邊界：它來自單一組織、單一營運領域，成本數字是平台層觀察，不是隨機控制實驗；在高度一次性、幾乎沒有重複模式的環境，固化效益會比較小。

三、論文真正想提醒我們什麼

論文提出什麼

Agent 平台不必永遠是固定成本中心。可以把 Agent 探索視為「發現流程」的階段，將反覆驗證的行為逐步轉成零或低 Token 的確定性工作流，並在退化時自動降級。

論文沒有證明什麼

它沒有證明所有 Agent 任務都能固化，也沒有提供放諸四海皆準的成功次數、升級門檻或成本比例。對創意、研究、危機處理與高度新穎任務，Type 3 可能長期保留。

自動升級還依賴驗收測試品質。如果測試太弱、觀察案例太少，流程可能過早固化，把 Agent 偶然成功誤認成穩定規律。論文因此把降級與人工審查納入設計。

本書的核心推論

每次讓 Agent 重新推理一個已知流程，都在支付一筆「探索稅」。探索稅在第一次合理，在第一百次可能只是浪費。

但固化太早也會產生「僵化債」：流程看似便宜，實際上無法處理環境變化，最後用更多人工修補。

Loop Engineering 的工作，不是消滅探索，而是在探索稅與僵化債之間找到動態平衡。

四、這個技術如何改變 AI 教學

AI 自動化課程常教學生「串出一條流程」，卻很少教流程如何成熟。可以把課程改成三輪：

第一輪：自由探索

學生讓 Agent 自行規劃，完整記錄工具、參數、失敗與修復。目標不是立刻最省，而是找到能成功的路。

第二輪：辨識穩定與不穩定

學生把每一步標成：

• 已穩定，可程式化

• 需要模型判斷

• 需要人工批准

• 只在例外時發生

並建立驗收測試。

第三輪：固化與回退

學生把穩定部分改成腳本或固定節點，再故意改變輸入、API 或資料格式，測試流程是否能偵測退化並退回 Agent。

這樣學生學到的不是「怎麼讓 AI 永遠做全部事情」，而是「怎麼讓系統愈做愈便宜、愈穩定，卻仍保留適應力」。

五、這個技術如何改變企業導入

企業可以把 Agent 投資分成兩種預算：

• 探索預算：允許模型試錯，找出可行流程。

• 營運預算：要求穩定、可預測與可稽核。

很多企業的錯誤，是用探索型 Agent 直接承擔永久營運，導致每次執行都昂貴；或者一開始就把流程寫死，還沒理解問題便失去彈性。

更合理的導入方式是建立「升降級委員會」或規則：

1. 某類任務執行量是否足夠？

2. 成功路徑是否高度一致？

3. 是否有可靠驗收測試？

4. 失敗是否可安全回退？

5. 固化後節省多少成本與時間？

6. 環境變動頻率是否可接受？

7. 誰批准轉成確定性流程？

企業不只要看自動化率，也要看三種類型的執行比例。對重複性高的系統，Type 1 占比逐步增加，可能代表知識已被吸收；但若所有事情都被硬推成 Type 1，反而可能代表系統失去適應力。

六、連到李詩民的實際場景

內容自動化：創意留給 AI，搬運交給系統

第一次建立「想法到影片」流程時，可以讓 Agent 探索文案拆解、聲音生成、首幀設計、字幕與上架方式。當流程跑過多次後，可以逐步固化：

適合固定化的部分

• 資料夾與檔名規則

• 素材讀取順序

• 音訊格式與取樣率轉換

• 字幕檔案格式

• 平台欄位與上傳順序

• 發布後驗證

• 檔案存在與非空白檢查

適合保留給 Agent 的部分

• 主題提煉

• 開場與觀點選擇

• 視覺風格候選

• 例外錯誤診斷

• 不同平台的語氣調整

必須保留給人的部分

• 作者觀點是否被扭曲

• 高風險技術與健康說法

• 正式發布批准

• 品牌與倫理判斷

Codex 專案：讓成功步驟變成腳本

如果 Agent 每次建立新專案都重做相同動作，可以將下列步驟固化：

• 建立標準資料夾

• 安裝固定依賴

• 執行 lint、test、build

• 產生驗收報告

• 檢查不得修改範圍

• 打包交付檔案

Agent 的價值改為處理需求理解、架構選擇、錯誤診斷與新例外，而不是一再重複機械工作。

課程生產：把每次備課變成可進化流程

一開始用 Agent 探索：研究來源、章節順序、案例與練習。當課程框架穩定後，把來源登錄、簡報格式、講義匯出、作業模板、檔案驗證固定化。每次更新只把新的研究與教學判斷交給 AI。

這樣課程不只是被 AI 做得更快，而是會隨每次執行累積成可重複的教學系統。

七、可以轉成課程的一句話

Agent 的工作不是永遠替系統重想一次，而是先替系統找到路，再把可重複的路交還給程式。

八、可以轉成 FB 貼文的一段話

很多人把 Agent 當成永遠在線的全能員工，同一件成功過幾十次的事，仍每次叫大模型重新規劃。這其實是在一直支付探索成本。比較成熟的做法是：第一次讓 Agent 自由找路，反覆成功後，把檔名、格式、測試、發布與驗收固化成確定性流程，只把創意、判斷與例外留給 AI。Agent 負責發現，系統負責記住。真正成熟的 Agent 平台，應該愈用愈便宜、愈穩定，而不是任務愈多，Token 帳單只會等比例上升。

九、這章的延伸問題

1. 一條流程要成功幾次，才有資格固化？

2. 驗收測試如何避免只覆蓋已看過的案例？

3. 確定性流程失效時，如何自動退回 Agent 而不造成中斷？

4. 哪些創意工作永遠不適合完全固化？

5. 固化後，原本的 Agent Trace 應保存多久？

6. 如何衡量探索稅與僵化債？

7. 企業應把「Type 1：Type 2：Type 3 比例」當成成熟度指標嗎？

李詩民式總結

我不會再把「Agent 參與愈多」當成系統愈先進。真正成熟的系統，應該知道哪些地方需要 AI，哪些地方其實早就不需要 AI。

第一次做，讓 Agent 探索；做出穩定模式後，讓程式接手；環境改變，再讓 Agent 回來。這不是削弱 Agent，而是把它放在最有價值的位置。

我希望建立的不是一套永遠依賴模型重新思考的流程，而是一套會從每次成功裡學到怎麼減少下次思考的系統。

章末金句

1. Agent 是探路者，不該永遠當同一條路上的作業員。

2. 每次重新推理已知流程，都是在支付探索稅。

3. 固化不是一次寫死，而是用證據逐步交接控制權。

4. 能升級也能降級，才是真正成熟的自動化。

5. 最好的 Agent 系統，會把自己的成功變成下一次不必再思考的基礎。

6. 創意留給模型，搬運交給程式，責任留給人。

7. 自動化的終點不是沒有 AI，而是每一種能力都被放在最適合的位置。
