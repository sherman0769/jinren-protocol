第十章｜從對話到委派：Codex 顯示 AI 工作單位正在變大

Agent 時代的工作單位，不再是一句回答，而是一段能持續執行、留下成果與紀錄的任務。

一、這一章要解決的問題

當我們使用聊天式 AI 時，最自然的節奏是：問一句、看回答、再問下一句。

每一輪都由人發動。模型停下來，人再決定下一步。這種互動很適合討論、腦力激盪、改寫與短任務。

Coding Agent 與一般工作型 Agent 出現後，任務開始變大。

使用者不再只問：「這段程式哪裡有錯？」

而是交付：「閱讀專案、重現錯誤、定位原因、修改程式、執行測試、更新文件，最後告訴我改了什麼。」

這已經不是一個回答，而是一段工作。

當 AI 接手的單位從幾秒鐘回答變成數十分鐘、數小時的委派任務，人面對的新問題也跟著改變：

• 任務怎麼寫才不會愈做愈偏？

• Agent 能讀、能改、能執行到什麼程度？

• 多個 Agent 並行時，如何避免互相覆蓋？

• 中途失敗如何恢復？

• 什麼叫完成？

• 人何時檢查，何時批准，何時接管？

• 最後交付的是一段文字，還是一組可驗證成果？

本章要處理的核心轉變是：

當 AI 的工作單位變大，使用者就不能只當提問者，而要開始成為任務設計者與 Agent 工作的管理者。

二、用白話講清楚核心技術

《The Shift to Agentic AI: Evidence from Codex》與 OpenAI 官方文章，分析 Codex 的採用與使用型態，試圖描述 AI 如何從短互動走向較長、可委派的工作。（R10）

從回答到行動

聊天模型的主要輸出是內容。

Agent 的主要特徵則是，它能在迴路裡採取行動：讀取檔案、呼叫工具、執行程式、觀察結果、修改方案，再繼續下一步。

可以用「問路」與「委託送貨」來比喻。

問路時，你需要一段清楚的說明。

委託送貨時，你還需要地址、物品、交付條件、時間、權限、收件證明與異常處理。即使對方很聰明，沒有任務規格也可能把東西送到錯的地方。

Agent 讓 AI 從提供建議，進入實際改變工作狀態的角色。

使用資料透露的方向

OpenAI 官方分析指出，Codex 活躍使用者在 2026 年上半年快速成長，非開發者的採用增速也很明顯。到 2026 年 5 月，在抽樣的個人使用者中：

• 80.6% 至少提出過一次估計超過三十分鐘人工作業的請求。

• 70.2% 至少提出過一次估計超過一小時的請求。

• 25.6% 至少提出過一次估計超過八小時的請求。（R10）

這些數字不能被解讀成 Codex 實際節省了相同工時。

論文與官方文章使用模型或分類器估計「若由人完成大約需要多久」，資料來自抽樣且有隱私與樣本範圍限制。它比較適合用來觀察任務複雜度的方向，而不是當成精準生產力會計。

研究也提到，部分使用者開始同時管理多個 Agent，並使用可重複的 Skills。這代表工作方式正從「一次只處理一個對話」，走向「分派多個任務、等待結果、檢查與整合」。但外部採用仍不平均，組織內部的高強度使用也不能直接代表所有產業。（R10）

Agent 任務需要什麼工作單位

一個可委派任務至少包含八個部分。這是本書根據 Agent 實務整理的「任務包」，不是論文原有標準。

1. Objective｜目標

最後要達成什麼狀態？不是只說「研究一下」，而是說明要產生什麼決策或交付物。

2. Workspace｜工作空間

Agent 在哪裡工作？可讀哪些資料夾、Repository、文件與系統？

3. Inputs｜輸入

哪些資料是權威來源？哪些只是參考？哪些資訊不能使用？

4. Constraints｜限制

不得修改哪些檔案、不得存取哪些資料、不得對外發布什麼、哪些工具禁止使用。

5. Acceptance Criteria｜驗收條件

什麼叫完成？測試要通過哪些項目？文件要包含哪些欄位？格式與品質標準是什麼？

6. Checkpoints｜檢查點

任務進行到哪裡需要保存狀態、回報風險或等待批准？

7. Authority｜權限

Agent 可以自行決定什麼？哪些行動需要人批准？哪些事情完全不能做？

8. Deliverables｜交付物

最後要交付檔案、變更摘要、測試報告、來源清單、失敗紀錄或其他證據。

Prompt 只是任務包的一部分。

當任務時間變長，任務包的重要性會比一句漂亮指令更高。

多 Agent 並行不是多開幾個視窗

如果三個 Agent 同時工作：一個查資料、一個寫程式、一個做文件，它們可能互相依賴，也可能修改同一份內容。

真正的並行需要：

• 明確分工

• 隔離工作空間或分支

• 共享狀態

• 依賴順序

• 衝突處理

• 統一驗收

• 最後整合責任

否則，多 Agent 只會把一個混亂放大成三個混亂。

從等待回覆到管理隊列

當工作單位變大，人不需要一直盯著每一個 Token，但需要管理任務隊列：

• 哪些任務正在執行

• 哪些任務卡住

• 哪些結果等待審查

• 哪些前置工作尚未完成

• 哪些結果可以進入下一階段

這也是 Human on Loop 的雛形。人不一定親自做每一步，而是設計優先順序、風險門檻與接管條件。

三、論文真正想提醒我們什麼

論文與官方資料提出什麼

Codex 的使用資料顯示，使用者正在交付較長、較複雜的任務，Agent 也從工程工作逐步擴散到其他知識工作。任務的持續時間、並行程度與可重複 Skills 都在增加。（R10）

它們沒有證明什麼

這些資料不等於 Agent 已在所有職業普遍取代人工，也不能單獨證明每一個長任務都成功、節省相同時間或帶來相同生產力。

使用者成長、任務估計工時與功能採用，是行為證據；真正的品質、重工、風險、組織改造與長期成效仍需要其他研究。

本書的核心推論

當工作單位變大，最重要的使用技巧會從「回答品質」轉向「委派品質」。

短對話出錯，人可以立刻修正。

長任務出錯，Agent 可能已經修改數十個檔案、呼叫多個工具、累積錯誤假設，再交付一個看似完整的成果。

因此，Agent 能力愈強，前置規格、過程可見性與驗收就愈重要。

這也解釋了本書前面幾章為什麼彼此相連：

• 工作流要保存，才能知道長任務發生什麼。

• 記憶要主動提醒，才能避免早期條件被埋沒。

• 契約要程式化，才能限制 Agent 的行動邊界。

• 成功路徑要固化，才能避免每次重新探索。

• 交接要結構化，才能讓任務一開始就有可執行方向。

四、這個技術如何改變 AI 教學

AI 教學需要從「提示詞練習」增加「委派練習」。

從單題作業改成任務包

例如，不只要求學生「請 AI 做一份市場分析」，而要交付：

• 問題定義

• 可用資料

• 來源邊界

• 分析步驟

• 風險假設

• 驗收條件

• 最終報告與執行紀錄

教學生設計可驗收成果

「寫得好」太模糊。

可以改成：

• 所有數字附來源與日期

• 明確區分事實與推論

• 提供三個方案與適用條件

• 不使用未查證案例

• 執行指定測試

• 產出可開啟的檔案

讓學生管理多 Agent，而不是只觀察展示

一個 Agent 研究、一個 Agent反駁、一個 Agent編輯，最後由學生整合。評分重點不是誰生成得最多，而是學生是否能分工、處理衝突與做最後責任判斷。

把失敗納入作業

學生應提交 Agent 哪裡做錯、為什麼、如何改規格或驗收。這比只展示成功結果更接近真實工作。

五、這個技術如何改變企業導入

企業要從「提供每個員工一個聊天介面」，走向「建立可治理的任務系統」。

任務分級

可以依風險與可逆性，把 Agent 任務分為：

• 建議型：只產生草稿或分析，不改變正式系統。

• 準備型：建立變更、文件或操作計畫，等待人批准。

• 執行型：在限定範圍內自動操作，可回退並有完整紀錄。

• 高風險型：涉及金錢、法律、健康、個資或生產環境，必須有更嚴格批准與監控。

工作空間隔離

Agent 應在沙盒、分支、暫存環境或最小權限帳號中工作，先驗證再合併，避免一次錯誤直接影響正式資料。

以交付證據取代「它說完成了」

系統應要求：

• 測試結果

• 變更差異

• 來源與版本

• 已知限制

• 未完成項目

• 批准與發布紀錄

Agent 的文字自述不是完成證明。

重新設計主管角色

主管不需要審閱每一個中間 Token，但需要定義任務模板、風險級別、驗收政策與例外處理。管理能力會從分配人力，延伸到分配 Agent、資料、工具與權限。

六、連到李詩民的實際場景

出書工作流：從「幫我寫一章」到完整出版任務

一個真正可委派的出書任務，不只包含章名。它還要交代：

• Book Bible

• 章節唯一任務

• 可用研究來源

• 禁止虛構的內容

• 字數與語氣

• 需要生成的 Markdown、DOCX 與 QA 報告

• 研究與引用規則

• 驗收方式

Agent 可以負責研究、寫作、整合與檔案建立，但最終主張、作者經驗與出版決策仍由人負責。

內容自動化：多 Agent 不等於無人管理

可以讓研究 Agent 找資料、文案 Agent 寫稿、視覺 Agent 產生分鏡、影片 Agent 組合素材、發布 Agent 準備平台欄位。

但它們需要共享同一個專案狀態，明確知道哪一版文案已鎖定、哪些事實已查核、哪些素材獲得批准。否則，每個 Agent 都可能各自做出「最合理」但彼此不一致的版本。

Codex 教學：交付一個可驗證專案

教學重點可以從「叫 Codex 寫一個函數」升級成：

• 讀懂現有 Repository

• 建立重現測試

• 在獨立分支修改

• 執行測試

• 說明影響範圍

• 產生變更摘要

• 保留人工合併權限

這才是真正的 Coding Agent 工作方式。

企業內訓：教主管管理 AI 任務

主管需要學的不只是寫 Prompt，還要學：

• 任務適不適合委派

• 怎麼設定權限

• 怎麼看檢查點

• 怎麼讀失敗紀錄

• 什麼情況要停止或接管

• 怎麼把成功模式變成組織流程

這會讓 AI 內訓從工具示範，走向工作設計。

七、可以轉成課程的一句話

當 AI 可以工作一小時，真正重要的就不再只是第一句怎麼問，而是整個任務怎麼定義、怎麼檢查、怎麼交付。

八、可以轉成 FB 貼文的一段話

Codex 帶來的改變，不只是程式寫得更快，而是 AI 的工作單位正在變大。以前我們交給 AI 一個問題，現在開始交給它一段任務：讀專案、找錯誤、修改、測試、寫文件、留下成果。當任務從幾秒變成幾十分鐘甚至數小時，Prompt 就不夠了。你要設計工作空間、資料來源、不得修改範圍、驗收條件、檢查點與批准權限。Agent 時代真正的新能力，不只是會用 AI，而是會把工作委派給 AI，並且知道怎麼驗收、接管與追責。

九、這章的延伸問題

1. 哪些工作適合整段委派，哪些工作應拆成短任務？

2. 多 Agent 如何共享狀態，又不互相污染工作空間？

3. Agent 的完成聲明需要哪些外部證據？

4. 任務估計工時如何避免被誤解成實際節省工時？

5. 非工程師使用 Agent 時，需要哪些新的數位能力？

6. 主管應審查每一個結果，還是建立抽查與風險分級？

7. Agent 造成錯誤時，責任如何在使用者、組織、模型供應商與系統設計者之間分配？

8. 當多個 Agent 同時工作，什麼條件下應暫停整個任務隊列？

李詩民式總結

以前我會把 AI 想成一個很會回答問題的人。

現在我更常把它看成一個可以接受任務的工作角色。

角色一改，管理方式就必須改。

我不能只丟一句話，然後等它回來告訴我「完成了」。我需要先把目標、資料、權限、驗收與交付說清楚，也要讓它在中間留下狀態與證據。

未來真正有價值的人，不只是自己做得快，也不只是 Prompt 寫得漂亮。

而是能把一件複雜工作拆成多個可委派、可驗收、可接管的任務，讓人與 Agent 一起完成更大的事。

章末金句

1. 回答是內容，委派是責任。

2. Agent 的任務愈長，前置規格就愈不能模糊。

3. 多開三個 Agent，不等於擁有一支團隊。

4. Agent 說完成了，只代表它停止了；驗收通過，才代表任務完成。

5. 未來的 AI 使用者，也會是 AI 工作的管理者。

6. 可委派的工作，必須先被定義成可驗收的工作。

7. 人不需要盯著每一步，但不能放棄對最後結果的責任。

8. 從對話到委派，改變的不只是介面，而是工作的基本單位。
