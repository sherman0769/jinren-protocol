序章｜為什麼我們不能只停留在 Prompt Engineering？

這本書以 2026 年 6 至 7 月間十項 AI Agent、工作流、記憶、企業治理、Coding Agent、影片推理、人體動作、AI 教育、營養安全與 Codex 使用研究為起點，目的不是把論文翻譯成摘要，而是協助作者理解、內化，再轉成課程、演講、企業內訓與社群內容。

正文用 R01–R10 標示主要研究來源，完整作者、連結、支持觀點與限制收錄於書末參考資料及 03_research/research_registry.md。

研究證據採分層閱讀：概念模型不當成成熟標準；單一生產案例不外推成所有產業保證；描述性使用紀錄不直接解讀為因果成效；視覺辨識與生成能力不自動升級成健康、教育或專業責任。

本書的九層 Loop Engineering、D／I／H／A、工作流護照、記憶觸發器、探索稅、僵化債務、五層教育評估、六段式健康安全迴路、Agent 任務包與成熟度分級，均為本書整合研究後提出的工作概念，不宣稱是既有產業標準。

書中內容自動化、Coding Agent、健身 AI、美髮 AI、教育與企業場景，除明確標示研究案例外，均以一般或假設情境呈現，不冒充作者已完成的客戶專案或學員成果。

AI 的下一階段，不是更會回答，而是更能進入真實工作流，並留下可檢查的證據。

一、這一章要解決的問題

過去幾年，我們學習生成式 AI，常從同一個問題開始：我要怎麼問，模型才會回答得更好？

這個問題沒有錯。模型剛進入日常工作時，提示詞確實是最直接的槓桿。角色說清楚、背景補完整、格式定義好、限制寫明白，輸出通常就會進步。於是我們學會了角色提示、少樣本示範、思考步驟、格式約束與上下文補充，也逐漸把「會不會用 AI」理解成「會不會下 Prompt」。

可是，當 AI 從聊天工具走向 Agent，困難開始出現在回答之後。

它讀了哪些檔案？用了哪些工具？為什麼選擇這條路？有沒有記住前面交代過的限制？結果由誰檢查？失敗後要重試、回退還是停下？它能不能修改正式資料？如果把內部資訊帶到外部輸出，誰來攔截？如果一個流程已經成功十次，為什麼第十一次仍要讓模型重新推理全部步驟？

這些問題，都不能只靠再補一句「請你務必遵守」解決。

OpenAI 對 Codex 使用情形的研究指出，Agentic AI 正把知識工作的單位，從一次互動轉向可委派的長時間任務。到 2026 年 5 月，抽樣個人使用者中，有 80.6% 至少送出過一次被估計為超過三十分鐘人工作業的任務，70.2% 曾送出超過一小時的任務，25.6% 曾送出超過八小時的任務。這些時間由模型估算，只能看成方向性指標；但方向非常清楚：人正在把更大的工作單位交給 AI。（R10）

以前，我們叫 AI 寫一段文案、解釋一個函數、整理一份會議紀錄。現在，我們開始叫它研究一個主題、修改一個專案、執行測試、建立檔案、比較版本、整理交付物，甚至同時讓多個 Agent 分工。

當工作單位變大，Prompt 就不再是全部。我們需要開始設計整個迴路。

二、用白話講清楚核心技術

最簡單的 Agent 迴路可以寫成：

接收目標 → 讀取脈絡 → 選擇行動 → 呼叫工具 → 觀察結果 → 判斷是否完成 → 繼續、重試、升級或停止

Prompt Engineering 主要處理的是：「我要怎麼對模型說？」

Loop Engineering 處理的是：「這套系統要怎麼讓模型持續工作，而且每一輪都知道自己正在做什麼、能不能繼續、做得對不對、出了問題由誰接手？」

可以把它想成餐廳。

Prompt 像客人下單：「我要五分熟牛排，不要奶油，配菜換成蔬菜。」訂單很重要，但餐廳能不能穩定營運，還取決於廚房是否收到正確訂單、過敏資訊是否被標記、食材是否符合規格、溫度是否被檢查、出餐前是否核對、出錯如何重做，以及哪些特殊情況必須交給主廚。

沒有人會認為，只要客人把點餐內容講得夠清楚，一間餐廳就會自動變成可靠的營運系統。但企業導入 AI 時，我們常做出類似的事：把規則全部塞進 Prompt，然後期待模型自己記得、自己遵守、自己驗證、自己判斷何時停止。

這就是 Prompt Engineering 與 Loop Engineering 的分界。

本書把 Loop Engineering 整理成九個層次。這是本書用來閱讀與整合近期研究的工作框架，不是已被產業正式認證的標準。

1. Prompt 層：把意圖說清楚

定義目標、背景、限制、輸出格式與完成條件。Prompt 仍然重要，只是不再承擔整套系統的責任。

2. Tool 層：提供可以採取的行動

檔案、瀏覽器、資料庫、程式執行環境、企業 API、MCP 連接器與其他外部服務，都屬於工具層。工具決定 Agent 能做什麼，也決定它可能造成什麼影響。

3. Workflow 層：安排任務如何前進

把工作拆成狀態、步驟、分支、重試、停止與交接。它回答的是：事情應該按照什麼順序前進？

4. Memory 層：在關鍵時刻恢復重要資訊

記憶不只是儲存。真正重要的是，哪一段資訊必須在什麼節點重新影響決策。

5. Contract 層：把不可違反的規則寫進系統

欄位、來源、權限、格式、敏感資訊與禁止行為，不能只靠模型自律。需要 Schema、Validator、政策與程式碼形成可執行契約。

6. Eval 層：定義什麼叫正確與完成

有些結果可以用單元測試驗證，有些需要 Rubric，有些需要第二個模型審查，有些必須由人批准。Eval 決定系統何時可以繼續、重試或停止。

7. Crystallization 層：把成功路徑逐步固化

Agent 適合探索未知；已經反覆成功的流程，不應永遠支付完整推理成本。成熟路徑可以逐步轉成確定性程式。

8. Governance 層：管理權限、稽核與責任

誰可以讀哪些資料？誰能批准高風險行動？模型與流程如何版本化？出錯後如何追溯？這些都不是模型自己決定的事。

9. Human on Loop 層：人站在迴路上方設計與放行

人不必每一步親手操作，但必須設計權限、驗收、升級與接管規則。真正成熟的 Human on Loop，不是等系統出事才救火，而是先定義什麼情況必須停下、什麼結果才能放行。

三、論文真正想提醒我們什麼

今天這批研究看似分散：有工作流保存、主動記憶、企業契約、Coding Agent、影片生成、人體動作、教育與營養健康。放在一起看，它們其實都在回答同一個問題：當 AI 開始進入真實工作，我們要如何管理它的過程，而不只欣賞它的輸出？

《Workflow as Knowledge》提醒我們，工作流本身可以成為可檢查、可恢復、可審查的知識物件。（R01）

《Remember When It Matters》提醒我們，長任務裡重要資訊即使仍存在，也可能不再影響行動；記憶系統必須決定何時介入。（R02）

《From Prompts to Contracts》提醒我們，企業規則不能只靠提示詞，而要用程式層契約攔截違規輸出。（R03）

《Progressive Crystallization》提醒我們，Agent 應該發現路徑，而不是永遠重走已經學會的路。（R04）

Bug report 研究提醒我們，Agent 不是讀心術；任務交接需要具體、可執行、可定位與可驗收。（R05）

OpenCoF 與 ARDY 顯示，Agentic 思維也在進入影片與動作生成：模型不只是產出一張結果，而是在時間中維持狀態、條件與變化。（R06、R07）

教育與健康研究則提醒我們，使用率、辨識能力與流暢語言，都不等於學習成效、物理準確度或專業安全性。（R08、R09）

這些研究共同指出：模型能力提升後，新的瓶頸會移到模型外面。下一步不只是找更聰明的模型，而是建立更可靠的系統。

四、這個技術如何改變 AI 教學

過去的 AI 課程常把主要時間放在提示詞：角色怎麼設定、格式怎麼要求、範例怎麼提供、語氣怎麼控制。這些仍然值得教，但如果停在這裡，學生學到的仍是一種「一問一答」的使用方式。

Agent 時代的課程，至少還要加入五種能力。

第一是任務定義。學生要能把模糊需求轉成目標、輸入、限制、完成條件、不得修改範圍與失敗處理方式。

第二是工具與權限。學生要知道 Agent 可以讀什麼、寫什麼、執行什麼，以及哪些操作具有不可逆影響。

第三是狀態與記憶。學生要能指出長任務中哪些資訊必須持續保存，哪些資訊只需在特定節點提醒。

第四是驗證。學生不能只說「看起來不錯」，而要能定義哪些部分可以程式測試、哪些需要評分規準、哪些一定要人批准。

第五是過程交付。未來的 AI 作業不應只交成品，還應交任務規格、來源、工作流、失敗紀錄、驗收結果與人工批准點。

AI 教學將從「如何叫模型產生東西」，進入「如何設計一套可以負責任地產生東西的系統」。

五、這個技術如何改變企業導入

企業導入 AI 最常見的起點，是做一個聊天機器人。它能查文件、回答問題、整理會議內容，第一階段往往看起來很成功。真正的問題通常在第二階段才出現：使用者變多、資料變多、權限變複雜、任務開始跨系統之後，企業才發現不知道答案引用了哪個版本、不知道 Agent 看過哪些資料、不知道錯誤發生在哪一步，也不知道換模型後規則是否仍然存在。

這時企業需要的已經不是再找一位提示詞高手，而是一套 Agent Operating Model：

• 哪些事情可以由模型判斷？

• 哪些事情必須程式驗證？

• 哪些事情需要人工批准？

• 哪些事情完全禁止執行？

企業 AI 的成熟度，不是只看 Agent 能做多少，而是看企業能否說清楚每個行動的依據、邊界、證據與責任。

六、連到李詩民的實際場景

這套觀念可以直接連到內容自動化、健身 AI、美髮 AI 與企業內訓。

在內容自動化裡，真正要建立的不只是「模糊語意 → 文案 → 語音 → 首幀 → 影片 → 字幕 → 上架」，而是一條能回答版本、來源、模型、人工批准、失敗重跑與驗收條件的流程。

在健身 AI 裡，系統不只要會推薦動作，還要知道何時喚回傷病紀錄、哪些角度屬於高風險、哪些建議必須由教練放行。

在美髮 AI 裡，系統不只要生成髮色，而要在配方形成前重新檢查過敏、漂髮歷史、頭皮狀態與客戶曾否決的方向。

在企業內訓裡，教學內容也會從「如何使用 ChatGPT」，升級成「如何建立一條可以被記憶、限制、驗證、稽核與接管的 AI 工作流」。

這正是 AI 架構師與一般工具講師拉開差距的地方。

七、可以轉成課程的一句話

Prompt Engineering 教你怎麼對 AI 開口；Loop Engineering 教你怎麼讓事情在你沒有逐步盯著時，仍然能正確前進。

八、可以轉成 FB 貼文的一段話

我們以前一直在學怎麼把 Prompt 寫得更好，但 Agent 時代真正的問題，已經不是「這一句要怎麼問」。當 AI 可以連續做幾十分鐘、幾小時的工作，我們要開始設計的是整條迴路：它讀了什麼、記住什麼、能做什麼、誰來檢查、什麼時候停止、出錯怎麼回退、成功後怎麼變成固定流程。Prompt 是起點，Loop 才是系統。未來真正有價值的人，不只是會叫 AI 做事，而是能設計一套讓 AI 做事之後，仍然可以被驗證、被接管、被追責的工作方式。

九、這章的延伸問題

1. 一個任務從多複雜開始，就不應只靠單次 Prompt 管理？

2. 哪些規則適合留在提示詞，哪些規則必須寫進程式？

3. Agent 的「完成」應由誰定義？

4. 多個 Agent 並行工作時，誰負責保存共同狀態？

5. Human on Loop 與傳統 Human in the Loop 的責任差異是什麼？

6. 如果 Agent 每次都需要人救火，它究竟是自動化，還是把操作介面換成聊天視窗？

李詩民式總結

我愈來愈確定，未來真正重要的能力，不只是會用哪一個模型，也不是知道多少提示詞技巧。模型會換、介面會換、工具也會換。真正不容易被取代的，是能不能把一件模糊的事，設計成一條可以前進、可以檢查、可以暫停、可以交接、可以持續改善的工作流。

以前我們站在 Prompt 前面，想著下一句要怎麼問。接下來，我們要站到整個迴路上方，決定這套系統應該怎麼運作。這就是我在這本書裡所說的 Loop Engineering。

章末金句

1. 模型能力愈強，系統設計的重要性愈高。

2. Prompt 決定 AI 聽見什麼，Loop 決定事情最後變成什麼。

3. 一個好回答可以讓人驚豔，一套好迴路才能讓組織放心。

4. Agent 能做事，不代表它知道自己什麼時候做對了。

5. 人不必操作每一步，但必須設計每一種責任。

6. AI 的下一個競爭點，不只在模型裡，也在模型外面的迴路。

7. 真正的自動化，不是沒有人，而是人不必一直救火。
