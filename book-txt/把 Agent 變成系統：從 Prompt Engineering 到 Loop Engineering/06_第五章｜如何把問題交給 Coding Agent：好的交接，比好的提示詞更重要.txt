第五章｜如何把問題交給 Coding Agent：好的交接，比好的提示詞更重要

Coding Agent 不怕問題困難，它更怕問題講得又長、又散、又不知道錯在哪裡。

一、這一章要解決的問題

很多人把錯誤交給 Coding Agent 時，只說一句：「這個不能用，幫我修好。」

接著貼上一大段聊天紀錄、幾張截圖、零散需求與猜測，期待 Agent 自己從整個 Repository 裡找出問題、推斷預期行為、建立重現方式、決定修復範圍，再自行判斷什麼叫完成。

有時候 Agent 做到了，讓人產生一種錯覺：只要模型夠強，交接品質不重要。

但程式修復是一個搜尋問題。Repository 可能有幾百、幾千個檔案，錯誤可能只出現在特定版本、特定輸入、特定環境。報告缺少位置與驗收條件時，Agent 必須把有限的工具呼叫與上下文預算花在猜測上。

人類工程師遇到模糊報告，還可以問：「你預期看到什麼？在哪個版本發生？能不能給我重現步驟？」許多自動修復 Agent 卻從問題敘述開始，一路執行到提交 Patch 或耗盡預算，中間未必能真正向回報者澄清。

所以，本章要解決的不是「Prompt 怎麼寫得更華麗」，而是：

如何把一個問題整理成 Agent 可以執行、定位與驗收的工作包？

二、用白話講清楚核心技術

《What Makes a Good Bug Report for an AI Agent?》用兩種研究回答這個問題。（R05）

第一個研究分析 433 個 SWE-bench Verified issues、87 個 repair agents，以及 27 種 bug-report features，觀察哪些特徵和修復成功有關。

第二個研究在 SWE-bench Pro 上，使用兩個模型與 17 種問題敘述變形，控制性地拿掉資訊、位置線索或結構，觀察解題率如何變化。

這兩種研究的證據強度不同。第一個是觀察性關聯，不能直接說某特徵必然造成成功；第二個在人工變形下提供較直接的因果線索，但場景仍是基準測試，不等於所有真實專案。

最有幫助的資訊：減少不必要的猜測

觀察研究中，和較高解決機率最明顯相關的特徵包括：

• 修復建議

• 可執行重現腳本

• Repository 原始碼片段

• 錯誤位置資訊，尤其是相關檔案

研究的混合效果模型中，修復建議的勝算比約為 3.61，Repository 原始碼約 2.82，可執行重現腳本約 2.52，指出相關檔案約 2.33。這些數字是關聯估計，不應解讀成普遍保證；但它們共同指向一件事：Agent 最受益的資訊，是能讓它少猜一點、少搜一點、快一點進入可驗證修復的資訊。（R05）

Expected Behavior：沒有預期，就沒有「修好」

控制實驗顯示，模型依賴清楚的預期行為。只有「目前錯了」不夠，還要描述正確結果應該是什麼。

例如：

模糊版本

匯出功能壞了，請修好。

可驗收版本

當使用者在報表頁選擇日期區間並按下「匯出 CSV」時，系統應下載 UTF-8 編碼檔案，第一列為固定欄位名稱，資料列數需等於目前篩選結果。現在按鈕顯示成功，但沒有下載任何檔案。

第二個版本同時提供觸發條件、預期結果與目前行為。Agent 不必自己發明產品規格。

Reproduction Script：把故事變成可執行證據

自然語言重現步驟對人類很友善，但對 Agent 而言，可直接執行的腳本通常更有價值。

例如與其只說：「建立新帳號後修改名稱，再重新登入就會出錯」，不如提供一個測試或命令：

pytest tests/test_profile.py::test_renamed_user_can_login -q

或提供最小程式：

user = create_user(name="before")

rename_user(user.id, "after")

assert login("after") is True

重現腳本把「相信回報者描述」轉成「Agent 可以自己看到失敗」。它也直接成為修復後的驗收測試。

Localization：告訴 Agent 從哪裡開始找

錯誤位置資訊不等於直接給答案，而是縮小搜索空間。

有幫助的資訊包括：

• 相關檔案或模組

• 可能的類別或函數

• Stack trace 的路徑與行號

• 最近改動的 Commit

• 受影響的 API 路由

• 對應測試檔案

如果不確定，也可以明確標示「初步懷疑」，不要把猜測冒充已驗證根因。

結構本身就是導航

研究特別有意思的一點是：即使文字內容沒有刪除，只把清單壓平成段落、拿掉小標，解題率也可能下降。（R05）

這表示標題、清單與段落不只是讓人看得舒服，也可能幫助模型定位資訊角色。Expected behavior、Steps to reproduce、Relevant files 等小標，相當於給 Agent 一張索引圖。

長篇敘事可能降低成功率，也不是因為所有長報告都不好，而是長度常伴隨雜訊、重複與線索稀釋。好的報告不是越短越好，而是每一段都有任務功能。

不同模型會以不同方式面對資訊缺口

研究觀察到，Qwen 在缺少資訊時傾向擴大搜索，可能因此耗盡回合預算；Gemma 則較早承諾一個合理解釋，再沿著該解釋修改。這提醒我們，報告缺口不只降低表現，也會改變 Agent 的失敗型態：有的迷失在搜索，有的太早鎖定錯誤假設。

良好交接的價值，就是讓模型不必在「找不到」與「太快猜」之間賭運氣。

三、論文真正想提醒我們什麼

論文提出什麼

AI Agent 的好 bug report 與人類開發者的好報告有重疊，但不完全相同。Agent 特別需要具體、可執行、可定位、可約束的資訊；自然語言可讀性與冗長敘述未必獨立帶來幫助。

論文沒有證明什麼

不能看到「fix suggestion 有正向關聯」就要求每個非技術使用者自行猜根因。錯誤建議可能把 Agent 帶偏。正確做法是把它標示為候選線索，仍以測試與程式碼證據驗證。

研究也不是說 Stack trace、Error message 或一般重現步驟沒有價值。部分特徵在觀察資料中沒有顯著獨立效果，可能和資料普及率、共變項、任務類型與其他資訊重疊有關。

本書的核心推論

交接品質可以被理解成「降低搜尋熵」。一份好報告不是把所有你知道的東西都倒進去，而是逐步縮小 Agent 必須猜測的空間：

• 它知道哪個行為錯了。

• 它知道正確行為應該是什麼。

• 它能自行重現。

• 它知道可能從哪裡找。

• 它知道哪些範圍不能改。

• 它有客觀測試判斷是否完成。

這比一句華麗的角色 Prompt 更重要。

四、這個技術如何改變 AI 教學

Coding Agent 課程不應只教「把錯誤貼給 AI」。可以要求學生先完成一張 AI-readable Bug Report，再啟動 Agent。

學生的評分也不只看 Patch 是否成功，而要看：

1. 問題是否可重現？

2. 預期行為是否可驗收？

3. 位置線索是否有證據？

4. 已嘗試方法是否避免重複？

5. 不得修改範圍是否明確？

6. 修復後是否新增回歸測試？

7. Agent 的變更是否超出任務？

更進一步，可以給同一個 Bug 三種報告：模糊敘事、資訊完整但無結構、結構化工作包，讓學生比較 Agent 的搜尋路徑、工具次數與成功率。

這會讓學生理解：使用 Coding Agent 的能力，不只是會下指令，也包括會做工程交接。

五、這個技術如何改變企業導入

企業若要讓 Agent 處理 Ticket、Bug 或營運事件，不能只把人類原有的自由文字表單直接丟給模型。應設計機器可讀的最小欄位：

• 目前行為

• 預期行為

• 影響範圍與嚴重度

• 可執行重現方式

• 環境與版本

• 相關檔案、服務或 API

• 錯誤訊息與證據

• 已嘗試方法

• 候選原因或修復方向

• 不得修改範圍

• 驗收測試

• 回退條件

表單不必要求每個人填滿所有欄位，但系統可以依任務風險判斷缺哪些資訊時不得自動修復。

低風險、可完整測試的 Bug，可以讓 Agent 自動開分支、提交 Patch 與執行測試；高風險變更則需要 Code Review、Security Review 或正式批准。

交接格式因此會和上一章的 Contract 連起來：Bug report 定義任務，Harness 限制 Agent 能改什麼，Eval 決定是否通過。

六、連到李詩民的實際場景

給 Codex 的實用交接模板

以下模板可以直接用在課程與專案。這是本書根據研究整理的實務格式。

# 問題標題

一句話描述錯誤與影響。

## 目前行為

實際發生什麼？附可觀察結果。

## 預期行為

正確結果應該是什麼？

## 重現方式

提供最小、可執行步驟或測試命令。

## 錯誤訊息與證據

貼出完整錯誤、Log、截圖路徑或測試結果。

## 環境

作業系統、Runtime、依賴與版本。

## 相關位置

可能的檔案、模組、函數、路由或 Commit。

不確定時標示為「初步懷疑」。

## 已嘗試方法

做過什麼？結果如何？避免 Agent 重複。

## 修復建議

候選方向與理由；不是已確認答案。

## 不得修改範圍

哪些 API、資料格式、相容性或檔案不可更動？

## 驗收測試

哪些命令必須通過？還要檢查哪些手動行為？

## 交付要求

需要 Patch、測試、變更說明與風險清單。

內容自動化的「Bug」也需要同樣交接

這套格式不只適用程式碼。假設字幕總是在片尾錯位，可以整理：

• 目前行為：最後 15 秒字幕逐漸落後音訊。

• 預期行為：每句誤差小於 200 毫秒。

• 重現方式：用指定音訊與字幕執行腳本。

• 相關位置：時間碼轉換函數與取樣率處理。

• 已嘗試方法：單純平移時間碼無效。

• 驗收測試：前、中、後段各抽查，並檢查總時長。

Agent 會得到一個可修復問題，而不是一句「字幕怪怪的」。

教學現場：把模糊問題改寫成任務包

可以讓學生從生活語句開始：

「我的網站跑不動。」

再逐步改寫成：

首頁在手機 Safari 開啟後，點擊導覽列第二項時畫面凍結；桌面 Chrome 正常。預期應平滑捲動到課程區塊。可使用附帶 Playwright 測試重現；請優先檢查 navigation.ts，不得改變桌面版行為，修復後所有 E2E 測試需通過。

學生會直接看見「問題描述」如何轉成「可委派工作」。

七、可以轉成課程的一句話

Coding Agent 的工作品質，往往在它開始寫程式之前，就被交接品質決定了一半。

八、可以轉成 FB 貼文的一段話

把 Bug 丟給 Coding Agent，不要只說「幫我修好」，也不要貼十頁故事讓它自己猜。研究顯示，Agent 特別需要可執行重現腳本、清楚的預期行為、相關原始碼與錯誤位置線索；報告太長、拿掉標題與清單，反而可能讓解題率下降。好的交接不是資訊越多越好，而是讓 Agent 少猜一點：現在怎麼壞、正確應該怎樣、怎麼重現、從哪裡找、哪些不能改、怎樣算修好。提示詞可以很短，任務規格不能模糊。

九、這章的延伸問題

1. 修復建議在什麼情況下會幫助，什麼情況下會造成錨定偏誤？

2. Agent 是否應在資訊不足時停止並提出澄清問題？

3. Bug report 的最小必要欄位應依風險如何調整？

4. 如何自動從 Log 與測試結果生成結構化報告？

5. Agent 自己產生的重現測試，應由誰驗證？

6. 不同模型對資訊缺口的失敗型態是否應影響交接模板？

7. 修復成功後，如何把 Bug report、Patch 與回歸測試保存成組織知識？

李詩民式總結

我以前會把 Coding Agent 的差異理解成模型強不強。現在我會多看一件事：我交給它的，到底是一句抱怨，還是一份可以工作的交接？

Agent 不是讀心術。你沒有說清楚正確結果，它就只能猜；沒有重現方式，它就只能到處找；沒有不得修改範圍，它可能修好一個地方、破壞另一個地方。

所以好的 Prompt 不一定很長，但好的任務一定有邊界、有證據、有驗收。未來真正會用 Coding Agent 的人，不只是會叫它寫 Code，而是會把問題整理成它能負責的工作包。

章末金句

1. 「幫我修好」不是任務規格，只是一個願望。

2. 沒有預期行為，就沒有客觀的「修好」。

3. 可執行重現，比一頁故事更接近證據。

4. 結構不是排版，而是 Agent 的導航系統。

5. 好交接的本質，是降低不必要的猜測。

6. 位置線索不是直接給答案，而是把搜索預算用在真正的問題上。

7. 提示詞可以簡短，驗收條件不能模糊。

8. Coding Agent 的能力，包含你管理它工作的能力。
