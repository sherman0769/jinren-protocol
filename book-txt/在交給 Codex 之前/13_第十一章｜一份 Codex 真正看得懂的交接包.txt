第十一章｜一份 Codex 真正看得懂的交接包

把一段聊天紀錄貼給 Codex，不等於完成交接。

聊天紀錄保留了討論過程，卻未必清楚標示哪些決定已鎖定、哪些只是提議、哪一份資料優先、什麼不能改、什麼狀態才算完成。Codex 可以閱讀很長的上下文，但若交接內容仍需要它重新整理、猜測與選擇，工作就沒有真正準備完成。

成熟交接的目標，是讓 Codex 在開始修改第一個檔案之前，就能回答六個問題：為什麼做？服務誰？做到哪裡？依據什麼？不能破壞什麼？如何證明完成？

這一章要把全書方法收斂成一個可以實際落地的成果：AI Handoff Package，也就是可以由 Work 準備、由人核准，再交給 Codex 執行的專案交接包。

交接的本質是決策狀態移轉

很多人認為交接只要把資料「全部給出去」。但真正影響接手品質的，是決策狀態是否清楚，不能只看資料總量。

一份成熟交接應分成四種狀態：

1. 已鎖定：可直接依此實作，除非發現重大矛盾。

2. 可由代理決定：在指定邊界內，Codex 可依工程判斷選擇。

3. 待驗證：需要原型、測試或資料才能確認。

4. 待人決策：涉及產品、法規、預算、品牌或高風險權限，不可由 Codex 自行決定。

若沒有狀態標記，所有文字看起來都一樣重要。Codex 可能把腦力激盪中的一個點子當正式需求，也可能忽略一句藏在對話中的禁止事項。

所以，Work 在交接前最重要的工作，是把決策整理得更明確，而非單純把所有對話摘要得更短。

什麼時候才適合交給 Codex？

可以用「五項 AI 交接條件」做第一道檢查：Goal、Context、Constraints、Deliverables、Acceptance 是否已經足夠。

但進入正式工程，還需要再加四個工程門檻。

一、Repository 已知

是新專案還是既有程式庫？使用什麼套件管理、分支策略、目錄結構與部署流程？若是既有專案，哪些模組不可任意重構？

二、資料與權限已知

主要資料實體、欄位、關係、來源與存取規則是否清楚？哪些資料是測試資料，哪些接近正式資料？是否需要資料遷移或安全規則？

三、測試與回報已知

Codex 要執行哪些 lint、typecheck、unit、integration、E2E 或建置檢查？失敗時如何回報？需要附上哪些證據？

四、變更邊界已知

可以新增哪些依賴？可以修改資料模型嗎？能否部署？能否碰 production？哪些行動必須先核准？

當五項交接條件與四個工程門檻都大致成立，Codex 才不必用程式碼替人補決策。

不必每個小專案都建立所有檔案。這個結構的價值，是提醒我們不要只交一份「需求.md」，卻漏掉資料、品質、執行與核准。

project_brief.md：讓 Codex 一分鐘內理解專案

專案簡報不應重複所有細節，而是提供最短的導航：

- 專案目的與成功狀態。

- 核心使用者與主要流程。

- 第一版範圍與明確不做項目。

- 技術環境與 Repository 狀態。

- 最高風險與人類核准點。

- 正式規格與測試檔案的位置。

- 本次 Codex 任務的具體目標。

好的 project brief 像地圖，不是百科。Codex 讀完後應知道先看哪裡、做什麼，以及遇到哪類問題要停下來。

decision_status.md：把未知管理起來

這份檔案列出所有會影響實作的重要決策，並標記狀態：

決策｜狀態｜目前結論｜負責人／下一步

登入方式｜已鎖定｜使用工作區帳號｜依規格實作

公開查詢欄位｜已鎖定｜遮蔽姓名＋手機末五碼｜不得擴大

通知信｜延後｜第一版不寄送｜第二階段再評估

資料保存期限｜待人決策｜尚未確認｜不得實作自動刪除

儀表板圖表｜可由代理決定｜以簡單表格優先｜不新增大型圖表套件

這張表能避免 Codex 把「尚未決定」誤當成「自由發揮」。

feature_scope.md：用範圍保護工程

範圍文件至少分成三區：Must Have、Later、Out of Scope。

Must Have 是本次必須完成且會驗收的內容；Later 是已知但延後；Out of Scope 是明確禁止被順手加入的內容。

例如活動網站第一版：

Must Have：活動資訊、報名、額滿、取消、公開遮蔽查詢、管理者匯出。

Later：多活動、電子郵件通知、候補名單、會員積分。

Out of Scope：金流、公開完整會員資料、社群帳號登入、跨組織共用資料庫。

這能防止代理因為「看起來完整」而加入未被要求的功能，也保護測試與時程不被無限擴張。

data_model.md：頁面背後真正的契約

很多交接只畫頁面，卻沒有定義資料。Codex 只好從 UI 推回資料模型，容易漏掉生命週期與權限。

資料模型不必一開始就寫成完整 SQL，但應說明：

- 核心實體與關係。

- 欄位型別、必填與唯一性。

- 建立、更新與刪除規則。

- 角色可見與可修改範圍。

- 個資遮蔽、加密或去識別要求。

- 來源、匯入與匯出格式。

- 保存、封存與刪除政策。

- 測試資料與正式資料的隔離。

資料定義越清楚，Codex 越能建立有意義的測試，而不是只驗證按鈕會動。

technical_constraints.md：讓工程自由有邊界

技術限制應只放真正需要固定的事項，避免把每一個偏好都鎖死。

可能包括：

- 必須沿用既有 Next.js、TypeScript 與 Firebase 架構。

- 套件管理器固定為 pnpm。

- 不得新增 production dependency，除非先提出必要性與替代方案。

- 不得直接修改 production 資料。

- 環境變數不得寫入 Repository。

- 所有資料寫入必須經伺服器端權限驗證。

- 必須通過 lint、typecheck、test 與 build。

- 介面需要符合指定行動裝置範圍與無障礙要求。

不應把「請寫得漂亮」「使用最佳架構」放進限制，因為它們沒有可執行定義。

AGENTS.md：把可重複規則帶進 Repository

OpenAI 官方文件指出，Codex 在開始工作前會讀取 AGENTS.md，並可依全域、專案與子目錄形成分層指令。較靠近目前工作目錄的規則具有更高優先性。[R12]

AGENTS.md 適合放每次都要遵守的專案規則：

- Repository 重要目錄與路由。

- 安裝、執行、測試與建置命令。

- 程式風格與命名慣例。

- 不可修改的區域。

- 新增依賴、資料遷移與部署的核准規則。

- 什麼叫完成，以及要附上哪些驗證證據。

- 變更後需要更新哪些文件。

它不適合塞入整份商業需求、所有會議紀錄或大量背景故事。官方最佳實務也建議保持精簡、準確；若內容太大，應把任務專屬規格放在其他 Markdown，再由 AGENTS.md 指向。[R13]

一份簡化範例：

AGENTS.md

Working agreements

- 使用 pnpm，不要更換套件管理器。

- 修改 TypeScript 後執行 pnpm lint、pnpm typecheck、pnpm test。

- 未經核准不得新增 production dependency。

- 不得直接存取或修改 production 資料。

- 個資公開顯示必須依 docs/privacy_rules.md 遮蔽。

- 每次任務回報修改檔案、測試結果、已知限制與待決策事項。

Source of truth

- 產品範圍：docs/feature_scope.md

- 資料模型：docs/data_model.md

- 驗收條件：docs/acceptance_criteria.md

這份檔案的價值不在讓提示詞變長，而在讓專案工作方式可以跨任務持續。

acceptance_criteria.md 與 test_scenarios.md

驗收條件描述使用者可觀察的合格狀態；測試情境把條件轉成可執行檢查。

建議每個核心流程使用 Given／When／Then 或同等清楚格式：

情境：活動剛好額滿

Given 目前有效報名數為 49，名額上限為 50

When 一名新使用者送出合法報名

Then 報名成功，有效報名數變為 50

And 後續一般報名被阻擋並顯示額滿狀態

再加入權限、重複、取消、網路失敗、資料格式錯誤與併發情境。對高影響功能，測試不只由 Codex 建立，也需要人類抽查需求是否被正確翻譯。

implementation_plan.md：先切成可驗證增量

好的執行計畫要讓每一階段都有可驗證成果，不能只列出「做前端、做後端、部署」三句話。

例如：

1. 基礎環境：確認 Repository、依賴、測試與本機啟動；不改功能。

2. 資料模型與權限：建立 schema／rules 與測試，先不做完整 UI。

3. 報名流程：完成正常、錯誤與額滿情境。

4. 公開查詢：完成遮蔽與查無資料情境。

5. 管理功能：登入、名單、匯出與權限測試。

6. 整合與品質：E2E、行動裝置、無障礙、建置與文件。

7. 部署準備：提供預覽、環境清單、回復方式；等待核准後才 production。

每個階段都能停止、檢查與修正，避免一次修改太大而難以審查。

codex_execution_prompt.md：指令應指向資料，而非重複資料

最終交給 Codex 的提示詞應該簡潔，因為正式資訊已放在交接包與 Repository。

例如：

請先閱讀根目錄 AGENTS.md 與 docs/handoff/README.md，再檢查現有 Repository。先不要修改程式，請回報你理解的目標、第一版範圍、關鍵限制、驗收條件、已知缺口與建議執行順序。若發現文件衝突，依 decision status 與 source-of-truth 規則處理；涉及 production、資料遷移、新增 production dependency 或未決產品決策時停止並要求核准。計畫確認後依里程碑實作，每個里程碑回報 diff、測試證據、已知限制與下一步。

這不是「神提示詞」。它的力量來自前面已經存在可靠的上下文與規格。

一個一般情境：Next.js＋Firebase 活動網站

假設一個組織準備建立活動報名網站，已選擇 Next.js、TypeScript、Firebase Authentication、Firestore 與 Vercel。這只是一般示範，並非作者已完成案例。

Work 可以先整理：

- 活動與管理者的問題定義。

- 報名者、工作人員與管理者角色。

- 單一活動第一版範圍。

- events、registrations 與 admins 等資料實體。

- 姓名遮蔽、電話末五碼與資料匯出規則。

- Firestore 權限與不直接信任前端的原則。

- 正常、重複、額滿、取消與未授權測試。

- Vercel preview 與 production 的核准點。

Codex 接手後，先讀 Repository 與交接文件，確認現況是否支持規格，再提出計畫。若發現既有專案使用不同登入方式或資料結構，它不應直接重寫，而要回報差異、影響與選項。

這正是交接包的價值：它不強迫現實符合文件，而是提供一個能辨識差異、做出決策的基準。

交接後，人與 Work 還要做什麼？

交給 Codex 不是人類退出，也不是 Work 任務結束。

Codex 的執行回報應回到 Work 或專案記錄中，更新：

- 已完成與未完成項目。

- 實際技術決策與原因。

- 測試、部署與已知限制。

- 新發現的產品問題。

- 需要更新的文件與訓練材料。

- 下一階段範圍。

Work 可以把工程結果整理成主管可讀報告、操作手冊、變更紀錄、培訓簡報與下一輪工作簡報。三層工作棧因此形成閉環，而不是單向丟包。

交接品質的四個驗收問題

最後，用四個問題檢查交接包：

1. 一位沒有參與前面對話的人，能否在合理時間內理解專案目的與範圍？

2. Codex 遇到衝突時，是否知道哪份資料優先、何時停止、要問誰？

3. 每個重要成果是否有可執行的驗收與測試，而非抽象品質詞？

4. Codex 完成後，是否能以差異、測試與限制證明工作，而不是只說完成？

四題若有任何一題答不出來，交接仍不成熟。

本章結論

一份 Codex 真正看得懂的交接包，會把問題、決策、範圍、資料、工程規則、驗收與執行方式整理成可定位的專案狀態，而非只是複製所有資料。

Work 在這裡最有價值的角色，是把跨文件、跨角色、跨成果的前置工作準備完整；人類則核准方向、邊界與高風險決策；Codex 進入工程世界，依 Repository 規則實作並提供證據。

當交接成熟，Codex 不必替我們猜整個產品；它可以把能力集中在真正困難的地方：理解程式庫、選擇合理實作、建立測試、處理錯誤，並把變更安全地帶進現實。

下一章將把這套方法帶回作者的五個主要工作領域，建立一套不是只用一次，而能每天持續運作的 AI 工作作業系統。

章末金句

1. 聊天紀錄保存了過程，交接包保存了可以執行的決策狀態。

2. Codex 不怕規格精簡，怕的是精簡到只剩願望。

3. AGENTS.md 應保存反覆適用的工作規則，不是承擔所有背景故事。

4. 好提示詞的力量，來自它能指向可信的正式來源。

5. 未決問題若沒有被標示，就會在程式碼裡被悄悄決定。

6. 交接包的目的不在消除變化，而在讓變化有基準、有證據、有責任人。

7. 工程代理最需要的自由，是在清楚邊界內做專業判斷。

8. 交給 Codex 之前準備得越成熟，Codex 才越有餘裕處理真正的工程難題。

9. 完成一次開發不是終點，能把決策、測試與限制帶回工作系統，才形成閉環。
