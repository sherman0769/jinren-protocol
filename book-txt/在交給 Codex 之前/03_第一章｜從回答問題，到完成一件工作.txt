第一章｜從回答問題，到完成一件工作

「幫我寫一則活動公告。」

這是一個很適合交給 ChatGPT 的要求。模型收到活動名稱、時間、地點與報名方式後，可以在幾秒內產生一篇清楚的文字。使用者稍微修正語氣，就能貼到社群平台。

但如果真正的需求是「完成一場活動的對外發布」，一則公告遠遠不夠。可能還需要報名表、海報文案、講師介紹、注意事項、名額管理、公開查詢頁、工作人員流程、提醒信、現場名單、會後新聞稿與成果報告。活動資訊改動時，所有成果還要同步更新，不能各自留著不同版本。

同一個「活動」裡，可以包含一個回答、一個任務、一個專案，以及一條持續運作的工作流。若沒有分清楚，我們會用一句提示詞期待一個完整系統，最後再把責任推給模型。

回答，是對一個問題的回應

回答的單位最小。它通常具有明確輸入與單一輸出：解釋一個概念、改寫一段文字、比較三種方案、計算一個結果、產生一段程式。

回答的品質可以從正確性、清楚度、相關性與語氣判斷。它不一定需要保存長期上下文，也不一定需要使用其他工具。回答完成後，使用者可能直接採用，也可能把它當成下一步的材料。

很多人過去使用 ChatGPT 的核心經驗都在這一層。因為模型非常會生成文字，我們很容易把「看起來完整」誤認為「事情已經完成」。

一篇企業 AI 導入建議可能寫得頭頭是道，但沒有讀過企業資料；一份課程大綱看起來完整，卻沒有考慮學員程度與可用時間；一段網站程式碼可以顯示頁面，卻沒有資料權限、錯誤狀態與測試。

答案可能是對的，卻仍然不能直接被使用。

任務，是有目標、邊界與完成狀態的工作

任務比回答多了三個條件：它有明確目的、有可執行範圍，也有完成判準。

「寫一篇公告」是一個回答型要求；「根據已核准的活動資訊，建立 Facebook、LINE 與電子郵件三個版本，保持日期與報名連結一致，完成後逐項檢查」才接近任務。

成熟任務至少應能回答：

- 為什麼要做？

- 使用什麼資料？

- 哪些內容不得改動？

- 要產生哪些成果？

- 放到哪裡、用什麼格式？

- 什麼狀態才算完成？

- 哪些例外需要回報？

任務可以只有一步，也可以有多個步驟。關鍵不在步驟數量，而在它能否被執行、檢查與結束。

Work 對使用者的第一個增強，就是把工作單位從「一次回應」拉高到「一個可持續推進的任務」。官方建議使用者在要求建立文件、試算表或簡報時，說清楚輸出位置、格式、必須保留的內容與不可變條件，並在完成後進行人工複核。[R03]

這反映一個重要觀念：代理不是只需要知道要產生什麼文字，它還要知道成果將被怎麼使用。

專案，是多個互相依賴的任務

當一件工作需要不同成果、不同角色、不同時間與多次決策，它就進入專案層級。

專案的難點不只是事情很多，而是任務之間有依賴關係。研究結果會影響規格；規格會影響簡報與預算；預算核准後才進入開發；開發完成還需要測試、教材與發布。只要前面一個決定改變，後面多份成果可能都要同步更新。

因此，專案需要：

- 一個正式目標與範圍。

- 一份可追溯的決策紀錄。

- 多個里程碑與成果。

- 任務之間的先後關係。

- 明確的責任與核准點。

- 版本、風險與待確認事項。

- 最終驗收與交付清單。

Work 能長時間處理多步驟工作、讓使用者跟進進度、補充方向並核准重要行動，正是因為專案不能只靠一問一答完成。[R01][R02]

不過，能執行多步驟，不代表代理自然擁有好的專案管理。若目標與里程碑仍然模糊，代理只是把猜測拆成更多步驟。Work 增強的是執行與交付能力；人仍必須提供工作結構。

工作流，是能重複運作與持續改善的系統

一次把活動辦完，是專案；下一次面對不同講師、日期與場地，仍能沿用相同資料結構、核准規則與交付格式，才接近工作流。

工作流不是「把上次提示詞存起來」那麼簡單。它至少需要：

- 固定輸入：每次需要哪些資料。

- 固定步驟：哪些處理順序通常不變。

- 固定輸出：每次必須交付哪些成果。

- 例外規則：資料缺漏、衝突或失敗時怎麼辦。

- 核准點：哪些外部行動不能自動執行。

- 版本：範本、規則與來源如何更新。

- 紀錄：本次做了什麼、改了什麼、為何如此決定。

ChatGPT 的 Skills、Plugins、Scheduled Tasks 與可重複範本，讓一次成功的做法有機會被沉澱成持續能力。[R06][R07][R08] 但工具只是容器；工作流是否成熟，仍取決於規則是否清楚、輸入是否可得、例外是否可處理，以及輸出是否能驗收。

任務成熟度階梯

本書提出一個工作概念：任務成熟度階梯（Task Readiness Ladder）。它用來判斷一個想法目前在哪個狀態，以及下一步應該用 Chat、Work 還是 Codex。

第一級：願望

「我想做一個會員管理系統。」

這是方向，不是問題。它沒有說明誰遇到什麼困難、現況成本為何，也沒有說明成功狀態。

最適合的工作是對話探索：為什麼想做？現在怎麼管理？真正痛點是名單、繳費、活動、權限還是溝通？

第二級：問題

「協會會員資料散落在不同試算表，活動報名與基本資料重複維護，工作人員無法確認哪一份是最新版本。」

這已說明使用者、現況與摩擦，但仍沒有可直接執行的成果。

下一步是定義目標、範圍、資料來源與成功狀態。

第三級：任務

「整理三份既有名單，建立欄位對照、重複資料規則與單一正式名冊；不得刪除原始檔，衝突資料列入待確認清單。」

現在已能交給 Work 執行。輸入、處理、限制與輸出較清楚，完成後可以檢查。

第四級：可驗收工作

「除正式名冊外，還要交付資料品質報告、未確認清單、欄位定義、變更紀錄與驗證結果；有效會員數需與核准紀錄一致，個資不得出現在公開檔案。」

這個層級不只知道要做什麼，也知道如何判斷完成。Work 可以完成整組成果；若需要建立正式管理介面，才準備進入工程。

第五級：可交接專案

「已定義使用者角色、第一版功能、資料模型、隱私規則、技術限制、Repository、測試情境、AGENTS.md、部署邊界與 Codex 執行順序。」

這時任務才真正適合交給 Codex。Codex 不必替人決定產品範圍，只需在工程邊界內實作、測試與回報。

這五級不是考試，也不要求所有小工作都寫一大份文件。它提醒我們：工作影響越大、越難回復、越需要交接，就越不能停留在願望層級。

成果導向，不等於只看最後一個檔案

「成品」很容易被理解成最後那份 Word、簡報或網站。其實成熟交付還包含證據與狀態。

例如一本完整書籍的交付，不只是一個 DOCX。還應包括正式 Markdown 來源、章節與合併稿一致性、研究登錄、字數報告、去重檢查、待補案例、版本紀錄、檔案清單，以及 ZIP 可解壓縮的驗證。

沒有這些證據，檔案可能看起來存在，卻無法確認內容是否完整、來源是否一致、舊版本是否混入、字數是否真實達標。

同樣地，一個網站說「完成」時，不能只給網址。還需要說明測試結果、已知限制、部署環境、回復方式、未完成項目與版本。成果導向要求接收者能判斷、使用、維護與承擔，不能只看外觀。

完成一件工作，需要四種證據

當代理宣告完成，我們至少可以從四種證據判斷，而不只看最後畫面。

第一是內容證據：必要資訊是否存在，論點、數字與來源是否正確，沒有把假設寫成事實。

第二是結構證據：成果之間的關係是否完整。報告的建議是否出現在簡報與行動表；資料欄位是否與表單、匯出與權限一致；正式母稿與衍生版本是否同源。

第三是操作證據：檔案能不能開啟，連結是否有效，公式是否計算，網站是否在正常與錯誤情境下運作。對程式而言，這會變成測試、建置、日誌與差異。

第四是責任證據：哪些事情由代理完成、哪些經過人工核准、哪些仍待決策、哪些限制已知。沒有責任狀態，接收者很容易把草稿當正式成果。

四種證據也對應四種常見假完成：文字很多但內容錯、檔案齊全但互相矛盾、畫面漂亮但操作失敗、技術可用但沒有負責人核准。

從一句要求到成熟任務的改寫

可以比較以下兩種寫法。

第一種是：

幫我整理這些活動資料，做成一套完整內容。

第二種是：

以 activity_master.md 為唯一正式來源，整理本次公開講座的發布包。交付 Facebook 貼文、LINE 短版、報名頁文字、工作人員流程與會後新聞稿草稿。日期、時間、場地、講師姓名與報名連結不得自行改動；資料衝突時列入 unresolved_items.md，不要猜測。所有公開文案不得包含報名者個資。完成後建立清單，逐項確認五份成果的活動資訊一致；不要直接發布。

後者之所以更成熟，在於加入正式來源、成果、不可變條件、例外處理、隱私與驗收，與篇幅長短無關。即使換一個代理或隔一週再做，工作仍能被理解。

成熟任務的文字不一定很多。真正重要的是，把會影響執行的決定放進來，把不需要代理知道的背景拿出去。

Work 增強了你的哪一段能力？

從回答走向工作後，Work 對個人的增強可以分成六個面向。

一、上下文持續

你不必每一步都重新貼上背景。代理可以在較長任務中保留目標、資料、決策與中間成果，並根據新的指示調整。

二、步驟推進

它可以把目標拆成研究、整理、產出、檢查與交付，不再每完成一步就完全停下來等待下一個提示。

三、工具使用

在支援的情況下，它能使用檔案、應用程式、瀏覽器、Library、Sites 或其他工具，把資訊取得與成果建立放進同一段工作。

四、多成果一致

它可以在同一份上下文中建立報告、簡報、試算表與網站，降低不同成果各自解讀需求而產生的落差。

五、人類介入

長任務中，人可以查看進度、補充資料、改變方向、要求檢查，並在高影響行動前核准。這讓代理工作不必等於完全放任。

六、流程沉澱

成功任務可以整理為範本、Skill、Plugin 或排程，讓工作能力不只存在於一次聊天。

這六項能力共同改變一件事：以前人類主要負責串接每一步，現在可以把一段完整流程交給代理，再把注意力集中在方向、品質與例外。

不是所有事情都要升級成 Work

理解成熟度，不代表所有小事都要變成複雜專案。

查一個概念、改一封信、整理三個重點，用 Chat 通常最快。只有當任務需要多個步驟、持續上下文、多份檔案、外部工具、不同成果或明確交付，Work 才真正展現價值。需要進入 Repository、終端、測試與部署時，再交給 Codex。

過度設計也有成本。一個只需要十分鐘完成的低風險任務，不值得先寫十頁規格。好的工作設計追求與風險相稱的清楚度，文件數量本身不代表成熟。

可以用三個問題快速判斷：

1. 做錯的代價有多大？

2. 完成後是否要被別人使用、維護或接手？

3. 這件事是否會重複發生？

代價越高、交接越多、重複越頻繁，越值得把工作從回答提升為任務、專案與工作流。

任務成熟度的快速自我診斷

面對一件新工作，可以在開始前用十分鐘回答八題：

1. 我說的是願望、症狀，還是已定義的問題？

2. 誰要使用結果？他要完成什麼工作？

3. 哪些資料是正式來源，哪些只是參考？

4. 做錯的代價與可逆性如何？

5. 最後要留下哪些具體成果？

6. 哪些品質可以被觀察與驗收？

7. 任務會不會重複，或需要別人接手？

8. 工作是否已進入 Repository、測試與部署？

如果前四題答不清楚，先留在 Chat；若前六題已大致清楚，而且需要多檔案、多步驟與完整成品，適合進 Work；若八題都已進入工程語境，才準備交給 Codex。

這並非機械評分；它是降低過早執行的提醒。小而可逆的工作可以快速開始，高影響工作則需要更完整證據。

同一件活動，四種工作單位

假設協會要舉辦一場公益講座。

回答層只需要一段活動介紹；品質重點是資訊正確、語氣合適。

任務層需要三個平台文案、報名連結、注意事項與一致性檢查；品質重點是輸入、格式與完成條件。

專案層加入講師資料、海報、名單、現場流程、主持稿、新聞稿與成果報告；品質重點變成依賴、版本、核准與多成果一致。

工作流層再把成功做法沉澱成活動簡報、個資規則、範本、核准表與交付清單，下一次只替換活動變數並重新查證。

若不分層，人會用一段文案的管理方式處理整場活動；若分層清楚，就能知道哪些部分值得代理長時間接手，哪些部分只需快速回答。

把一句願望改寫成任務卡

任務成熟度不是抽象分級，可以透過一張簡單任務卡落地。假設原句是：「幫我做一份 Work 企業課程。」這仍是願望，因為「企業」「課程」與「完成」都有很大解釋空間。

第一步，把願望改成問題：企業主管已聽過生成式 AI，卻無法判斷哪些工作適合 Chat、Work 或 Codex，因此導入討論常停在工具示範。

第二步，把問題改成任務：為十到二十位部門主管設計三小時工作坊，使他們能分類一項真實工作、建立五項交接條件，並決定是否需要進入 Codex。

第三步，補上可驗收成果：講師版教案、學員講義、兩個分組案例、一張任務成熟度評分表、一張 Chat／Work／Codex 路由表，以及課後行動清單。所有例子不得包含未授權的客戶資料；技術能力以指定查證日為準。

第四步，補上證據：試講後，每組能在二十分鐘內把模糊需求整理成 Goal、Context、Constraints、Deliverables、Acceptance；講師能依評分表指出至少一項過早執行風險。

同一句「做一份課程」，經過這四步後，代理不只知道要寫什麼，也知道這份課程要改變誰、在什麼情境使用、哪些檔案必須交付，以及如何證明真的能教。

四種成本，決定任務要準備到哪一級

任務不需要一律寫成厚重規格。準備程度應與四種成本相配。

做錯成本：錯了只是刪掉一段草稿，還是會造成錯誤報價、個資外洩或 production 中斷？

回復成本：成果能否一鍵撤回，還是已經寄出、發布、付款、刪除或改動正式資料？

協作成本：只有自己使用，還是要交給客戶、同事、工程師與下一個代理？接手者越多，狀態越不能只存在聊天裡。

重複成本：只做一次，還是每週、每月都會再做？重複越高，越值得建立正式來源、範本、例外與測試。

四種成本都低時，可以讓 Chat 快速協助；任一成本升高，就要把任務提升到可驗收工作或可交接專案。這並非官僚化；它是讓準備成本與錯誤後果保持合理比例。

任務規模與代理自治要一起設計

同樣是交給 AI，適合的自治程度不會只由模型能力決定，還要看工作成熟度與錯誤代價。

一項低風險、可逆、輸入穩定的任務，例如把已確認主稿轉成固定格式，可以讓代理一次完成並自動檢查。相反地，一項高風險、方向仍模糊的工作，例如替企業承諾導入成效，應縮短循環，先產出假設與決策材料，再由人決定是否往下。

可以把工作放在兩條軸上思考：一條是「不確定性」，另一條是「影響程度」。

- 不確定性高、影響低：適合用 Chat 探索或建立可丟棄原型。

- 不確定性高、影響高：先做研究、訪談與問題定義，不能急著授權行動。

- 不確定性低、影響低：最適合交給 Work 自主完成，甚至沉澱為排程或 Skill。

- 不確定性低、影響高：可以自動執行大部分步驟，但要保留證據、權限與人類核准點。

這個判斷也提醒我們，成熟任務不等於文件很長。真正需要的是「最小充分契約」：足以讓代理少猜、讓人能驗收，又不把每一個微小選擇都鎖死。

當一件工作層級提高時，增加的不應只是提示詞字數，而是狀態、正式來源、權限、證據與接手能力。這些元素才決定代理能否得到更大的自治空間。

本章收束

回答解決一個問題；任務完成一個有邊界的目標；專案協調多個互相依賴的任務；工作流讓成功做法可以重複、更新與改善。

Work 的真正增強，在於讓人有機會把更大的工作單位交給 AI，而非讓每次回答更華麗。下一章，我們要進一步決定：在 Chat、Work 與 Codex 之間，這些不同成熟度的工作應該如何分工。

章末金句

1. 一段文字可以很完整，一件工作仍可能完全沒有完成。

2. 回答看內容，任務看完成，專案看依賴，工作流看能否重複。

3. 任務成熟度越低，代理需要猜測的責任越高。

4. 做錯代價越大，越不能用一句願望取代正式任務。

5. 成果包含檔案、狀態、證據與交接能力，不能只看最後一個檔案。

6. Work 增強的是上下文、步驟、工具、檔案與交付之間的連續性，與字數無關。

7. 一次完成只證明這次運氣不錯；能重複、能更新、能驗收，才證明方法成立。

8. 好的工作設計不追求文件最多，而追求猜測最少。
