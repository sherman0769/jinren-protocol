第二章｜Chat、Work 與 Codex，不是強弱，而是分工

一個人有了「做一個會員管理網站」的想法，通常會本能地尋找最強的模型。他可能會想：既然 Codex 會寫程式，那就直接把這句話交給 Codex；如果 Work 比一般聊天模式更能做事，那也許 Work 就是介於 Chat 與 Codex 之間的中階版本。這種理解很自然，卻很容易讓整個專案從第一步就走錯。

問題不在於哪一個模式比較強，而在於你現在到底處於工作的哪一個階段。

「做一個會員管理網站」還不是一份可以開發的需求。它可能只是想解決會員資料散落的問題，也可能是要管理活動報名、會費、志工排班、電子報或理監事權限。網站只是使用者首先想到的形式，不一定是最合適的答案。若直接開始寫程式，Codex 只能在大量未說明的空白裡自行猜測；若一直留在 Chat 裡討論，又可能產生很多文字，卻始終沒有形成可交付的專案。

截至 2026 年 7 月 19 日，OpenAI 對三種體驗的分工其實相當清楚：Chat 適合快速問答、搜尋、腦力激盪與對話協助；Work 適合研究、分析，以及建立文件、試算表、簡報、報告或 Site 等完整成果；Codex 則聚焦在寫程式、除錯、執行測試與命令、檢視變更，以及處理程式庫。這是官方產品分工的起點，但還不夠成為一套工作方法。[R02]

本書因此提出一個工作概念：三層 AI 工作棧（Three-Layer AI Work Stack）。這並非 OpenAI 官方架構；它是用來判斷工作應在哪裡開始、何時切換、交接時要帶走什麼的觀察框架。

三層分別是：

1. Chat Layer｜意圖釐清層：把感覺、願望與問題說清楚。

2. Work Layer｜任務準備與成果交付層：蒐集上下文、整理範圍、建立成果規格、安排核准點，並完成一組可使用的交付物。

3. Codex Layer｜工程執行層：進入程式庫、終端、測試、版本控制與正式軟體工程。

這三層不是三個階級，也不是三種價格對應的能力排名。它們更像一條工作從模糊走向具體的路徑。很多任務只需要走到第一層；有些知識工作在第二層就已經完成；只有需要正式軟體工程的部分，才要進入第三層。

Chat 的價值，是讓錯誤可以便宜地發生

在想法還模糊時，最大的危險是太早把猜測固定成規格，而非問題問得不夠完整。

Chat 最適合處理的，重點不在「幫我把整個專案做完」，而在這些尚未確定的問題：

- 我真正想解決的是什麼？

- 使用者是誰？他現在怎麼做？

- 這件事一定要做成網站嗎？

- 有哪些可能方案？各自的代價是什麼？

- 哪些假設最可能錯？

- 先做哪一個最小實驗，能最快確認方向？

對話層的核心價值，是探索的成本低。你可以推翻上一分鐘的想法，可以要求模型扮演反方，可以比較三種完全不同的方案，也可以暫時不追求任何正式檔案。這個階段最有價值的產出，往往是更好的問題，而不只是一個答案。

例如，一位講師說想做一套 AI 課程網站。Chat 可以先協助拆出幾種不同目標：它可能是招生頁、學習管理系統、課堂資源庫、學員作品牆，也可能只是讓企業客戶快速理解課程價值的提案入口。這些方向看似都叫「課程網站」，但背後的使用者、資料、權限、成本和完成條件完全不同。

在這一層，人類仍然是主要思考者。AI 可以擴大選項、指出盲點、整理矛盾，卻不能替你決定什麼值得做。若問題牽涉組織目標、個人價值、客戶承諾或資源取捨，決策責任不會因為模型更強而消失。

Chat 的完成條件不以「已經寫了很多字」為準，而在於你可以清楚說出：誰遇到什麼問題、為什麼現在值得處理、成功後應出現什麼改變，以及目前仍有哪些關鍵未知。

Work 的價值，是把想法準備成工作

當方向大致清楚，下一個難題往往是把散落資訊組成一份可執行的工作，還不到急著寫程式的時候。

這時需要處理的事情包括：讀取既有文件、比對版本、研究外部資料、整理使用者需求、建立流程圖、決定交付格式、列出限制、設計驗收條件、產生簡報與報告，甚至建立可測試的互動原型。這些工作不再只是對話，卻也未必需要直接進入程式庫。

Work 正好位於這個區域。官方把它描述為能處理較長、多步驟工作並產生完整交付成果的代理。它可以使用檔案、Project context、連接的 apps、支援的瀏覽器能力與範本；使用者可以跟進進度、回答問題、改變方向，並在重要動作前核准。[R01][R02]

本書把 Work 理解為兩個互相重疊的角色。

第一個角色是任務準備層。它把對話中已經釐清的意圖，整理成目標、上下文、限制、交付成果與驗收條件。這裡的工作包括研究、彙整、比較、規格化與版本管理。

第二個角色是成果交付層。如果任務本身就是一份企業提案、一組課程教材、一份資料分析、一套簡報、一個報名頁原型或一個互動 Site，Work 可能已經是終點，不需要再交給 Codex。

這一點非常重要。Work 並不是所有任務通往 Codex 的候車室。對大量知識工作而言，文件、試算表、簡報、報告和可分享網站本來就是最終成果。只有當成品需要正式程式碼、資料庫、部署、測試與長期維運時，Work 才扮演 Codex 前置準備層。

假設要替一家企業設計 AI 導入提案。Chat 可以協助釐清企業真正想改善的是內部效率、知識管理、客服品質，還是主管決策；Work 可以讀取訪談記錄與公司材料，研究產業背景，建立現況分析、導入路線圖、預算試算表、主管簡報與風險清單。這組成果已經能交付給客戶，未必需要寫任何程式。

相反地，若提案中包含一個正式的內部知識入口，Work 可以進一步整理需求、角色、資料來源、頁面架構與驗收條件，再把成熟規格交給 Codex。此時 Work 的價值不在「也會寫一點程式」，而在讓後面的工程代理不必從模糊願望開始猜。

Codex 的價值，是在工程世界裡負責任地改變東西

軟體開發不是把自然語言翻譯成程式碼那麼簡單。真正的工程工作會碰到現有架構、套件版本、測試、資料遷移、權限、部署、日誌、錯誤回復、版本控制與團隊規範。

Codex 的主場就在這裡。官方文件把它定位為 coding agent，可使用 local folders、repositories、terminals 與 developer tools；不同客戶端還包括桌面模式、CLI、IDE extension 與獨立 web 體驗。[R02][R15]

進入 Codex Layer，代表工作已不只是「提出一個好主意」，而是要對實際變更負責。你需要知道它可以修改哪些檔案、採用什麼技術、要跑哪些測試、哪些依賴不可新增、如何回報變更，以及失敗時如何復原。

這也是為什麼一個成熟的 Codex 專案不該只靠一段長提示詞。它需要持續存在於 repository 裡的規則，例如 AGENTS.md；需要可執行的 acceptance criteria；需要測試資料與完成定義；需要說明哪些決定已鎖定，哪些仍可由代理提出建議。Codex 可以很會做，但它不應被迫替專案擁有人猜測產品責任。

三層之間真正要交接的是「狀態」

很多人以為從 Chat 切到 Work，只要複製最後一段對話；從 Work 切到 Codex，只要貼上最終提示詞。這樣的交接往往會丟失最重要的東西：決策是怎麼形成的、哪些假設已被排除、什麼不能改、什麼才算完成。

好的交接不只傳遞文字，而是傳遞一個工作的狀態。至少應包含：

- 已確認的目標與成功狀態。

- 重要背景與可信來源。

- 已鎖定及尚未鎖定的決策。

- 範圍內與範圍外事項。

- 權限、限制與人類核准點。

- 必須產生的交付成果。

- 驗收條件、測試情境與已知風險。

- 下一個代理應從哪一個未完成項目開始。

因此，三層工作棧的關鍵不只是「用哪個工具」，而是每一層結束時，要替下一層準備一個不需要重新猜測的起點。

同一個任務，三層如何分工

情境一：會員管理網站

在 Chat Layer，先確認會員類型、管理痛點、資料敏感度、使用頻率與真正必要功能。也許最後發現第一階段只需要一個安全的會員名冊與活動簽到流程，而不是完整 CRM。

在 Work Layer，整理既有名單欄位、使用者角色、頁面流程、資料保護規則、功能優先順序、Wireframe、交付里程碑與驗收條件。若需要，也可以先建立可展示的 Site 或靜態原型。

在 Codex Layer，建立 repository、資料模型、認證、權限規則、測試、部署與監控。此時「會員不能看到其他會員完整電話」「管理員匯出資料必須留紀錄」等規則，應已經寫進專案文件，而不是等開發完成才臨時補充。

情境二：企業 AI 導入提案

Chat Layer 用來釐清企業表面需求背後的決策問題。

Work Layer 研究、分析並建立報告、簡報、試算表與導入路線圖。大多數情況到此即可交付。

只有當企業決定建立原型或內部系統，才把特定工程範圍交給 Codex。這表示同一個商業專案可能長期留在 Work，只有一小部分進入 Codex。

情境三：Podcast 生產

Chat Layer 用來找主題觀點、反方問題與節目敘事。

Work Layer 讀取來源資料，建立口播稿、節目簡介、Show Notes、社群貼文、TTS 版本與發布清單；若流程固定，還可沉澱為範本或 Skill。

通常不需要 Codex。只有當你要建立自動抓取、音檔處理、內容管理與發布系統時，才進入工程層。

三個情境共同說明一件事：Codex 並不是每條路的終點，Work 也不是只有在寫程式前才有價值。 分層的目的，是讓工作在最合適的環境完成，而不是把所有事情送進看起來最強的模式。

何時該切換，而不是繼續留在原地

從 Chat 切到 Work，可以問五個問題：

1. 這件事是否需要多個步驟與持續上下文？

2. 是否要讀取多份檔案、外部資料或連接系統？

3. 最終是否要交付一組可使用的成品，而不只是一段答案？

4. 是否需要中途檢查、核准、改向或長時間推進？

5. 做完後是否值得變成可重複的範本或流程？

若其中兩項以上為「是」，就值得考慮 Work。

從 Work 切到 Codex，則應確認：

- 問題、使用者與成功狀態已足夠清楚。

- 功能範圍與非範圍已定義。

- 關鍵資料、流程、權限與技術限制已整理。

- 交付成果與驗收條件可被測試。

- Repository 規則、執行順序與變更回報方式已存在。

若這些條件尚未成熟，切換到 Codex 只會讓不確定性變成程式碼。

分層是一種責任感，不是僵硬流程

真實工作不會永遠從第一層直線走到第三層。Codex 在開發中可能發現需求矛盾，需要回到 Work 更新規格；Work 在研究時可能發現核心問題尚未想清楚，需要回到 Chat 重新討論；一個已完成的系統也可能回到 Work，產生使用手冊、訓練教材與營運報告。

因此，三層 AI 工作棧不是瀑布式流程。它比較像三種工作空間：你可以來回，但每次切換都應帶著最新狀態，不應讓不同代理各自持有互相衝突的版本。

這套框架也不保證所有產品名稱永遠不變。OpenAI 可能調整介面、方案、同步方式與能力邊界。但只要 AI 工作仍包含「想清楚、準備完整、正式執行」三種不同責任，這個分層就仍然有用。

真正的成熟，在於知道當前的不確定性屬於哪一層、下一步需要產生什麼證據，以及何時不應急著往下走；找到最強按鈕遠遠不夠。

三層切換失敗時，如何回復

分層的目的不在於追求一次判斷全對，而在於讓錯誤能退回正確位置處理。

若 Chat 討論很久仍只有抽象口號，代表需要加入真實資料、角色與摩擦，才能轉成 Work 任務。若 Work 建立大量文件卻彼此矛盾，代表正式來源與決策狀態沒有治理，應先停止產出、整理上下文。若 Codex 反覆追問產品規則或自行新增功能，代表交接仍不成熟，應把缺口送回 Work，而不是只追加一段更強硬的程式提示詞。

反過來，若 Work 已把文件、簡報與 Site 全部完成，卻沒有任何 Repository 或正式工程需求，就不必為了流程完整硬交給 Codex。三層工作棧的目的，是讓工作在適當位置結束，而不是一定走到最下層。

一張切換判斷卡

可以在每次切換前問：

- Chat → Work：方向是否足以建立任務？是否需要持續上下文、多來源與完整交付？

- Work → Codex：工程範圍、資料、限制、測試與完成定義是否足以進入 Repository？

- Codex → Work：是否產生需要整理、教學、對外說明或下一輪決策的新狀態？

- 任何層 → 人類：是否涉及價值衝突、敏感資料、不可逆行動或授權變更？

真正的架構能力，是能看見工作性質已改變，並把狀態完整帶到下一個位置；沒有人能永遠一次選對工具。

三層之間要帶走的「狀態封包」

工具切換最常失敗，往往因上一層只交出結果、沒有交出狀態，而非下一個代理能力不足。為了讓切換可重複，可以要求每一層都產生一個最小狀態封包。

Chat 離開時，至少留下：真正問題、目標使用者、成功狀態、主要分歧、已採用觀點與尚待驗證假設。這些內容告訴 Work，討論已走到哪裡，不必重新腦力激盪。

Work 離開時，至少留下：正式來源、範圍、限制、交付清單、驗收條件、核准點、決策紀錄、未決問題與下一步。這些內容告訴 Codex，哪些是產品責任，哪些是工程自由。

Codex 離開時，至少留下：實際修改、測試結果、未通過項目、環境與版本、已知限制、部署狀態、回復方式與後續建議。這些內容讓 Work 可以整理交付，也讓人類知道系統發生了什麼。

狀態封包不必每次都是十份文件。小任務可以是一張表，大專案才需要資料夾。但它必須回答三個問題：我們從哪裡來、目前什麼是真的、下一個責任是什麼。

路由錯誤的四個診斷訊號

第一個訊號是討論過熱：在 Chat 裡反覆改寫語氣與功能名稱，卻沒有新的事實或決策。這表示工作已需要正式簡報與交付，不應繼續停在探索層。

第二個訊號是文件膨脹：Work 產出很多表格、簡報與規格，但核心問題仍互相矛盾。這表示缺的是問題定義與上下文治理，應先退回處理，而非繼續增加成果。

第三個訊號是工程猜測：Codex 不斷自行決定角色權限、資料保存、商業規則或第一版範圍。這表示前置準備不足，應暫停擴大實作，把決策送回 Work。

第四個訊號是責任真空：代理即將寄信、公開、部署、付款或處理敏感資料，卻找不到核准人。這並非工具選錯而已；它是人類責任沒有被寫進流程。

三層工作棧因此是一個可回復的控制系統，並非只能向前的流水線。成熟使用者的能力，不在於一次把任務送到最強模式，而在於能根據診斷訊號把工作送回正確層級。

三種不確定性，決定工作應該在哪一層停留

三層分工還可以用「目前最主要的不確定性」判斷。

第一種是價值不確定性：不知道真正問題、使用者與成功狀態。這時最重要的是對話、反問、比較與重新定義，應先停在 Chat。若直接產出大量檔案，只會讓一個尚未被確認的方向看起來更正式。

第二種是證據與工作不確定性：方向大致清楚，但資料散落、來源衝突、成果格式與流程尚未整理。這是 Work 的核心區域。代理可協助研究、建立正式來源、形成交付契約，並用中間成果讓人檢查。

第三種是實作不確定性：產品方向與驗收已清楚，問題集中在現有程式、技術相依、效能、測試或部署。這時 Codex 可以在工程環境中透過閱讀 Repository、執行命令與實驗找到答案。

一個專案可能同時包含三種不確定性，但要辨認哪一種正在阻塞下一步。若商業問題未決，增加程式實驗無法解決；若規格已完整，卻一直留在對話中討論，也只會延遲必要的工程證據。

三層之間最重要的交接物，是一組已更新的狀態物件，而非整段聊天：問題敘述、正式來源、決策紀錄、交付規格、測試與未決事項。只要這些物件仍然可信，換一個對話、裝置或代理，工作就不必重新從記憶開始。

因此，分層的本質在於把不同種類的不確定性放進最適合消除它的回路，工具選擇只是表面。

本章收束

Chat 讓我們用低成本探索問題；Work 把探索結果整理成可執行與可交付的工作；Codex 在工程環境中完成程式與系統變更。三者之間沒有單純的高低關係，只有是否適合當前責任的差別。

下一章要進一步處理一個常見誤會：當 Codex 做出來的東西不符合期待，我們常先怪模型不夠強。但許多專案真正的失敗，其實在第一行程式碼出現以前就已經發生。

章末金句

1. 最強的模式，不一定是當下最正確的起點。

2. Chat 的任務是讓問題變清楚，Work 的任務是讓工作變完整，Codex 的任務是讓工程變成現實。

3. 一個模糊願望進入 Codex，只會更快地變成一套具體誤解。

4. Work 不只是 Codex 的候車室；對很多知識工作而言，它本身就是交付終點。

5. 好的交接要移交一個已被整理過的工作狀態，不能只貼上一段提示詞。

6. 不確定性應先被討論、整理與驗證，不應直接被寫進程式碼。

7. 工具分工的目的是減少猜測，而非增加流程。

8. 真正的 AI 素養，是知道何時前進，也知道何時不該急著執行。
