第三章｜很多 Codex 專案，在寫程式之前就失敗了

Codex 完成了一個活動報名網站。首頁能開、表單能送出、資料也寫進資料庫。從技術角度看，它確實完成了使用者的指令。

但真正準備使用時，問題一個接一個出現：報名者可以重複送出；主辦方不知道如何匯出名單；手機上的欄位太擠；公開查詢頁顯示完整電話；取消報名沒有流程；活動額滿後仍能繼續登記；資料蒐集同意文字也不存在。

這時最容易得到的結論是：「Codex 還不夠聰明。」

然而，回頭看最初的指令，可能只有一句：

幫我做一個活動報名網站，要好看、可以收集姓名和電話。

Codex 並沒有違反這句話。它只是把沒有被定義的部分，用自己的推測補完。真正的問題不一定發生在程式碼，而是發生在任務被交出去以前。

代理會填滿空白，但不會替你承擔空白的責任

人類溝通經常依賴默契。你對熟悉的同事說「照上次的活動做」，對方知道使用哪份表單、名單怎麼隱碼、誰要收到通知、什麼時候關閉報名。這些知識沒有出現在句子裡，卻存在共同經驗中。

AI 代理沒有這些默契。它能從上下文推論，也能主動提問，但當上下文不足、問題沒有被標示為未知，它仍然必須選一條路往前走。模型愈能自主執行，這種填補空白的能力愈強；同時，錯誤假設被快速擴大的風險也愈高。

一個只回答問題的模型，猜錯時可能只是產生一段不準確的文字。一個能修改 repository、建立資料庫、執行命令與部署系統的代理，猜錯時會把假設變成架構、欄位、權限與使用者流程。這些結果一旦形成，後面每一項修改都會建立在前面的決定上。

因此，代理時代最危險的狀態，並非單純「AI 不知道」，而是AI 不知道自己不知道，人類也沒有把未知標示出來。

四種看起來像技術問題的前置失敗

第一種：目標被功能取代

「做一個報名網站」是一項功能需求，不是目標。

目標可能是降低人工整理名單的時間，可能是避免重複報名，可能是讓參加者能確認自己是否成功，也可能是保護公開名單中的個人資料。不同目標會導致完全不同的產品設計。

若沒有說明成功後要產生什麼改變，代理只能把「有一個網站」當成完成。於是畫面做出來了，真正的營運問題卻沒有被解決。

第二種：上下文被當成附件數量

有些人知道要提供資料，於是一次丟進十幾份舊文件、三個不同版本的 Logo、兩份互相矛盾的名單，以及去年活動的過期規則。資料很多，看起來比一句話完整，實際上卻增加了代理判斷的負擔。

上下文不足會讓 AI 猜；上下文過量、過時或互相衝突，則會讓 AI 在錯誤證據中選擇。沒有優先順序、版本日期與正式來源，附件只是更多不確定性。

第三種：限制在出事後才出現

很多限制直到代理做完才被提出：

- 原始檔不能覆寫。

- 不能新增付費套件。

- 會員資料不能離開指定區域。

- 公開頁面不能顯示完整電話。

- 不能直接寄信給所有人。

- 部署前一定要人工審查。

當這些規則沒有事先寫入任務，代理可能採取技術上合理、組織上不可接受的做法。後續修正不只是改一行程式，往往要調整資料模型、權限設計與整個流程。

第四種：完成由代理自己定義

若沒有驗收條件，代理只能用一般性的信號判斷完成：程式可執行、頁面能載入、測試沒有立即失敗、要求的檔案已存在。

但人類真正關心的可能是：不同角色看到的內容正確嗎？錯誤輸入會怎樣？手機能不能使用？敏感資料有沒有遮蔽？ZIP 能不能解壓縮？文件字數是否達標？

「程式跑起來」與「工作可以交付」之間，往往隔著一整套未定義的品質標準。

表面錯誤與根本錯誤

遇到不符合預期的成果時，可以先把問題分成兩層。

表面錯誤是執行層能直接處理的問題，例如語法錯誤、測試失敗、欄位拼錯、排版溢出、API 回傳格式改變。這些問題通常可以在需求不變的前提下修正。

根本錯誤則是專案本身沒有回答的問題，例如誰能看到什麼、是否需要登入、資料保存多久、成功指標是什麼、第一版到底包含哪些功能。若根本問題未解決，要求 Codex「再修好一點」只會讓代理在同一片霧中繼續前進。

判斷兩者的一個簡單方法是：

如果不同工程師在閱讀目前規格後，很可能做出三種都算合理、但互不相容的方案，那麼問題還不在程式碼，而在任務定義。

這時最有效的動作，是暫停執行、回到 Work Layer 補足決策，而非換模型、增加推理強度或重跑任務。

本書提出的 Codex 前置準備層

為了避免過早進入開發，本書提出Codex 前置準備層（Pre-Codex Preparation Layer）。這是一個作者工作概念，不是 OpenAI 官方產品名稱。

它的定義是：

在正式程式開發以前，把人的模糊意圖整理成可由工程代理理解、執行、測試與回報的專案狀態。

這個準備層至少處理九類內容：

1. 問題：誰遇到什麼阻礙，為什麼值得解決？

2. 目標：完成後應產生什麼可觀察的改變？

3. 使用者與角色：誰使用、誰管理、誰只能查看？

4. 範圍：第一版做什麼、不做什麼？

5. 上下文：有哪些正式資料、規則、品牌與既有系統？

6. 限制與權限：哪些技術、資料與外部動作有邊界？

7. 交付成果：最後要存在什麼檔案、功能、頁面與說明？

8. 驗收與測試：用哪些情境證明成果合格？

9. 交接規則：Codex 從哪裡開始、怎麼回報、遇到什麼情況要停？

前置準備層不是要求在開發前寫一份永遠不變、厚達數百頁的規格。它的目的，是把會造成方向性返工的關鍵未知提早暴露，並把可以延後的細節清楚標示為可探索。

成熟的準備不要求「所有事情都決定好了」，但必須讓已決定、尚未決定，以及授權代理自行決定的範圍，都被分開寫清楚。

從一句願望到可執行專案

比較下面兩種交付方式。

版本一：直接執行

幫我做一個公益講座的報名網站。要現代、好看，用 Next.js，資料放 Firebase，完成後部署到 Vercel。

這段話提供了技術選擇與大致成果，卻留下大量空白：活動是否只有一場？額滿怎麼處理？要不要寄確認信？公開名單是否存在？取消報名如何驗證身分？資料由誰匯出？是否需要管理後台？哪些欄位是必填？

Codex 可以開始，但開始本身就會產生隱性決策。

版本二：經過前置準備

問題：目前使用 Google 表單收件，主辦方每天人工去重並回覆是否報名成功，公開名單也有個資暴露風險。目標：讓參加者能完成報名並立即看到結果；主辦方可查看與匯出名單；公開查詢只顯示姓名遮蔽與電話末五碼。角色：訪客、已報名者、活動管理員。第一版範圍：單場活動、100 人上限、候補名單、取消報名、管理員 CSV 匯出。暫不做會員系統、線上付款與多場活動。限制：不得顯示完整電話；所有 secrets 使用環境變數；不得直接改動 production；新增付費服務前必須核准。交付成果：Next.js repository、Firebase rules、測試資料、README、部署設定、操作說明。驗收：重複手機不得產生兩筆有效報名；第 101 人進入候補；取消後第一位候補遞補；公開頁不出現完整個資；手機寬度 375px 可完成主要流程；測試與 build 必須通過。

第二個版本仍可能需要澄清，但它把最昂貴的方向性問題先放到桌面上。Codex 可以針對已知範圍做計畫，也能在遇到未決事項時提出具體問題，而不是從空白中發明產品。

過早寫程式，會讓暫時猜測變成沉沒成本

軟體一旦開始成形，人類會產生一種心理偏差：因為已經做了很多，就傾向沿用目前方向。即使發現資料模型不合理、登入方式不適合、第一版範圍太大，團隊也可能選擇繼續修補，而不是回頭重定義問題。

這就是過早執行的成本。AI 讓寫程式變快，並沒有消除沉沒成本；它只是讓沉沒成本更早、更大量地形成。

假設代理先建立了一套完整會員帳號系統，後來才確認活動其實只需要以手機末五碼查詢報名。此時多出來的不只是幾個頁面，而是認證、密碼重設、資料欄位、權限規則與隱私責任。模型可以快速重構，但每一次重構仍需要驗證，也可能留下錯誤與複雜度。

因此，速度不應只用「第一個畫面多快出現」衡量。更好的指標是：

- 多快發現錯誤假設？

- 多早把不可逆或高成本決定提出來？

- 第一次正式實作，有多少內容能保留下來？

- 完成後是否能用明確證據驗收？

最快開始的專案，不一定最快到達可交付狀態。

什麼問題可以讓 Codex 自行決定

強調前置準備，不代表人類要把每個按鈕顏色、每個函式名稱都規定好。過度規格化會消耗時間，也會限制代理提出更好的做法。

可以授權 Codex 自行決定的事項，通常具備三個特徵：

1. 決定可逆，改動成本低。

2. 不涉及核心使用者價值、法律、個資、財務或組織承諾。

3. 有清楚的品質標準可以驗證，而不必指定實作細節。

例如，你可以要求「符合現有 design system、通過 accessibility audit、主要流程在手機可用」，讓代理選擇具體 layout；可以要求「測試涵蓋報名上限與取消遞補」，讓代理設計測試結構。這是用標準管理結果，而不是微操每一步。

相反地，誰可以查看會員資料、付款何時成立、資料保留多久、是否可自動寄出對外訊息，這些不是純技術細節，應由人類或組織明確決定。

交給 Codex 前的停看聽

在按下開始以前，可以做一個簡單的前置檢查。

停：先停止把願望當需求

若目前句子主要是「我想要一個……」「幫我做得專業一點」「功能像某某產品」，先不要開發。這表示你描述的是形式或感覺，還不是問題與成功狀態。

看：看見仍由代理猜測的地方

把目前文件交給另一個人，請他列出所有必須自行假設的事項。若清單包含使用者角色、資料可見性、核心流程與完成條件，代表準備不足。

聽：聽代理提出的計畫與疑問

成熟的交接不是要求 Codex 毫不提問地執行。先讓它摘要理解、列出假設、提出風險與開發計畫，可以暴露上下文衝突。真正需要避免的是無止境追問已經明確的事情，而不是禁止任何必要澄清。

在代理工作中，人類要追求的是讓問題出現在成本最低的時間點，而非幻想零問題。

Work 在前置準備層扮演什麼角色

Work 的優勢，在於它能同時處理研究、文件、資料、範本與多項交付成果。你可以讓它讀取既有需求、訪談、品牌規範與舊系統說明，找出衝突與缺口，建立問題定義、角色表、功能範圍、資訊架構、驗收清單與 Codex handoff package。

這並不表示 Work 會自動知道正確答案。它仍可能誤解資料、選錯版本或產生看似完整但缺乏決策依據的規格。人類必須審查關鍵主張，尤其是涉及政策、個資、法律、財務與對外承諾的內容。

Work 的價值，是把前置準備從一連串零散對話，提升為一個可以被檢查、修改、保存與交接的成果。它讓「我腦中大概知道」變成「專案裡有一份明確文件」。

成熟專案會管理未知

即使準備充分，軟體開發仍然會發現新問題。使用者可能改變需求，外部 API 可能有限制，技術測試也可能推翻原先假設。

因此，Codex 前置準備層用來把不確定性分成三類，而非消滅所有不確定性：

- 必須在開發前決定：角色、資料權限、核心範圍、不可逆限制。

- 可以用原型或 spike 驗證：技術可行性、第三方服務行為、效能假設。

- 可以授權代理決定：低風險、可逆、可透過測試驗證的實作細節。

這種分類讓 Codex 不必等待完美規格，也不會被迫替產品擁有人做高風險決策。

真正成熟的專案，會讓每一個重要問號都有負責人、驗證方法與處理時機；表面沒有問號並不可靠。

決策債，比技術債更早出現

技術債是為了速度採取暫時工程方案，未來必須付出維護成本；在它之前，還有一種「決策債」：產品、資料與權限問題尚未決定，卻先讓實作替我們做出暫時選擇。

例如沒有決定會員刪除政策，就先把資料表設成永久刪除；沒有決定公開名單規則，就先讓前端直接讀取完整資料；沒有決定第一版是否需要帳號，就先建立一套複雜登入。這些選擇一旦被其他功能依賴，後來改動的成本遠高於最初多問幾個問題。

決策債不代表任何未知都不能進開發。重要的是標示：這是已鎖定決策、暫時假設、待驗證實驗，還是不得由代理決定的問題。只有被標示的未知，才能被管理。

決策債務登錄：不要把未決事項藏進程式碼

技術債通常在程式寫出來後被看見；決策債務則更早。它指的是那些尚未回答、卻已經開始影響資料、流程與架構的問題。

例如「是否需要帳號」「取消後保存多久」「誰能看到完整電話」「第一版是否寄通知」都可能暫時沒有答案。未決本身不是錯誤，真正危險的是它們沒有被標示，Codex 只好用預設值繼續。

可以建立一份簡單的 decision_debt.md，每一項記錄：問題、影響範圍、目前假設、證據、負責人、需要決定的時機，以及在未決前代理可以做什麼。這能把三種狀態分開：

- 可以延後，且不影響目前架構。

- 必須先做探索性實驗才能決定。

- 若不先決定，就會造成方向性重工。

對第二種，可以建立「探索契約」。例如只用合成資料做登入原型、只比較兩種資料庫交易方案、不部署 production，完成後交付差異、風險與建議。探索的成果是減少未知，不是把原型直接升格成正式系統。

決策債務也要有利息概念。某個問題若會影響愈來愈多檔案與功能，拖延成本就愈高，應提前處理；若只是文案細節，可以在更晚的里程碑決定。這比一律要求「先把所有需求想完」更務實，也比把所有未知交給 Codex 更負責。

交給 Codex 前的紅旗清單

出現下列情況時，應先停在前置準備層：

- 同一個核心需求在不同文件有不同版本。

- 使用者與管理者權限只用「看情況」描述。

- 任務包含個資、付款或 production，卻沒有核准與回復方式。

- 對「完成」只有視覺感受，沒有測試與證據。

- 第一版範圍持續增加，沒有不做清單。

- Codex 必須自行選擇商業模式、法規解釋或資料保存政策。

- Repository 與技術限制尚未被檢查，卻已鎖定大量實作細節。

紅旗不表示專案不能開始；它表示下一個可執行任務應是「消除或管理紅旗」，還不適合直接完成整套系統。

在開發前做一次「失敗預演」

專案啟動會議常問「我們要做什麼」，很少問「三週後最可能因為什麼返工」。在交給 Codex 之前，可以用二十分鐘做一次失敗預演：假設第一版已經做完，但團隊拒絕上線，請每個角色寫下最可能的原因。

產品負責人可能寫：核心流程做錯，因為需求文件只列頁面，沒有說明成功狀態。使用者可能寫：系統增加了輸入步驟，反而比試算表更慢。管理者可能寫：公開與內部資料沒有分流。工程人員可能寫：技術棧與現有環境衝突。維運者可能寫：沒有日誌、備份與回復路徑。法務或資安人員可能寫：測試直接使用真實個資。

把原因分類後，不要急著要求所有風險歸零，而是決定每一項的處理方式：

- 在開發前回答：若不回答就會改變架構或責任，例如使用者角色與資料公開規則。

- 以小實驗驗證：可以透過原型、假資料或短期試用降低未知，例如使用者是否理解新的流程。

- 授權 Codex 決定：屬於可回復、可測試的工程細節，例如符合 Repository慣例的元件拆分。

- 建立核准點：只有特定責任人可以放行，例如 production 部署與資料遷移。

- 列為第一版不做：價值不明、風險過高或會讓範圍失控的功能。

失敗預演的價值，是把未來的「早知道」變成現在可處理的工作。

決策成熟度比文件厚度更重要

有些專案有上百頁文件，仍然無法開始；有些專案只有幾份精簡 Markdown，Codex 卻能穩定推進。差別在於決策是否成熟，而不是文件是否看起來正式。

可以把決策分成四種狀態：

1. 已鎖定：本輪不可自行改變，若衝突必須停止並回報。

2. 暫定假設：可以先實作，但必須可替換，並註明驗證時機。

3. 授權決定：代理可依既有規範選擇，完成後說明理由與證據。

4. 尚待回答：目前不得用猜測固化，需要指定責任人與期限。

一份交接包若能清楚標示這四種狀態，就算仍有未知，也比一份假裝所有事情都確定的完整規格更可靠。未知本身不是失敗；讓未知悄悄進入架構，才會形成決策債。

前置準備的完成門檻

Codex 前置準備層不追求完美，而應有最低通過門檻：核心問題與第一版價值能用同一段話說明；主要角色、資料與權限沒有方向性矛盾；範圍與不做清單清楚；高影響動作有核准與回復；核心流程有驗收情境；Repository、技術與環境限制已被檢查；重大未知已被回答或轉成有邊界的實驗。

通過這個門檻，就可以把工程未知交給 Codex；未通過時，下一個工作不應是「再寫更多程式」，而應先消除最可能造成方向性返工的缺口。

本章收束

很多 Codex 專案的失敗，源於人類把尚未成形的願望當成可執行任務，未必是代理不會寫程式。目標、上下文、限制與驗收缺失時，代理仍會前進，只是它前進的方向建立在猜測上。

Codex 前置準備層的目的，是在猜測變成架構以前，把關鍵問題轉成可見的決策。下一章將從最前面的那一步開始：如何把「我想要一個功能」重新整理成真正值得解決的問題。

章末金句

1. Codex 做錯的第一行程式碼，可能源自人類沒說清楚的第一句話。

2. 代理會替你填滿空白，卻不會替你承擔空白造成的責任。

3. 程式可以重寫，但被程式固定下來的錯誤目標，往往更難推翻。

4. 沒有定義成功，任何能執行的結果都可能被誤認為完成。

5. 前置準備把最昂貴的錯誤移到最便宜的階段發現，因此能降低返工，並非拖慢開發。

6. 好規格不必回答所有問題，但必須分清楚哪些已決定、哪些待驗證、哪些可授權代理決定。

7. AI 讓實作變快之後，問題定義反而成為更稀缺的能力。

8. 成熟專案允許未知存在，但每個重要未知都要有負責人、方法與處理時機。
