第五章｜上下文不是愈多愈好

一個專案開始前，使用者把整個資料夾丟給 AI：去年的企畫書、今年的會議記錄、三個版本的簡報、十幾張截圖、沒有日期的報價單、兩份互相矛盾的品牌規範，還有一個叫做「final_final_真的最後版」的檔案。

他以為自己提供了完整上下文。AI 也真的讀了很多資料，最後卻使用了舊價格、錯誤 Logo 與已經被取消的流程。

真正的問題在於資料沒有秩序，未必是數量太少。

在單次問答時，我們常把注意力放在提示詞怎麼寫；當 AI 開始執行長任務、使用工具並跨檔案工作時，真正決定成果品質的，往往是它在每個步驟看到了什麼、哪一份資料被視為正式、哪些內容已過時，以及發生衝突時應聽誰的。

這就是上下文工程（context engineering）真正要處理的問題：設計一個能支持正確判斷、持續更新與可靠交接的資訊環境，而非把更多內容塞進模型。

資料很多，為什麼反而更容易做錯

每一份新增資料都可能帶來價值，也可能帶來新的決策負擔。

如果兩份文件都寫了課程價格，AI 要選哪一份？如果品牌簡報使用舊 Logo，而最新網站使用新色系，哪個優先？如果會議記錄提到「可能增加付款功能」，但正式範圍文件明確寫第一版不做付款，代理應如何判斷？

人類熟悉專案時，會憑經驗忽略舊資料；AI 看到的只是內容本身。檔名、日期、位置、來源與指示都會影響它的選擇。當這些訊號不清楚時，模型可能採用看起來更完整、文字更多，卻不是最新或最正式的版本。

因此，上下文有兩種常見失敗。

第一種是上下文缺口：缺少關鍵資料，代理只能猜。

第二種是上下文負債：資料雖多，卻過時、重複、衝突、無法定位，讓每一次工作都必須重新判斷。

上下文負債和技術負債相似。它不一定讓任務立即失敗，但會在每次更新、交接與重複執行時增加成本。

上下文的五項品質

本章用五個問題檢查上下文品質：相關、可信、最新、完整、可定位。

一、相關：這份資料是否真的影響當前決策

不是所有可取得的資料都應進入任務。若要建立一份三小時企業課程提案，過去五年的所有社群貼文可能沒有必要；若要模仿作者語氣，幾篇具代表性的正式口播稿，可能比數百篇零散短文更有價值。

判斷相關性時，不能只問「這份檔案是否和主題有關」，而要問「它會影響哪一項決策或哪一個交付成果」。答不出來時，先不要放進核心上下文，可以保留在參考區。

二、可信：誰寫的、為什麼能相信

官方政策、已簽核決策、作者親自確認、客戶提供的正式資料，通常具有較高權重；網路文章、會議中的暫時想法、模型生成的摘要，則需要再確認。

可信不代表內容一定正確，而是來源責任清楚。當 AI 產生推論時，應標示它是推論，不應因為文字流暢就升格為事實。

三、最新：資料是否仍適用於現在

產品功能、價格、方案、組織人員、活動日期與技術版本都可能改變。最新不只是看檔案修改時間，因為一份舊文件被重新上傳後，也會看起來很新。

更可靠的做法，是在內容中記錄生效日期、查證日期與版本。對 Work 這類快速更新的產品，本書把方案、平台與上限集中在版本矩陣，就是為了避免舊資訊散落在正文各處。

四、完整：足以完成當前責任，而不是包辦所有未來

完整指當前任務需要的關鍵條件沒有缺漏，並非無所不包。

若任務是建立課程簡報，完整上下文可能包括受眾、時數、學習目標、品牌範本、必要案例與禁止內容；不一定需要整個組織的歷史資料。若任務是交給 Codex 開發，則還要加入資料模型、技術限制、測試與驗收。

完整性必須依工作層級判斷。Chat、Work、Codex 所需的上下文不會完全相同。

五、可定位：代理能否知道去哪裡找、哪一段最重要

一個 200 頁 PDF 可能包含關鍵規則，但若沒有頁碼、章節、索引與摘要，代理每次都必須重新搜尋。可定位的上下文會清楚說明：檔名、用途、正式程度、相關章節與優先順序。

對長專案而言，一份 context_index.md 往往比再多十個附件更有價值。它不複製所有內容，而是告訴代理每份資料負責什麼。

建立上下文的四層結構

為了讓 Work 與 Codex 不必在一堆檔案中自行猜測，可以把上下文分成四層。

第一層：正式基準

這一層包含不可被一般參考資料覆蓋的內容，例如：

- Book Bible 或 project brief。

- 已鎖定的需求與決策。

- 正式品牌規範。

- 資料與權限政策。

- 技術版本與 repository 規則。

- 最新的完成定義。

正式基準應少而清楚。若有多份文件自稱最終版本，本身就是需要先解決的問題。

第二層：任務材料

這是完成當前工作直接需要的資料，例如訪談記錄、數據、產品文件、會議摘要與來源文章。它們可以很多，但每一份都應標示用途與日期。

第三層：參考示例

示例用來說明風格、格式或品質，不等於正式事實。舊簡報可以當版面參考，不能自動成為最新方案；過去文章可以當語氣示例，不能把其中的舊技術資訊沿用到現在。

第四層：排除與歷史

過時版本不一定要刪除，但應移出工作主路徑，標示「歷史資料」「不得作為現行規則」。保留歷史有助於追蹤決策，卻不能讓代理每次都重新猜哪份有效。

這四層讓上下文從一個資料堆，變成有權重的資訊架構。

單一正式內容來源

長專案最常見的混亂，是同一內容同時存在於 Markdown、Word、簡報、聊天記錄與雲端文件，每一份都被不同人修改。

解決方法是指定單一正式內容來源（single source of truth），而非只允許一種檔案：真正的內容修改先發生在哪裡，其他格式從哪裡生成。

在本書出版專案中，正式章節來源是 chapter_XX_main.md，全書來源是 full_book.md。DOCX、演講筆記、簡報大綱與金句都從完成編輯的 Markdown 產生。若只改 Word 而沒有回寫 Markdown，下次重新生成時修改就會消失。

同樣的原則也適用於軟體專案。需求可能以 project_brief.md 與 acceptance criteria 為正式來源；資料結構以 migration 與 schema 為準；環境設定以 repository 裡的配置為準。聊天裡的討論只有在回寫正式文件後，才成為可交接的決策。

單一正式來源讓不同代理與人類知道什麼可以相信；檔案整齊只是附帶效果。

當資料互相衝突時

衝突不可避免。真正重要的是事先定義處理順序。

可以採用以下優先規則：

1. 使用者在當前任務中的最新明確指令。

2. 已鎖定的正式決策與基準文件。

3. 具日期與責任人的正式來源。

4. 任務材料中的較新、較直接證據。

5. 參考示例與歷史資料。

當兩個同層級來源衝突，代理不應偷偷選一個。它應列出差異、說明影響，並把需要人類決定的事項變成明確問題。

例如，會議記錄寫「報名需收集身分證字號」，正式個資政策卻只允許姓名與電話。這不是可由模型依「較詳細」原則決定的格式問題，而是權限與風險衝突，必須停下來確認。

壓縮上下文，不等於把內容摘要到失真

長任務需要壓縮。模型不應每一步都重新讀取全部資料，人類也不可能在每次交接時附上所有對話。

但壓縮若只追求短，可能刪掉例外、限制與決策理由。好的上下文壓縮會保留四種資訊：

- 結論：目前已決定什麼。

- 理由：為什麼這樣決定。

- 邊界：哪些情況不適用。

- 來源：需要查證時去哪裡看原文。

因此，一份好的摘要重點不在「所有文件的縮短版」，而在一張可返回原始證據的地圖。

可以使用兩層文件：context_summary.md 提供任務所需的精簡狀態，context_index.md 列出原始來源、版本與用途。Work 先讀摘要，遇到細節再定位原文。

一份可交接的上下文包

以下是一個通用結構：

context_pack/

├── 00_read_me_first.md

├── 01_project_brief.md

├── 02_locked_decisions.md

├── 03_open_questions.md

├── 04_constraints_and_permissions.md

├── 05_acceptance_criteria.md

├── source_index.md

├── references/

└── history/

00_read_me_first.md 說明閱讀順序與優先規則；locked_decisions.md 防止已確認事項被重問；open_questions.md 讓未知保持可見；source_index.md 告訴代理每份檔案的用途、日期與可信層級。

這個結構不必機械套用到每個小任務。它適合多步驟、多人或多代理、會中斷、需要正式交接的工作。

Library、Project 與本機資料夾只是容器，規則仍要自己建立

截至 2026 年 7 月 19 日，ChatGPT Library 會保存上傳與生成的檔案，讓使用者搜尋、篩選與重複使用；Project 可以把相關 chats、files 與 instructions 放在一起；desktop Work 經授權後還能使用本機檔案，而 local outputs 不會自動同步到 web 或 mobile。[R02][R03][R05]

這些能力解決的是「檔案放在哪裡、能否再次找到」，卻不會自動解決「哪一份是正式版、誰可以修改、何時過期」。

Library 不是永遠正確的知識庫，Project 也不是自動完成治理的資料夾。沒有版本、命名與責任規則，再好的儲存能力也只會保存更多混亂。

因此，使用這些功能時仍要回答：

- 哪些檔案是核心基準？

- 哪些只供參考？

- 什麼情況必須更新？

- 誰能修改正式來源？

- 本機與雲端成果如何同步或明確分離？

- 任務結束後，哪些敏感資料應刪除？

最小必要上下文，也是一種安全設計

把所有資料交給代理不只影響品質，也增加隱私與權限風險。任務只需要活動報名資料，就不應順便開放整個會員資料庫；只要讀取某個專案資料夾，就不必授權整個硬碟。

最小必要上下文的原則是：

讓代理看見足以完成當前責任的資料，但不要因為方便，就把與任務無關的資訊一併暴露。

對個人方案，檔案是否用於改善模型取決於 Data Controls；對 Business、Enterprise、Edu 等商業工作區，官方承諾商業資料預設不用於訓練，但仍要遵守組織自己的分類、存取與保留政策。[R05][R16][R17]

安全要在建立上下文時就決定哪些資料不應進來，不能等到任務最後才加一句「注意隱私」。

上下文需要維護，不是一次準備完成

一份今天正確的資料，三個月後可能已經過時。成熟工作流要替上下文設計更新機制：

- 每份易變資料標示查證日期。

- 已鎖定決策記錄變更原因。

- 舊版本移入 history，而非與現行文件並列。

- 定期檢查外部功能、價格與政策。

- 任務結束時，把新決策回寫正式來源。

Work 可以協助比對版本、找出矛盾與建立更新摘要；Scheduled Tasks 也可監測某些外部變化，但不能假定所有 Project files 都能被排程任務直接讀取。官方在基準日明確指出，Project 中建立的 task 目前不能存取該 Project files。[R06]

這個限制反而提醒我們：上下文設計必須知道執行時真正可用的來源，不能只因檔案「存在某處」就假定代理看得到。

上下文準備的實作順序

面對一個新專案，可以依序完成：

1. 列出這次要做的決策與交付成果。

2. 對每項決策標出必要來源。

3. 指定正式基準與優先順序。

4. 排除過時、重複與不相關資料。

5. 建立摘要與來源索引。

6. 標示已鎖定決策、待確認問題與授權代理自行決定的部分。

7. 檢查敏感資料是否超過最小必要範圍。

8. 任務完成後把新狀態回寫正式來源。

這個流程的目標不在建立完美檔案系統，而在讓代理在需要做判斷時，有一條可信而可追溯的路。

一份最小可用的 Context Brief

長任務不必每次攜帶完整資料庫，可以先建立一頁上下文簡報：

任務：

正式目標：

本次必讀來源：

來源優先順序：

只供參考的資料：

已失效／不得使用的資料：

已鎖定決策：

尚待確認問題：

敏感資料與存取限制：

完成後要更新的正式來源：

這份簡報用來提供導航，不能取代原始資料。代理要能從摘要回到正式來源；人也能快速檢查是否把舊檔、未證實推論或不必要個資帶進任務。

上下文衝突的處理演練

假設舊提案寫課程費用為十萬元，近期會議紀錄提到可能調整為十二萬元，但正式報價表尚未更新。成熟代理不應自行選一個「看起來最新」的數字。

它應回報：兩份來源的角色、日期與衝突；說明若採用任一數字會影響哪些文件；在取得核准前，以 【待確認價格】 或不含價格的版本繼續不受影響的工作。人類決定後，先更新正式報價表與變更紀錄，再同步所有衍生成果。

這個小例子呈現上下文治理的核心：遇到衝突時，應讓工作在不把未知偽裝成事實的前提下繼續，而非鼓勵模型更勇敢地猜。

建立「上下文預算」

模型可以讀很多資料，不代表任務應把所有資料一起帶入。上下文預算是一個治理概念，不是固定字數：每一份加入任務的內容，都要說明它支援哪一個判斷，以及加入後是否會增加衝突、隱私或版本風險。

可以把內容分成四種：

- 必讀：不讀就無法正確完成，例如正式需求、品牌禁則與資料字典。

- 按需查閱：遇到特定問題才回看，例如完整會議紀錄、歷史報告與技術文件。

- 示例：用來理解語氣、版面或品質，不代表內容本身是事實。

- 排除：已過時、未核准、重複或不應暴露的資料。

上下文預算的目的，是讓代理先讀導航與正式基準，再依任務查回原文，而不是在大量附件中自行猜測哪一份最重要。

來源優先序要寫在衝突發生前

一個成熟專案可以預先定義來源優先序。例如：已核准決策紀錄高於會議口頭筆記；正式資料表高於簡報截圖；官方文件高於媒體轉述；本輪鎖定規格高於歷史提案；Repository 目前行為與測試結果用來描述現況，但不自動取代產品決策。

這個順序不能一概套用所有專案。法規、合約、技術行為與作者觀點各有不同的權威來源。重要的是，代理遇到衝突時知道要比較來源角色、日期、適用範圍與核准狀態，而不是只選檔名看起來最新的一份。

衝突無法自行解決時，回報格式可以是：

1. 衝突內容與涉及成果。

2. 來源 A 與來源 B 的日期、角色與適用範圍。

3. 依既定優先序的暫定判斷。

4. 若判斷錯誤會造成的影響。

5. 需要哪一位責任人核准。

6. 在等待期間仍可繼續的工作。

這讓問題不會因等待決策而完全停住，也不會在無聲猜測中向下游擴散。

任務結束時的上下文回寫

很多流程只在開始時準備資料，完成後卻沒有把新狀態寫回正式來源。結果下一次任務仍從舊版本開始，重複同一輪修正。

回寫至少包含：已核准的新決策、被淘汰的舊說法、來源更新日期、成果位置、已知限制、未決問題與下次重查條件。若本輪只是產生衍生內容，則不應讓衍生稿反過來成為新的正式事實。

一個簡單原則是：任何會影響下一次判斷的改變，都要回到正式來源；只影響本次呈現的改動，留在交付成果。

這條規則讓上下文成為會維護的知識結構，而不是一次任務前的附件集合。

上下文也有生命週期

上下文治理不只發生在任務開始前。資料會進入、啟用、修改、封存與刪除，每一個階段都有責任。

收件時，先記錄來源、日期、擁有者、敏感性與用途，不因為能上傳就立即放進核心上下文。

啟用時，指定它支援哪一項決策、優先權與有效範圍。真正被載入的，應是本次任務所需的最小集合。

使用中，重要結論要能回到原文；若代理產生摘要或轉換資料，必須保留來源關係與變換規則。

修改時，先更新正式來源，再同步索引與衍生成果。舊版保留在封存區，明確標示失效，不與現行資料混用。

任務結束後，判斷哪些內容可重用、哪些只屬於本案、哪些應依個資或合約要求刪除。Library、Project、本機與外部 App 的副本也要納入清理，不只刪掉眼前對話。

做一次「可檢索測試」

上下文看起來井然有序，不代表下一個代理真的找得到。可以請一個沒有讀過前面聊天的人或代理，只依正式資料回答：目前目標是什麼？哪份文件最高優先？最近一項重大決策是什麼？有哪些未決問題？下一個可執行項目在哪裡？

若答案需要作者憑記憶補充，代表可定位性仍不足。修正方法可能是增加 context_index.md、更新 Project brief、移出過時資料，或把聊天裡的決策寫回正式文件。

可檢索測試比單純確認「檔案都在」更有意義。它驗證的是，工作狀態能否離開原作者仍被理解。

本章收束

上下文不是資料量的競賽。真正有用的上下文，會讓 AI 知道什麼相關、什麼可信、什麼最新、什麼足夠，以及去哪裡查回原文。

當上下文有正式來源、優先順序、版本與索引，Work 才能長時間推進而不反覆迷路，Codex 也才能在開發中持續遵守同一套決策。下一章要處理的是另一個不可缺少的面向：即使目標與資料都清楚，代理仍需要知道它可以動到哪裡、什麼不能做，以及哪些動作必須先由人類批准。

章末金句

1. 上下文的價值不在於多，而在於能不能支持正確判斷。

2. 缺少資料會讓 AI 猜，資料失序則會讓 AI 在錯誤證據中選擇。

3. 一份正式來源，勝過五份都叫最終版的檔案。

4. 好摘要要保留結論、理由、邊界與回到原文的路，不能只刪掉細節。

5. Library 可以保存檔案，卻不會自動替你決定哪一份值得相信。

6. 能被找到不等於能被正確使用，存在某處也不等於執行時可存取。

7. 最小必要上下文同時提升品質，也降低資料暴露風險。

8. 每次任務完成，都應留下比開始時更清楚的正式狀態。
