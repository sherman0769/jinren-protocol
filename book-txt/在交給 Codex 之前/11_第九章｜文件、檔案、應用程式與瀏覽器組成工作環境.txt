第九章｜文件、檔案、應用程式與瀏覽器組成工作環境

有人說，Work 等於在瀏覽器裡送你一台電腦。這句話很容易理解，卻會讓人對它能看什麼、能保存什麼、能登入什麼、能控制什麼產生錯誤期待。

Work 的能力並不來自一個單一神奇環境，而是來自多種資源的組合：對話與 Project context、使用者上傳或生成的檔案、Library、連接的 Apps、Cloud Browser、桌面本機檔案與內建瀏覽器、文件工具，以及 Sites 等交付環境。每一種資源有不同的平台、資料位置、權限、持久性與限制。

所以，真正有用的問題不該停在「Work 有沒有一台虛擬機」，而應進一步追問：

這次任務需要哪些資料、工具與執行環境？它們在哪裡、誰能授權、結果保存在哪裡，又有什麼不能做？

本章不打算列出所有按鈕，而是建立一張工作環境地圖。產品能力會更新，選擇環境的判斷原則應該更耐久。

先把工作環境拆成五個角色

一個代理任務需要的環境，可以拆成五個角色。

1. 任務狀態：目標、對話、決策與進度放在哪裡。

2. 來源材料：代理依據哪些檔案、資料與外部來源。

3. 工具與行動：代理能用哪些 App、瀏覽器、程式或本機應用程式。

4. 執行與暫存：程式、檔案轉換與中間結果在哪裡運作。

5. 正式交付：完成品放在哪裡、如何分享、如何更新與驗收。

若五個角色混在一起，使用者會把對話記憶當成正式資料庫，把暫存執行環境當成永久硬碟，或把能預覽的 Site 當成已經通過正式部署。清楚分工，才能知道哪裡需要備份、版本與權限。

Project：保存任務脈絡，不等於替代正式來源

Project 適合把相關對話、檔案與指令放在同一個工作脈絡中。它能降低每次重新說明背景的成本，尤其適合長期研究、課程、出版與顧問專案。[R02]

但 Project context 仍不應取代 Book Bible、規格文件、研究登錄或 Repository 裡的正式規則。對話中可能包含腦力激盪、被推翻的方案與暫時假設；若後續代理把全部內容視為同等權威，就會產生上下文負債。

比較可靠的做法是：Project 保存工作歷程，正式 Markdown 保存目前決策。每當方向鎖定，更新正式文件；每當版本變更，記錄生效日期與影響。這樣即使切換對話或代理，專案仍有清楚的狀態入口。

Library：可搜尋與重用的檔案區，不是無條件永久硬碟

截至 2026 年 7 月 19 日，OpenAI 說明上傳與 ChatGPT 生成的檔案可保存到 Library，之後能搜尋、重新下載或用於新工作。Library 的容量與聊天附件限制分開，方案上限與檔案大小也有明確規則。[R05]

這對 Work 很重要，因為成果不必只存在某一則訊息裡。品牌手冊、簡報範本、研究 PDF、正式圖片與生成文件可以成為後續任務的來源。

但 Library 有三個容易誤解的地方。

第一，檔案保存不等於專案版本治理。Library 可以放多個版本，卻不會自動知道哪一個是正式版。檔名、日期、索引與正式來源規則仍要由人設計。

第二，Library 不等於模型永久記住所有內容。檔案存在，和每次任務都自動讀取，是兩件事。工作簡報仍要指定這次需要哪些來源。

第三，保存與刪除規則要分開理解。官方說明中，刪除聊天不一定會刪除已保存到 Library 的檔案；若資料敏感，使用者要到正確位置管理，不應假設刪掉對話就完全移除。[R05]

因此，Library 適合做「可重用素材庫」，正式專案仍應有自己的資料夾、版本與清單。

來源材料與範本：這一次參考，還是之後都要重複？

官方文件把 Reference File 與 Template 區分開來：參考檔主要為當前任務提供內容或風格；範本則結合結構、指令、例子與預期輸出，可被後續任務重複使用。[R03]

這個差異會改變你如何準備資料。

一份去年的企業提案可以是參考檔，讓 Work 了解語氣與大致章節；若要把它變成範本，還要移除客戶特有資料、標示可替換欄位、說明哪些段落不可省略、加入驗收條件，並提供一個合格輸出例子。

同樣地，一篇 Podcast 口播稿可以是風格參考；真正的 Podcast Skill 或範本還要定義輸入、處理步驟、時長、繁簡體版本、禁止虛構、來源規則、節目介紹與發布包。

只把成功成品丟給代理，未必能讓它知道成功的原因。範本要把隱藏規則變成可重複的工作結構。

Apps：把外部資料與動作帶進任務

Apps 讓 ChatGPT 連接外部系統、搜尋資料或在核准後執行動作。可用能力會受方案、地區、工作區管理、使用者角色與底層服務權限影響。[R08]

使用 App 時要分清三層授權。

第一層是外部服務本身的帳號權限。代理不會因為接上 App 就超越你在原服務裡的角色。

第二層是 ChatGPT 工作區與管理者政策。企業可能允許讀取某些服務，禁止寫入或限制特定資料來源。

第三層是這次任務授權。即使 App 技術上能修改資料，本次工作仍可以只允許搜尋與建立草稿。

這三層中最窄的邊界，才是代理真正能安全採取的行動。

Apps 也帶來第三方責任。資料離開一個系統、經過另一個整合，再由代理處理時，使用者應確認第三方條款、資料分類、保留與稽核要求。連接方便不代表所有資料都適合送進同一工作流。

Cloud Browser：適合公開網站，不是任意登入世界

Cloud Browser 是遠端的瀏覽器能力。推出初期主要用於未登入的公開網站，例如研究公開資料、比較頁面、擷取公開內容或完成支援的網站操作。[R04]

它有清楚邊界：不能讓代理輸入登入憑證、使用密碼管理器、完成付款；遇到 CAPTCHA、網站阻擋或需要登入時可能停止。對具有後果的動作，系統也可能要求確認。[R04]

這意味著 Cloud Browser 很適合：

- 查閱官方文件與公開公告。

- 比較公開方案與產品資料。

- 整理可公開取得的研究來源。

- 操作不需要登入的頁面流程。

不適合把它描述成「代理可以替我登入所有網站、跑完整後台」。即使未來功能擴大，登入、身分、付款與外部承諾仍應受到核准治理。

網頁內容本身也不可信。頁面可能包含錯誤、惡意指令、過時內容或誘導代理偏離任務。代理從瀏覽器取得的文字應被視為外部資料，而不是新的最高指令。任務規則與使用者授權不能被網頁內容覆蓋。

桌面內建瀏覽器：由人登入，再共同操作

桌面版 Work 的內建瀏覽器與 Cloud Browser 不同。官方說明中，使用者可以在獨立的瀏覽器 profile 中自行登入網站、下載檔案，再讓 Work 或 Codex 在取得許可後協助操作。[R11]

這種環境更接近人與代理共用一個桌面工作區。適合需要登入但仍可由人掌握身分的流程，例如從內部系統下載報表、在網站後台建立草稿、預覽更新內容。

它也帶來更高風險。代理可能看到已登入服務中的敏感資料，網頁操作可能直接改變正式狀態。因此，桌面瀏覽器任務應先設定：允許的網域、可讀與可寫範圍、禁止動作、核准點、下載位置與工作完成後的登入管理。

內建瀏覽器與使用者平常的瀏覽器工作階段分離，也不應假設所有 Cookies、擴充功能與密碼狀態都會自動共用。[R11]

桌面本機檔案與應用程式：最接近真實工作，也最需要邊界

官方把雲端 Work 與桌面 Work 分開說明。雲端工作主要使用上傳檔案、連接服務與雲端工具；桌面版在授權後可以接觸本機檔案、資料夾與應用程式。雲端對話可在支援平台同步，本機執行緒與本機檔案則可能留在該部電腦。[R02]

本機能力非常適合：

- 整理一個明確資料夾中的活動素材。

- 讀取本機專案並產生報告。

- 將錄音、逐字稿與圖片按規則分類。

- 在 Excel 或其他支援應用程式中處理檔案。

- 讓 Work 準備 Repository 交接資料，再交給 Codex。

但「可以使用本機」不代表「整台電腦都可以自由操作」。任務應指定資料夾、輸出位置、原始檔保護、可使用應用程式、刪除與覆寫規則。若成果需要跨裝置持續，也要把正式檔案移到受控的同步或版本系統，而不是依賴某次本機執行緒。

文件、試算表與簡報：原生格式不代表不需驗收

Work 可以依指令、來源材料、參考檔與範本建立或編輯文件、試算表、簡報、報告與分析。[R03]

在支援的 Google Workspace 環境中，它可以建立原生 Docs、Sheets 與 Slides；Microsoft Office 的整合則依平台與產品不同。例如官方說明指出，直接控制 Excel 的路徑與 Codex＋Excel add-in 有關，PowerPoint 在推出初期也不等同所有 Work 桌面流程都可直接編輯。[R03]

這些差異提醒我們：不要寫「Work 全面支援 Office」這種過度概括的說法。每次任務要確認：

- 建立的是原生線上文件，還是下載格式？

- 公式、圖表、字體、動畫與批註是否保留？

- 檔案會存到哪個帳號與資料夾？

- 多人協作與分享權限如何設定？

- 最終檔是否需要在另一套軟體開啟？

文件能生成，只是第一步。正式交付仍要檢查內容一致性、公式、渲染、頁面與相容性。

Sites：快速交付互動成果，但不要省略 production 判斷

Sites 讓 Work 建立、託管、分享網站、Web App 或互動成果。官方資料將它列為公開測試能力，可支援快速原型、儀表板、專案追蹤、互動報告與其他可分享成果。[R01][R10]

對知識工作而言，Sites 補上文件與簡報之間的空白。資料可以被搜尋、篩選、互動，成果也能用網址分享。活動公開頁、課程資源站、原型儀表板與研究展示都很適合。

但「公開網址可用」與「正式企業系統合格」是兩件事。若 Site 涉及登入、持久資料、個資、組織權限、法規、可用性承諾或長期維運，就要重新檢查資料區域、安全、備份、監控、服務責任與退出方案。官方也把每個部署網址視為 production 意義上的公開成果，使用者不能因為它是快速生成，就把發布當成無後果的預覽。[R10]

因此，Sites 最適合被視為一種交付載體，而不是自動通過所有正式系統標準的捷徑。

執行環境：能跑程式，不代表有固定硬體保證

Work 可以執行程式、分析資料與處理檔案，使用者也可能在環境中觀察到 CPU、記憶體或作業系統資訊。但這些觀察只能說明某次執行環境呈現的資源，不能直接推導為每位使用者永久獨享的硬體規格。

雲端服務可能採容器、虛擬化、動態限額、共享底層資源與任務結束後回收。套件、程序、暫存檔與網路規則也可能依任務、方案與平台不同。

因此，書中若要討論「9 核、15 GB」傳聞，最準確的結論是：目前沒有官方承諾能支持「每人固定配一台專屬 VM」。真正穩定的能力描述應聚焦：Work 提供代理可執行程式與處理檔案的環境；任何具體資源需以當下官方文件與實測為準。[R01][R02]

對重要任務，也不應把暫存環境當成唯一正式保存位置。成果要主動輸出到 Library、專案資料夾、雲端硬碟、Repository 或其他受控儲存。

用環境矩陣選擇工具

每次任務可以用六個問題選環境：

1. 資料在哪裡：公開網站、雲端服務、本機、Repository、Library？

2. 是否需要登入：完全公開、由人登入、代理可核准動作？

3. 需要做什麼：讀取、轉換、建立、修改、分享、發布？

4. 成果放哪裡：聊天、Library、雲端文件、Site、本機、Git？

5. 是否跨裝置與跨人接手？

6. 資料敏感性與正式環境責任有多高？

簡化後可以形成以下判斷：

工作｜較自然的環境｜主要注意

公開研究與來源整理｜雲端 Work＋Cloud Browser｜來源可信度、登入與網站阻擋

多檔案報告與簡報｜Work＋Library／雲端文件｜正式版本、格式與分享權限

本機資料夾整理｜桌面 Work｜原始檔保護、範圍與持續性

登入後台建立草稿｜桌面內建瀏覽器｜身分、核准點、正式狀態

快速互動展示｜Sites｜公開範圍、資料與 production 責任

Repository 開發與測試｜Codex｜AGENTS.md、測試、祕密與部署

矩陣是一張判斷提醒，並非固定的產品規則：環境選擇要由資料位置、行動權限與交付責任共同決定。

資料治理要先於方便

對個人帳號、Business、Enterprise、Edu，不同方案的資料使用與治理規則不完全相同。官方說明中，組織方案的業務資料預設不作模型訓練；個人使用者可以透過 Data Controls 關閉「Improve the model for everyone」，Temporary Chat 也有不同保留規則。[R16][R17]

但「不作訓練」不等於所有風險消失。還要考慮：第三方 App、外部網站、分享連結、工作區可見性、Library 保存、Memory、下載檔與本機副本。組織也可能有比產品預設更嚴格的資料分類與法規要求。

因此，敏感任務開始前要問：資料是否可上傳？是否需要去識別？可否透過第三方 App？成果能否公開？保存多久？誰可以刪除？能否使用真實 production 資料測試？

方便是一項價值，但不應成為默認授權。

三個任務，三種環境組合

出版專案

Project 保存對話脈絡；Book Bible、章節 Markdown 與研究登錄放在正式專案資料夾；官方 PDF 與範本可放 Library；Work 用雲端瀏覽器查證公開資料；DOCX 在受控環境生成與渲染；最後 ZIP 保存到正式交付區。每一層都知道哪個是來源、哪個是衍生成果。[R02][R05]

協會活動

雲端 Work 整理公開活動資訊與宣傳內容；桌面 Work 在明確資料夾處理報名檔；敏感原始資料留在受控位置；公開 Site 只使用遮蔽後資料；寄信與發布設人類核准點。若要建立正式管理系統，再把需求交給 Codex。

Podcast 生產

Library 保存作者語氣範例、節目說明與封面素材；Work 依本次題材與來源建立口播稿、簡體 TTS 稿、Show Notes 與社群包；範本或 Skill 保存固定結構；Scheduled Task 只負責監測題材，不在沒有作者確認時自動發布。

這些組合沒有一個「最強環境」。選擇的標準，是任務是否能在清楚資料、適當權限與可驗收交付下完成。

用資料流圖選擇環境

只列出工具名稱，容易忽略資料實際走向。開始任務前，可以畫一張最小資料流圖：資料從哪裡來、在哪個環境被讀取、是否傳給第三方、產生什麼中間檔、最後保存在哪裡、誰能看見、何時刪除。

以協會公開名單為例，原始報名表可能包含姓名、電話、電子郵件與備註。桌面 Work 只在受控資料夾讀取；遮蔽規則將姓名中間字隱藏、電話只保留末五碼；公開資料表與原始資料分開；Site 只讀取遮蔽後版本；發布前由人複核；原始檔不被打包進公開成果。

若不畫資料流，使用者可能只注意「最後頁面有沒有遮蔽」，卻忽略中間檔、日誌、同步資料夾與共享權限。環境選擇的本質，在於資料整段生命週期是否仍符合目的與授權，不能只看哪個介面方便。

環境選擇的六個問題

1. 必要資料目前在哪裡，這個 surface 真的能取得嗎？

2. 資料能否上傳，還是必須留在本機或組織環境？

3. 任務是否需要登入身分、Browser 操作或外部 App？

4. 產生的成果是暫存、正式、公開，還是要進 Repository？

5. 中斷、失敗或換裝置後，狀態能否恢復？

6. 哪些動作會改變外部世界，需要核准與稽核？

回答後，才決定使用 Cloud Work、Desktop Work、Browser、Library、Apps、Sites 或 Codex。不要從「哪個功能最新」反推任務，而要從資料、責任與交付反推環境。

中斷與復原也是工作環境的一部分

代理環境可能因工作階段結束、網路、權限、網站阻擋、額度或工具錯誤而中斷。可靠任務不能假設一次跑到底。

重要中間成果要定期寫入正式位置；套件、暫存檔與執行狀態若未被官方承諾持久保存，就不應作為唯一資料；外部動作要能辨認是否已執行，避免重試時重複寄送、建立或付款；長任務要留下 checkpoint，包含已完成、下一步、輸入版本與驗證結果。

環境韌性讓任務中斷後不必靠聊天記憶猜測，也不會因重跑造成第二次後果，無須假裝永不中斷。

可攜性與退出路徑

選擇工作環境時，還要問一個常被忽略的問題：若平台、方案、帳號或工具改變，成果能不能被帶走？

重要專案應優先使用可匯出的正式格式，例如 Markdown、CSV、標準圖片、DOCX 與 Git Repository；同時保留資料字典、環境變數範例、依賴版本與產生方式。只存在某個互動頁面或聊天工作階段的內容，很難被長期維護。

對外部 App 與 Site，也要記錄擁有者、連接帳號、共享範圍、資料位置、停用方式與替代流程。工具停止支援時，至少知道如何匯出資料、撤銷權限與恢復人工作業。

本機與雲端之間的移動也需要明確。若桌面 Work 在本機建立成果，正式檔應主動放入受控專案；若雲端任務要交給本機 Codex，應傳遞文件與 Repository 狀態，不假設聊天與套件環境會完整同步。

可攜性要避免專案知識與責任只存在供應商無法保證的暫時狀態，並不排斥使用平台特色。真正屬於使用者的資產，應能被看見、匯出、驗證與交接。

把版本敏感資訊移出思想主軸

Work 剛推出時，方案、地區、平台與整合能力都可能快速變動。若一本書把大量篇幅花在按鈕位置與當前上限，很快就會失效。

更耐久的寫法是：正文保留環境角色、資料治理與選擇方法；附錄記錄截至某日的功能矩陣、方案限制與更新風險。讀者即使面對新版本，也能用同樣問題重新判斷。

Work 的真正增強，在於把文件、資料、應用程式、瀏覽器與執行能力組成一段工作；工具邊界仍然存在。使用者的責任，是讓這段組合具有正式來源、最小權限、清楚保存與可驗收終點。

下一章將進一步處理：當這套環境成功完成一次任務後，如何把它沉澱成範本、Skill、Plugin 或 Scheduled Task，避免每次都從一段新的提示詞重新開始。

章末金句

1. Work 的能力來自資料、工具、權限與交付環境的編排，不能簡化成一台神奇電腦。

2. 檔案存在於 Library，不代表它自動成為這次任務的正式上下文。

3. 能連接一個 App，不等於本次任務已取得所有可用權限。

4. Cloud Browser 適合公開世界；需要身分的工作，必須重新設計登入與核准。

5. 快速發布一個 Site，不代表它已通過正式系統的安全與維運要求。

6. 能看到硬體資訊，只能描述當下環境，不能替供應商做永久承諾。

7. 暫存環境負責運作，正式資料夾與版本系統負責保存。

8. 最好的工作環境讓資料、權限與成果責任最清楚，工具數量不是重點。
