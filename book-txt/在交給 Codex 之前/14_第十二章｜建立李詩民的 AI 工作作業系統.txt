第十二章｜建立李詩民的 AI 工作作業系統

理解一套方法，和每天真的照著它工作，是兩件不同的事。

我們可以很會解釋 Chat、Work、Codex 的分工，也能說出 Goal、Context、Constraints、Deliverables、Acceptance 五項交接條件；但下一次收到語音想法、企業邀約、協會活動、Podcast 題材或網站需求時，若仍然從一個空白對話框開始，方法就還沒有變成系統。

這一章會根據李詩民目前真實的角色與工作領域，設計一份可以逐步實施的 AI 工作作業系統（AI Work Operating System），不會替作者虛構一套已經完全運作的自動化成果。

它的目的不在把所有事情交給 AI，而在讓每一種工作都有固定入口、正式來源、適合的代理層、明確交付、核准點與改善紀錄。

先看見真正的工作組合

李詩民的工作由一組互相影響的角色構成，不能只用單一職位理解：

- AI 架構師與產業觀察者。

- 講師與教育推廣者。

- 桃園市 AI 推廣教育協會理事長。

- 內容創作者與 Podcast 製作者。

- 出版方法與思想資產的整理者。

- 網站、工具與 AI 工作流的規畫者。

這些角色共用很多素材：一項最新 AI 功能，可能先成為研究筆記，再變成 Podcast、社群貼文、課程教材、企業內訓與一本書的章節。一次企業顧問訪談，也可能轉成需求規格、主管簡報、課程案例與後續系統原型。

如果每一個成果都從零開始，時間會消耗在重複搜尋、複製、改寫與找版本。AI 工作作業系統的第一個目的，就是讓同一份可信理解能在不同用途之間流動，但不讓各種衍生稿反過來污染正式來源。

一套個人 AI Work OS 的六個核心元件

一、統一入口：所有新工作先被分類

入口可以是一段語音、一封邀約、一份檔案、一個研究題目或一項排程事件。進來之後先不急著執行，而是完成最小分類：

- 這是問題、任務、專案還是工作流？

- 最終用途是內化、公開、授課、交付還是開發？

- 需要最新研究嗎？

- 會接觸個資、客戶資料或外部行動嗎？

- 應停在 Chat、進 Work，還是準備交給 Codex？

統一入口不是一定要建立一套複雜軟體。起步可以是一份 project_brief.md 範本，或一個固定的 Work 任務簡報。重要的是，任何較大的工作都不要只存在於腦中的一句話。

二、正式來源：每個專案只有一個內容基準

出版專案以 Markdown 為正式來源；活動以核准後的活動資料表為正式來源；企業提案以已確認的訪談、方案與報價版本為準；網站開發以 Repository 與交接文件為準。

正式來源應回答：

- 目前版本是什麼？

- 哪些決策已鎖定？

- 誰可以修改？

- 衍生檔案由哪裡產生？

- 發現錯誤時先更新哪一份？

這能避免 Word、簡報、社群貼文與網站各自留著不同日期、價格與說法。

三、任務路由：用三層工作棧選擇環境

建立一張個人路由表：

狀態｜主要工具｜完成條件

想法模糊、需要反思與比較｜Chat｜問題、使用者、成功狀態與關鍵未知已清楚

需要研究、多檔案、完整成果或流程整理｜Work｜交付物與驗收通過；若需工程，交接包成熟

需要 Repository、終端、測試、版本與部署｜Codex｜程式變更有測試、差異、文件與回復資訊

路由不是一次決定。Codex 發現需求矛盾，可以回到 Work 更新規格；Work 發現問題尚未定義，可以回到 Chat。每次切換都更新正式狀態。

四、可重複資產：保存方法，不只保存成品

每次做完後，判斷哪些內容值得沉澱：

- 品牌與語氣規範。

- 研究來源與名詞表。

- 提案、課程、活動與 Podcast 範本。

- Skills 與品質檢查。

- Codex 的 AGENTS.md 與測試規則。

- 核准點與例外處理。

成品屬於一個專案；方法才能跨專案累積。

五、核准與責任：把人的位置寫進流程

每個工作流都要明確說明：哪些步驟 AI 可自主完成，哪些步驟只產生草稿，哪些動作需要李詩民本人、協會、客戶或其他負責人核准。

典型核准點包括：

- 對外發布與寄送。

- 報價與商業承諾。

- 個資顯示與名單分享。

- 正式課程立場與研究結論。

- Repository 合併、資料遷移與 production 部署。

- 書名、章節與作者真實案例。

六、改善紀錄：每次工作都讓系統更成熟

每個重要任務完成後，簡短記錄：

- 哪些輸入經常缺少？

- 哪些錯誤反覆發生？

- 哪一個步驟最耗人工？

- 哪些規則應進範本或 Skill？

- 哪些自動化應取消或降低頻率？

- 哪些新風險需要加入核准？

沒有這一層，作業系統只是一組漂亮文件，不會學習。

領域一：出版作業系統

「每日出本書」最適合展示 Chat、Work 與 Codex 如何合作。

Chat 負責

- 理解語音輸入背後真正想寫的問題。

- 比較不同定位、書名與讀者承諾。

- 反駁作者初步觀點，找出論證缺口。

- 區分一本書應寫與不應寫的範圍。

完成條件是形成一條清楚思想主軸，一張大綱本身還不夠。

Work 負責

- 建立 Book Bible、章節藍圖、風格與名詞表。

- 查證最新技術與官方資料。

- 撰寫正式 Markdown、合併全書、去重與品質檢查。

- 從正式書稿建立演講、課程、Podcast 與社群衍生內容。

- 建立 DOCX、manifest、QA 報告與 ZIP 交付包。

Work 在這裡不只「幫忙寫文章」，而是承接完整出版流程。

Codex 負責

- 建立或維護產生 DOCX、網站、字數報告與打包驗證的工具。

- 管理 Git Repository、自動測試與版本。

- 建立正式出版網站、內容管理或自動化管線。

正式來源

- 每章：chapter_XX_main.md

- 全書：full_book.md

- 決策：book_bible.md

- 研究：research_registry.md

- 進度：project_status.md

人類核准點

- 核心主張、作者立場與真實案例。

- 書名、副標、章節鎖定與最終交付。

- 可能引發法律、商業或聲譽影響的內容。

待補實作證據

【待補作者案例】比較「直接要求 Codex 建立整本書檔案」與「先由 Work 建立完整內容與驗收，再交給 Codex／工具處理檔案」的差異。

領域二：Podcast 與內容生產作業系統

Podcast 的難點不只是寫口播稿，而是讓研究、作者觀點、朗讀節奏與發布包保持一致。

任務入口

一段語音想法、一則最新消息、一篇論文、一個課堂問題或一本書的章節。

Work 處理流程

1. 修正語音辨識中的明顯錯字與斷句，但不改變觀點。

2. 判斷哪些事實需要最新查證。

3. 整理「事件事實、作者主張、推論與待確認」四種內容。

4. 建立節目核心問題與一句話答案。

5. 完成繁體中文口播母稿。

6. 從母稿衍生簡體 TTS 版、標題、簡介、Show Notes 與社群貼文。

7. 檢查不同版本的數字、名稱、日期與立場一致。

8. 建立來源與發布檢查表。

可沉澱 Skill

- 李詩民聊天式、可朗讀語氣。

- 五至十分鐘節目結構。

- TTS 標點與中英混讀處理。

- 最新 AI 產品的官方來源優先規則。

- 禁止虛構親身經驗與學員對話。

人類核准點

- 核心立場與批判角度。

- 最終口播是否符合本人語氣。

- 可能涉及爭議、法律、醫療、投資或政治的公開內容。

- 真正發布到 Podcast 與社群。

可用指標

- 從題材到完整發布包的人工介入次數。

- 事實修正數與來源漏失數。

- 同一觀點在不同衍生版本的一致性。

- 聽眾實際反饋，而不是只看產出量。

領域三：企業 AI 導入與內訓作業系統

企業邀約常從一句模糊需求開始：「請來教大家用 AI。」如果直接做課程，最終可能很熱鬧，卻沒有解決工作問題。

Chat 負責釐清

- 這是工具教學、流程改善、主管決策，還是正式系統導入？

- 主要部門與工作摩擦是什麼？

- 學員能力、時數、設備、政策與成果期待為何？

- 課後要能做到什麼？

Work 負責準備

- 研究公司與產業公開資料。

- 整理訪談與內部文件。

- 建立部門痛點、機會與風險矩陣。

- 設計不同時數與深度的方案。

- 建立報價假設、主管簡報、課程大綱、教材與課後行動表。

- 區分一般教學案例、公司專屬案例與不可公開資料。

Codex 何時進場

只有當企業決定建立工具、原型、內部入口、資料工作流或正式系統時，才由 Work 建立 Codex 交接包，進入 Repository、測試與部署。

人類核准點

- 客戶問題的判斷與課程承諾。

- 報價、時程與範圍。

- 企業機密與學員資料使用。

- 對外可公開案例。

- 是否適合進入正式工程。

待補作者素材

【待補作者案例】選一個已獲授權的企業內訓或顧問專案，記錄從邀約、需求整理、方案、教材到課後改善的真實流程。

領域四：協會活動作業系統

協會活動牽涉公益目的、品牌、講師、場地、名額、會員、個資、現場執行與會後紀錄。最容易出錯的往往是資訊同步，文案反而只是其中一部分。

正式資料入口

建立一份核准後的活動主檔，至少包含：

- 活動名稱、目的與對象。

- 日期、時間、場地與名額。

- 講師與介紹。

- 報名政策、費用、取消與候補規則。

- 個資蒐集、公開顯示與保存規則。

- 工作人員、流程與緊急聯絡。

- 目前核准狀態。

所有海報、貼文、表單與提醒都從主檔產生。

Work 交付包

- 活動企畫與任務分工。

- 宣傳文、海報文字與報名頁內容。

- 報名資料結構與公開遮蔽規則。

- 工作人員流程、主持稿與現場清單。

- 提醒、新聞稿、成果報告與資料封存清單。

Codex 交接條件

若需要正式報名網站、會員管理、公開查詢、後台與資料庫，先完成角色、資料模型、權限、個資規則、額滿與取消情境，再交給 Codex。

人類核准點

- 活動對外發布。

- 講師資料與合作承諾。

- 報名者個資、公開名單與資料匯出。

- 活動取消、額滿與退款等外部通知。

- 網站 production 部署與資料遷移。

待補作者案例

【待補作者案例】選一場協會活動，記錄哪些資訊在活動前反覆變動，據此設計真正需要的 source of truth 與核准節點。

領域五：網站與系統開發作業系統

網站開發最能體現本書主軸：不要把一句願望直接交給 Codex。

Chat 階段

- 誰使用？解決什麼問題？

- 為什麼要做成網站？

- 第一版真正必要的是什麼？

- 哪些假設可先用 Site 或原型驗證？

Work 階段

- 問題定義、使用者角色與流程。

- 功能範圍、非範圍與優先順序。

- 資訊架構、內容、資料模型與隱私規則。

- Wireframe 或 Site 原型。

- 技術限制、驗收、測試與核准點。

- Codex Handoff Package。

Codex 階段

- 讀取 Repository 與 AGENTS.md。

- 檢查現況、提出可驗證計畫。

- 依里程碑修改、測試與回報。

- 提供 diff、建置、已知限制與部署準備。

- 未經核准不碰 production、高風險資料或不可逆遷移。

回到 Work

Codex 完成後，Work 將工程結果轉成：

- 主管或客戶可讀的變更摘要。

- 操作手冊與課程教材。

- 發布公告與下一階段需求。

- 更新後的專案狀態與交接文件。

如此才形成 Chat → Work → Codex → Work 的閉環。

待補作者案例

【待補作者案例】選一個 Next.js／Firebase／Vercel 專案，保留直接交給 Codex 的第一版需求，以及經 Work 準備後的交接包，做真實比較。

建立一張「我的 AI 工作控制台」

最終不一定需要另做一套複雜軟體。起步版本可以是一個清楚的專案索引：

ai_work_os/

├── 00_inbox/

│ └── new_ideas_and_requests.md

├── 01_projects/

│ └── project_name/

│ ├── project_brief.md

│ ├── source_of_truth.md

│ ├── project_status.md

│ ├── research_registry.md

│ ├── deliverables/

│ └── CHANGELOG.md

├── 02_templates/

│ ├── book_project/

│ ├── podcast/

│ ├── enterprise_proposal/

│ ├── association_event/

│ └── codex_handoff/

每一個專案至少有四個狀態欄位：

- 現在在哪個階段？

- 哪些決策已鎖定？

- 第一個未完成項目是什麼？

- 下一次進入時要讀哪一份正式來源？

這能解決中斷後重新開始的問題，也讓 Work 與 Codex 不必從歷史對話猜進度。

每週十五分鐘的系統檢查

一套個人 AI Work OS 若沒有定期檢查，很快會堆滿過時範本與未完成排程。

每週可以只回答七個問題：

1. 哪三個專案最重要？

2. 每個專案第一個未完成項目是什麼？

3. 有沒有等待人類核准而被卡住的任務？

4. 哪些資料或功能已可能過時？

5. 哪個工作本週重複了兩次以上，值得沉澱？

6. 哪個自動化產生太多噪音或錯誤？

7. 哪一個真實案例值得留下，成為課程或書稿素材？

這十五分鐘的價值，是防止 AI 產出速度超過人的治理能力。

實施順序：不要一次建立所有自動化

建議分四階段落地。

第一階段：統一格式

先建立五個領域的 project brief、source of truth、status、deliverables 與核准清單。暫時仍可手動啟動任務。

第二階段：沉澱範本與 Skill

選擇最常重複、最穩定的 Podcast 或出版流程，建立一套可重複資產，連續使用數次後修正。

第三階段：連接工具與排程

只有在輸入、例外與核准穩定後，才加入 Library、Apps、Plugins、Browser 與 Scheduled Tasks。

第四階段：建立 Codex 交接與工程自動化

把成熟的網站與工具需求交給 Codex，建立 AGENTS.md、測試、CI、部署與回報規則。

這個順序讓系統先可靠，再追求自動。

本章收束

李詩民的 AI 工作作業系統不應是一個炫目的控制台，而是一套能讓出版、Podcast、企業、協會與開發工作共享方法、保持版本、清楚分工並持續改善的規則。

Chat 負責讓方向變清楚；Work 負責讓任務、內容與交付變完整；Codex 負責讓正式工程可以被測試與維護；人則站在整個循環之上，決定什麼值得做、哪些資料可用、什麼不能發生，以及何時真正完成。

這套系統的第一個成果，是讓每一份產出都知道從哪裡來、要去哪裡、誰負責、如何驗證，以及下一次如何做得更好；每天自動產生更多東西並非首要目標。

章末金句

1. 方法只有進入日常入口、正式來源與核准規則，才會變成作業系統。

2. 同一份理解可以衍生很多成果，但每個專案只能有一個正式版本。

3. AI 工作控制台最重要的功能，是指出第一個未完成項目，任務總數只是次要資訊。

4. 成品屬於一次專案，範本、Skill、驗收與教訓才屬於長期能力。

5. 出版、Podcast、企業、協會與網站看似不同，共同需要的都是目標、上下文、邊界、交付與驗收。

6. 不要先自動化混亂；先讓流程可靠，再讓代理加速。

7. 每週檢查一次哪些自動化應該停止，和建立新自動化同樣重要。

8. AI Work OS 的目的不在讓人退出工作，而在讓人的注意力回到判斷、創造與責任。

9. 真正的個人 AI 系統，重視每一次工作能否被理解、驗證、交接與改善，產出數量不是唯一指標。
