第八章｜Work 如何拆解、推進與回報任務

當一個任務需要工作兩個小時，人類最容易犯的錯有兩種。

第一種是微操。代理每做一步，人就插入一句新的要求；看到中間稿還不完整，就立刻改方向；尚未蒐集完資料，就要求先排版；才建立第一張表，就開始爭論字體。最後，代理沒有機會形成完整計畫，人類也被迫重新成為每一步的操作員。

第二種是放任。只丟下一句「幫我全部做完」，不設定里程碑、不檢查來源、不定義核准點，等到最後才發現代理理解的目標與自己不同。此時已經產生大量檔案，修正成本比一開始多問幾個問題高得多。

Work 的價值，不在於讓人從此完全不介入，而在於讓人可以從「步驟操作」轉向「里程碑管理」。

截至本書查證基準日，OpenAI 對 Work 的描述包括：代理可以處理較長、多步驟的工作，使用者能查看進度、回答問題、補充資料、改變方向，並在重要行動前核准。[R01][R02] 這些能力提供了新的合作空間，但不會自動產生好的合作節奏。

本書因此提出一個工作模型：Work 執行循環（Work Execution Loop）。

目標 → 計畫 → 蒐集 → 產出 → 檢查 → 修正 → 交付

這七個階段是一條可以反覆回圈的主幹，並非僵硬流程。每一階段都應留下可觀察的狀態，讓人知道代理正在做什麼、依據什麼、下一步是什麼，以及什麼情況需要介入。

第一階段：目標——先確認要改變什麼

長任務開始前，最重要的是讓代理重述目標，而非立刻動手。

一份企業研究報告的目標可能是「讓主管了解市場」，也可能是「在三個候選方案中做投資決策」。前者需要廣度，後者需要比較尺度、風險與建議。若目標不同，資料來源、分析深度、圖表與結論都會不同。

開始長任務時，可以要求 Work 先回答：

- 它理解的目的與使用者是什麼？

- 最終要產生哪些成果？

- 哪些條件已確定，哪些仍然缺少？

- 目前最大的三個風險是什麼？

- 它準備如何驗證關鍵事實？

這不是多一道官僚程序。它是最便宜的錯誤偵測點。當重述仍不正確，現在修正只要幾句話；等到十份檔案產生後才修正，就會變成版本災難。

第二階段：計畫——把大任務切成可驗證增量

「研究、撰寫、完成」不是足夠的計畫。好的計畫要讓每一段都有可檢查的成果。

例如，要完成一套企業 AI 導入提案，可以拆成：

1. 建立來源與現況基準。

2. 整理部門問題與使用情境。

3. 建立機會優先矩陣與排除條件。

4. 設計三種導入方案與成本假設。

5. 產生主管報告、簡報與九十天行動表。

6. 交叉檢查數字、名詞、來源與版本。

7. 建立待決策清單與最終交付包。

每個里程碑都能回答：「完成了什麼？證據在哪裡？是否足以進下一步？」

計畫還應標記依賴。若企業尚未確認資料分類政策，就不能先承諾某個敏感資料工作流；若預算上限未知，可以先提出假設，但不能把假設寫成正式數字。

Work 可以提出計畫，人類則應檢查三件事：順序是否合理、是否漏掉關鍵驗證、是否太早執行不可逆行動。

第三階段：蒐集——資料取得不是把網路搬回來

代理開始蒐集時，速度通常不是問題，選擇才是問題。

同一個主題可能存在官方文件、新聞、業者文章、社群討論、過時簡報與內部會議記錄。Work 能讀取檔案、使用支援的 Apps 與瀏覽器，但能取得不等於應該相信。[R01][R04][R08]

蒐集階段應建立最小的來源紀錄：

- 來源名稱、日期與位置。

- 這份來源支持哪一個觀點。

- 它是官方事實、外部分析、內部紀錄或作者判斷。

- 有哪些限制、利益關係或過時風險。

- 若來源衝突，哪一份優先及原因。

研究型任務常見的失敗，是代理先產生一個流暢結論，再回頭找支持它的資料。成熟流程應反過來：先建立證據基準，再形成判斷；需要推論時，明確標示「根據哪些事實做了何種推論」。

人類不必檢查每一個搜尋步驟，但應在高影響結論前要求來源與限制，尤其是價格、法規、版本、方案、效能與安全能力。

第四階段：產出——先完成結構，再精修表面

代理很會迅速產生看起來完整的成品，這既是優勢，也是風險。

如果一開始就要求華麗簡報、精美網站與完整排版，結構問題會被視覺掩蓋。較好的順序是：

1. 先建立內容架構與主要論點。

2. 確認數據、範圍與決策狀態。

3. 建立第一版成果。

4. 再依用途調整敘事、格式與視覺。

例如主管簡報不應只是把研究報告切成二十頁。它需要重新設計決策順序：主管要先知道問題與影響，再看到方案與取捨，最後才是行動與核准事項。相同資料在報告、試算表與簡報裡的表達方式不同，但核心數字與決策不能互相矛盾。

這也是 Work 能在同一段任務中產生多種成果的價值：資料與決策可以共用，表達形式則按使用者調整。[R03]

第五階段：檢查——要求證據，不要只問「你確定嗎」

對代理說「請再檢查一次」，常會得到另一段自信文字。真正有效的檢查，要指定檢查方法與證據。

文件任務可以檢查：

- 標題、名詞與版本是否一致。

- 所有數字是否能追溯到來源或計算。

- 是否把假設寫成事實。

- 必要章節、欄位與附錄是否齊全。

- 引用是否支持相鄰文字。

- 是否存在互相矛盾的決策。

- 檔案是否可開啟、非空白、命名正確。

資料任務可以檢查：

- 筆數與總數是否對得上。

- 遺漏值、重複值與異常值如何處理。

- 公式是否覆蓋所有資料列。

- 篩選、排序與日期格式是否一致。

- 原始資料是否保持不變。

網站或程式任務則需要測試、建置、差異、日誌與可重現步驟。

檢查的本質，是讓「我認為完成」轉成「我能提出完成證據」。這一點會在交給 Codex 時變得更重要。

第六階段：修正——改方向時也要管理版本

長任務中途改變方向很正常。問題不在於改，而在於改了之後，舊決策是否仍殘留在其他成果裡。

例如企業方案原本規畫三個月導入，後來改成六個月。Work 不能只修改報告中的一個句子，還要同步檢查：

- 甘特圖與預算試算表。

- 簡報中的里程碑。

- 風險與人力假設。

- 九十天行動表是否仍合理。

- 版本與變更紀錄。

有效修正需要一個變更聲明：改了什麼、為什麼、影響哪些成果、哪些地方已同步、哪些仍待確認。這能避免多檔案專案裡最常見的問題——每一份都對，但不是同一個版本。

人類介入時，也應優先修改上游決策，而不是逐份檔案人工修補。若正式範圍改變，先更新 source of truth，再讓代理同步受影響成果。

第七階段：交付——把成果、限制與下一步一起交出去

交付不是把下載連結貼出來。成熟交付至少包含：

- 成果清單與用途。

- 正式版本與日期。

- 已完成、未完成與待核准事項。

- 使用的主要來源與假設。

- 品質檢查與驗證結果。

- 已知限制與風險。

- 下一個使用者或代理應從哪裡開始。

若交付的是多檔案包，還需要 manifest、檔名一致性、壓縮檔驗證與解壓縮測試。若成果要交給 Codex，還需要把決策狀態、工程限制、測試與執行順序帶進 Repository。

完成工作最重要的證據，是接收者能打開、理解、使用、驗證並繼續；代理說「已完成」遠遠不夠。

什麼時候該讓 Work 繼續，什麼時候該介入？

Human on the Loop 強調依事件介入，而非固定每十分鐘檢查一次。

以下情況通常可以讓代理繼續：

- 仍在已核准範圍內蒐集與整理。

- 中間稿的粗糙屬正常階段，不影響核心方向。

- 使用的是可逆、低風險的本地或草稿操作。

- 已知缺口有明確的待確認標記，不會被當成事實。

以下情況應立即介入：

- 目標或核心使用者被重新解讀。

- 來源衝突會改變重要結論。

- 代理準備發布、外寄、刪除、覆寫或修改權限。

- 任務擴張到未核准範圍。

- 成本、法規、個資或品牌風險增加。

- 驗收方式不存在，卻準備宣告完成。

- 代理反覆失敗，仍沿用同一條路徑。

這裡的判斷重點不在「代理有沒有犯錯」，而在錯誤是否會累積、外溢或難以回復。

進度回報應該包含什麼？

沒有結構的進度回報，只會變成「我正在努力」。對長任務而言，一份有效的回報可以只有五行：

1. 已完成什麼。

2. 目前正在做什麼。

3. 發現了什麼重要問題或新證據。

4. 需要人類決定什麼。

5. 下一個可驗證里程碑是什麼。

若任務複雜，再加入：變更影響、風險狀態與預估交付清單。不要要求代理回報所有低層操作，否則注意力會被日誌淹沒；也不要只在最後回報，否則人失去修正方向的機會。

好的進度設計，是讓人用最少時間掌握最高價值的狀態。

代理卡住時，不要只重複原指令

長任務失敗時，最無效的做法是把同一句要求再說一遍，期待模型突然理解。

可以依失敗類型採取不同恢復策略。

找不到資料

先判斷是來源不存在、權限不足、網頁阻擋，還是查詢策略錯誤。可改用官方替代來源、要求使用者提供檔案，或把該結論降級為待確認。不要讓代理用沒有來源的常識填補需要最新查證的事實。

資料互相衝突

不要要求代理「選一個最合理的」。先列出來源、日期、適用範圍與衝突影響，再依正式來源優先規則或交回人類決定。衝突本身就是工作成果的一部分。

成果方向偏離

回到最近一個正確里程碑，檢查目標、使用者與成功狀態。不要逐段修補已經錯誤的完整成品。必要時廢棄受影響的衍生稿，由更新後的 source of truth 重建。

工具反覆失敗

設置重試上限。超過上限後應回報錯誤、已嘗試方法、可能原因與替代路徑，而不是無限循環。對外部系統寫入，尤其不能在不確定是否成功時盲目重送，以免產生重複資料或交易。

任務太大

將任務縮成最小可驗證增量。先交付來源表、資料清理結果或一個核心流程，而不是勉強產生一套看似完整、實際無法驗證的成果。

恢復能力是代理工作品質的一部分。成熟代理會在失敗時留下狀態、保護已完成成果，並提供可判斷的下一步；永遠不失敗並不現實。

平行工作需要合併規則

較複雜的 Work 任務可能同時研究多個主題、建立多份成果，甚至使用多代理平行處理。平行化可以加快速度，也容易產生重複與矛盾。

在平行開始前，應先定義：

- 每個工作單元唯一負責什麼。

- 共用的名詞、版本與來源。

- 哪些檔案只能由一個單元修改。

- 中間成果如何命名與回報。

- 合併時由誰處理衝突。

- 哪些結論必須交叉檢查。

合併不能只把多份文字串在一起。它要做結構編輯：刪除重複、統一術語、處理衝突、確認每一章或成果有唯一任務，並重新檢查全局論點。

這對長篇寫作尤其重要。每個章節單獨看都很好，不代表合成一本書後仍有清楚思想線。代理平行產生內容之後，必須有一個總編輯角色負責全書責任，而不是用檔名順序代替編輯。

三種不值得繼續的長任務

有些任務應該停止，而不是努力完成。

第一，目標已失效。新的證據顯示原問題不存在，或組織已改變方向。此時最好的成果是停止報告，而不是繼續消耗資源證明原計畫。

第二，必要權限與資料不可得。若缺少資料會使核心結論無法成立，應明確說明限制，不要用外部一般資料假裝完成內部分析。

第三，完成條件無法定義。當委託者只要求「做到最好」卻拒絕決定用途、範圍與取捨，代理無法可靠收斂。此時應把未決問題交回，而不是無限擴張內容。

知道何時停止，是 Work 執行循環裡重要但常被忽略的能力。

一般情境：完成一套企業研究與提案

以下是一個一般情境，不是作者已完成的 Work 案例。

任務目標是：根據一家中型製造企業提供的訪談紀錄、現況文件與公開資料，提出 AI 導入優先順序，交付主管報告、十五頁簡報、預算試算表與九十天行動表。

Work 執行循環可以這樣運作：

目標：先重述決策用途，確認任務並非「介紹 AI」，而是幫主管選出第一階段投資方向。

計畫：先完成現況基準與問題地圖，再建立候選情境與評分，最後才做預算與簡報。

蒐集：把內部資料與公開資料分開，建立來源、日期、可信度與限制；個資與商業敏感資料依規則處理。

產出：先交付問題矩陣與候選清單，經人確認後才建立完整方案；避免一開始就花時間排版錯誤方向。

檢查：驗證所有人數、時程與成本假設；確認主管簡報與試算表使用相同版本。

修正：若主管決定第一階段不碰生產資料，更新範圍、風險、方案與預算，而不只刪除簡報一頁。

交付：提供正式成果、來源、假設、待核准事項與下一步，並說明哪些內容適合進一步交給 Codex 建立原型。

這個流程的重點不在 Work 能不能一次做完，而在整段工作始終可被看見、修正與驗證。

建立一張 Work 控制板

長任務最怕狀態藏在對話裡。可以用一張簡單控制板保存七個欄位：目前目標、當前階段、已完成成果、下一個可執行步驟、阻塞問題、等待核准、最新證據。

控制板不需要即時顯示每一次工具呼叫。它的用途是讓人一眼知道：方向有沒有改、代理卡在哪裡、下一次介入需要做決策還是只需等待，以及中斷後能否從正確位置繼續。

一個好的狀態更新可以寫成：

已完成兩個官方來源的能力比對與章節引用表；發現 Scheduled Tasks 的官方頁面對活動數上限有不一致敘述，因此正文不採固定數字，版本風險已登錄。下一步是完成附錄能力矩陣，不需核准。書名與方法已鎖定；目前保留的待補項目是真實作者案例與介面截圖。

這種回報同時提供成果、發現、決策處理與下一步，比「研究進行中」更能支援人類監督。

升級規則：代理何時必須停下來

不是每一個未知都要詢問。可建立四種升級條件：

方向衝突：新資訊推翻核心目標、讀者或成功標準，繼續做會造成大範圍返工。

來源衝突：兩個高權威來源無法依既定優先序解決，且差異會影響結論或交付。

邊界衝突：任務需要超出已授權的資料、帳號、環境或對外行動。

證據不足：完成條件要求的測試無法執行，或結果與預期不一致。

停下來時，代理不應只丟出問題，而要帶著最小決策包：目前事實、衝突、已嘗試方法、可行選項、各自影響，以及在等待期間可以繼續的安全工作。

變更控制：一句新指令可能影響多少地方

長任務中，人類常隨口說「那就改成另一個名稱」「這個功能先不要」「價格調整一下」。代理若只改眼前檔案，很容易留下不一致。

任何會影響多個成果的變更，都應先做影響分析：正式來源在哪裡、哪些章節或檔案引用、測試與驗收是否改變、舊版本是否需要淘汰、是否要更新變更紀錄。修改順序應先正式來源，再衍生成果，最後重新驗證。

Work 的優勢正是能跨檔案處理這類連動；但只有在正式來源與依賴關係明確時，跨檔案能力才不會變成跨檔案混亂。

人類應在里程碑問的五個問題

1. 現在的成果仍服務原目標嗎？

2. 有哪些新事實改變了原先假設？

3. 下一階段會採取哪些外部或不可逆行動？

4. 用什麼證據判斷當前階段通過？

5. 若今天中斷，下一個接手者能否安全繼續？

這五題比逐段改字更接近 Human on the Loop。人類不必介入每一個細節，卻要在會改變方向、風險與完成判斷的節點保持清醒。

介入預算：把人的注意力留給高資訊量節點

代理能長時間工作後，人的稀缺資源轉為注意力，已不再是按鈕操作。可以替大型任務設計「介入預算」：事先決定哪些里程碑一定看、哪些例外必須通知、哪些低風險偏差由代理自行修正。

高資訊量節點通常包括：目標第一次被重述、核心資料衝突、最小端到端成果完成、重大範圍變更、對外行動前，以及最終驗收。這些節點能用少量時間改變大量後續工作。

低資訊量通知則包括每個檔案已讀、每一次搜尋完成、每一段文字生成。它們讓人感覺有掌握，卻容易掩蓋真正需要決策的事情。

介入不應只依固定時間觸發，也要有條件觸發，例如：來源可信度低於基準、任務超出已鎖定範圍、同一工具連續失敗、預估外部影響增加、驗收未通過或需要新的權限。

平行分支必須有合併閘門

Work 可以同時研究、分析資料與建立不同成果，但平行工作會產生新的風險：各分支可能使用不同版本或假設。

因此，平行分支在進入正式交付前要經過合併閘門：確認共同事實基準、名詞、數字、決策與限制一致；若衝突，先更新正式來源，再重新生成受影響成果。

例如研究報告、主管簡報與預算表可以平行產出，但不能各自維護公司人數、時程與方案名稱。合併時應產生差異摘要，而不是只把檔案放進同一資料夾。

進度回報也最好報「自上次里程碑以來的狀態差異」：新增了什麼、改變了什麼、哪項風險升高、哪些決策等待人。這比每次重新敘述全部工作更適合長任務。

本章收束

長任務不需要人類一直握著滑鼠，也不能只靠一句「全部交給你」。成熟合作以目標、里程碑、證據、變更與核准點管理。

Work 執行循環讓代理知道如何推進，也讓人類知道何時介入。下一章要處理另一個關鍵：代理到底在什麼環境裡工作？檔案、Library、Apps、瀏覽器、桌面與 Sites 各自能提供什麼，又有哪些不能混為一談的邊界？

章末金句

1. 微操讓代理失去整體，放任讓人失去方向。

2. 長任務最好的管理單位，是可驗證的里程碑，而非每一個微小步驟。

3. 先讓代理重述目標，是成本最低的錯誤偵測。

4. 能取得資料不等於能相信資料，能產生成品不等於已通過檢查。

5. 「請再檢查一次」不是驗證方法；證據、測試與對照才是。

6. 改方向不可怕，可怕的是舊方向仍殘留在其他檔案裡。

7. 進度回報的價值，不在於證明代理很忙，而在於讓人知道是否需要決策。

8. 完成交付的標準，是下一個人能打開、理解、使用、驗證並繼續。
