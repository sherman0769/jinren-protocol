第十章｜從一次成功，變成可重複的工作流

第一次請 Work 完成一組 Podcast 發布資料時，你花了不少力氣：說明語氣、節目長度、題材查證、標題風格、繁簡體版本、TTS 格式、Show Notes 與社群貼文。成果終於符合期待。

下一集開始，你又重新說一次。第三集再說一次。只要換一個對話、補一項新規則或漏貼一份範例，結果就有差異。

這時你擁有的是一次成功，不是一套工作流。

AI 生產力最容易被高估的地方，是把單次完成速度當成長期效率。真正能累積的是下列工作資產，而不只是一段提示詞：固定輸入、可靠步驟、正式來源、交付格式、例外處理、核准點、驗收與版本。當這些元素能被重複使用，工作才從「每次請 AI 幫忙」變成一個可改善的系統。

重複工作流的八個構成

要把一次成功沉澱下來，可以先記錄八個部分。

觸發條件

什麼時候開始？由人主動啟動、固定時間排程、收到新檔案、偵測到網站變化，還是某個狀態成立？

觸發條件要避免過度寬鬆。例如「有 AI 新聞就做快報」可能每天產生大量雜訊；更好的條件是「官方來源出現會影響一般使用者、企業導入或既有教材的重大變更」。

輸入

每次需要哪些必填資料、可選資料、正式範本與外部來源？缺少資料時能否繼續？

Podcast 工作流的必填輸入可能是核心觀點、來源與預計時長；企業提案則可能需要公司名稱、受眾、邀約內容、課程時數與預算狀態。輸入若沒有最低要求，代理會在不同批次使用不同假設。

處理步驟

哪些步驟有固定順序，哪些可平行？例如先查證，再建立觀點架構，完成口播稿後才衍生簡體 TTS 與社群貼文。若先做所有版本，核心稿修改後就會產生同步成本。

正式來源

哪一份是後續衍生內容的唯一依據？出版專案以 Markdown 為正式來源；Podcast 可以以繁體口播稿為核心稿；企業提案可能以核准後的 proposal.md 為基準。

沒有正式來源，工作流每次修正都會產生多個版本。

交付成果

每次固定交付哪些檔案、欄位、格式與命名？「做完整一點」不能成為工作流規格。交付成果要能被下游工具或人直接使用。

例外與停止條件

來源衝突、資料不足、登入失敗、功能版本改變、內容涉及敏感資訊時，要自動降級、標記、暫停分支，還是停止整體？工作流最容易在例外發生時回到人工救火。

人類核准點

哪些步驟可以自動完成，哪些需要作者、主管、活動負責人或資訊人員批准？監測可以自動，對外發布未必適合自動；報告可以生成，涉及客戶報價仍需人確認。

驗收與版本

如何知道這次成果合格？範本與規則何時更新？更新後如何記錄變更、測試既有案例並回復上一版？沒有版本治理的自動化，會把錯誤穩定地重複。

這八項不必每次寫成八個文件，但必須在某個可定位的地方存在。

從參考檔到範本

最簡單的重用方式，是提供一份過往成品作為參考。它能讓 Work 理解語氣、版型與內容密度，但參考檔只展示結果，不一定說明規則。

範本則把可變與不可變的部分標示出來。例如一份企業提案範本可以規定：第一頁必須回答決策問題；第二部分描述現況與證據；方案固定分成基礎、進階與導入；預算欄位由試算表提供；任何未確認數字標示待補；不得虛構客戶成果。

官方文件也把 Reference File 與 Template 分開：前者主要服務當前工作，後者包含可重複使用的結構、指令、例子與預期輸出。[R03]

要把參考檔升級為範本，可以做四件事：

1. 移除特定客戶、日期與一次性資料。

2. 標出必填、選填與禁止內容。

3. 補上處理順序與驗收條件。

4. 提供一個合格例子與一個不合格反例。

範本的目的不在讓每次成果一模一樣，而在讓品質底線與工作責任一致。

Skill：把可重複判斷封裝起來

截至 2026 年 7 月 19 日，OpenAI 將 Skill 描述為可重複、可分享的工作指引，可以包含指令、例子與程式，系統在合適情境中使用。相關設計採 Agent Skills 開放標準，但個人建立、管理、桌面與雲端同步等能力仍依方案與推出狀態而異。[R07]

Skill 適合處理具有穩定方法、需要多次使用、但不一定要連接外部系統的工作。例如：

- 把語音輸入整理成可出版的繁體中文稿。

- 依研究登錄規則查證 AI 產品資訊。

- 從正式章節產生演講筆記與章末金句。

- 檢查 Codex 交接包是否缺少五項條件。

- 將活動名單依固定遮蔽規則產生公開版本。

一個成熟 Skill 不只是一段角色設定。它應說明適用與不適用情境、輸入格式、處理步驟、正式來源、輸出、例外、禁止事項與測試案例。

例如「出書章節 Skill」可以規定：先讀 Book Bible 與章節藍圖；只完成該章唯一任務；不虛構作者案例；新產品事實需查證；正文完成後才衍生簡報；所有修改先回寫 Markdown。這些規則比每次臨時提醒穩定。

Plugin：把方法、外部資料與工具組成一個能力包

OpenAI 在 2026 年 7 月的產品架構中，將原 App Directory 移轉為 Plugin Directory；Plugin 可以封裝 Skills、Apps 與 App templates，讓一個工作流程同時擁有方法、外部資料與可採取的動作。[R08]

可以這樣理解：

- Skill 告訴代理「這類工作怎麼做」。

- App 讓代理「連到哪個外部系統、讀什麼、做什麼」。

- Plugin 將一組相關 Skills 與 Apps 整理成可發現、可安裝、可管理的工作能力。

例如協會活動 Plugin 可能包含：活動企畫 Skill、名單遮蔽 Skill、Google Drive App、Calendar App 與活動報告範本。使用者啟動後，代理可以依任務選擇相關能力，但仍受工作區、App 權限與本次核准限制。

Plugin 不應成為無限制存取的理由。它只是封裝能力，沒有改變最小權限、人類核准與資料治理原則。

Scheduled Task：把「記得再問一次」變成系統觸發

Scheduled Tasks 可以在指定時間執行一次、重複執行，或監測資料變化後回報。截至寫作基準日，官方說明也指出其頻率、同時啟用數量、Project files 存取與自動暫停等存在限制；具體上限應在實際帳號中確認，不適合當成永久承諾。[R06]

排程最適合兩類工作。

第一類是固定節奏，例如每週一整理官方 AI 更新、每月底生成協會活動摘要。

第二類是條件監測，例如官方文件出現版本變更、狀態頁出現重大中斷、某個公開資料達到門檻時通知。

但排程不應把所有下游動作一起自動化。可以把流程分成：監測 → 摘要 → 人類判斷 → 產生成果 → 核准發布。對外發文、客戶報價、修改正式資料與付款，不應因為排程存在就跳過核准。

排程也要避免「每天重新生成一份完整內容」造成資訊垃圾。更好的設計是增量工作：只回報自上次基準後的變化，沒有重要變化時不產生長報告。

自動化層級要與風險相配

同一個流程可以有不同自動化深度。

- 輔助：人啟動，代理產生草稿，人完成。

- 半自動：系統觸發，代理完成多數步驟，高影響節點由人核准。

- 條件自主：在範圍、來源與驗收穩定時，代理自行完成低風險工作，只在例外通知。

成熟度不應只看「人是否還要點一下」，而要看輸入是否穩定、錯誤能否被偵測、結果能否復原、外部影響是否受控。

例如每週官方更新摘要可以高度自動；把摘要改成作者觀點並公開發布，仍需要作者判斷。活動名單去重可以自動標記候選；真正合併會員資料需要人工核准。

工作流需要測試集

一次成功案例不能證明範本或 Skill 穩定。工作流應保留一組代表性測試：正常輸入、缺欄資料、互相矛盾的來源、超長內容、敏感資料、需要停止的情境。

每次修改規則後，用同一組測試比較：

- 是否仍產生所有必要成果？

- 是否遵守禁止事項？

- 是否對缺資料誠實標示？

- 格式與名詞是否一致？

- 是否引入新的重複或錯誤？

對內容工作，測試不一定完全自動化。可以結合機械檢查與人工評分。例如字數、檔名、來源引用、敏感欄位可自動檢查；觀點深度、可朗讀性與是否像作者則由人審閱。

版本治理：成功的方法也會過時

AI 產品、來源、品牌、組織規則與讀者需求都會變。工作流若沒有版本，就會把過去正確的方法永久重複。

每個重要範本或 Skill 可以記錄：

- 版本與生效日期。

- 修改內容與原因。

- 受影響的輸出。

- 測試結果。

- 相容的工具與平台。

- 已知限制與下一次檢查日期。

產品敏感內容應從穩定方法中分離。例如 Work 的方案與 Library 容量放在版本資料，而「正式來源、最小權限與驗收」留在核心 Skill。如此功能更新時，不必重寫整套工作法。

工作流需要可觀測性

工作流一旦自動或半自動執行，人很容易只看到輸出，看不到過程是否健康。成熟流程應保留最小的觀測資訊：

- 本次使用的流程與範本版本。

- 輸入是否完整、來源是否成功取得。

- 哪些步驟成功、失敗、重試或降級。

- 產生哪些成果、保存在哪裡。

- 哪些驗收通過或失敗。

- 哪些行動等待核准。

- 本次與上次的重大差異。

觀測要讓人可以回答以下問題，無須把每一個低層日誌都交給使用者：流程今天有沒有正常工作？輸出為什麼不同？錯誤發生在哪一層？

對內容流程，品質指標可以是來源覆蓋、事實修正、版本一致與人工退件原因；對資料流程，可以是缺漏、重複、異常與處理筆數；對工程流程，可以是測試、建置、錯誤率與回復時間。

不要只用「產出多少」衡量 AI 工作流。產出量很容易增加，真正應觀察的是可用率、修正成本、錯誤外溢與人類決策時間。

何時不該使用排程

Scheduled Task 很方便，卻不是每個重複念頭都值得排程。

以下情況通常不適合：

- 來源與需求仍頻繁改變。

- 每次都需要大量人類判斷，固定流程很少。

- 輸出沒有人閱讀或採取行動。

- 監測條件過寬，會產生大量無關通知。

- 任務需要 Project files 或權限，但目前 surface 無法取得。

- 失敗後可能產生重複外寄、重複寫入或其他外部影響。

- 法規、價格或帳號狀態需要即時人工確認。

排程之前，先問三個問題：沒有變化時要不要輸出？有變化時誰要做什麼？如果失敗或重複執行，會發生什麼？三題答不清楚，排程只會把模糊工作變成固定噪音。

工作流的升級、降級與退休

一套流程成熟後，可能升級：增加 App、加入排程、減少人工步驟，或建立正式 Plugin。它也可能需要降級：取消自動發布，改成人工核准；降低檢查頻率；拿掉不可靠來源；把外部寫入改為只產生草稿。

更重要的是，工作流應該能退休。

退休條件可以包括：

- 目的已消失。

- 輸出長期沒有人使用。

- 維護成本高於節省時間。

- 來源或工具已不再支援。

- 新流程已完整取代。

- 風險超過可接受範圍。

退休時要停用排程、撤銷不再需要的 App 權限、保存必要紀錄、標記範本為停用，並確認沒有其他流程仍依賴它。建立自動化很有成就感；安全地關閉自動化，才是治理成熟的證明。

用工作流畫布把隱性規則攤開

在把成功做法升級為 Skill、Plugin 或排程前，可以先完成一張工作流畫布。它至少包含：目的、觸發、必填輸入、正式來源、處理階段、工具、權限、交付成果、驗收、例外、核准與版本。

其中最容易遺漏的是「狀態」。畫布要說明工作目前在哪一階段、重複啟動時如何避免重做、失敗後從哪裡繼續，以及同一輸入是否允許產生兩次外部行動。

例如 Podcast 流程若在 TTS 生成後中斷，重新啟動時應讀取已核准主稿與現有成果，只補未完成部分；不能重新研究並悄悄改變觀點。活動通知流程則要有寄送批次 ID，避免重試時重複寄出。

畫布也應明確標示「人類仍保留的判斷」。若每次都需要作者決定核心論點，就不要把這一步偽裝成可自動化規則；可以自動準備證據與選項，再等待決策。

從草稿流程到正式流程，需要評測閘門

新的工作流不應一建立就進入高權限排程。可以分成四個狀態：

1. 草稿：只在代表性樣本上手動執行。

2. 試行：在真實但低風險工作中使用，所有外部行動仍由人完成。

3. 啟用：品質、例外與回復已穩定，可讓代理在既定範圍自主執行。

4. 受限／停用：錯誤、來源或政策改變時降級，等待修正。

升級前要比較基準。至少觀察成果可用率、人工修正原因、重要事實錯誤、外部動作失敗、平均介入點與中斷恢復。對內容工作，可保留幾組固定題材；對資料工作，保留正常、缺漏、重複與敏感資料案例。

評測應依原始問題與驗收判斷，不能只問「代理喜不喜歡這個結果」。若新版本產生更多內容，卻增加事實修正與發布退件，不算升級。

保留人工備援

自動化流程也要知道如何回到人工。來源服務中斷、排程失效、權限撤銷或版本不相容時，至少保留最小可用手冊：需要哪些輸入、哪幾個步驟由人完成、成果放哪裡、如何避免重複。

人工備援承認真實系統會變，並不等於自動化失敗。能安全降級的流程，比只能在理想環境全自動運作的流程更可靠。

三個可沉澱的工作流

每日 AI 快報

觸發：每天固定時間檢查官方來源，但只有重大變化才產生完整摘要。

輸入：官方來源清單、受眾、關注主題、上次基準。

處理：比對變化、查證日期與狀態、區分功能事實與產業推論、評估對教學與企業導入的影響。

輸出：變更摘要、教學解釋、待更新教材清單、可選 Podcast 題目。

核准：任何作者觀點、公開貼文與課程結論由人確認。

例外：來源互相矛盾或僅有傳聞時，標示待確認，不自動下結論。

Podcast 生產線

觸發：作者提供一個觀點、語音草稿或已確認題材。

輸入：核心主張、來源、目標時長、作者語氣範例。

處理：理解語音錯字、查證、建立論證、完成繁體口播稿，再產生簡體 TTS、標題、節目介紹、Show Notes 與社群稿。

正式來源：繁體口播主稿。

核准：作者確認核心觀點與可公開內容後，才進入發布；不得自動替作者虛構親身案例。

協會活動包

觸發：活動定位與日期鎖定。

輸入：活動簡報、講者、場地、品牌、報名規則與個資政策。

處理：企畫、宣傳、報名表、流程表、主持稿、名單、新聞稿與成果報告依階段生成。

權限：原始名單只在受控環境處理；公開成果使用遮蔽資料；寄信、發布與改正式名單設核准點。

版本：活動前、活動中、活動後是三個不同工作狀態，不能共用一份永遠叫「最新版」的檔案。

先做一個「有人看著的自動化」

第一個工作流不要從完全無人監督開始。選擇一件高頻、規則相對穩定、錯誤可回復、成果容易檢查的工作，連續跑三到五次，每次保留輸入、輸出、人工修正與例外。

第一次只建立固定任務簡報與交付清單；第二次找出重複說明，整理成範本；第三次把穩定判斷寫進 Skill；只有當例外與核准已清楚，才加入 App、Plugin 或 Scheduled Task。

這種做法可以稱為「有人看著的自動化」。人的角色轉為觀察，而非逐步操作：哪些資料每次都缺、哪些規則模型常誤解、哪些產出從未被使用、哪些例外需要停止。經過數次真實運作，才知道哪一段值得自動化，避免把想像中的流程直接固化。

工作流要有營運指標

速度只是其中一項。至少可以追蹤：

- 首次交付通過率：第一次交付有多少不需方向性重做？

- 人工修正類型：修正是語氣微調，還是目標、資料與權限錯誤？

- 例外頻率：流程多久遇到一次未定義情境？

- 核准等待時間：真正瓶頸在代理，還是在責任人無法決策？

- 來源新鮮度：多久會因資料過期影響結果？

- 成果使用率：產出的報告、摘要與貼文是否真的被閱讀或採用？

- 回復能力：錯誤發生時能否定位、撤回並重新執行？

若一個流程產出更快，卻需要更多方向性重做或製造沒人使用的內容，它並沒有真正改善工作。

變更、暫停與退役流程

工作流是需要維護的產品。任何影響輸入格式、來源、政策、功能、模型、外部 App 或交付責任的改變，都應有版本紀錄與重新測試。

可以定義三種狀態：

啟用：目前來源、權限、測試與責任人有效，可依既定頻率運作。

暫停：發現資料過時、錯誤率升高、權限變更或產品功能不穩，停止外部動作，但保留記錄與修復計畫。

退役：原問題已不存在、流程被新方法取代，或維護成本長期高於價值。移除排程與權限，保存必要歷史，更新入口與文件，避免舊流程仍被誤用。

成熟自動化的標誌，是知道什麼時候不應繼續，而非永遠運作。

一張工作流上線前檢查表

- 觸發條件是否明確，能避免重複或錯誤啟動？

- 輸入是否有格式、來源與敏感資料規則？

- 正常、邊界與失敗案例是否至少跑過一次？

- 外部動作是否有核准、冪等或回復設計？

- 成果存放與版本是否可追？

- 責任人知道如何暫停與修正嗎？

- 功能或資料多久重查一次？

- 有沒有一個指標能證明它仍然創造價值？

通過後才值得從「一次任務」提升成長期工作流。

工作流也需要退出條件

有些自動化應該停止。來源改版、錯誤率上升、流程低頻、維護成本高於價值，或組織政策改變時，應暫停、降級或移除。

Scheduled Task 若長期產生無人閱讀的摘要，只是在製造資訊；Skill 若每次都需要大量人工修正，代表規則或輸入仍不成熟；Plugin 若取得過度權限，方便性不應凌駕治理。

每個工作流可以定期問：它仍解決原問題嗎？輸入與成果有人負責嗎？錯誤會被發現嗎？版本有人維護嗎？若答案是否，就不應因為已經建好而永久運作。

提示詞是入口，工作系統才是資產

提示詞當然重要。它能啟動一次任務，也能成為範本或 Skill 的一部分。但只收藏提示詞，會忽略影響結果的其他條件：檔案、版本、資料來源、工具權限、例外、驗收與人類決策。

真正可累積的資產，是一套能讓不同任務在相同品質邊界內運作的系統。它允許人中斷後繼續、工具更新後調整、代理切換後交接，也允許錯誤被記錄而不是再次發生。

下一章會把這套可重複性推到另一個代理：當 Work 已經整理好問題、上下文、限制、成果與驗收，如何建立一份 Codex 能直接進入工程工作的交接包。

章末金句

1. 一次成功證明這次做得到；可重複工作流證明下次不必重新猜。

2. 範本保存結構，Skill 保存方法，Plugin 組合能力，Scheduled Task 決定何時啟動。

3. 自動化的成熟度，不在於完全沒有人，而在於錯誤能被發現、外部影響能被控制。

4. 監測可以自動，公開觀點與正式承諾仍需要責任人。

5. 沒有例外與停止條件的流程，只是在等待第一次真實世界的意外。

6. 成功工作流要有測試集，也要有退場機制。

7. 產品功能會變，正式來源、權限邊界與驗收原則應比版本更耐久。

8. 提示詞可以收藏，工作系統才能累積。
